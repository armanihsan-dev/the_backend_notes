Google Zanzibar: The Authorization Engine

Google **Zanzibar** is a **globally distributed, high-performance system** designed for **authorization** and **access control** in Google's services. It answers the fundamental question: "Can user X access object Y?".

It was built to handle the **massive scale** (trillions of objects) and **strict consistency** requirements of Google products like YouTube, Google Cloud, and Google Drive, where access rules are complex and must be checked almost instantly.

🏛️ Core Concepts of Zanzibar

Zanzibar's design is centered around the concept of **relationship tuples** and a specialized query language based on them.

1. Relationship Tuples

The entire authorization model is defined by these three-part statements, which form the **core data** stored in Zanzibar's database:

Component Description Example
Object The resource being accessed (e.g., a document, photo, video, or group). document:proposal
Relation The specific type of relationship or access the user has with the object. owner, reader, can_edit, member
User/Set The principal who has the relationship. This can be a user or a group of users (a user set). user:alice, group:eng_team#member

Example Tuple:

document:my\_doc#reader@user:bob

This tuple reads: "Bob has the **reader** relation on the **document:my_doc** object."

2. Namespaces and Schemas

To manage the structure and semantics of these tuples, Zanzibar uses **Namespaces** and a declarative **Configuration Language (Schema)**.

  • **Namespace:** Defines the type of object (e.g., document, user, group).
  • **Schema (Configuration):** Defines the **valid relations** within a namespace and, crucially, **how those relations are computed**. This is where the core logic of RBAC and ACLs lives.

The schema uses a specialized syntax to define relations based on existing ones:

Relation Definition Type Description Example
Directly defined Access is granted only via an explicit tuple. define owner as user:*
Union Combines the results of multiple relations (**OR** logic). define can_read as owner or editor
Intersection Requires a user to be in both specified sets (**AND** logic). define admin_edit as admin and editor
Exclusion (Difference) Grants access to one set, excluding members of another (**NOT** logic). define public_reader as reader but not banned_user
Computed Userset Propagates a relation from a related object. define reader as owner from parent

This declarative approach allows complex rules (like "an editor of a folder is also a reader of all documents inside it") to be defined statically and evaluated efficiently.

⚙️ Zanzibar Components and Data Flow

Zanzibar is a **distributed system** composed of several primary services designed for **low latency**, **high availability**, and **strong consistency**.

1. Client and the Check Service

  • **Client (Application):** The Google service (e.g., Drive) that needs to perform an authorization check.
  • **Check Service:** The public interface of Zanzibar. Applications query this service using the **Check** operation: Check(user, relation, object).
  • Example: Check(user:alice, reader, document:report).

2. Relationship Database (Spanner)

  • The core persistence layer is built on a **highly consistent, globally distributed database**, often cited as being based on **Google Spanner**.
  • It stores the vast collection of relationship tuples.
  • **Consistency:** Zanzibar provides a form of **"external consistency"** for reads, ensuring that every check observes a globally consistent view of the access control state.

3. Change and Watch Services

To maintain consistency and minimize latency, Zanzibar uses a mechanism to track and propagate changes to access control state.

  • **Change Service:** Handles updates (**writes**) to the relationship tuples. This includes adding or removing relationships.
  • **Watch Service:** Allows clients (like caching layers or other applications) to subscribe to changes in the relationship tuples. This is crucial for **cache invalidation** and real-time security responses.

4. Cache and Enforcement Layers

  • **Caches:** Zanzibar uses multiple layers of caching, including local caches within the service frontends, due to the high frequency of authorization checks.
  • **Timestamping (Zookie):** To ensure cached results don't violate consistency, every authorization check is performed against the relationship data as of a specific **timestamp** (or **Zookie**).

📈 Consistency and Scalability

Zanzibar tackles two major engineering challenges:

1. Scaling the Check

The system is designed to scale horizontally to handle **millions of authorization checks per second**. It uses techniques like:

  • **Distributed Evaluation:** Complex permission checks are broken down into sub-checks and run concurrently across many servers.
  • **Low Latency:** Optimized to return results in the **low single-digit milliseconds**.

2. Consistency (The "Zookie")

This ensures strong consistency between a write (share) and a subsequent read (check).

  • **Zookies (Consistency Tokens):** A Zookie is a **read timestamp** that represents the state of the system at the moment of a write operation.
  • When an application writes a new tuple, Zanzibar returns a Zookie.
  • The application then passes this Zookie back for subsequent read/verify operations.
  • Zanzibar guarantees the read will be performed against a database snapshot that is **at least as new** as the time indicated by the Zookie, preventing stale reads.

This strong consistency model is essential for maintaining trust and security in a distributed environment.

OpenFGA: Open Source Authorization

**OpenFGA** is an **open-source authorization system** based on the principles and core design of Google's **Zanzibar**. It provides a fast, flexible, and reliable service to determine whether a user can access a specific object. OpenFGA focuses on solving the **Authorization (AuthZ)** problem—specifically, answering the question: "Can user X access object Y?".

OpenFGA is designed to be highly scalable and strongly consistent, making it suitable for complex authorization needs in large, distributed applications.

🏗️ Core Concepts and Components

OpenFGA is built around three primary concepts that define the authorization model:

1. Relationship Tuples (Data)

Authorization state is stored as a set of immutable three-part relationships, similar to Zanzibar. These tuples represent explicit grants of access.

Component Description Example
Object The resource being protected, defined by its type and ID. document:roadmap_2026
Relation The type of relationship between the user and the object. reader, owner, editor
User The principal accessing the object, which can be a user, a group, or even a public token. user:alice, group:devs#member

Example Tuple: document:report#reader@group:sales#member (A member of the 'sales' group is a reader of 'document:report').

2. Authorization Model (Schema)

The model is the **blueprint** that defines the object types, the valid relations, and the logic used to compute complex access rules. It is written in the **FGA Domain Specific Language (DSL)**.

The model defines relations in terms of other relations using specialized keywords:

Keyword Logic Description
define viewer as self Direct Grant User is explicitly granted access (via a tuple).
or writer Union (**OR**) If the user is a viewer **or** a writer, they are granted access.
but not banned Exclusion (**NOT**) User is a viewer but **not** a banned user.
from parent Computed Userset Access is granted via an existing relation on a related object (e.g., if you are the owner of the folder, you are the reader of the document inside).

3. API Endpoints (Operations)

OpenFGA provides a simple gRPC/REST API for applications to interact with the authorization data. The two primary operations are:

  • **Check:** The fundamental authorization query. It takes a user, a relation, and an object, and returns **true** or **false**.

    Query: Check(user:alice, reader, document:report)

  • **Write:** Used to create or delete relationship tuples. This is how access is granted or revoked.

    Query: Write(document:report#owner@user:bob)

  • **ListObjects:** Finds all objects of a given type that a specific user has a relation to. This is crucial for building user interfaces (e.g., "Show me all documents Alice can read").
  • **ListUsers:** Finds all users who have a specific relation with a given object.

💡 Benefits and Use Cases

Why Use OpenFGA?

  • **Performance and Scale:** Inheriting Zanzibar's distributed architecture, OpenFGA is built for low-latency checks at **massive scale**, often crucial for highly active APIs.
  • **Decoupling:** It **separates the authorization logic** from the application logic. Your application no longer needs to query multiple databases or run complex nested joins to figure out access.
  • **Strong Consistency:** Ensures that a change in access (a **Write**) is **immediately reflected** in subsequent access checks (**Check**), preventing security gaps caused by stale caches.
  • **Flexibility:** Easily models various authorization patterns, including:
    • **Role-Based Access Control (RBAC):** Defining access via roles (e.g., role:admin).
    • **Attribute-Based Access Control (ABAC):** Complex relations can model attributes (e.g., membership in a department group).
    • **Access Control Lists (ACLs):** Direct user-to-resource grants (e.g., direct sharing).

Common Use Cases

  • **Multi-Tenant SaaS Applications:** Defining permissions across different organizations and tenants (e.g., restricting a user to resources within their own tenant:id).
  • **Document and File Sharing:** Implementing complex sharing models like those found in Google Drive or Dropbox.
  • **Microservices:** Providing a centralized, consistent authorization layer that every microservice can query reliably.
