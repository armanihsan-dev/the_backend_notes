Rate Limiting

Rate limiting is a technique used in networking and application development to **control the rate of incoming or outgoing requests** for a service or resource, defining how many operations a client can perform within a specific time period.

⚙️ How Rate Limiting Works

Rate limiting works by enforcing a **policy** that defines the allowed request rate. When a request arrives, the system identifies the client (typically by **IP address** or **API key**), tracks their request count in a store, and makes a decision:

  • Check: The system checks the client's current request count against the **maximum limit** defined for the current time window.
  • Allow: If the count is below the limit, the request is **processed**, and the counter is incremented.
  • Deny/Throttle: If the count is at or above the limit, the request is **blocked**, and the client receives an **HTTP 429 "Too Many Requests"** status code, often including a Retry-After header.
  • Reset: The counter is reset once the time window expires.

🛡️ Why Use Rate Limiting?

The primary goals of implementing rate limiting are:

  • Prevent Abuse & Security: Mitigate **Denial-of-Service (DoS)** and **Distributed Denial-of-Service (DDoS)** attacks, brute-force attacks on login/registration endpoints, and spamming.
  • Resource Protection: Prevent specific users from consuming **excessive server resources** (CPU, memory, database connections), which ensures **fair usage** and maintains system stability for all users.
  • Cost Control: For services that use third-party APIs or cloud functions billed per use, limiting requests helps control operational costs.

💡 Common Use Cases

Area Example Endpoint Limit Objective
Security /login, /register, /forgot-password Limit attempts per IP address to prevent **brute-force attacks**.
API Access /api/v1/data Limit requests per API key/user per hour/day to enforce **subscription tiers** (e.g., Free vs. Premium).

⏱️ Rate Limiting Strategies

Different algorithms are used to implement the tracking and policy enforcement:

  • Fixed Window Counter:

    The simplest method. A fixed-size time window (e.g., 60 seconds) is used. Requests are counted until the window ends, then the counter is reset to zero.

    Limitation: It can lead to a **"burst" problem**, where a client makes the maximum allowed requests right before the window resets and then immediately makes another maximum burst right after, effectively doubling the rate in a short period around the reset boundary.

  • Sliding Window Log:

    The most accurate but resource-intensive. It stores a **timestamp log** for every request made by a client. When a new request comes, the system sums up all timestamps that fall within the current time window (e.g., the last 60 seconds). If the sum exceeds the limit, the request is denied.

    Benefit: Prevents the burst problem since the window effectively slides with the current time.

  • Token Bucket:

    Requests consume **tokens** from a bucket. Tokens are added to the bucket at a fixed rate (the refill rate). If a request arrives and the bucket has tokens, it consumes one and proceeds. If the bucket is empty, the request is blocked.

    Benefit: Allows for occasional bursts (up to the bucket size) while strictly limiting the long-term average rate.

  • Sliding Window Counter (Hybrid):

    Combines the fixed window and the sliding window log for better performance and accuracy. It uses the counts from the previous and current fixed windows, weighted by how much of the previous window has elapsed.

🖥️ Express.js Server Example and Explanation

The following example uses the **Fixed Window Counter** strategy for the /register endpoint.

Practical Example using Express.js

import express from "express";
import bcrypt from "bcrypt";

const app = express();
const PORT = 4000;
const rateLimitStore = {}


app.use((req, res, next) => {
  res.setHeader("Access-Control-Allow-Origin", "*");
  next();
});

app.get("/", (req, res) => {
  res.send("<h1>Hello World!</h1>");
});

function rateLimiter({ windowSize, numberOfRequest }) {
  return function (req, res, next) {
    const currentTime = Date.now()
    if (!rateLimitStore[req.ip]) {
      rateLimitStore[req.ip] = {
        startTime: currentTime,
        count: 1
      }
      return next()
    }
    if (currentTime - rateLimitStore[req.ip].startTime > windowSize) {
      rateLimitStore[req.ip] = {
        startTime: currentTime,
        count: 1
      }
    } else {
      if (rateLimitStore[req.ip].count > numberOfRequest) {
        return res.status(429).json({ message: "Too many requests. Please slow down." });
      }
      rateLimitStore[req.ip].count += 1
    }
    console.log(rateLimitStore);
    next()
  }
}

app.get(
  "/register",
  rateLimiter({ windowSize: 15000, numberOfRequest: 7 }),
  async (req, res) => {
    bcrypt.hashSync("123456", 14);
    return res.json({ message: "Registered Successfully" });
  }
);

app.listen(PORT, "0.0.0.0", () => {
  console.log(`🚀 Visit http://localhost:${PORT}`);
});

3. Middleware Logic

Step Code Section Explanation
New Client if (!rateLimitStore[req.ip]) { ... } If the IP is not in the store, this is the **first request**. Initialize the window with the current time and a count of 1. Allow the request (return next()).
Window Reset if (currentTime - rateLimitStore[req.ip].startTime > windowSize) { ... } If the difference is **greater than** windowSize (15,000ms or 15 seconds), the window has expired. Reset the window by setting a new startTime and a count of 1.
Limit Check if (rateLimitStore[req.ip].count > numberOfRequest) { ... } If the window is active, check if the current request count has **exceeded** the limit (numberOfRequest, which is 7). If it has, block the request and send **HTTP 429** response.
Increment rateLimitStore[req.ip].count += 1 If the request is allowed (the limit hasn't been reached), increment the request count for the IP.
Proceed next() Allows the request to continue to the target route handler (/register).

4. Implementation on Route

The middleware is applied to the /register route: 

app.get(
  "/register",
  rateLimiter({ windowSize: 15000, numberOfRequest: 7 }),
  // ... route handler ...
);

This configuration means a client is allowed a maximum of **7 requests** every **15 seconds** to the /register endpoint.

⚠️ Limitations of Rate Limiting

While essential, rate limiting has limitations:

  • IP Spoofing/NAT: Rate limiting by **IP address** can be ineffective in environments where many users share a single IP address (e.g., users behind a **NAT** firewall in an office or a mobile carrier) or where attackers can easily **spoof** IP addresses.
  • Distributed Attacks: Advanced **DDoS attacks** use a large botnet of unique IP addresses, making it difficult for simple IP-based rate limiting to block the attack without affecting legitimate users.
  • State Management: In a distributed system with multiple application servers, the rateLimitStore must be shared and synchronized (e.g., using **Redis**). Using a simple in-memory object (like in the example) only works for a **single server instance**.
  • User Experience: An overly strict rate limit can negatively impact legitimate user experience if they unintentionally hit the limit (e.g., rapid page refreshes).
