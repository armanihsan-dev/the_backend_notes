🔑 What is a CSRF Token?

A **CSRF Token** (or **Anti-CSRF Token**) is a unique, secret, and unpredictable value generated by the server and included in every sensitive request (like POST, PUT, DELETE) that modifies data.

The purpose of a CSRF token is to protect your application when your server must set a cookie with SameSite=None, ensuring secure cross-site requests.

How it Prevents CSRF Attacks

The CSRF Token employs the **Synchronizer Token Pattern**.

  • Server Generates and Stores: When the user loads a form page (e.g., /), the server generates a unique token and stores it in the user's **session** (or in a secure, non-HTTP-only cookie).
  • Form Inclusion: The token is embedded as a **hidden field** inside the HTML form.
  • Request Validation: When the user submits the form, the token is sent in the request body along with the other form data. The server then compares the token in the **request body** to the token stored in the session/cookie.
  • Rejection: An attacker, operating from a different domain, **cannot read the legitimate token** embedded in your form due to the browser's **Same-Origin Policy**. Therefore, the forged request they submit will either be missing the token or contain an invalid one, causing the server to reject the transaction.

🛠️ Generating and Implementing CSRF Token in Your Express Server

To implement CSRF protection, we'll use a widely adopted solution for Node.js: the **csurf** middleware (which often requires the use of the **express-session** middleware for session management, or a cookie parser for storage).

Since your current server uses cookie-parser but not express-session, we'll use a slightly different, common setup that uses a package to generate and validate the token and store the secret **in a cookie**.

Step 1: Install Required Packages

You will need the csurf middleware and a library to generate unique IDs, like uid-safe.

Bash
npm install express-session csurf uid-safe

(Note: We'll introduce express-session as it's the standard way to handle the secret, making the solution more robust than just cookie-based secrets.)

Step 2: Modify Your Server Code

Here is the updated and corrected server code using the standard express-session and csurf implementation.

JavaScript
import express from "express";
import cookieParser from "cookie-parser";
import session from "express-session"; // 1. Import session middleware
import csrf from "csurf"; // 2. Import csurf middleware

const app = express();
const PORT = 4000;
let amount = 10000;

// Set up middleware
app.use(cookieParser());
app.use(express.urlencoded({ extended: false })); // To read POST body data

// 3. Configure and use session middleware
// This is required for csurf to store the secret key server-side.
app.use(session({
    secret: 'A_LONG_AND_VERY_SECRET_STRING_34890', // Use a secure, long secret key
    resave: false,
    saveUninitialized: true,
    cookie: { 
        httpOnly: true, 
        sameSite: 'lax',
        secure: true // Should be true in production (HTTPS)
    }
}));

// 4. Use csurf middleware
// This generates the token and stores it in the session and a cookie.
const csrfProtection = csrf({ cookie: true });
app.use(csrfProtection); // Apply it globally or just to routes that need protection

// Middleware to set CSP (Your existing middleware)
app.use((req, res, next) => {
    if (req.headers.accept?.includes("text/html")) {
        res.setHeader("X-Frame-Options", "DENY");
        res.setHeader(
            "Content-Security-Policy",
            `default-src 'self'; script-src 'self';\
            frame-ancestors 'none'`
        );
    }
    next();
});

// Serve dynamic HTML with the CSRF Token
app.get("/", (req, res) => {
    // Check for login (simulated by your sid cookie)
    if (!req.cookies.sid) {
        return res.send('You are not logged <br> <a href="/login">Login</a>');
    }

    // 5. Get the CSRF token generated by the csurf middleware
    const csrfToken = req.csrfToken(); 

    res.send(`
        <!DOCTYPE html>
        <html>
        <head>
          <title>Secure Bank App</title>
          <meta charset="UTF-8" />
        </head>
        <body>
          <h1>Amount: ₹<span id="amount">${amount}</span></h1>
          <form method="POST" action="/pay">
            <input type="hidden" name="_csrf" value="${csrfToken}">
            <button type="submit">Pay</button>
          </form>
        </body>
        </html>
    `);
});

// Handle payment (This route is automatically protected by the csurf middleware applied globally)
app.post("/pay", (req, res) => {
    // csurf has already verified the token before this middleware runs.
    if (!req.cookies.sid) {
        return res.send("You are not logged.");
    }
    
    // The request body contains the validated token, e.g., req.body._csrf
    amount -= 1000;
    console.log(`Amount deducted. New balance: ₹${amount}`);
    res.redirect("/");
});

app.get("/login", (req, res) => {
    res.cookie("sid", "54321", {
        httpOnly: true,
        sameSite: 'lax',
        secure: true
    });
    res.redirect("/");
});

app.listen(PORT, () => {
    console.log(`🚀 Visit http://localhost:${PORT}`);
});

Key Changes Explained

express-session: This is used to store the secret key that csurf uses to generate and validate the token.

csrf (from csurf): We initialize this middleware and apply it using app.use(csrfProtection). It performs two main tasks:

  • GET/Initial Request: It generates a new token and makes the method req.csrfToken() available. It also sets a **CSRF secret cookie** in the user's browser.
  • POST/Sensitive Request (/pay): It automatically checks the token submitted in the form body (req.body._csrf) against the secret stored in the session/cookie. If they don't match, it throws an error and the request is blocked.

req.csrfToken(): In your / (GET) route, we call this method to retrieve the unique token for the current user's session.

Hidden Input Field: We embed the retrieved token inside the payment form using a hidden input field named _csrf:

HTML
<input type="hidden" name="_csrf" value="${csrfToken}">

The csurf middleware is configured to look for this specific field name in the POST request body for validation.

With these changes, your /pay route is now protected by the CSRF token. Any request coming from an external malicious domain will be rejected because it won't be able to provide the secret, dynamically generated token.
