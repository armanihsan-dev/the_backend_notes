# Important Security Headers for Web Applications

Security headers help protect your website from common attacks like XSS, clickjacking, data injection, and more. Here's a list of the most important ones, starting with the most critical.

🛠️ Express.js Setup with helmet

We'll use a single app.use(helmet({...})) block to configure all the headers that helmet supports, and a separate middleware for those it doesn't.

Bash


# Install required packages
npm install express helmet

server.js (ES6 Syntax)


import express from 'express';
import helmet from 'helmet';

const app = express();
const port = 3000;

// ===============================================
// 1. HELMET MIDDLEWARE (Handles Headers 1-5, 8, 9)
// ===============================================
app.use(helmet({
    // 1. Content-Security-Policy (CSP) - Requires custom config
    contentSecurityPolicy: {
        directives: {
            defaultSrc: ["'self'"], 
            scriptSrc: ["'self'", 'https://apis.example.com'], // Example from prompt
            imgSrc: ["'self'", 'data:'], // Allow self and data URIs for images
            styleSrc: ["'self'", "'unsafe-inline'"], // Note: unsafe-inline should be avoided if possible
            frameAncestors: ["'self'", 'https://trusted-partner.com'], // CSP way to replace X-Frame-Options
        },
    },
    // 2. X-Frame-Options (via frameguard) - Set to DENY for maximum security
    frameguard: {
        action: 'deny' 
    },
    // 3. X-Content-Type-Options (via noSniff) - Enabled by default, explicitly setting to ensure it's on
    noSniff: true, 
    // 4. Strict-Transport-Security (HSTS) - Set the recommended max-age
    hsts: {
        maxAge: 63072000, // 2 years
        includeSubDomains: true,
        preload: true, // For HSTS preload list submission
    },
    // 5. Referrer-Policy
    referrerPolicy: {
        policy: "no-referrer-when-downgrade"
    },
    // 8. Cross-Origin-Opener-Policy (COOP)
    crossOriginOpenerPolicy: {
        policy: "same-origin"
    },
    // 9. Cross-Origin-Resource-Policy (CORP)
    crossOriginResourcePolicy: {
        policy: "same-origin"
    }
}));

// ===============================================
// 2. MANUAL MIDDLEWARE (Headers 6 & 7 are set manually)
// ===============================================

// 6. Permissions-Policy (formerly Feature-Policy)
app.use((req, res, next) => {
    // Blocks access to sensitive device APIs entirely
    res.setHeader('Permissions-Policy', 'geolocation=(), microphone=(), camera=()');
    next();
});

// 7. Cross-Origin-Embedder-Policy (COEP)
app.use((req, res, next) => {
    // Crucial for enabling performance features like SharedArrayBuffer
    res.setHeader('Cross-Origin-Embedder-Policy', 'require-corp');
    next();
});

// Simple route for demonstration
app.get('/', (req, res) => {
    res.send('<h1>Application Secured with All Important Headers!</h1>');
});

app.listen(port, () => {
    console.log(`Server running securely at http://localhost:${port}`);
});

🛡️ Header Deep Dive: Definition, Syntax, and Mechanism

1. Content-Security-Policy (CSP)

  • Definition: CSP is an anti-XSS and anti-data injection mechanism that dictates which content sources (scripts, styles, images) a browser can trust and execute.
  • Syntax: 
    Content-Security-Policy: <directive> <source-list>; ...
  • Mechanism: When the browser receives the page, it parses the CSP header and creates a whitelist for different resource types. If a resource (e.g., a JavaScript file) is requested from a domain not explicitly on the list, the browser blocks the request, preventing the execution of malicious injected code.
Directive Purpose Example Rule
default-src Fallback for any content type. 'self'
script-src Sources for JavaScript. 'self' https://trusted-cdn.com
frame-ancestors Controls embedding (replaces X-Frame-Options). 'none' or 'self'

2. X-Frame-Options (Deprecated, but widely supported)

  • Definition: A legacy header used specifically to prevent clickjacking attacks by controlling whether a page can be rendered inside a <frame>, <iframe>, <embed>, or <object>.
  • Syntax: 
    X-Frame-Options: DENY
  • Mechanism: When the browser attempts to render your page inside another site's frame:
    • DENY: The browser completely refuses to render the content.
    • SAMEORIGIN: The browser checks the top-level URL. If it matches your site's origin, it renders; otherwise, it blocks the frame.
  • Note: frame-ancestors in CSP is the modern, preferred replacement for this header.

3. X-Content-Type-Options

  • Definition: A header with a single value, nosniff, that prevents browsers from overriding the Content-Type header (MIME sniffing).
  • Syntax: 
    X-Content-Type-Options: nosniff
  • Mechanism: Without this header, a browser might see a file declared as text/plain but mistakenly interpret it as executable JavaScript, leading to a security vulnerability. nosniff **forces the browser to honor the declared Content-Type**, preventing the misinterpretation of files.

4. Strict-Transport-Security (HSTS)

  • Definition: A header sent only over a secure HTTPS connection that instructs the browser to communicate with the domain (and optionally its subdomains) using HTTPS only for a specified period.
  • Syntax: 
    Strict-Transport-Security: max-age=<seconds>; includeSubDomains; preload
  • Mechanism: It addresses **protocol downgrade attacks** and cookie hijacking over unsecured Wi-Fi. The browser creates an internal "HSTS list" and, for the duration of max-age, will automatically rewrite any http:// request to https:// **before** the request even leaves the client, ensuring a secure connection.

5. Referrer-Policy

  • Definition: Controls how much information about the original page (the referrer) is included when a user clicks a link to a new destination. This mitigates the risk of sensitive URLs or session identifiers leaking to third parties.
  • Syntax: 
    Referrer-Policy: <policy-value>
  • Mechanism: The policy determines what value is put into the Referer HTTP header. For example:
    • no-referrer: Sends no Referer header at all.
    • no-referrer-when-downgrade: Sends the full URL only when navigating from HTTPS to HTTPS, and sends nothing when navigating from HTTPS to HTTP. This is a common and secure default.

6. Permissions-Policy (formerly Feature-Policy)

  • Definition: Allows a site to explicitly allow or deny its use of browser features, such as device sensors (camera, microphone, geolocation), full-screen mode, or asynchronous scripts.
  • Syntax: 
    Permissions-Policy: <feature-name>=<allow-list>; ...
  • Mechanism: This header acts as a **sandbox**, preventing embedded third-party content (like ads or analytics scripts) from accessing sensitive APIs without explicit permission. The () value in the example means the feature is **denied** to all origins, including the current one.

7. Cross-Origin-Embedder-Policy (COEP)

  • Definition: A crucial header for enabling Cross-Origin Isolation. It prevents a document from loading any cross-origin resource unless that resource explicitly grants permission via CORS or the Cross-Origin-Resource-Policy (CORP) header.
  • Syntax: 
    Cross-Origin-Embedder-Policy: require-corp
  • Mechanism: By setting this to require-corp, you ensure all cross-origin resources are checked. This isolation is necessary to enable high-performance features like SharedArrayBuffer and performance.measureUserAgentSpecifics.

8. Cross-Origin-Opener-Policy (COOP)

  • Definition: Controls whether a document can share a **browsing context group** (i.e., communicate via JavaScript) with cross-origin pop-ups or iframes it opens.
  • Syntax: 
    Cross-Origin-Opener-Policy: same-origin
  • Mechanism: This protects against **tab-nabbing** and side-channel attacks like Spectre.
    • same-origin: Isolates the document from any pop-up it opens unless the pop-up has the same origin.
    • same-origin-allow-popups: Allows pop-ups to retain their opener relationship, but prevents the opener from being opened by a cross-origin document.

9. Cross-Origin-Resource-Policy (CORP)

  • Definition: Used by the resource owner to explicitly prevent other, potentially malicious, websites from loading their sensitive resources (like JSON files or images) via embedding mechanisms like <img>, <script>, or fetch().
  • Syntax: 
    Cross-Origin-Resource-Policy: same-origin
  • Mechanism: This stops unauthorized embedding of your content, protecting against data leakage attacks like Cross-Site Request Forgery (CSRF) for read operations.
    • same-origin: Only allows resources to be loaded by pages from the exact same origin.
    • cross-origin: Allows resources to be loaded by any origin (use with caution).
    • same-site: Allows resources to be loaded by pages from the same site (different origins, same domain).
