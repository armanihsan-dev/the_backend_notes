Scalable Rate Limiting with Redis

Using the express-rate-limit package with **Redis** as a store is the standard, scalable way to implement rate limiting in a Node.js API.

Here is a deep dive, covering the definitions, syntax, a complete practical example, and how it all works together.

🔒 Implementing Scalable Rate Limiting

To implement rate limiting using express-rate-limit with Redis, we need three core components:

Component Definition Role in Rate Limiting
express-rate-limit An Express.js middleware package. Defines the **policy** (window, limit) and enforces the rate limiting logic.
ioredis A fast, robust client for Redis. The primary **caching/storage layer** that holds the request counts for every IP address across all application servers.
rate-limit-redis A store adapter for express-rate-limit. Connects the middleware to the Redis client so it can persist counts outside of the application's memory.

1. Project Setup and Installation

Before starting, ensure you have a running **Redis server** accessible to your application. 

# Install the core packages
npm install express express-rate-limit ioredis rate-limit-redis

2. Complete Practical Example

This example sets a limit of **5 requests per IP address every 1 minute** for the /api/login route. 

// server.js
import express from 'express';
import rateLimit from 'express-rate-limit';
import Redis from 'ioredis';
import RedisStore from 'rate-limit-redis';

// --- 1. REDIS CONFIGURATION ---
// Connect to Redis (assuming it's running on localhost:6379)
const redisClient = new Redis({
  port: 6379,
  host: '127.0.0.1',
});

// Handle connection errors
redisClient.on('error', (err) => {
  console.error('Redis Error:', err);
});

// --- 2. RATE LIMITER CONFIGURATION ---
const limiter = rateLimit({
  // The store (Redis) is used to track and store request counts
  store: new RedisStore({
    // @ts-expect-error - TODO: Known issue with store typings
    sendCommand: (...args) => redisClient.call(...args),
  }),
  
  // 1 minute window (in milliseconds)
  windowMs: 60 * 1000, 
  
  // Limit each IP to 5 requests per `windowMs`
  max: 5, 

  // Send an HTTP 429 status code on rate limit exceeded
  standardHeaders: true, // Return rate limit info in the `RateLimit-*` headers
  legacyHeaders: false,  // Disable the deprecated `X-RateLimit-*` headers
  
  // Custom message when rate limited
  message: {
    status: 429,
    message: "Too many requests from this IP, please try again after a minute.",
  },
});


// --- 3. EXPRESS SERVER SETUP ---
const app = express();
const PORT = 4000;

app.use(express.json());

// Apply the rate limiter middleware only to the API routes
app.use("/api/", limiter);

// Public route - No limit applied
app.get('/', (req, res) => {
  res.send('<h1>Welcome to the API!</h1>');
});

// Protected route - Rate Limit applied (max 5 requests/min)
app.post('/api/login', (req, res) => {
  // Authentication logic here (e.g., check username/password)
  res.json({ message: 'Login successful.' });
});

// Start server
app.listen(PORT, '0.0.0.0', () => {
  console.log(`🚀 API Server running on http://localhost:${PORT}`);
});

🧠 How the Implementation Works

The express-rate-limit package uses the **Fixed Window Counter** algorithm by default, which is managed entirely by Redis in this setup.

A. Initialization

  • Redis Client: const redisClient = new Redis(...) establishes a persistent connection to the Redis server.
  • Redis Store Adapter: new RedisStore({ sendCommand: ... }) creates an adapter that translates the requests from the rateLimit middleware into native Redis commands.

B. Request Flow and Redis Interaction

When a client sends a request to a rate-limited endpoint (e.g., POST /api/login):

  1. Key Generation: The rateLimit middleware determines the unique key to track. By default, this is the client's **IP address** (e.g., 127.0.0.1).
  2. Redis Command: The RedisStore executes a combined Redis command to **atomically check and update the count**.
    • It uses the **INCR** command to increment the counter for the IP key.
    • It uses the **EXPIRE** command to set a **Time-To-Live (TTL)** on the key, which corresponds to the windowMs (1 minute). This ensures the key is automatically deleted when the time window expires, resetting the limit.
  3. Policy Decision:
    • If the incremented count is $\le 5$ (the max limit): The request is allowed, and the middleware calls next().
    • If the incremented count is $ > 5$: The request is blocked, and the middleware immediately sends the custom 429 Too Many Requests response.

C. Scalability

By using **Redis**, the request count for a single IP is stored in a **centralized, shared store**.

  • If you have **multiple Express servers** (e.g., running behind a load balancer), they all check the **same Redis store** before processing the request.
  • This prevents a client from being able to bypass the limit by simply hitting a different server instance, which is a key weakness of the in-memory store.
