💉 Deep Dive into SQL Injection (SQLi) Vulnerability

SQL Injection (SQLi) is a type of attack that exploits vulnerabilities in an application's code by injecting malicious Structured Query Language (SQL) statements into an entry field (like a login form or URL parameter) that is then executed by the application's backend database. This occurs when an application dynamically constructs a SQL query string using user-supplied input without properly validating or sanitizing that input.

The core vulnerability is the failure to separate the application's **control plane** (the SQL command) from the **data plane** (the user's input).

🛠️ How SQLi Works (The Flaw)

A typical, vulnerable application might construct a SQL query like this: 

query = "SELECT * FROM users WHERE username = '" + user_input + "';"

If a legitimate user enters **jsmith**, the executed query is: SELECT * FROM users WHERE username = 'jsmith';

If an attacker enters a malicious payload, such as **' OR '1'='1**, the executed query becomes: SELECT * FROM users WHERE username = '' OR '1'='1';

Since **'1'='1'** is always true, the WHERE clause evaluates to true for **every row**, potentially returning all user records, thus **bypassing authentication** or disclosing unauthorized data. Attackers often use the SQL comment characters (**--** or **#**) to ignore the rest of the original query's logic.

🔥 Common MongoDB Injection Vectors using mongoDB queries

🔹 1. Logical Operators

Operator Risk Example
$ne Matches anything not null { name: { $ne: null } }
$gt Matches anything "greater" { name: { $gt: "" } }
$exists Bypasses required fields { password: { $exists: false } }

🔹 2. Regex Injection

Code vulnerability example:

find({ username: { $regex: req.body.username } })

Attack input: { "username": ".*" }

→ matches all usernames. Can also cause **ReDoS (regex denial of service)** if the regex is complex or nested.

🔹 3. Array Injection

If you're using **$in** and accept user input as an array:

find({ role: { $in: req.body.roles } })

Attack input: { "roles": [ { "$ne": "admin" } ] }

→ This can match any role that's not "admin".

🔹 4. Nested Operators via JSON Parsing

If you do something like:

const filters = JSON.parse(req.body.query); // 🧨 dangerous
find(filters);

Then the attacker can send: { "isAdmin": { "$ne": false } }

→ and bypass any role-based condition.

🔹 5. Projection Abuse

If you allow projections from user input:

find({}, req.body.fields)

And the attacker sends: { "password": 1 }

→ They can extract sensitive fields like hashed passwords or tokens.

🔹 6. Command Injection (less common but real)

Some older MongoDB driver setups or ORMs allow users to specify parts of the query pipeline — if not validated, a user could inject: 

{ "$where": "this.password.length < 100" }

→ which executes raw JavaScript in Mongo (⚠️ **eval-like behavior**).

🛡️ How to Prevent Mongo Attacks

Strategy Description
Use Zod or similar Validate all user input before passing to Mongo queries
Never trust objects from client Don’t allow { key: { $ne: null } } to be constructed from raw input
Avoid passing raw query/filter Don’t do find(req.body)
Whitelist fields explicitly Only accept known filter keys and sanitize values
Cast IDs with ObjectId.isValid() Prevent ID-based injection attacks

✅ Summary of Risky Operators for Mongo Injection

Type Operators Logic
Logic $ne, $gt, $lt, $exists, $eq All comparative operators
Regex $regex, $options Regex matching
Array $in, $nin Array inclusion/exclusion
JS Eval $where, $function, $accumulator Executing raw JS in Mongo
Projection dynamic field selection (e.g. { password: 1 })

📜 The Genesis of SQL Injection

The history of SQL Injection (SQLi) officially begins in **1998** with its public documentation, but the vulnerability's existence is tied to the introduction of dynamic database query generation in web applications.

1. The Discovery (1998)

  • **The Researcher:** The SQL injection attack vector was first publicly documented by security researcher **Jeff Forristal**, who wrote under the alias "Rain Forest Puppy" (RFP).
  • **The Publication:** His findings were detailed in an article titled "NT Web Technology Vulnerabilities" in **Phrack Magazine, Issue 54, in December 1998**.
  • **The Vulnerability:** RFP demonstrated how an attacker could "piggyback" unauthorized SQL commands onto legitimate commands by inserting simple characters like a single quote (**'**) into an input field, which was then executed by an unsecured Microsoft SQL Server product. The core problem was the **vulnerable practice of concatenating user input directly into the SQL query string.**

2. The Early 2000s: The Rise to Notoriety

While documented in 1998, SQLi did not gain widespread notoriety until the early 2000s when dynamic web development and connected databases became the norm.

  • **OWASP Top 10:** Since the inception of the **Open Web Application Security Project (OWASP) Top 10** list in **2003**, SQL Injection (or the broader "Injection" category) has consistently been ranked as one of the most critical and widespread web application security risks, often taking the number one spot.
  • **Major Breaches:** As web applications became the gateway to vast amounts of sensitive data, successful SQLi attacks began to cause massive, high-profile data breaches, including:
    • **Heartland Payment Systems (2009):** One of the largest breaches at the time, resulting in the theft of over **100 million** credit and debit card numbers.
    • **Sony Pictures (2011):** Attacked using SQLi, leading to the leak of personal information for **millions** of users.

🛠️ Developer Response and Security Upgrades

The industry's response to SQLi has been a gradual shift from **reactive filtering** to **proactive secure coding practices**.

1. Initial Ineffective Defense (Blacklisting)

The initial, primitive defense involved the **blacklist approach**, which was quickly proven insufficient:

  • **Strategy:** Developers attempted to clean user input by manually checking for and stripping malicious characters or keywords, such as the single quote (**'**), double dashes (**--**), or the word **UNION**.
  • **Failure:** Attackers easily bypassed these filters by using alternative encodings (like hex or URL encoding) or by employing advanced, lesser-known SQL syntax, turning defense into an **unwinnable race**.

2. The Modern Standard: Parameterized Queries

The most significant and effective security upgrade was the adoption of **Parameterized Queries** (or Prepared Statements) as the industry standard.

Security Upgrade Description Why It Works
**Parameterized Queries** The application separates the SQL command logic from the user-supplied data. Placeholders are used in the query template. The database receives the user input as **literal data only**, not as executable SQL code. Malicious input is treated as an impossible username/value, not a command.
**Principle of Least Privilege** The database user account that the web application connects with is restricted to only the necessary permissions (e.g., only **SELECT** access, no **DROP TABLE** or **DELETE** rights). This mitigates the **impact** of a successful SQLi attack, preventing the attacker from causing major structural damage or unauthorized administrative actions.
**Strict Input Validation** Employing a **Whitelisting** approach, where input is strictly checked against an approved list of characters, formats, and types (e.g., a field expecting a numeric ID must reject any non-digit characters). This reduces the chance of injection by rejecting malformed or unexpected data **before** it ever reaches the query construction logic.

This evolution—from simply trying to strip out known bad input to fundamentally changing how code interacts with data—is the primary reason why SQLi is preventable today, though it remains a persistent threat due to the maintenance of legacy code and continuous coding errors.
