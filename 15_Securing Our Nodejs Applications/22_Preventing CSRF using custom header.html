Deep Dive: CSRF Prevention with Custom Headers

1. Why CSRF Happens (simple & clear)

CSRF happens because:

  • ✔ Browsers automatically attach cookies even on cross-site requests

Example:

A user is logged in at:

bank.com

Attacker page sends:

<form method="POST" action="https://bank.com/pay">
</form>

Browser automatically attaches:

Cookie: session=abc123

→ Server cannot know the request came from attacker.com.

This is CSRF.

2. How Custom Header Prevents CSRF

Attackers cannot set custom request headers (like X-CSRF-Token) from:

  • HTML forms ❌
  • Image tags ❌
  • Script tags ❌
  • iframes ❌
  • Links ❌

Only JavaScript on the same origin can set custom headers.

So if your client sets:

fetch("/pay", {
  method: "POST",
  headers: {
    "X-CSRF-Token": "12345"
  }
});

Then the attacker cannot:

  • run JS due to CORS ❌
  • send custom header ❌
  • bypass the requirement ❌

Therefore, custom header = strong CSRF prevention.

3. The “Double Submit Cookie” Pattern (the correct method)
  • 📌 Server sets a non-HttpOnly cookie called csrfToken.
  • 📌 Client reads that cookie using document.cookie and sends it back inside a custom header (X-CSRF-Token).
  • 📌 Server compares the cookie value with the header value.

If they match → request is valid.

If not → CSRF attack.

This works because:

Attackers can’t:

  • read cookies → browser blocks cross-site cookie reading
  • send custom headers → CORS blocks them
  • guess your token → random & long
4. Practical Example — Complete Express.js CSRF Protection

✔ Step 1 — Install dependencies

npm install express cookie-parser

✔ Step 2 — Server generates CSRF token and sets cookie 

import express from "express";
import cookieParser from "cookie-parser";
import crypto from "crypto";

const app = express();
app.use(cookieParser());
app.use(express.json());

// Generate token
function generateToken() {
  return crypto.randomBytes(20).toString("hex");
}

// Middleware: attach csrf cookie if not exist
app.use((req, res, next) => {
  if (!req.cookies.csrfToken) {
    const token = generateToken();
    res.cookie("csrfToken", token, {
      sameSite: "strict",   // reduce CSRF chance
      secure: false,        // set true in production (https)
    });
  }
  next();
});

✔ Step 3 — CSRF Validate Middleware

function csrfProtection(req, res, next) {
  const csrfCookie = req.cookies.csrfToken;
  const csrfHeader = req.headers["x-csrf-token"];

  if (!csrfHeader || csrfHeader !== csrfCookie) {
    return res.status(403).send("CSRF Attack Blocked!");
  }

  next();
}

✔ Step 4 — Protected POST route

app.post("/pay", csrfProtection, (req, res) => {
  return res.send("Payment Success!");
});

✔ Step 5 — Frontend Example (Same Origin)

Automatically send header using fetch:

<script>
  const csrf = document.cookie
    .split("; ")
    .find(row => row.startsWith("csrfToken="))
    ?.split("=")[1];

  async function pay() {
    const res = await fetch("/pay", {
      method: "POST",
      credentials: "include",
      headers: {
        "Content-Type": "application/json",
        "X-CSRF-Token": csrf,
      }
    });
    alert(await res.text());
  }
</script>
<button onclick="pay()">Pay</button>
  • ✔ Custom header added
  • ✔ Cookies included
  • ✔ Tokens compared
  • ✔ CSRF prevented
5. Why Attackers CANNOT Bypass This

❌ Attacker cannot set X-CSRF-Token

Browsers block custom headers from attackers unless server explicitly allows it via CORS: 

Access-Control-Allow-Headers: X-CSRF-Token

Since attacker.com does NOT have this permission → fetch fails at preflight.

❌ Attacker cannot read your CSRF cookie

document.cookie is blocked in cross-site contexts.

❌ Attacker cannot guess the token

Token is long & random.

❌ Attacker’s HTML form cannot attach custom header

Only JavaScript can, but JS from attacker.com cannot run on your domain (same-origin policy).

✔ Fully secure.

6. Quick Summary Table

Custom header + token ❌ No attacker can't set header & JS blocked by CORS
