SameSite Cookie Attribute Notes

🍪 What is the SameSite Cookie Attribute?

The SameSite cookie attribute is a flag that tells a browser whether a cookie should be sent along with cross-site requests.

Its primary purpose is to mitigate risks associated with Cross-Site Request Forgery (CSRF) attacks and to help protect user privacy by limiting the exposure of cookies to third-party contexts.

---

💡 Why It Matters and History of SameSite

Why It Matters

The SameSite attribute matters because, by default, cookies are sent with all requests made to the server domain, including those initiated from a completely different domain (a "cross-site" request). This behavior enables CSRF attacks.

  • Before SameSite: An attacker could trick a user's browser into sending a request (e.g., a bank transfer) to a target site that the user is logged into. Since the user's session cookie would automatically be included, the target site would treat the request as legitimate.
  • With SameSite: The browser is instructed to withhold the cookie in many cross-site request scenarios, effectively blocking the CSRF vector.

History and Introduction

  • Introduction (2016): The SameSite attribute was first introduced in 2016 as an optional flag that developers could implement to protect against CSRF.
  • Chrome's Default Change (2020 - "SameSite by Default"): This was the major shift. Google Chrome, followed by other major browsers (Firefox, Edge), began enforcing a new default behavior:
    • If a cookie did not specify a SameSite attribute, the browser would treat it as SameSite=Lax. This significantly boosted security by automatically protecting older sites that hadn't adopted the attribute.
    • To allow a cookie to be used in a third-party (cross-site) context, developers were forced to explicitly set SameSite=None and also require the Secure attribute (meaning the cookie must be sent over HTTPS).
---

⚙️ SameSite Attribute Values and Their Effect

The SameSite attribute accepts three primary values, defining the conditions under which a cookie will be sent with a request.

Value Cookie Sent for Cross-Site Requests? How It Works Security Implication
Strict No (Only for same-site requests) The cookie is only sent for requests where the site in the URL bar exactly matches the cookie's domain. The cookie is withheld even when navigating from an external link. Highest Security. Provides excellent protection against CSRF. Can be inconvenient, as a user clicking an external link to your site might arrive logged out.
Lax Yes, only for safe top-level navigations. The cookie is withheld for most cross-site requests (e.g., image loads, XHR/Fetch). However, it is sent for a top-level navigation (e.g., clicking a link) that uses a "safe" HTTP method like GET. Good Default Security. Protects against typical CSRF attack vectors while allowing a better user experience (users remain logged in when navigating from external sites).
None Yes (For all cross-site requests) The cookie is sent with all cross-site requests, provided it is also set with the Secure attribute. Lowest Security/Highest Compatibility. Required for legitimate cross-site use cases, such as an API cookie used by a frontend hosted on a different domain or cookies used for third-party embedding.

Note: The "same-site" definition is based on the registrable domain (the domain plus the top-level domain). For example, app.example.com and api.example.com are considered same-site because they share the registrable domain example.com.

---

🔐 Security Implications and Use Cases

1. Protection Against CSRF

SameSite=Strict and Lax are the primary defenses against CSRF. They prevent an attacker's external site from successfully including the user's session cookie in a malicious request to your application.

2. Cross-Site Usage (Third-Party Cookies)

Use Case: You are running an application where your frontend is hosted on frontend.com and your backend API is hosted on api.com. When the frontend makes an API call, it is a cross-site request.

Solution: For the session cookie to be included in the API request, it must be set to: 

SameSite=None; Secure

This signals to the browser that this cookie is intended to be a third-party cookie and requires the connection to be secure (HTTPS).

3. Privacy

By defaulting to SameSite=Lax, modern browsers are effectively phasing out third-party cookies (cookies used for tracking across different sites), enhancing user privacy.

💻 Practical Example in Express.js

In an Express.js application, you primarily configure cookies using the built-in res.cookie() method or via the popular express-session middleware.

1. Setting a Cookie with SameSite=Lax (Default and Recommended)

This is the standard, secure way to set a session cookie. The user will be logged out if they navigate to your site from a POST request on another site, but not if they click a simple link (GET).

JavaScript

// Express route handler
app.get('/login',  (req, res) => {
  // Sets a cookie that will be sent for same-site requests and GET top-level navigations.
  res.cookie('session_id', 'user123', {
    maxAge: 3600000, // 1 hour
    httpOnly: true, // Good practice: prevents client-side JavaScript access
    secure: true, // Good practice: require HTTPS
    sameSite: 'Lax' // Explicitly setting the default for clarity
  });
  res.send('Logged in with Lax cookie.');
});

2. Setting a Cookie with SameSite=None (For Cross-Site APIs)

Use this only when you explicitly need the cookie to be sent with cross-site requests (e.g., a frontend on domain-a.com calling an API on domain-b.com). You MUST include secure: true.

JavaScript

// Express route handler for a cross-site API
app.get('/api/cross-site-endpoint',  (req, res) => {
  // Sets a cookie that WILL be sent for cross-site requests
  res.cookie('cross_site_session', 'api_token_xyz', {
    maxAge: 3600000,
    httpOnly: true,
    secure: true, // MANDATORY when SameSite=None
    sameSite: 'None' // Allows third-party usage
  });
  res.send('Cookie set for cross-site usage.');
});

3. Using express-session

If you are using the express-session middleware, you configure the SameSite setting in the options object:

JavaScript

const session = require('express-session');

app.use(session({
  secret: 'a_secure_secret_key', // Used to sign the session cookie
  resave: false,
  saveUninitialized: true,
  cookie: {
    // Set the cookie properties here
    httpOnly: true,
    secure: true, // Set to true if you are behind HTTPS
    sameSite: 'Lax' // Or 'None' if needed for cross-site
  }
}));
