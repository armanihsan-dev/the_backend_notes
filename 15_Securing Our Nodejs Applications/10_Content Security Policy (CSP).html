Content Security Policy (CSP) Notes

A **Content Security Policy (CSP)** is a computer security standard that acts as an added layer of defense against certain types of attacks, primarily **Cross-Site Scripting (XSS)** and **clickjacking**.

It works by allowing website administrators to explicitly **define which resources** (like scripts, styles, images, and media) are trusted and allowed to be loaded by a user's browser for a given page. Think of CSP as a **"whitelist" mechanism** for web resources.

🛡️ Why is CSP Important?

CSP is a critical security measure because it helps mitigate attacks that exploit the browser's implicit trust in the content it receives from a server.

Mitigates Cross-Site Scripting (XSS):

This is the main benefit. XSS attacks occur when an attacker injects malicious scripts into a trusted website. Without CSP, the browser executes this malicious script because it appears to come from the trusted source. A well-configured CSP prevents this by:

  • **Restricting script sources:** Only allowing scripts to load from explicitly whitelisted domains.
  • **Blocking inline code:** Disabling the execution of inline JavaScript (``) and inline CSS (`style="..."`), which are common vectors for XSS.
  • **Blocking eval() and similar functions:** Preventing the execution of dynamic code from strings.

Prevents Clickjacking:

Content Security Policy (CSP) can prevent clickjacking by using the frame-ancestors directive in an HTTP response header. This directive instructs the browser which domains are permitted to embed the web page in a frame (such as an iframe, frame, or object tag), thereby preventing malicious sites from framing the content

  • How the frame-ancestors directive works
  • Content-Security-Policy: frame-ancestors 'self' https://trusted-site.com

Enforces Secure Connections (HTTPS):

Directives like **`upgrade-insecure-requests`** can instruct the browser to rewrite all HTTP URLs to HTTPS, enforcing encryption and protecting against man-in-the-middle attacks.

⚙️ How Does CSP Work?

A Content Security Policy is delivered to the user's browser, which then enforces the policy's rules.

1. Delivery

The policy is primarily delivered using the **`Content-Security-Policy` HTTP response header.**

// Example Header: HTTP

Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.trusted.com; img-src 'self' data:;

A less-recommended alternative (which has some limitations) is to use an HTML `` tag:

// HTML

<meta http-equiv="Content-Security-Policy" content="default-src 'self';">

2. Directives

✅ A directive are some rule that tells the browser what is allowed and what is blocked.

The policy consists of one or more directives, separated by semicolons. Each directive controls a specific resource type or security behavior.

Directive Purpose Example
default-srcFallback for all other resource types if they don't have a specific directive.default-src 'self'
script-srcSpecifies valid sources for JavaScript files.script-src 'self' cdn.example.com
style-srcSpecifies valid sources for CSS stylesheets.style-src 'self' fonts.googleapis.com
img-srcSpecifies valid sources for images.img-src * (allows images from any origin)
connect-srcRestricts which URLs can be loaded by scripts (e.g., AJAX, WebSockets).connect-src 'self' api.example.com
frame-ancestorsRestricts which sites can embed the current page (prevents clickjacking).frame-ancestors 'none'

3. Source Values

Directives take a value called a **source expression** to define what is allowed. Common source expressions include:

Value Meaning
'self'Allows resources from the same origin (protocol, host, and port).
https://example.comExplicitly allows resources from that domain (over HTTPS).
*Wildcard, allows resources from any source (use with caution).
'none'Disallows resources of this type.
'nonce-*'Allows an inline script/style tag only if it has a matching cryptographically secure, single-use token (nonce). **Crucial for modern strict CSPs.**

4. Enforcement

When the browser loads the web page:

  1. It reads the Content-Security-Policy header.
  2. For every resource the page tries to load (e.g., an external script, an image, or an inline script), the browser checks the relevant CSP directive.
  3. **If the source is allowed** by the policy (it's on the "allowlist"), the browser loads/executes the resource.
  4. **If the source violates the policy**, the browser blocks the resource from loading and registers a violation.

🛠️ Policy Modes

CSP can be deployed in two different modes:

Enforcement Mode:

The browser actively blocks resources that violate the policy. This is the final, production state.

Header: Content-Security-Policy: ...

Report-Only Mode:

The browser monitors for violations and sends reports, but **does not block** any content. This is crucial for safely testing a new policy before enforcing it, as it helps identify legitimate resources that might be blocked.

Header: Content-Security-Policy-Report-Only: ...

Content Security Policy (CSP) Directives Categorized

A comprehensive list of Content Security Policy (CSP) directives, categorized by their purpose.

✅ 1. Fetch Directives

These control where different types of resources can be loaded from.

DirectiveDescription
default-srcFallback for other resource types unless overridden
script-srcControls JavaScript loading (e.g., <script>)
style-srcControls CSS loading (e.g., <style>, link rel="stylesheet")
img-srcControls image loading (e.g., <img>, CSS url())
font-srcControls font loading (e.g., from @font-face)
connect-srcControls connections (e.g., fetch, XHR, WebSocket)
media-srcControls <audio> and <video> sources
object-srcControls <object>, <embed>, <applet> loading
manifest-srcControls web app manifest file loading
child-srcDeprecated, use frame-src or worker-src
frame-srcControls embedding via <iframe> or <frame>

✅ 2. Navigation Directives

Control how and where navigation can occur.

DirectiveDescription
frame-ancestorsRestrict which sources can embed your content via <iframe>
form-actionRestrict where forms can submit data to
navigate-toRestrict where anchor tags can redirect (Removed from the spec and not implemented in browsers)

✅ 3. Other Directives

DirectiveDescription
worker-srcControls loading of Web Workers and Service Workers
webrtcControls WebRTC communication (not widely supported)

✅ 4. Reporting Directives

Allow monitoring of policy violations.

DirectiveDescription
report-uri(Deprecated) Sends CSP violation reports to this URI
report-toModern alternative to report-uri using Reporting API

✅ 5. Document Directives

Control document behavior and structure.

DirectiveDescription
sandboxApplies sandbox restrictions to the page (like <iframe sandbox>)
base-uriRestricts URLs used by <base> element
upgrade-insecure-requestsAutomatically upgrade HTTP requests to HTTPS

Tip: Always start with a restrictive policy like **`default-src 'none';`** and open only what’s required.

6 Practically use case : add CSP header before serving public files :

app.use((req, res, next) => {
  if (req.headers.accept?.includes('text/html')) {
    res.setHeader(
      'Content-Security-Policy',
      "default-src 'self';\
        script-src 'self'  https://cdn.tailwindcss.com http://localhost:8000;\
        img-src 'self' https://images.unsplash.com/;\
        style-src 'unsafe-inline';\
        connect-src 'self' http://localhost:8000"
    )
  }
  next()
})
app.use(express.static("./public"));
