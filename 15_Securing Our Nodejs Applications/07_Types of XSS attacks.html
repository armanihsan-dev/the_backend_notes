🛡️ Deep Dive into the 4 Types of XSS Attacks

Cross-Site Scripting (XSS) is a type of **injection attack** where an attacker injects malicious client-side scripts into a website viewed by other users. While XSS is often classified into three primary categories (Stored, Reflected, and DOM-based), a fourth, less common but potent type, **Self-XSS**, is sometimes included for completeness in risk discussions.

Here is a deep dive into how each of the four types works, their primary risks, and their typical risk levels.

1. Stored XSS (Persistent)

Stored XSS is the **most dangerous** and potent form of XSS because the malicious script is permanently saved on the target server (e.g., in a database, a comment file system, or a content management system).

Aspect Details
How it Works Injection: An attacker submits a malicious script (e.g., in a comment box, user profile, or forum post). Storage: The web application saves this script directly to its backend database without proper sanitization. Execution: When any legitimate user (including administrators) views the page containing the stored content, the malicious script is retrieved from the database, included in the HTML response, and executed by the user's browser.
Primary Risk Widespread and Persistent Compromise. Since the payload is served to every user who visits the infected page, it has a high potential for mass compromise, including session hijacking, data theft, and defacement across a broad user base.
Risk Level Critical (Highest severity)
Analogy A **booby-trapped water source**—once poisoned, everyone who drinks from it is affected until the source is cleaned.

2. Reflected XSS (Non-Persistent)

Reflected XSS is the **most common** type. The malicious script is "reflected" off a web application back to an individual user, typically delivered via an email or a malicious link.

Aspect Details
How it Works Injection: An attacker crafts a URL containing a malicious script as part of the query parameter (e.g., https://example.com/search?q=<script>alert('XSS')</script>). Reflection: The attacker sends this link to a victim. When the victim clicks the link, the application immediately takes the script from the URL and includes it in the HTTP response page (e.g., displaying the search query in an error message). Execution: The victim's browser executes the script immediately.
Primary Risk Targeted Compromise. The attack only affects users who click the specific malicious link. It is commonly used for phishing, session hijacking, or harvesting credentials from specific targets.
Risk Level High
Analogy A **poison dart**—it targets a single, specific victim but is immediately effective upon impact.

3. DOM-based XSS (Client-Side)

DOM-based XSS occurs entirely within the **client-side browser environment**, and the vulnerability is not visible in the server's response. The payload is executed when client-side script (often JavaScript) processes user-supplied data (e.g., from the URL hash fragment) without sanitization, modifying the page's Document Object Model (DOM).

Aspect Details
How it Works Injection: The attacker places a script in the URL fragment (e.g., https://example.com/page#name=<script>...</script>). Execution: A legitimate script on the page reads the data from the URL (like document.location.hash) and writes it back into the page's HTML using an unsafe sink (like element.innerHTML = ...). The script is executed by the browser without ever sending the malicious payload to the server.
Primary Risk Difficult to Detect. Since the malicious code isn't seen by the server, traditional server-side security scanners may miss it. It is often used to modify the page interface (e.g., create a fake login form) or steal user data processed locally.
Risk Level High
Analogy A **faulty house blueprint**—the structure is sound, but a specific worker (the vulnerable client-side script) misreads the local instructions and builds a dangerous trap.

4. Self-XSS (Social Engineering)

Self-XSS relies on **social engineering** to trick a user into executing malicious code in their own browser console. While technically not a web application vulnerability itself, it is a significant risk vector often used to bypass security controls on major platforms.

Aspect Details
How it Works Deception: The attacker convinces a victim (e.g., through a message promising a free item or a "hack" to view private profiles) to copy and paste a malicious JavaScript payload directly into their browser's developer console and execute it. Execution: The victim executes the script, which runs with full privileges within their session context.
Primary Risk Session Compromise (Self-Inflicted). The script can steal the victim's session cookies or perform actions on their behalf, such as posting content, liking pages, or changing settings.
Risk Level Moderate to High (Relies on user error)
Analogy Tricking someone into **sabotaging their own car**—the tool used is legitimate (the console), but the instructions provided lead to harm.
