🛡️ CSRF Attack: Definition and Mechanism

Definition

Cross-Site Request Forgery (CSRF), sometimes pronounced "sea-surf," is an attack that forces an end-user to execute unwanted actions on a web application in which they are currently authenticated.

The key: The attack exploits the trust a web application has in a user's browser. If a user is logged into an application (like a bank), the browser sends the session cookie automatically with every request to that application's domain. The attacker doesn't need to steal the cookie; they just need to trick the user's browser into sending a request containing it.

Mechanism: How it Works

The CSRF attack relies on an authenticated user visiting a malicious site while their session cookie for the vulnerable application is active.

  • Authentication: The user logs into a Vulnerable Web App (e.g., bank.com). The browser stores the session cookie.
  • Luring: The attacker sends the user a link, email, or message (e.g., "Check out this funny meme!") which leads to a Malicious Site (e.g., attacker.com).
  • The Forge: The malicious site contains hidden code designed to submit a request to the vulnerable app (e.g., bank.com). This is typically done using an invisible form or an <img> tag that attempts to load a sensitive URL.
  • Execution: When the user's browser loads the malicious site, it executes the hidden code. Because the request is targeted at bank.com, the browser automatically attaches the user's valid session cookie for bank.com.
  • Success: The bank.com server receives the request, sees a valid session cookie, assumes the request came from the legitimate, logged-in user, and executes the forged action (e.g., transferring money).

💻 Practical Example: The Express.js Bank App

Let's illustrate this with a simplified Express.js bank application and an attacker's site.

1. The Vulnerable Bank Application (bank-app.js)

This application is vulnerable because it only checks for a valid session and uses a simple GET or POST request to handle a money transfer.

JavaScript
// A very basic Express setup for a bank application
const express = require('express');
const cookieParser = require('cookie-parser');
const session = require('express-session');
const app = express();
const port = 3000;

app.use(express.urlencoded({ extended: true }));
app.use(cookieParser());
app.use(session({ 
    secret: 'super-secret-key', 
    resave: false, 
    saveUninitialized: true 
}));

// --- Middleware to simulate a user login (Simplistic) ---
// If not logged in, 'user' will be undefined.
const requireLogin = (req, res, next) => {
    if (!req.session.userId) {
        return res.status(401).send('Please log in first.');
    }
    next();
};

// --- SIMULATED LOGIN ROUTE ---
app.get('/login', (req, res) => {
    // In a real app, this would check username/password
    req.session.userId = 'alice';
    res.send('You are now logged in as Alice. <a href="/transfer">Go to Transfer</a>');
});

// --- VULNERABLE TRANSFER ROUTE ---
app.post('/transfer', requireLogin, (req, res) => {
    const { amount, targetAccount } = req.body;
    
    // In a real app, this is where the money transfer logic goes
    console.log(`[BANK] User ${req.session.userId} successfully transferred ${amount} to account ${targetAccount}.`);
    res.send(`SUCCESS: Transferred $${amount} to account ${targetAccount}.`);
});

// --- TRANSFER FORM (User-facing) ---
app.get('/transfer', requireLogin, (req, res) => {
    res.send(`
        <h1>Transfer Money</h1>
        <p>You are logged in as ${req.session.userId}.</p>
        <form action="/transfer" method="POST">
            <label for="targetAccount">Target Account:</label>
            <input type="text" id="targetAccount" name="targetAccount" value="Bob" required><br><br>
            <label for="amount">Amount ($):</label>
            <input type="number" id="amount" name="amount" value="1000" required><br><br>
            <button type="submit">Transfer</button>
        </form>
    `);
});

app.listen(port, () => {
    console.log(`Bank app listening at http://localhost:${port}`);
});

To run this:

  1. Run the bank app: node bank-app.js
  2. In a browser, visit http://localhost:3000/login to log in (this sets the session cookie).
  3. The user is now authenticated.

2. The Malicious Attack Site (attacker-site.html)

The attacker hosts this simple HTML page on a completely different domain (or port, e.g., 8080).

HTML
<html>
<head>
    <title>You Won a Prize!</title>
</head>
<body>
    <h1>Congratulations! You've won a new car!</h1>
    <p>Loading your prize information...</p>

    <form id="csrfForm" action="http://localhost:3000/transfer" method="POST">
        <input type="hidden" name="targetAccount" value="AttackerAccount99">
        <input type="hidden" name="amount" value="5000"> 
    </form>

    <script>
        // Automatically submit the form as soon as the page loads
        document.getElementById('csrfForm').submit();
    </script>
</body>
</html>

The Attack Flow

  • Victim Logs In: Alice visits http://localhost:3000/login. She is logged in, and her browser has a valid session cookie for localhost:3000.
  • Victim Visits Malicious Site: Alice receives an email and clicks the link to http://localhost:8080/attacker-site.html.
  • The Forge: As the malicious page loads, the JavaScript instantly submits the hidden form to http://localhost:3000/transfer.
  • Browser Compliance: Crucially, the browser sees the request going to localhost:3000 and automatically attaches Alice's session cookie.
  • Bank Execution: The Express server at localhost:3000 receives the POST request. It sees a valid session ID for **Alice**, processes the targetAccount=AttackerAccount99 and amount=5000 from the forged request body, and executes the transfer **without Alice's permission**.

🔐 How to Prevent CSRF

1. SameSite Cookies

Setting the SameSite attribute on cookies tells browsers **when to include cookies in cross-site requests**.

HTTP Header
Set-Cookie: sessionId=abc123; SameSite=Lax; Secure; HttpOnly
  • SameSite=Lax blocks cookies on most cross-origin POSTs, but allows them on top-level navigations.
  • SameSite=Strict is even more restrictive.

2. CSRF Tokens (also called Anti-CSRF Tokens)

  • Server generates a **unique token** per user/session.
  • The token is embedded in each HTML form or request.
  • The server **verifies the token** with each modifying request (like POST, PUT, DELETE).
  • This works because **attackers can’t read the token** from the page if same-origin policies are enforced.

3. Custom Headers + CORS

  • Require a **custom header** like X-CSRF-Token.
  • Browsers **block custom headers on cross-origin requests** unless allowed via CORS.
  • This adds a layer of protection, as attackers using HTML forms can't set these headers.
