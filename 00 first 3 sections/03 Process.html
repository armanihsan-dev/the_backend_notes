Operating System Concepts

Process ID (PID)

  • A unique numerical identifier assigned by an operating system (like Windows, Linux, or macOS) to each running program or "process."
  • Think of it like a Social Security Number for a program that's currently active on your computer.

Need to the Processor (and the Operating System)

The PID is absolutely essential for the operating system to manage and control processes efficiently. Here's why it's so crucial, especially in relation to the processor:

  1. Unique Identification: In a multitasking environment, many programs can be running simultaneously. The PID ensures that the operating system can distinguish between them, even if multiple instances of the same program are running. Without a unique identifier, the OS wouldn't know which specific instance of a program to interact with.
  2. Process Management: The operating system's primary role is to manage all the active processes. The PID allows it to:
    • Allocate Resources: The OS needs to know which process gets how much CPU time, memory, disk I/O, etc. The PID helps in tracking and allocating these resources to the correct process.
    • Schedule Execution: The processor can only execute one instruction at a time (per core). The operating system's scheduler uses PIDs to decide which process gets to use the CPU next and for how long.
    • Control State: Processes can be in different states (running, waiting, ready, etc.). The OS uses the PID to track the current state of each process and manage transitions between these states.
    • Termination: When a process needs to be stopped (either gracefully or forcefully), the OS uses its PID to target and terminate it, freeing up its resources. This is what happens when you "end task" in Task Manager (Windows) or use the kill command (Linux).
  3. Inter-Process Communication (IPC): If different processes need to communicate or share data, they often use PIDs to refer to each other. For example, one process might send a signal or message to another process using its PID.
  4. Monitoring and Troubleshooting: System administrators and users rely on PIDs to monitor system performance, identify resource-intensive processes, and troubleshoot issues. Tools like Task Manager (Windows) or ps and top (Linux) display PIDs, allowing users to see what's running and take action if needed.
  5. Parent-Child Relationships: When one process creates another (e.g., a web browser launching a new tab, or a command-line shell executing a command), the new process is called a "child process," and the creating process is the "parent process." The operating system often tracks these parent-child relationships using PIDs (e.g., each child process also has a Parent Process ID or PPID). This helps in managing process hierarchies.

1. What is a Process?

Definition:

  • A program in execution.
  • A process in Node.js is an instance of a running program that has its own memory space and system resources. Node.js provides the child_process module to create and manage subprocesses, allowing you to execute system commands or other programs from within your Node.js application.

Process vs. Program

Feature Program Process
Nature Passive entity (e.g., an executable file) Active entity (an instance of a program being executed)
State Static, on disk Dynamic, exists in memory, has a state (running, waiting, etc.)
Resources No direct resource allocation Requires CPU time, memory, I/O devices, files
Execution Cannot execute itself Executes instructions, consumes resources
Multiple Instances One copy on disk Multiple instances of the same program can run simultaneously as separate processes (e.g., multiple tabs in browser)

Process Lifecycle: New → Ready → Running → Waiting → Terminated

Processes move through various states during their lifetime. This lifecycle describes the typical transitions:

  • New: The process is being created. Resources are being allocated, and the Process Control Block (PCB) is being initialized.
  • Ready: The process is waiting to be assigned to a processor. It has all the necessary resources allocated and is ready to execute, but the CPU is currently busy with another process.
  • Running: The process's instructions are being executed by the CPU. At any given time, only one process can be running on each CPU core.
  • Waiting (or Blocked) OR Sleep State: The process is waiting for some event to occur, such as the completion of an I/O operation (e.g., reading from a disk, waiting for user input), or the availability of a resource. While waiting, the process is not consuming CPU time.
  • Terminated (or Exit): The process has finished execution, either normally (completed its task) or abnormally (due to an error or termination signal). Resources are deallocated, and its PCB might be retained for a short period for parent processes to collect its exit status.

States of a Process

These states provide a more detailed view of the process lifecycle. The transitions between these states are managed by the operating system's scheduler.

  • Admitted: Transition from New to Ready.
  • Dispatcher (CPU Scheduler): Selects a process from the Ready queue and assigns it to the CPU (Ready to Running).
  • Interrupt: A running process can be interrupted (e.g., by a timer interrupt or a higher-priority process arriving) and moved back to the Ready state (Running to Ready).
  • I/O or Event Wait: A running process requests an I/O operation or waits for some event, moving to the Waiting state (Running to Waiting).
  • I/O or Event Completion: The event the process was waiting for occurs, moving it back to the Ready state (Waiting to Ready).
  • Exit: The process finishes execution (Running to Terminated).

Process Control Block (PCB)

  • The Process Control Block (PCB), also known as a task control block, is a data structure maintained by the operating system for each process.
  • It contains all the information needed to manage a process, essentially serving as its "identity card or process ID" and "status report."
  • When a process is switched out of the CPU (context switch), its state is saved in its PCB, and when it's reloaded, the information from the PCB is used to restore its context.
  • Typical information stored in a PCB includes:
    • Process State: (e.g., new, ready, running, waiting, terminated)
    • Program Counter: The address of the next instruction to be executed for this process.
    • CPU Registers: Values of all CPU registers (accumulators, index registers, stack pointers, general-purpose registers, etc.) when the process was last running.
    • CPU Scheduling Information: Process priority, pointers to scheduling queues, and other scheduling parameters.
    • Memory-Management Information: Base and limit registers, page tables, segment tables, etc., depending on the memory management scheme.
    • Accounting Information: CPU time used, real time elapsed, time limits, account numbers, process IDs, etc.
    • I/O Status Information: List of I/O devices allocated to the process, list of open files, etc.

2. Process Management

Process management involves creating, scheduling, terminating, and coordinating processes. The operating system is responsible for these crucial tasks to ensure efficient resource utilization and system stability.

Process Creation: fork(), exec(), wait() in Unix/Linux

In Unix-like operating systems, process creation typically involves a combination of these three system calls:

  • fork():
    • Creates a new process, called the child process, which is an almost identical copy of the calling process, known as the parent process.
    • Both parent and child processes continue execution from the point of the fork() call.
    • fork() returns 0 to the child process and the PID (Process ID) of the child process to the parent process. It returns -1 on failure.
    • The child process inherits copies of the parent's memory segments (code, data, stack, heap), file descriptors, and environmental variables.
  • exec() (e.g., execve, execlp, etc.):
    • Replaces the current process's image (code, data, stack, heap) with a new program.
    • It does not create a new process. Instead, the calling process is transformed into the new program. The PID remains the same.
    • Typically, fork() is followed by exec() in the child process. The child process uses exec() to load and run a different program, while the parent continues its original execution path (or waits for the child).
  • wait() (e.g., waitpid, wait):
    • The parent process uses wait() to pause its own execution until one of its child processes terminates.
    • When a child process terminates, its exit status is returned to the parent, and the child process's resources are fully deallocated.
    • wait() prevents zombie processes.

Parent-child relationships

Processes form a hierarchy. The process that creates another process is its parent, and the newly created process is its child. This relationship is critical for:

  • Resource Inheritance: Children often inherit resources like file descriptors from their parents.
  • Process Grouping: Related processes can be grouped together.
  • Termination: If a parent terminates, its children might become orphan processes (though the init process often adopts them). Conversely, a parent often waits for its children to complete before terminating itself.

Process Termination

A process can terminate in several ways:

  • Normal Exit: The process completes its last instruction and explicitly calls exit() (or implicitly returns from main()).
  • Error Exit: The process terminates due to an unrecoverable error (e.g., division by zero, invalid memory access).
  • Killed by Another Process: A process (usually the parent or a privileged process) sends a signal to terminate another process (e.g., kill command in Unix/Linux).
  • Killed by the Operating System: The OS might terminate a process due to system errors, resource limits, or security violations.

Zombie & Orphan Processes

  • Zombie Process (Defunct Process):
    • A process that has completed its execution (terminated) but its entry in the process table still exists because its parent process has not yet called wait() to collect its exit status.
    • The OS retains the PCB of a zombie process so the parent can retrieve information about its child's termination.
    • Zombie processes consume minimal system resources (just a process table entry) but too many can exhaust process table entries. They cannot be killed by signals directly. The parent process must call wait() or terminate itself for the zombie to be fully removed.
  • Orphan Process:
    • A child process whose parent process has terminated before the child process.
    • Orphan processes are automatically "adopted" by the init process (PID 1 in Unix/Linux systems). The init process is responsible for periodically calling wait() on its adopted children, thus preventing them from becoming zombies. Orphan processes continue to run normally under init's guardianship.

3. Threads and Multithreading

While a process is a program in execution with its own isolated memory space, a thread is a lightweight unit of execution within a process. Multithreading allows a single process to have multiple threads of execution, enabling parallelism within that process.

Difference between Process and Thread

Feature Process Thread
Isolation Independent, isolated memory space Share the same memory space (code, data, heap) with other threads in the same process
Resource Ownership Owns its own resources (memory, files, I/O) Shares resources of its parent process
Overhead High overhead for creation, termination, context switching Low overhead for creation, termination, context switching
Communication IPC mechanisms (complex) Easy (shared memory, no explicit IPC needed)
Robustness Failure of one process doesn't affect others Failure of one thread can crash the entire process
Switching Context switching involves changing memory maps and registers Context switching involves saving/restoring thread-specific registers and stack

User-level vs. Kernel-level Threads

  • User-level Threads (ULTs):
    • Managed by a thread library at the user level, without kernel involvement.
    • The kernel is unaware of their existence; it sees only a single process.
    • Advantages: Faster to create/destroy and switch between (no kernel mode switch), flexible scheduling by the application.
    • Disadvantages: If one ULT blocks (e.g., for I/O), the entire process blocks. Cannot take advantage of multiple CPU cores as the kernel only schedules the single underlying process.
  • Kernel-level Threads (KLTs):
    • Managed directly by the operating system kernel.
    • The kernel maintains context information for each thread.
    • Advantages: If one KLT blocks, other KLTs in the same process can still run. Can be scheduled on different CPU cores, enabling true parallelism.
    • Disadvantages: Slower to create/destroy and switch between (requires kernel mode switch).

Benefits of Multithreading

  • Responsiveness: A program can remain responsive to user input even if a part of it is blocked or performing a long operation.
  • Resource Sharing: Threads within the same process can easily share resources (code, data, files) without complex IPC mechanisms.
  • Economy: Cheaper to create, terminate, and context switch between threads than processes.
  • Scalability: On multi-core processors, multiple threads can execute in parallel, significantly improving performance for computationally intensive tasks.

Thread Lifecycle

Similar to processes, threads also go through various states:

  • New: Thread is created.
  • Runnable (Ready): Thread is ready to run, waiting for CPU time.
  • Running: Thread is currently executing on a CPU core.
  • Blocked (Waiting): Thread is waiting for an event (e.g., I/O completion, acquiring a lock, sleep timer).
  • Terminated (Dead): Thread has completed its execution or was explicitly stopped.

Thread Libraries: POSIX threads (pthreads), Windows threads

  • POSIX threads (pthreads):
    • A standard API for thread creation and synchronization.
    • Widely used in Unix-like operating systems (Linux, macOS) and supported on Windows.
    • Provides functions for thread creation (pthread_create), termination (pthread_exit), joining (pthread_join), mutexes (pthread_mutex_init), condition variables, etc.
  • Windows threads:
    • The threading API specific to Microsoft Windows operating systems.
    • Provides functions like CreateThread, ExitThread, WaitForSingleObject, CreateMutex, etc.

4. CPU Scheduling

CPU scheduling is the process of deciding which of the ready processes (or threads) in the ready queue should be allocated the CPU. Its goal is to maximize CPU utilization, ensure fairness, and meet performance objectives.

Scheduling Criteria

  • CPU Utilization: Keep the CPU as busy as possible. Range from 0% to 100%.
  • Throughput: The number of processes completed per unit time.
  • Turnaround Time: The total time from process submission to completion (including waiting, ready, execution, and I/O).
  • Waiting Time: The total amount of time a process spends in the ready queue waiting for the CPU.
  • Response Time: For interactive systems, the time from submission of a request until the first response is produced.
  • Fairness: Ensure that each process gets a fair share of the CPU.

Types of Schedulers

  • Long-term Scheduler (Job Scheduler):
    • Selects processes from the job pool (e.g., programs on disk) and loads them into the ready queue (main memory) for execution.
    • Controls the degree of multiprogramming (number of processes in memory).
    • Executes much less frequently than short-term schedulers.
  • Short-term Scheduler (CPU Scheduler):
    • Selects a process from the ready queue and allocates the CPU to it.
    • Executes very frequently (milliseconds), so it must be fast.
  • Medium-term Scheduler:
    • Part of a swapping scheme. It removes processes from memory (swapping them out) to reduce the degree of multiprogramming and swap them back in later.
    • Used to manage memory and reduce contention for the CPU.

Scheduling Algorithms

  • First-Come, First-Served (FCFS):
    • Non-preemptive: Processes are executed in the order they arrive in the ready queue. Once a process starts, it runs until completion or it blocks.
    • Simple to implement.
    • Disadvantage: Can lead to high average waiting time if a long process arrives before short ones (convoy effect).
  • Shortest-Job-First (SJF):
    • Non-preemptive: Selects the process with the smallest next CPU burst time.
    • Preemptive (Shortest-Remaining-Time-First - SRTF): If a new process arrives with a shorter CPU burst time than the remaining time of the currently executing process, the current process is preempted.
    • Optimal: Gives the minimum average waiting time for a given set of processes.
    • Disadvantage: Requires knowledge of the next CPU burst length, which is difficult to predict accurately in real systems (often estimated).
  • Priority Scheduling:
    • Each process is assigned a priority, and the CPU is allocated to the process with the highest priority.
    • Can be preemptive or non-preemptive.
    • Problem: Starvation – low-priority processes may never execute if high-priority processes keep arriving.
    • Solution: Aging – gradually increasing the priority of processes that wait for a long time.
  • Round Robin (RR):
    • Designed for time-sharing systems.
    • Each process gets a small unit of CPU time, called a time quantum (time slice).
    • If a process does not complete within the time quantum, it is preempted and added to the end of the ready queue.
    • Preemptive.
    • Advantages: Fair, good response time for interactive systems.
    • Disadvantage: Higher context switching overhead. Performance highly depends on the choice of time quantum.
  • Multilevel Queue & Multilevel Feedback Queue:
    • Multilevel Queue: Partitions the ready queue into multiple separate queues (e.g., foreground interactive processes, background batch processes). Each queue might have its own scheduling algorithm. Processes are permanently assigned to a queue.
    • Multilevel Feedback Queue (MLFQ): More flexible. Processes can move between queues based on their CPU burst characteristics. A process that uses too much CPU time might be moved to a lower-priority queue. A process that waits too long in a lower-priority queue might be moved to a higher-priority queue (aging). Prevents starvation and allows for different priorities.

Context Switching

When the CPU switches from one process (or thread) to another, it performs a context switch. This involves:

  1. Saving the state (CPU registers, program counter, etc.) of the currently executing process into its PCB.
  2. Loading the saved state of the next process from its PCB into the CPU registers.

Context switching is pure overhead; the system does no useful work during this time. The efficiency of context switching is crucial for overall system performance, especially in systems with many processes or threads and frequent switching (e.g., Round Robin).

5. Inter-Process Communication (IPC)

Inter-Process Communication (IPC) refers to mechanisms that allow independent processes to communicate and synchronize their actions with each other. Since processes typically have isolated memory spaces, direct data access is not possible. IPC is essential for:

Why IPC is needed

  • Information Sharing: Multiple processes may need to access and share the same data (e.g., a shared database server).
  • Computation Speedup: A task can be divided into subtasks that run concurrently as separate processes, speeding up overall execution.
  • Modularity: Breaking down a complex system into smaller, manageable processes.
  • Convenience: For instance, allowing a shell script to pipe the output of one command to the input of another.

Mechanisms:

  • Pipes (Named & Unnamed):
    • Unnamed Pipes (Anonymous Pipes):
      • Used for communication between related processes (e.g., parent and child) that share a common ancestor.
      • One-way communication (simplex).
      • Created using pipe() system call in Unix/Linux.
      • Data is written to one end and read from the other.
    • Named Pipes (FIFOs - First-In, First-Out):
      • Can be used for communication between unrelated processes.
      • Exist as a special file in the file system.
      • Can be opened by multiple processes for reading and writing, providing a two-way (but still half-duplex) communication channel.
  • Message Queues:
    • A linked list of messages stored within the kernel.
    • Processes can send messages to a queue, and other processes can read messages from the queue.
    • Messages are tagged with types, allowing processes to selectively retrieve messages.
    • Provides asynchronous communication.
  • Shared Memory:
    • The fastest IPC mechanism.
    • A region of memory that is jointly accessible by multiple processes.
    • Once the shared memory region is established, processes can read and write data to it directly, bypassing the kernel for each data transfer.
    • Challenge: Requires careful synchronization to prevent race conditions (multiple processes accessing and modifying the shared data concurrently without proper coordination).
  • Semaphores:
    • Not primarily a data transfer mechanism, but a synchronization tool.
    • A variable or an abstract data type used to control access to a common resource by multiple processes in a concurrent system.
    • Can be binary (like a mutex, 0 or 1) or counting (for managing multiple instances of a resource).
    • Operations: wait() (or P or down) decrements the semaphore; signal() (or V or up) increments it.
  • Sockets:
    • A more general and flexible IPC mechanism, especially for network communication (processes on different machines) but also usable for inter-process communication on the same machine.
    • An endpoint for communication.
    • Can be stream-oriented (TCP) or datagram-oriented (UDP).
    • Allows for client-server communication models.

6. Process Synchronization

Process synchronization deals with the problem of ensuring that concurrent processes (or threads) execute in an orderly manner, especially when they share resources or data. The goal is to prevent inconsistencies and maintain data integrity.

Race Conditions

A race condition occurs when two or more processes (or threads) access and manipulate shared data concurrently, and the final outcome depends on the specific order in which their accesses take place. This can lead to unpredictable and incorrect results, as the output is not deterministic.

Critical Section Problem

The critical section problem is a classic synchronization problem. It defines a segment of code in which a process accesses shared resources. The challenge is to design a protocol such that:

  1. Mutual Exclusion: Only one process can be executing in its critical section at any given time.
  2. Progress: If no process is executing in its critical section and some processes wish to enter their critical sections, then only those processes that are not executing in their remainder section can participate in the decision of which process will enter its critical section next, and this selection cannot be postponed indefinitely.
  3. Bounded Waiting: There must be a limit on the number of times other processes are allowed to enter their critical sections after a process has made a request to enter its critical section and before that request is granted.

Software Solutions: Peterson’s algorithm

  • Peterson's Algorithm: A classic software-based solution to the critical-section problem for two processes. It uses two shared variables: flag[2] (to indicate if a process wants to enter its critical section) and turn (to indicate whose turn it is).
  • Pros: Satisfies all three critical-section requirements (mutual exclusion, progress, bounded waiting).
  • Cons: Limited to two processes, relies on busy waiting (consumes CPU cycles while waiting), and might not work correctly on modern architectures with aggressive compiler optimizations or caching.

Hardware Support: Test-and-set, Compare-and-swap

Modern systems provide hardware instructions to facilitate synchronization, which are typically atomic (indivisible) operations:

  • test_and_set():
    • Reads the value of a memory word and sets it to true (or 1) in a single, atomic operation.
    • If the original value was false (or 0), the process can enter the critical section.
    • Used to implement mutual exclusion.
  • compare_and_swap() (CAS):
    • Compares the content of a memory location with a given value. If they are equal, it updates the content of the memory location to a new given value. All as an atomic operation.
    • More powerful than test_and_set and can be used to implement more complex synchronization primitives, including lock-free data structures.

Synchronization Tools:

These are higher-level programming constructs built using hardware support or lower-level primitives to simplify synchronization.

  • Mutexes (Mutual Exclusion Locks):
    • A binary semaphore (can be in one of two states: locked or unlocked).
    • Used to protect a critical section. Only one thread can hold the mutex at a time.
    • A thread acquires the mutex before entering the critical section and releases it upon exiting. If a thread tries to acquire a locked mutex, it will block until the mutex is released.
  • Semaphores:
    • As mentioned in IPC, semaphores are integer variables (or abstract data types) used for signaling between processes/threads.
    • A wait() operation decrements the semaphore's value; a signal() operation increments it.
    • If a wait() operation causes the value to become negative, the process blocks.
    • Can be used to implement mutual exclusion (binary semaphore) or to control access to a resource with multiple instances (counting semaphore).
  • Monitors:
    • A high-level synchronization construct that encapsulates data and the procedures that operate on that data.
