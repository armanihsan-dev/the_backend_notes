🚀 The Complete Authentication Flow

The authentication process involves three distinct phases and four key actors: the User, your Frontend (running on localhost:5500), your Backend (Express on localhost:3000), and Google's Authorization Server.

Phase 1: Initiation and Authorization (Frontend to Google)

This phase starts when the user decides to log in.

Phase 2: Authorization Code Exchange (Backend to Google)

This is the most critical server-side phase, where the Authorization Code is received and exchanged for tokens. This process is **server-to-server** (back-channel) and highly secure.

How the Auth Code is Received on Express Route

1: When Google successfully authenticates the user and receives their consent, it then redirects the user's browser back to the **`redirect_uri`**. This URI must exactly match one of the authorized redirect URIs configured in your Google Cloud project credentials and must also match the `redirect_uri` parameter contained in the original authorization request URL sent to Google. The redirection response includes the **Authorization Code** as a query parameter.

The user's browser, after getting redirected by Google, hits the following Express route: 

// app.js - Backend route is the target of the Google redirect
app.get('/auth/google/callback', async (req, res) => {
    // 👈 The Authorization Code is automatically passed here by Google in the URL query string
    const code = req.query.code; 
    // ... logic proceeds to call fetchUserFromGoogle(code) ...
});

The req.query.code variable extracts the code from the URL, which looks something like http://localhost:3000/auth/google/callback?code=4/0Af.....

Summary of Communication Types

  1. Browser Redirects (Front-channel)

    Used to direct the user between your app and Google's login pages.

    Data transmitted via URL: redirect_uri, scope, and crucially, the Authorization Code (code=...).

  2. Server-to-Server Requests (Back-channel)

    Used for sensitive operations, primarily the exchange of the Authorization Code for tokens. This is secure because the client_secret is never exposed to the browser.

    Data transmitted via secure HTTPS POST: The Authorization Code and client_secret (from Express to Google), and the Access/ID Tokens (from Google to Express).

  3. Client-to-Server API Calls (Fetch)

    Used by your JavaScript to manage the session and retrieve protected resources.

    Authentication done via Cookies: The browser automatically includes the sid cookie in requests to http://localhost:3000/profile and http://localhost:3000/logout because of the credentials: 'include' setting and CORS configuration.
