OIDC ID Token Verification

Verifying the ID Token is the crucial security step that validates the user's identity within the OpenID Connect (OIDC) flow. It ensures that the token is genuine, hasn't been tampered with, and was issued by the legitimate identity provider (Google).

The verification process is performed by your server (the Relying Party) after receiving the ID Token.

🔒 What is ID Token Verification?

The ID Token is a JSON Web Token (JWT). Verification is the process of cryptographically validating the JWT's integrity and payload claims against a set of known rules.

Verification involves three primary checks:

  1. Signature Verification (Integrity Check)

    The most important step is ensuring the token hasn't been modified in transit. This is done using asymmetric cryptography:

    • The ID Token contains a Signature (the third part of the JWT). This signature was created by Google using its Private Key.
    • Your server must obtain Google's corresponding Public Key to decrypt or verify this signature.
    • If the signature verifies successfully, it proves two things:
      • The token was signed by the holder of the private key (Google).
      • The Header and Payload (the first two parts) have not been altered since they were signed.

  2. Standard Claim Validation (Payload Check)

    Once the signature is verified, your server checks the contents (claims) of the token's payload:

    Claim Check Purpose
    iss (Issuer) Must be exactly https://accounts.google.com. Confirms the token came from Google.
    aud (Audience) Must match your application's Client ID. Confirms the token was specifically intended for your application.
    exp (Expiration Time) Must be in the future (not expired). Ensures the token is still valid for use.
    iat (Issued At) Checks the time the token was issued. Used for security auditing.

  3. Nonce/State Validation (Replay Attack Check)

    If you used a nonce parameter in the initial authorization request (or the state parameter is used to link the token to the original request):

    • The nonce value in the ID Token must match the unique nonce value your application sent in the first step.
    • This prevents an attacker from reusing an intercepted token in a replay attack.

🔑 Key Formats: JWK and PEM

Your server needs Google's public key to verify the signature, but these keys come in different formats.

1. JWK (JSON Web Key)

The JWK format is a standard way to represent cryptographic keys using JSON data structures. It is the format most commonly used when transferring public keys over the web, as it is easily consumed by web services.

  • Structure: It's a JSON object that specifies the key type (kty), the algorithm (alg), the modulus (n), and the exponent (e) for RSA keys.
  • Google's Use: Google publishes its public keys for verification in a JWKS (JSON Web Key Set) endpoint (e.g., https://www.googleapis.com/oauth2/v3/certs). Your server fetches this JSON file to get the keys.

2. PEM (Privacy-Enhanced Mail)

The PEM format is an older, widely recognized standard for storing cryptographic keys and certificates.

  • Structure: A text file containing Base64-encoded data, enclosed by boundary markers like -----BEGIN PUBLIC KEY----- and -----END PUBLIC KEY-----.
  • Use: This format is common in backend languages and tools (like OpenSSL) that need to load keys from disk.

Conversion: Verification libraries often take a JWK from Google's endpoint and automatically convert it internally to a format like PEM (or its binary equivalent) to perform the cryptographic checks.

💻 How We Verify the Token Only Using JWT

The term "only using JWT" essentially means using a JWT library (or JWT Verifier) tailored to your backend language (e.g., node-jose in Node.js, python-jose in Python, or various libraries in Java/C#).

A robust JWT library automates the entire verification process:

  • Parse the Header: The library reads the token's header to determine the key ID (kid) and the signing algorithm (alg).
  • Fetch the Public Key: Using the kid, the library searches the Google JWKS endpoint (or cached keys) and selects the matching public key.
  • Validate the Signature: The library uses the selected public key and the specified algorithm to cryptographically check if the signature matches the hash of the Header + Payload.
  • Validate Claims: The library automatically checks all required standard claims against the rules you provide (e.g., it ensures aud matches your Client ID and exp is in the future).
