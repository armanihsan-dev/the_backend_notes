OpenID Connect (OIDC) Deep Dive

OpenID Connect (OIDC) is an **authentication layer** built on top of the **OAuth 2.0 framework**. It allows clients (applications) to **verify the identity of the end-user** based on the authentication performed by an Authorization Server (the **OpenID Provider**), and to obtain **basic profile information** about the user.

🧐 Purpose of OpenID Connect

The primary purpose of OIDC is to provide a **standardized, secure, and interoperable method for user authentication** across different applications and services.

  • Identity Verification: To reliably confirm "who the user is" without the client application having to handle or store the user's sensitive credentials (like passwords).
  • Single Sign-On (SSO): To enable users to sign in once to an **OpenID Provider (OP)** and gain access to multiple independent applications (**Relying Parties**) without re-entering credentials.
  • Profile Information Sharing: To obtain basic user profile data (e.g., name, email) in a predictable and standardized format (**Claims** in an **ID Token** or via the **UserInfo Endpoint**) with the user's consent.

⚙️ How OpenID Connect Works

OIDC uses **JSON Web Tokens (JWTs)** called **ID Tokens** for identity verification, in addition to the **Access Tokens** used for authorization in OAuth 2.0. The most common flow is the **Authorization Code Flow**.

Simplified Step-by-Step Breakdown (using the Authorization Code Flow):

  • Request: The **End-User** tries to access the **Relying Party (RP)** (the application). The RP determines the user isn't authenticated and redirects the user's browser to the **OpenID Provider (OP)'s Authorization Endpoint**, including a request for the `openid` scope.
  • Authentication & Consent: The **OP** authenticates the **End-User** (e.g., asks for username/password). The OP also asks the user for **consent** to share their identity and profile information with the RP.
  • Authorization Code: Upon successful authentication and consent, the **OP** sends a one-time-use **Authorization Code** back to the RP's redirect URI.
  • Token Exchange: The **RP's backend server** securely sends the Authorization Code, along with its own credentials (`client_id` and `client_secret`), to the **OP's Token Endpoint**.
  • Tokens Issued: The **OP** validates the code and credentials, and responds with two main tokens:
    • ID Token (JWT): Used for **Authentication**. Contains **Claims** (identity data like `sub`, `iss`, `aud`) to verify the user's identity and when they were authenticated.
    • Access Token: Used for **Authorization**. A token the RP can use to access protected resources, such as the OP's **UserInfo Endpoint**, to get additional user profile data.
  • Verification & Session: The **RP** validates the **ID Token** (checking the signature, audience, issuer, etc.). If valid, the RP establishes a secure session for the **End-User**.
  • Resource Access (Optional): The **RP** can use the **Access Token** to call the **UserInfo Endpoint** on the **OP** to retrieve additional, standardized user claims.

🧱 Components of OpenID Connect

OIDC defines three main **actors** and several key **data structures and endpoints**:

Actors

  • End-User: The person who is trying to access the Relying Party (application).
  • Relying Party (RP): The client application (e.g., website, mobile app) that needs to verify the End-User's identity.
  • OpenID Provider (OP): The Authorization Server that authenticates the End-User and issues tokens containing their identity information. (Examples: Google, Facebook, a corporate identity service).

Key Data Structures & Endpoints

  • ID Token (JWT): A **JSON Web Token** that proves the user's identity. It is cryptographically signed and contains **Claims** (like subject, issuer, expiration time) about the authentication event and the user.
  • Claims: Pieces of information about the user (e.g., `name`, `email`, `sub` which is the unique user identifier). These are standardized by OIDC.
  • Authorization Endpoint: The OP's endpoint where the RP directs the user to log in and give consent.
  • Token Endpoint: The OP's endpoint where the RP exchanges the Authorization Code for an ID Token and Access Token (a secure, back-channel communication).
  • UserInfo Endpoint: An optional, but common, endpoint on the OP where the RP can use the Access Token to retrieve a more complete set of user profile Claims.

🎯 Use Cases of OIDC

OIDC is the modern standard for identity on the internet and is widely used for:

  • Consumer-Facing Single Sign-On (SSO): Allowing users to log in to third-party applications using their existing accounts from major providers (e.g., "Log in with Google" or "Sign up with Apple" buttons).
  • Enterprise Single Sign-On (SSO): Providing employees with one set of credentials to access multiple internal applications or SaaS tools.
  • Mobile and Native Applications: Securely authenticating users in mobile apps and allowing those apps to access APIs without ever handling the user's password.
  • Microservices Security: Authenticating users across a distributed system of microservices, often using the ID Token for identity and the Access Token to control resource access between services.
  • Federated Identity: Allowing an organization to delegate user authentication to an external, trusted Identity Provider.

Difference Between OAuth and OpenID Connect

The key difference between **OAuth 2.0** and **OpenID Connect (OIDC)** lies in their primary goal: **OAuth 2.0 handles authorization**, and **OpenID Connect handles authentication** by building an identity layer on top of OAuth 2.0.

// Think of it this way:
OAuth 2.0: Answers the question, "What can you do?" (e.g., "This app can post on your behalf.")
OpenID Connect (OIDC): Answers the question, "Who are you?" (e.g., "You are John Doe, email: john.doe@example.com.")

🔑 Core Differences

Feature OAuth 2.0 (Open Authorization) OpenID Connect (OIDC)
Primary Goal Authorization (Delegated Access) Authentication (Identity Verification)
What it Provides A framework for granting **limited access** to protected resources on a server (e.g., granting a photo app access to your Google Photos). An **Identity Layer** built on OAuth 2.0 to verify the user's identity and provide basic profile information.
Relationship The underlying **framework** OIDC is built upon. An **extension** of OAuth 2.0 that adds identity capabilities.
Key Token **Access Token** (Used to access a protected resource, like an API). **ID Token** (A **JWT** used to prove the user's identity and authentication time). Also issues an Access Token for resource access.
Identity Information No standardized way to get user profile information. Defines the **UserInfo Endpoint** and standardizes **Claims** (like name, email, subject) inside the ID Token.
Use Case Example A third-party printing app being allowed to **read** files from your Dropbox account. Using a **"Log in with Google"** button to sign into a new shopping website.

🤝 How They Work Together

In most modern applications that require a user to log in and then access their protected data (like "Log in with Google" and then accessing your Google Drive files), **OIDC and OAuth 2.0 work in tandem**:

Authentication (OIDC): The application uses the OIDC protocol to redirect the user to an Identity Provider (like Google) to log in. The provider authenticates the user and returns an ID Token to the application. The application verifies this token to confirm the user's identity.
Authorization (OAuth 2.0): Simultaneously, the provider issues an Access Token to the application. This token (the OAuth component) is used by the application to request access to protected resources (like the user's profile or API data) on behalf of the user.

OIDC is essentially the standardized way to use the OAuth 2.0 framework for the specific purpose of **user login and identity federation** (**Single Sign-On**).
