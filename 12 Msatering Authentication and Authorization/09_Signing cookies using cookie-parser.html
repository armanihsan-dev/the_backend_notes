🍪 What is Meant by Signing Cookies?

Signing a cookie means adding a **cryptographic signature** (often an **HMAC**) to the cookie's value before sending it to the client. This signature is generated using a **secret key** known only to the server.

The primary purpose of signing a cookie is **tamper detection**.

  • When the server sets the cookie: It computes a signature of the cookie's value using a secret key and appends it to the value.
  • When the client sends the cookie back: The server (using **cookie-parser**) re-computes the signature based on the value it received and compares it to the attached signature.
  • If the signatures **match**: The server can be reasonably confident that the cookie's value has **not been altered** by the user or an attacker.
  • If the signatures **don't match**: The server knows the cookie has been **tampered with** and will ignore the tampered value.
**Note:** Signing does not **encrypt** the cookie's value, which means the content is still **readable** by the client. It only ensures **integrity**.

🛠️ Signing Cookies with cookie-parser in Express.js

You sign cookies by passing a secret string when initializing the **cookie-parser** middleware.

1. Initialize cookie-parser

The secret key is used internally by the middleware for all signing and verification. 

const cookieParser = require('cookie-parser');
const express = require('express');
const app = express();

// Use a long, random, and secret string for the secret
const SECRET_KEY = 'your_super_secret_key_123456789';

app.use(cookieParser(SECRET_KEY));

2. Setting a Signed Cookie

When setting a cookie using res.cookie(), you must pass the option { signed: true }. 

app.get('/set-signed-cookie', (req, res) => {
    // This cookie will be signed using the SECRET_KEY
    res.cookie('user_id', '12345', { 
        signed: true, // <--- Key part for signing
        httpOnly: true, // Recommended for security (not accessible via client-side JS)
        maxAge: 3600000 // 1 hour
    });
    res.send('Signed cookie set!');
});

The cookie sent to the browser will look something like this: **user_id=s:12345.HMAC_SIGNATURE_HERE**. The **s:** prefix indicates it's a signed cookie.

3. Reading a Signed Cookie

**cookie-parser** automatically attempts to verify and parse signed cookies. Verified signed cookies are available on the **req.signedCookies** object, while unsigned cookies are on req.cookies. 

app.get('/read-cookies', (req, res) => {
    const userId = req.signedCookies.user_id;
    
    if (userId) {
        // Cookie is present and verified (signature matches)
        res.send(`Verified User ID: ${userId}`);
    } else {
        // Cookie is either not present, or was tampered with (signature mismatch)
        res.send('No valid signed user_id cookie found.');
    }
    // req.cookies will contain the raw, potentially tampered value (e.g., 's:12345.SIGNATURE')
    // req.signedCookies will contain the *verified* value (e.g., '12345')
});

⚙️ How cookie-parser Works Behind the Scenes

When you use app.use(cookieParser(SECRET_KEY)), the middleware is executed for every incoming HTTP request:

  • **Read Header:** It reads the Cookie header from the client's request.
    • *Example header:* Cookie: session_id=abc1234; user_id=s:54321.HMAC_SIG
  • **Parse and Attach req.cookies:** It splits the header into key/value pairs and attaches the raw, unsigned values to req.cookies.
    • req.cookies.session_id → 'abc1234'
    • req.cookies.user_id → 's:54321.HMAC_SIG'
  • **Identify Signed Cookies:** It looks for cookies prefixed with s: (e.g., user_id).
  • **Verification and Attach req.signedCookies:** For each signed cookie:
    • It extracts the original value (54321) and the attached signature (HMAC_SIG).
    • It re-computes the expected signature of the value (54321) using the server's secret key (SECRET_KEY).
    • If the re-computed signature **matches** the attached signature (HMAC_SIG): The cookie is considered valid and the original value is attached to req.signedCookies.
      • req.signedCookies.user_id → '54321'
    • If the signatures **do NOT match**: The cookie is considered tampered with. It is ignored and not attached to req.signedCookies (or attached as false depending on the version/config).

🔒 Complete Authentication Example (Login/Signup with Signed Cookies)

This is a conceptual example focusing on the cookie mechanism. For a real-world app, you would integrate this with a database (like MongoDB or PostgreSQL) and use a library for password hashing (like **bcrypt**).

Dependencies: npm install express cookie-parser body-parser

server.js:

const express = require('express');
const cookieParser = require('cookie-parser');
const bodyParser = require('body-parser');
const app = express();
const PORT = 3000;

// --- CONFIGURATION ---
const SESSION_SECRET = 'a_very_secure_and_random_string_for_signing'; 
const COOKIE_NAME = 'sessionId';

// --- IN-MEMORY USER DATA (Replace with a DB in production) ---
const users = []; // { id: 1, username: 'test', password: 'hashedpassword' }
let nextUserId = 1;

// --- MIDDLEWARE SETUP ---
app.use(bodyParser.json()); 
app.use(cookieParser(SESSION_SECRET)); 

// --- HELPER FUNCTION: Simple Session ID Generation (Replace with a real session/JWT) ---
const generateSessionId = (userId) => {
    // In a real app, this would be a long, cryptographically secure ID, 
    // often stored in a server-side session store (e.g., Redis). 
    // Here, we'll just use the user ID as a simplified example.
    return `session_${userId}_${Date.now()}`;
};

// --- ROUTES ---
// 1. SIGNUP Route
app.post('/signup', (req, res) => {
    const { username, password } = req.body;
    
    if (users.find(u => u.username === username)) {
        return res.status(400).send('User already exists.');
    }
    
    // In real app, HASH the password here (e.g., with bcrypt)
    const newUser = { id: nextUserId++, username, password }; 
    users.push(newUser);
    
    res.status(201).send(`User ${username} registered successfully. ID: ${newUser.id}`);
});

// 2. LOGIN Route
app.post('/login', (req, res) => {
    const { username, password } = req.body;
    
    const user = users.find(u => u.username === username);
    
    // In real app, COMPARE the password HASH here (e.g., with bcrypt.compare)
    if (!user || user.password !== password) {
        return res.status(401).send('Invalid credentials.');
    }
    
    // Successful login:
    const sessionId = generateSessionId(user.id);

    // Set a SIGNED, HTTP-ONLY cookie to hold the session identifier
    res.cookie(COOKIE_NAME, sessionId, {
        signed: true,          // <--- THIS is how we sign the cookie
        httpOnly: true,        // Prevents client-side JS access (XSS defense)
        maxAge: 24 * 60 * 60 * 1000, // 24 hours
        // secure: true,       // Use in production for HTTPS only
    });
    
    res.send('Login successful! Signed cookie set.');
});

// 3. AUTHENTICATION MIDDLEWARE
const requireAuth = (req, res, next) => {
    // 1. Check req.signedCookies for the session ID. 
    //    cookie-parser has already verified its signature.
    const sessionId = req.signedCookies[COOKIE_NAME]; 
    
    if (!sessionId) {
        // No cookie, or cookie was tampered with (signature mismatch)
        return res.status(401).send('Access Denied: Not authenticated or session tampered.');
    }

    // 2. In a real app, LOOK UP the sessionId in your database/session store 
    //    to retrieve the associated user and ensure the session hasn't expired/revoked.
    //    For this example, we'll just assume validity.
    
    // Optional: Attach user data to the request object
    // req.user = lookUpUserBySessionId(sessionId); 

    console.log(`Verified session ID: ${sessionId}`);
    next(); // Proceed to the protected route
};

// 4. PROTECTED Route
app.get('/dashboard', requireAuth, (req, res) => {
    res.send('Welcome to the PROTECTED dashboard! Your session is verified.');
});

// 5. LOGOUT Route
app.post('/logout', (req, res) => {
    // To 'delete' a cookie, you set it again with a past expiration date.
    res.clearCookie(COOKIE_NAME);
    // In a real app, you would also delete the session record from your database.
    res.send('Logged out successfully.');
});

// Start Server
app.listen(PORT, () => {
    console.log(`Server running on http://localhost:${PORT}`);
});

🧠 How Things Work:

  • **Sign Up:** A new user is created.
  • **Login (/login):**
    • The server authenticates the user (checks username/password).
    • A unique sessionId is created for the user.
    • res.cookie(COOKIE_NAME, sessionId, { signed: true, ... }) is called. The **cookie-parser secret** is used to create an **HMAC signature** of the sessionId, and the combined value (value + signature) is sent to the client.
  • **Access Protected Route (/dashboard):**
    • The client's browser automatically sends the signed cookie back in the Cookie header.
    • The requireAuth middleware runs.
    • **cookie-parser's logic runs first**, verifying the signature against its secret key.
    • If **valid**, the original sessionId is available at req.signedCookies.sessionId.
    • If **tampered with**, the value is not added to req.signedCookies, and the check if (!sessionId) fails, denying access.

How cookie-parser makes the cookie signed even though the cookie is set from another module:

The way **cookie-parser** enables signing cookies, even when they are set from another module or deep within a route handler, is by **attaching the secret key to the Express req object** and by **overriding the native res.cookie() method**.

🔑 1. The Secret Key is Globalized on the Request

When you initialize **cookie-parser** and pass it a secret key: 

const cookieParser = require('cookie-parser');
app.use(cookieParser('your_secret_key_here'));

The **cookie-parser** middleware function runs first for every incoming request. Its primary task for signing is to:

  • Read the secret key you provided.
  • Attach this secret key to the incoming request object as **req.secret**.

This makes the secret key accessible to any subsequent middleware or route handler that receives the req object, regardless of which module or file it is in.

✍️ 2. Express's res.cookie() Method Uses req.secret

Express is designed to integrate with middleware like **cookie-parser**. When you call res.cookie() in any of your modules: 

// This can be in a controller file, a service file, or an auth middleware
res.cookie('my_cookie', 'my_value', { signed: true });

The **res.cookie()** method in Express checks for two things when the { signed: true } option is present:

  • It checks if a secret key is available on **req.secret**.
  • If **req.secret** exists, it uses the key and an internal signing utility (often the **cookie-signature** module, which is part of the Express ecosystem) to generate an **HMAC signature** for the cookie's value.

The Signing Formula

The final cookie value that is sent in the Set-Cookie header follows this format:

$$\text{Final Cookie Value} = \text{s:}+\text{Value}+\text{.}+\text{HMAC}(\text{Value, req.secret})$$

The cookie is then correctly formatted into the HTTP response header and sent back to the browser.

🔁 Summary of the Flow

The key takeaway is that **cookie-parser** only needs to run once at the beginning of the middleware stack to **inject the secret**. The actual signing logic is then executed by the built-in res.cookie() method later in the request cycle, leveraging the secret that **cookie-parser** prepared.

Step Action Responsibility Mechanism
1. Initialization app.use(cookieParser(SECRET)) cookie-parser Attaches SECRET to the Express req object as req.secret.
2. Setting res.cookie(name, value, { signed: true }) Express's res.cookie() Checks for { signed: true }. If true, it retrieves the secret from req.secret and uses it to sign the cookie value before setting the Set-Cookie header.
3. Reading/Verification req.signedCookies.name cookie-parser On the next request, it runs again, retrieves the cookie, and uses req.secret to verify the signature.

How behind the cookie-parser sets the cookie with HMAC?

The actual process of setting a cookie with an **HMAC signature** is handled by **Express's res.cookie() method**, which uses an underlying utility module like **cookie-signature**.

The role of the **cookie-parser** middleware is to **prepare the environment** so that Express knows **what secret to use** for the signing.

1. Middleware Setup: Providing the Secret Key 🔑

The process begins when you configure the cookie-parser middleware: 

app.use(cookieParser('your_strong_secret_key'));

When this middleware runs, it performs one critical action to enable signing:

  • It assigns the provided string ('your_strong_secret_key') to the **req.secret** property of the Express request object. This makes the secret accessible to all subsequent middleware and route handlers.

2. Cookie Setting: Triggering the Signature Generation ✍️

In your route handler, when you instruct Express to set a signed cookie: 

res.cookie('user_id', '12345', { signed: true });

Express's res.cookie() method checks the options. When it sees signed: true, it does the following:

  • **Retrieves the Secret:** It looks for the secret on **req.secret**.
  • **Calls the Signing Utility:** It calls an internal function (from a library like cookie-signature) to create the HMAC. The inputs for the HMAC function are:
    • The cookie value: '12345'
    • The secret key: 'your_strong_secret_key'
  • **Generates the HMAC:** The **HMAC** (Hash-based Message Authentication Code) is calculated as a unique cryptographic digest of the value and the secret. HMAC ensures that if the value is ever tampered with, the signature will no longer be valid.
  • **Concatenates the Final Value:** The cookie value is then formatted into a single string to be sent to the client.

The final string format sent to the client is:

$$\text{s:}\langle\text{original value}\rangle\text{.}\langle\text{HMAC signature}\rangle$$

For the example above, the final cookie value might look like this:

s:12345.M4T67uJg...

3. Response: Sending the Cookie to the Client 🌐

The final signed value is placed into the HTTP **Set-Cookie header** of the response and sent to the client's browser.

The signature is for **integrity**, not **encryption**. The cookie value (12345) is still visible to the client, but any attempt to change it (e.g., to s:99999.M4T67uJg...) will be detected on the next request because the signature will not match the recalculated HMAC for the new value.
