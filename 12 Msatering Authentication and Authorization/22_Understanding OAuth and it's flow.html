🛡️ OAuth (Open Authorization) Notes

OAuth (Open Authorization) is an open standard( protocol ) that was developed to solve the problem of sharing access to protected resources (like a user's photos or contact list) on one service with a third-party application without sharing the user's login credentials (username and password). In simpler terms, it provides a mechanism for **secure delegated access**.

🔑 Key Problem Solved by OAuth

Before OAuth, if a third-party application needed to access a user's data on a service (e.g., a photo printing service needing access to a user's Google Photos), the user had to provide their username and password for that service directly to the third-party application.

This was a major security risk because the third-party application:

  • Could store and potentially misuse the user's credentials.
  • Gained full, unrestricted access to all the user's data on that service, not just the data it needed.
  • Maintained access permanently, until the user changed their password.

OAuth solves this by using Access Tokens with limited scope and limited lifetime to grant access instead of passwords.

📚 Terminologies of OAuth

The OAuth 2.0 framework defines four main roles:

  • Resource Owner: The entity (typically the end-user) who owns the protected resources (data) and has the ability to grant access to them.
  • Client: The application (e.g., a photo printing app, a website, a mobile app) that wants to access the Resource Owner's protected resources.
  • Resource Server: The server hosting the protected resources (e.g., the API that serves the user's photos). It accepts and validates access tokens.
  • Authorization Server: The server that authenticates the Resource Owner and issues Access Tokens to the Client after getting the Resource Owner's authorization. (Often, the Authorization Server and Resource Server are part of the same service provider, like Google or Facebook).
  • Access Token: A credential issued by the Authorization Server to the Client, which the Client uses to access the protected resources on the Resource Server on behalf of the Resource Owner. It has a specific scope and a limited lifetime.
  • Scope: Defines the limitations of the access granted (e.g., 'read-only access to calendar' or 'write access to photos').

🌐 How OAuth Connects Two Different Applications

OAuth is an **authorization layer** that sits between the third-party application (Client) and the application hosting the user data (Resource Server).

It connects them by enabling the Client to obtain an Access Token from the data host's Authorization Server. This token is the key that opens a specific, pre-approved door to the Resource Server.

  1. User Initiation: The user interacts with the Client application (App A) and clicks a button like "Connect with Google."
  2. Redirection to Authorization Server: App A sends the user's browser to the Authorization Server (Google).
  3. Authentication & Consent: The user logs in to Google and is presented with a **consent screen** asking if they grant App A the requested scope of access (e.g., read contacts).
  4. Token Issuance: If the user consents, Google issues an Access Token to App A.
  5. Access Granted: App A (Client) presents this Access Token to the Google API (Resource Server) to access the contacts. The Resource Server validates the token and only grants access to the specific resources defined by the token's scope.

Crucially, App A (Client) **never sees the user's login credentials** for Google. The connection is established via the secure, limited-use Access Token.

⚙️ How OAuth Works Behind the Scenes (Authorization Code Flow)

The **Authorization Code Grant Flow** is the most common and secure method for web and mobile applications.

Here is a simplified flow:

  1. Authorization Request: The Client sends the Resource Owner's browser to the Authorization Server with its client_id, requested scope, and a redirect_uri.
  2. Authentication & Consent: The Authorization Server authenticates the Resource Owner (user logs in) and asks for permission (consent) for the requested scope.
  3. Authorization Code Grant: If consent is given, the Authorization Server sends the Resource Owner's browser back to the Client's registered redirect_uri with a short-lived **Authorization Code** in the URL.
  4. Code Exchange (Back Channel): The Client (securely, from its server) sends a request directly to the Authorization Server's **Token Endpoint**. This request includes the Authorization Code, its client_id, and its client_secret (a private key) to authenticate itself.
  5. Access Token Response: The Authorization Server validates the code and the Client's secret. If valid, it returns an **Access Token** (and optionally a Refresh Token) to the Client.
  6. Protected Resource Access: The Client uses the Access Token to make requests to the Resource Server (API) on behalf of the Resource Owner.
  7. Resource Response: The Resource Server validates the Access Token and, if valid, returns the requested resource (data) to the Client.

🎯 Use Cases of OAuth

OAuth is the foundation for **delegated access** and is used widely across the internet:

  • **"Sign in with..." Buttons (Social Login):** When a user signs up for a new website using "Sign in with Google," "Log in with Facebook," or "Continue with Apple." This authenticates the user's identity (often combined with **OpenID Connect**) and allows the new website to access basic profile information (name, email) without getting the user's password.
  • **Third-Party App Integrations:**
    • A printing service requesting access to a user's photos on Google Photos.
    • A scheduling app requesting access to a user's events on Google Calendar or Microsoft Outlook.
    • A data analytics tool requesting read access to a user's data on Salesforce.
  • **Device Authorization (IoT/Smart TVs):** Allowing applications on input-constrained devices (like a Smart TV app or a headless device) to access a user's account by providing a short code that the user enters on a separate, easily accessible device (like their phone or computer).
  • **Machine-to-Machine Communication:** Automated processes or microservices accessing protected APIs using their own credentials instead of a user's.

💡 What is Meant by "OAuth is a Standard Protocol"

A protocol is a set of rules that defines how computers communicate. A standard protocol is one that is agreed upon by different organizations and is widely adopted.

When it is said that "OAuth is a standard protocol," it means two primary things:

🏛️ It is an Open, Agreed-Upon Set of Rules (Standard)

  • Public Specification: OAuth is governed by the Internet Engineering Task Force (IETF) and is defined in several **Request for Comments (RFCs)** documents (primarily RFC 6749 for OAuth 2.0). This means the rules are public, peer-reviewed, and agreed upon by industry experts.
  • Interoperability: Because it's a standard, any company (like Google, Facebook, Microsoft) can implement OAuth according to the same established set of rules. This guarantees interoperability, meaning a third-party application written to comply with the OAuth standard can securely interact with any service that also follows the standard.
  • Avoids Vendor Lock-in: It prevents a single company from controlling the authorization process, ensuring a consistent and expected behavior across different service providers.

🔒 It is a Defined Process for Authorization (Protocol)

  • Defined Steps: A protocol establishes a clear sequence of communication. OAuth defines the **specific steps** that the different parties (Client, Resource Owner, Authorization Server, Resource Server) must follow to safely delegate access.
  • Specific Terminology and Messages: The protocol mandates the use of specific terms (like Access Token, Scope, Redirect URI) and defines the exact format of the messages (HTTP requests and responses) that must be exchanged at each step.

In essence, calling OAuth a standard protocol means it's the official, universally accepted instruction manual for safely and securely granting limited access to a user's data on one service from another application, without ever sharing the user's password.
