Git uses **SHA-1 hashing** extensively to ensure data integrity and track changes, particularly for commits. Behind the scenes, the **commit hash** is a unique identifier generated by calculating the SHA-1 hash of the **serialized content** of the commit object.

1. How Git Hashing Works for Commits

A Git **commit object** is essentially a text file that contains specific metadata. The structure used for hashing is:

  • Header: The object type (commit) followed by a space, then the size (in bytes) of the object's contents, and a null byte (\0).
    • \text{`commit }<\text{size}>\backslash0\text{`}\]
  • Contents: The actual commit metadata:
    • \text{tree}: The SHA-1 hash of the **root tree object** (representing the state of the directory at that time).
    • \text{parent}: One or more SHA-1 hashes of the preceding commit(s) (zero for the initial commit, two or more for merge commits).
    • \text{author}: The author's name, email, and the commit timestamp.
    • \text{committer}: The committer's name, email, and the commit timestamp (can be different from the author).
    • \text{GPG signature} (optional): A cryptographic signature.
    • \text{commit message}: The descriptive message for the commit.

The entire **blob**—Header + Contents—is fed into the SHA-1 hash function, and the 40-character hexadecimal output is the **commit hash** you see (e.g., 8d407d...).

Key Role of Hashing:

  • Immutability: Since the hash is calculated from all contents, even a single-byte change in the commit message, timestamps, or the files referenced in the tree would result in a completely different hash. This means commits are effectively immutable.
  • Content Addressing: Git uses a **content-addressable filesystem**. The hash **is** the address (name) of the object, ensuring that the content can be looked up reliably by its identifier.
  • Integrity: If any part of the commit object is corrupted, re-hashing it would produce a different result, revealing the corruption.

2. Practical Hashing with Node.js Crypto Module

We can simulate Git's hashing process using Node.js to see how a commit hash is generated.

Prerequisites:

To replicate a real Git commit, you need the following information from an existing commit:

  • **Commit Contents (Metadata)**: The actual text of the commit object (excluding the initial SHA-1 header).
  • **Size**: The byte length of the commit contents.

Steps:

Step 1: Get the Raw Commit Object Data

For a real commit (e.g., HEAD), you can use the git cat-file -p <commit-hash> command to view the contents and git cat-file -s <commit-hash> to get the size.

Assume the following as our **Commit Contents**:

tree a94c65377f082e75e54d1947b1c313a076495b6a
parent 8d407d65b7468233f211322d7a5b3a86c62c3e41
author Jane Doe <jane.doe@example.com> 1635420000 +0500
committer Jane Doe <jane.doe@example.com> 1635420000 +0500

Initial commit

The byte size of these contents (including newlines) is 221.

Step 2: Construct the Git Hashing Blob

The full blob for hashing is:

\text{`commit }221\backslash0\text{tree a94c65377f082e75e54d1947b1c313a076495b6a\dots`}\]

Step 3: Implement Hashing in Node.js (ES6 Module)

In an ES6 module (.mjs file or using "type": "module" in package.json), you can use the built-in crypto module.

JavaScript

import crypto from 'crypto';
import { Buffer } from 'buffer';

// --- Data from the commit ---
const COMMIT_CONTENTS = `tree a94c65377f082e75e54d1947b1c313a076495b6a
parent 8d407d65b7468233f211322d7a5b3a86c62c3e41
author Jane Doe <jane.doe@example.com> 1635420000 +0500
committer Jane Doe <jane.doe@example.com> 1635420000 +0500

Initial commit
`;

// Calculate the byte size of the contents
const CONTENT_SIZE = Buffer.byteLength(COMMIT_CONTENTS, 'utf8'); // Should be 221

// --- 1. Construct the complete blob for hashing ---
// Format: "object_type size\0contents"
const HASHING_BLOB = `commit ${CONTENT_SIZE}\0${COMMIT_CONTENTS}`;

// --- 2. Calculate the SHA-1 hash ---
const calculateGitCommitHash = (blob) => {
    // 2a. Create a SHA-1 hash object
    const shasum = crypto.createHash('sha1');
    
    // 2b. Update the hash with the full blob (encoding must be consistent with size calculation)
    shasum.update(blob, 'utf8');
    
    // 2c. Get the final hexadecimal hash
    return shasum.digest('hex');
};

const calculatedHash = calculateGitCommitHash(HASHING_BLOB);
const expectedHash = "85a1f26a7e0294e5a953a99281a8c3d806554b5f"; // A hypothetical real hash for this content

console.log(`Commit Contents Size: ${CONTENT_SIZE} bytes`);
console.log("------------------------------------------");
console.log(`Calculated SHA-1 Hash: ${calculatedHash}`);
console.log(`Expected Git Commit Hash: ${expectedHash}`);

// --- 3. Practical Comparison ---
if (calculatedHash === expectedHash) {
    console.log("\n✅ Hash comparison successful: The calculated hash matches the expected Git hash.");
} else {
    console.log("\n❌ Hash comparison failed: There is an error in the input data or calculation.");
}

This code snippet demonstrates the exact mechanism Git uses: it concatenates the **object type**, **size**, a **null byte**, and the **object's contents**, and then computes the **SHA-1 hash** of that entire buffer. If your calculatedHash matches the real commit's hash, you've successfully replicated Git's behind-the-scenes commit hashing.
