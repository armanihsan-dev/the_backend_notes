🔐 What is Federated Authentication?

Federated authentication is a system that allows a user to access multiple independent applications or services across different domains (or companies) using a single set of credentials provided by a trusted third party, known as the Identity Provider (IdP).

In essence, a website (the Service Provider or Relying Party) delegates the responsibility of authenticating the user to the IdP. Instead of creating and managing a new account and password for every site, the user can sign in using an existing account (like Google or Facebook).

Key Components:

  • User: The person trying to access a service.
  • Identity Provider (IdP): Manages the user's digital identity and credentials (e.g., Google, Okta).
  • Service Provider (SP) or Relying Party (RP): The website or application the user wants to access.

💻 GSI vs. FedCM

Google Identity Services (GSI) and Federated Credential Management (FedCM) are both mechanisms related to using a Google account as an Identity Provider for signing into third-party websites.

Feature Google Identity Services (GSI) Federated Credential Management (FedCM)
Type A library and API suite from Google (built on OAuth 2.0/OpenID Connect) for authentication and authorization. A standard browser API designed as part of the Privacy Sandbox initiative to manage federated sign-in flows.
Mechanism Relied heavily on third-party cookies, cross-site iframes, and redirects to maintain the sign-in state across different websites. The browser acts as a secure intermediary between the Relying Party and the Identity Provider. It does not use third-party cookies or redirects.
User Interface (UI) The sign-in prompts (like the "One Tap" prompt) are created and displayed by the GSI JavaScript library, which runs on the website. The sign-in prompts are browser-mediated and displayed by the browser itself, giving users more visual control and consistency.
Privacy Prone to being used for cross-site tracking because of its reliance on third-party cookies/iframes (even when not Google's intent). Privacy-preserving by design. The browser only contacts the IdP after the user gives explicit consent via the browser's UI.
Future Deprecated as a standalone solution for the core sign-in flow and is migrating to use FedCM APIs internally. The future standard for federated identity, especially for Google Sign-In on Chrome.

🔒 FedCM vs. GSI: Which is More Secure?

FedCM is generally considered more secure than the traditional GSI implementation (which relied on third-party cookies and iframes), especially from a privacy and user tracking perspective.

Why FedCM is more secure:

  • Elimination of Third-Party Tracking: Traditional GSI flows could be used for cross-site tracking because the IdP could know which websites the user was visiting by reading its third-party cookies or watching iframes load. FedCM completely removes this risk by having the browser mediate the flow and only communicate with the IdP after the user interacts with the browser's UI and gives consent.
  • Browser Mediation: The browser controls and renders the sign-in prompt. This prevents phishing attacks where a malicious website might try to fake a sign-in pop-up, as the user knows the authentic dialog is controlled by the browser, not the website itself.
  • Cross-Origin Isolation: FedCM is designed to work in a way that provides more security and privacy isolation between the IdP and the Relying Party, making it harder for one to infer information about the user's activity on the other.

✈️ Why Google Chrome is Migrating to FedCM

Google Chrome (and other browsers) is migrating to FedCM primarily due to the deprecation of third-party cookies as part of the broader Privacy Sandbox initiative.

  • Phasing Out Third-Party Cookies: The traditional method for federated identity (including GSI's "One Tap" feature) often relied on third-party cookies to check if a user was already logged into the IdP. As Chrome phases out third-party cookies to enhance user privacy, a new mechanism is needed to allow federated sign-in to function. FedCM provides a privacy-preserving replacement.
  • Increased User Privacy: FedCM is designed to prevent the Identity Provider from passively tracking the user's navigation across different sites. The browser explicitly requests credentials from the IdP only when needed and with user consent.
  • Improved User Experience: By using a standardized, browser-mediated UI, the sign-in prompt is cleaner, more consistent, and less disruptive across different websites, addressing the "NASCAR problem" of cluttered login pages with multiple buttons.

Google is automatically migrating existing GSI implementations to use FedCM under the hood to ensure a continued, secure, and private sign-in experience after third-party cookies are fully restricted.

🖼️ What is an iFrame?

That's a very important question, as the concept of the iframe is central to understanding the security and privacy issues that FedCM is designed to solve!

Here is a detailed explanation of what an iframe is and how it relates to federated authentication and tracking.

What is an iFrame?

An iframe (short for Inline Frame) is an HTML element used to embed another HTML document (a separate, complete web page) within the current one.

Think of an iframe as a mini-browser window embedded right inside the main webpage.

Key Characteristics:

  • Separate Document: The content inside the iframe is a completely separate HTML document, with its own independent Document Object Model (DOM), CSS, and JavaScript.
  • Source URL: An iframe uses a src attribute to point to the URL of the content it should display.
  • Isolation: The content inside the iframe is generally isolated from the parent page by the browser's Same-Origin Policy—meaning a script on the parent page cannot directly read data from an iframe whose source is a different website, and vice-versa.

Common Uses of iFrames:

  • Embedding Multimedia: Embedding a YouTube video player or a Spotify playlist onto a blog.
  • Displaying Maps: Embedding a Google Map showing a business location.
  • Third-Party Widgets: Integrating things like payment forms (e.g., Stripe) or social media feeds.

💔 The Problem with "Cross-Site iFrames" and Tracking

The term "cross-site iframe" is used when the domain of the parent page is different from the domain of the content loaded inside the iframe. This is where the security and privacy issues arose, especially in the context of older Federated Authentication systems like GSI.

1. The Old GSI/iFrame Flow (Why it was a problem)

In the traditional Google Sign-In (GSI) implementation, the prompt (the "Sign in with Google" button or the "One Tap" dialog) was often loaded inside a hidden or nearly invisible cross-site iframe. 

// The Relying Party (RP) Website
Website: example.com (the Relying Party)

// The Identity Provider (IdP) content loaded in a hidden iframe
iFrame Source: accounts.google.com (the Identity Provider)

When example.com loaded, it would embed a hidden iframe from accounts.google.com.

How Tracking Worked (The Problem): When the browser loaded the iframe from accounts.google.com, the browser would also send any third-party cookies it had for accounts.google.com (which contained the user's login session).

Passive Tracking: Simply by loading the iframe, Google (the IdP) could determine that a logged-in user was currently visiting example.com. This allowed the IdP to passively track a user's activity across any website that included this iframe, even if the user never clicked the sign-in button.

2. How FedCM Solves the iFrame Tracking Issue

FedCM (Federated Credential Management) removes the need for this cross-site iframe mechanism entirely for the authentication check:

  • Browser Mediation: With FedCM, the browser is the intermediary. The website tells the browser, "I need credentials from Google."
  • No Passive Loading: The browser does not passively load a hidden Google iframe and send cookies. Instead, it checks its local data to see if the user is already signed in to Google. The browser only communicates with the IdP's server (accounts.google.com) after the user gives explicit, visual consent via a clear, browser-controlled dialog.
  • No Third-Party Cookies: By eliminating the reliance on cross-site iframes and the associated third-party cookies, FedCM prevents the IdP from performing cross-site tracking, making the sign-in flow much more private and secure.

In summary, the iframe is a standard web tool, but when used to load content from a different site that relies on third-party cookies for authentication, it became a major vector for the cross-site tracking that modern privacy initiatives like FedCM are designed to block.

📝 Key Resources and Documentation (FedCM)

The Federated Credential Management (FedCM) API is part of Google's Privacy Sandbox initiative and is being implemented across the web, including within the Google Identity Services (GSI) library.

Here are the key resources you should refer to, depending on whether you are a website owner (Relying Party) or an Identity Provider:

1. Google's Migration Guide (For websites already using Google Sign-In)

If your website currently uses "Sign in with Google" (the GSI library), this guide explains the minimal changes required for a seamless transition to the FedCM-based flow:

  • Migrate to FedCM (Google for Developers): https://developers.google.com/identity/gsi/web/guides/fedcm-migration
  • Key Action: This guide shows you how to enable FedCM (by setting a use_fedcm flag) and details changes needed for cross-origin iframes or custom button layouts.

2. General FedCM Documentation (For all developers)

This documentation explains the FedCM API from a browser-agnostic perspective:

  • FedCM Overview (Chrome for Developers): https://developer.chrome.com/docs/identity/fedcm
    This is the main entry point to understand how FedCM benefits users, Relying Parties, and Identity Providers.
  • Implementing FedCM on the Relying Party side (Chrome for Developers): https://developer.chrome.com/docs/identity/fedcm/implement/relying-party
    This covers the JavaScript calls a website needs to make to initiate the sign-in flow.
  • W3C Federated Credential Management API Specification: https://www.w3.org/TR/fedcm/
    For the most technical and up-to-date details on the browser API and protocol, this is the official W3C specification document.

3. Identity Provider (IdP) Integration

If you are building your own Identity Provider service and want it to work with FedCM, you need to implement several server-side endpoints:

  • Implement an identity solution with FedCM on the Identity Provider side (Chrome for Developers): https://developer.chrome.com/docs/identity/fedcm/implement/identity-provider
    This explains the required configuration files (like the .well-known/web-identity file) and the endpoints the IdP must expose to the browser.
