OAuth 2.0 Grant Types

Grant types in OAuth 2.0 define the specific method an application (Client) uses to obtain an Access Token—a credential that grants limited access to a user's (Resource Owner's) protected resources, hosted on a Resource Server, without exposing the user's password.

OR

A grant type is a way for a client to request authorization servers and receive tokens. It determines how the client authenticates itself and/or the user.

The choice of grant type depends heavily on the client application's security capabilities and its interaction model with the user and the authorization server.

🔑 Common OAuth 2.0 Grant Types and Use Cases

Here are the most common grant types, their processes, and their typical use cases:

  1. 1. Authorization Code Grant (Recommended for Web Apps)

    This is generally considered the most secure and most widely used grant type.

    Process:

    The client redirects the user to the Authorization Server to log in and approve the request.

    The Authorization Server sends back a single-use Authorization Code to the client's registered redirect URI.

    The client's backend securely exchanges this code, along with its own credentials (Client ID and Client Secret), for an Access Token and, optionally, a Refresh Token.

    Use Case:

    Confidential Clients like traditional Web Applications running on a server (e.g., PHP, Java, Python apps). The code exchange happens server-to-server, protecting the Access Token from being exposed in the user's browser.

    Authorization Code with PKCE (Proof Key for Code Exchange) is the current best practice for Single Page Applications (SPAs) and Mobile/Native Apps because these clients cannot securely store a Client Secret. PKCE adds an extra layer of security to this flow.

  2. 2. Client Credentials Grant

    This flow is used for machine-to-machine communication, where there is no human user involved.

    Process:

    The client (acting on its own behalf) directly sends its Client ID and Client Secret to the Authorization Server.

    The Authorization Server verifies the credentials and returns an Access Token.

    A Refresh Token is typically not issued since there's no user session to maintain.

    Use Case:

    Server-to-Server communication, where a backend application needs to access an API that protects its own resources, not a user's data (e.g., a scheduled batch job fetching application-wide configuration data from another service, or an internal microservice calling another internal API).

  3. 3. Refresh Token Grant

    This grant type allows a client to obtain a new Access Token without requiring the user to re-authenticate.

    Process:

    The client sends an expired Access Token and its Refresh Token to the Authorization Server.

    The server validates the Refresh Token and issues a new Access Token (and sometimes a new Refresh Token).

    Use Case:

    Extending sessions and maintaining continuous access to resources when the Access Token (which usually has a short lifespan) expires. This improves the user experience by avoiding frequent log-in prompts.

  4. 4. Resource Owner Password Credentials Grant (Not Recommended)

    This flow is generally discouraged due to security risks.

    Process:

    The client application collects the user's username and password.

    The client sends these credentials (along with its own Client ID and Secret) directly to the Authorization Server.

    The server verifies the credentials and returns an Access Token.

    Use Case:

    It was originally intended for highly trusted first-party applications (owned and operated by the resource provider) where a user is willing to hand over their credentials. However, because it violates the principle of never sharing credentials with the client, it is now largely considered an anti-pattern. Authorization Code with PKCE is the recommended alternative.

  5. 5. Device Code Grant (Device Authorization Flow)

    Used for devices with limited input capabilities (e.g., smart TVs, printers, or command-line apps) that cannot easily perform web redirects.

    Process:

    The device requests a Device Code and User Code from the Authorization Server.

    The device displays the User Code and a verification URL to the user.

    The user goes to the verification URL on a separate, input-enabled device (like a smartphone or laptop), enters the User Code, and grants permission.

    The original device periodically polls the Authorization Server with the Device Code until authorization is granted, at which point it receives the Access Token.
