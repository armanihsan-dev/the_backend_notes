Redis Key Iteration: SCAN vs. KEYS

The **SCAN** and **KEYS** commands in Redis serve the same goal—listing keys—but they use fundamentally different execution models, which results in drastically different impacts on your Redis server and Node.js client application.

Here's a breakdown of the differences and their effects:

🔑 Execution and Performance Difference

The primary distinction lies in how the Redis server processes each command.

Feature KEYS pattern SCAN cursor [MATCH pattern] [COUNT count]
Execution Model Synchronous & Blocking Asynchronous & Incremental
Time Complexity $O(N)$, where $N$ is the total number of keys. Amortized $O(1)$ per call. Total $O(N)$ for full iteration.
Server Impact **High/Severe.** Blocks the Redis server for the entire duration of the operation. **Low.** Performs a small, quick step, returning control immediately.
Guarantees Returns all keys matching the pattern at the moment of execution. Returns elements incrementally; provides **best-effort guarantees** (keys might be missed or returned multiple times if the dataset is modified during iteration).
Output A single, large list of all matching keys. A **cursor** (for the next call) and a small batch of keys.

💥 Effect on the Redis Server

The choice between KEYS and SCAN directly impacts the health and availability of your Redis instance, especially in production environments.

1. KEYS Command Effect (The Bad)

When you run KEYS * or a similar broad pattern:

  • **Server Blockage (Single Threaded):** Redis is single-threaded. KEYS is a **blocking operation** that must iterate over every single key in the database to compile the result. During this process, **no other commands** (reads, writes, or even simple checks) can be processed by Redis.
  • **High Latency:** For a large dataset (e.g., millions of keys), KEYS can block the server for seconds or even minutes. This causes **massive latency spikes** for all other clients and can trigger monitoring alerts for unavailability.
  • **Production Danger:** Using KEYS in production is widely considered a **dangerous practice** and should be avoided entirely.

2. SCAN Command Effect (The Good)

When you run SCAN 0 MATCH *:

  • **Non-Blocking:** SCAN performs an **atomic, bounded amount of work** (based on the COUNT hint) on each call. It quickly finds a small batch of keys and returns the new cursor.
  • **Consistent Performance:** Because the work per call is limited, it maintains **low latency** and doesn't monopolize the server's CPU. The rest of your application's commands continue to be served quickly.
  • **Scalability:** It allows you to iterate over extremely large databases without fear of taking the server down.

💻 Effect on the Node.js Server (Client)

The effects also extend to the client application, which in this case is your Node.js server.

1. KEYS Command Effect

  • **Memory Pressure:** When KEYS returns a huge list of millions of keys, your Node.js process must **allocate memory to hold this massive array**. This can lead to **high memory consumption** and trigger the garbage collector more frequently, causing performance hiccups.
  • **I/O Blocking (If not pipelined):** While Node.js itself is single-threaded and non-blocking, the initial Redis connection might be saturated waiting for the single, large response, which can tie up that connection resource.

2. SCAN Command Effect

  • **Asynchronous-Friendly:** SCAN is perfectly suited for Node.js's non-blocking, asynchronous nature. The Node.js client initiates a SCAN call, **awaits the small response**, and then immediately processes it before scheduling the next SCAN call, allowing the Node.js event loop to handle other requests in between.
  • **Controlled Memory Usage:** Because you only receive a small batch of keys at a time, the client application's memory usage is kept stable and manageable, preventing large, sudden garbage collection pauses.

❓ When to Use Which Command

The decision of when to use KEYS versus SCAN is crucial for maintaining the performance and stability of your Redis server. It primarily depends on the **size of your database** and the **environment** you are operating in.

In summary: **Always use SCAN for iterating over keys.** KEYS should only be used in development or testing environments on small, non-critical datasets.

🚫 When NOT to Use KEYS (The General Rule)

Never use KEYS in a production environment with a large dataset (thousands of keys or more).

  • **Use KEYS only when:**
    • **Development/Testing:** You are working locally, in a staging environment, or on a small, dedicated test instance.
    • **Small Dataset:** Your database is guaranteed to have a very small, manageable number of keys (e.g., fewer than a few hundred), and the execution time will be negligible.
    • **One-Time Scripts:** You are running a rare, administrative command (like an overnight cleanup script) on a temporary, non-critical database copy.
  • **Why?** Because KEYS is a **blocking operation** with $O(N)$ time complexity, it stops all other Redis operations until it completes. In a production environment, this will cause massive latency spikes and potentially downtime for your application.

✅ When to Use SCAN (The Best Practice)

Always use SCAN when iterating over keys in a production environment or on any large dataset.

  • **Use SCAN when:**
    • **Production Environment:** You need to retrieve keys on a live system where low latency is critical.
    • **Large Datasets:** Your database contains millions of keys or is expected to grow significantly.
    • **Background Jobs:** You are implementing background tasks (like data migration, cleanup, or analytics) that must iterate through the entire keyspace without impacting foreground application performance.
    • **Incremental Processing:** You need to process the keys in batches (chunks), which is the natural way SCAN works and is very friendly to non-blocking client servers like Node.js.
  • **How to Use SCAN:** SCAN is used in a loop until the cursor returns to 0. This breaks a large operation into many tiny, quick $O(1)$ operations:
    1. Start with SCAN 0.
    2. Receive a **cursor** and a **batch of keys**.
    3. Use the new cursor to make the next SCAN call.
    4. Repeat until the cursor is 0.
In summary, for virtually all real-world scenarios, **SCAN** is the required tool for keyspace iteration. **KEYS** is reserved for casual, non-critical debugging.
