⚡ Single Server Instance vs. Redis Cluster

Here’s the clear and simple difference between a single Redis server instance and a Redis cluster.

⚡ 1. Single Server Instance (Standalone Redis)

  • ✔ **What it means**: Only **one Redis server** is running. All data is stored in this single server’s memory.
  • ✔ **Problem**: If this server goes down → your Redis becomes **unavailable** (No automatic failover).
  • ✔ **Best for**: Local development, small projects, caching, rate limiting, etc.
  • ✔ **Pros**: Easy to use, Simple configuration, Fast and perfect for development.
  • ✔ **Cons**: No automatic failover, No distributed scaling (All data must fit on one machine).
  • ✔ **Example**: 
    redis-server

⚡ 2. Redis Cluster

  • ✔ **What it means**: **Multiple Redis servers** working together. Data is automatically partitioned across multiple Redis **nodes**.
  • ✔ **Benefit**: If one node fails → another node takes over (Automatic failover). You can scale Redis horizontally across multiple servers.
  • ✔ **Example Cluster**: 3 masters and 3 replicas:
    • Master 1 → Replica 1
    • Master 2 → Replica 2
    • Master 3 → Replica 3

📌 Major Differences (Simple & Important)

Feature Standalone Redis Redis Cluster
Servers 1 3+ servers
Scaling Vertical (upgrade RAM/CPU) Horizontal (add more nodes)
Failover ❌ No ✔ Automatic
High availability ❌ No ✔ Yes
Data partitioning ❌ No ✔ Yes (slots)
Complexity Low High
Best for Dev, small apps Large-scale apps, microservices

📌 When do you need a Redis cluster?

You only need a cluster if:

  • ✔ Your data is **too large for one machine** (e.g., 20GB+ cache or 100M+ keys).
  • ✔ You want **high availability** (If one machine goes down → app continues running).
  • ✔ You run a **large-scale distributed system**.

**Summary (1-line explanation):** Standalone Redis = **one server**, simple, fast, but no failover. Redis Cluster = **multiple servers**, scalable + highly available.

📌 Cluster Node Placement and Relationships

✅ 1. Are all Redis cluster nodes running on a single computer?

  • ✔ **Option A: All nodes on a single machine**: This is usually for **testing or learning** (e.g., different ports on 127.0.0.1).

    👉 **Not useful in production** because if the machine dies → **entire cluster dies**.

  • ✔ **Option B: Nodes on different machines (REAL cluster)**: This is how Redis is used in **production**: 
    Server A → Master 1 + Replica 1
Server B → Master 2 + Replica 2
Server C → Master 3 + Replica 3

    👉 If Server A goes down → Replica 1 on another machine becomes the new master. This gives you **high availability**.

✅ 2. Are cluster nodes children of a parent node?

**No.** There is **NO parent node** in Redis Cluster. Redis Cluster is **peer-to-peer**, not parent-child.

📌 How Redis Cluster Works:

  • ✔ All **masters are equal**—they communicate with each other using the **Gossip Protocol**.
  • ✔ Each master node is responsible for a range of **hash slots** (16,384 slots total).
  • ✔ The **ONLY** parent-child relationship is: Master → Replica (Slave). Replicas follow their master, but all masters are equals.

📌 Correct Relationships

Master 1 <──> Master 2 <──> Master 3   (all equal, gossip protocol)
   │              │              │
Replica 1     Replica 2     Replica 3   (each only follows its own master)

⚡ Replica Placement & Failover (Clearing Confusion)

❗ No — A replica does **NOT** have to be on the same computer as its master.

Placing a replica on a **different machine** is **RECOMMENDED** so that if the master’s machine dies, you still have its data.

✅ Three Possible Replica Setups

  1. Replica on the SAME machine (NOT recommended)
    • If the computer shuts down → **Master AND Replica die** → totally useless for high availability.
  2. Replica on a DIFFERENT machine (RECOMMENDED for production) 
    Computer 1: Master 1
Computer 2: Replica 1 (Copy of Master 1)
    • ✔ If Computer 1 dies → **Replica 1 becomes the new master**. Your system continues running with **no data loss**. This is the **correct production setup**.
  3. Multiple replicas across different machines (High Availability)
    • ✔ If Computer 1 fails → Redis elects **Replica 1 OR Replica 2** as the new master. This is the **safest option**.

In production, replicas are placed on **different machines**, so the cluster **survives machine failures**.

📌 How a Replica Knows its Master (Across Machines)

This is the core of how Redis clusters work. The nodes explicitly tell each other: "Hey, I am your replica."

✅ How it Works:

  1. ✔ **The replica is manually assigned to a master**

    You explicitly tell the replica its master's address using the cluster setup command: 

    redis-cli --cluster add-node <replica-ip>:7001 <master-ip>:7000 --cluster-slave

    The replica stores this info internally: master_ip, master_port, and unique master Node ID.

  2. ✔ **Redis nodes talk to each other using the Gossip Protocol**

    Every node sends small heartbeat messages (about 10 times a second) to every other node, containing:

    • I am alive
    • My role is master/replica
    • My master ID is xyz

    This ensures every node knows **who is master** and **who is a replica of whom**.

  3. ✔ **Replicas maintain a TCP connection to their master**

    The replica opens a **persistent TCP connection** to its master across the network (Replica → Master). Through this connection, it:

    • Receives data changes (the "direct copy" mechanism).
    • Sends ACK responses.

Even though they are separate machines, the replica **explicitly knows** its master's address and ID, and they maintain a live connection.

📌 Redis Node vs. Redis Server — The Difference

This is very important to understand Redis clusters properly.

🔵 1. Redis Server (redis-server)

A Redis server is simply a **running instance of Redis** (one process, listening on 1 port).

  • ✔ A Redis server can run **standalone**.
  • ✔ A Redis server can also be part of a cluster.
  • **Definition**: A Redis server = a **single running Redis process**.
  • **Example (Standalone)**: 
    redis-server --port 6379

🟢 2. Redis Node

A Redis node is a **Redis server that is participating in a cluster**.

  • ✔ **Every Redis node is a Redis server**, but not every Redis server is a Redis node.
  • ✔ A node has **cluster responsibilities**:
    • Knows other nodes and talks via **gossip protocol**.
    • Has a unique **Node ID**.
    • May be a Master or a Replica.
    • Owns certain **hash slots**.
  • **Example (Cluster)**: 
    redis-server --port 7000 --cluster-enabled yes

⭐ Simple Analogy

Think of Redis servers like people:

  • **Redis Server**: A person living alone, no connections.
  • **Redis Node**: A person who has joined a society/group and now communicates with others.

The server becomes a **“node”** only when it **joins a cluster**.

🟦 What is a Cluster?

A cluster is a group of computers or servers that **work together as a single system** to distribute work and stay alive even if some machines fail.

🔥 Redis Cluster (Specific Definition)

A Redis Cluster is a setup where multiple Redis servers (nodes) work together to:

  • ✔ **Store data across many machines** (Scaling).
  • ✔ **Handle more load** (Load balancing).
  • ✔ **Stay alive even if some machines fail** (High availability/Failover).

📌 How Redis Cluster Stores Data

Redis divides data into 16,384 **hash slots**. Each master node takes a range of slots: 

Master 1 → Slots 0–5500
Master 2 → Slots 5501–11000
Master 3 → Slots 11001–16383

Based on the key, Redis automatically decides which master stores the data (e.g., SET user:100 → Goes to Master 2).

🛡️ High Availability (Self-Healing)

Every master has replicas (e.g., Master 1 → Replica 1). If Master 1 dies:

👉 Replica 1 becomes the **new master**. The cluster continues working with **no downtime**.

🟩 Why do developers use clusters?

  • ✔ Store **large data sets**.
  • ✔ **High availability** (no downtime) and **automatic failover**.
  • ✔ **Scaling horizontally** (add more machines).

**Final Short Answer:** Cluster = **many servers** working together as **one**. Redis Cluster = many Redis servers working together to store data, distribute load, and survive failures.
