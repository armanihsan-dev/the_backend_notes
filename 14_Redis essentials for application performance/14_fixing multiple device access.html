🔑 Redis Session Management Logic

1. Identify Existing Sessions

The code uses the ft.search (Full-Text Search) command to find all active sessions for the current user ID. This is the key application of Redis Search/RediSearch:

JavaScript

const sessions = await redisClient.ft.search(`@userId:{${existingUser._id}}`)

Assumption: A RediSearch index must have been created previously that indexes the userId field (which is part of the JSON session object stored in Redis) as a TAG.

Search Query: The query string @userId:{${existingUser._id}} performs an exact TAG match on the userId field within all Redis keys covered by the index.

Result: sessions contains the list of all active session keys and their data for that user, along with a sessions.total count.

2. Enforce the 2-Session Limit

The logic checks the total number of active sessions. If the limit is reached or exceeded (>= 2), the oldest session is forcibly terminated.

JavaScript

if (sessions.total >= 2) {
    await redisClient.del(sessions.documents[0].id)
}

Session Eviction: If the total count is $\ge 2$, the key corresponding to the **first document** in the results array (sessions.documents[0].id) is deleted from Redis using redisClient.del().

"Oldest" Session Logic: RediSearch's FT.SEARCH results are ordered by default based on the index's internal score, but in this context, the order is likely based on the insertion order or a simple key sort. For this logic to reliably delete the oldest session, the index definition should include a SORTBY clause, or the Redis keys must be created in a specific format that ensures the oldest one is consistently returned first (though this search command doesn't explicitly guarantee chronological order without SORTBY). Assuming the first result is the one to be evicted, this effectively makes space for the new session.

3. Create New Session

A new session is always created for the current login attempt.

JavaScript

const sessionId = crypto.randomUUID()
const redisKey = `session:${sessionId}`
// Session data stored in a JSON object with the user ID
const session = await redisClient.json.set(redisKey, '$', { userId: existingUser._id }) 
const sessionExpiryTime = 60 * 1000 * 60 * 24 * 7 // 7 days in milliseconds
redisClient.expire(redisKey, sessionExpiryTime / 1000)

New Key: A unique sessionId is generated, and the corresponding Redis key is session:<UUID>.

JSON Storage: The session data, including the crucial userId, is stored as a **Redis JSON** data type. This is what the RediSearch index is targeting.

Expiration (TTL): The key is given a Time-To-Live (TTL) of 7 days, after which it will automatically be deleted by Redis.

💡 Importance of the RediSearch Index

This entire mechanism relies on a previously configured **RediSearch index**. If the index didn't exist, the code would throw an error on redisClient.ft.search.

The index must be defined to:

  • Target keys matching the session pattern (e.g., session:).
  • Use the JSON data source type.
  • Index the JSON path $.userId as a **TAG** type, enabling fast, exact-match lookup for session keys based on a user ID.

Example Index Creation (Conceptual)

The RediSearch command, likely run on application startup or during deployment, would look something like this: 

FT.CREATE idx:user_sessions ON JSON PREFIX 1 "session:" SCHEMA $.userId AS userId TAG

This single index allows the system to instantly retrieve all sessions for any user by querying the indexed userId field.
