Redis Pub/Sub Messaging 📢

🔥 What is Pub/Sub?

Pub/Sub = Publish / Subscribe

Redis Pub/Sub is a way for applications to send messages to each other through channels.

  • A **publisher** sends (publishes) a message.
  • A **subscriber** listens (subscribes) to some channels.
  • Only subscribers who are **currently connected** will get the message.

💡 Important: Redis does NOT store messages in Pub/Sub.

If a subscriber is **offline**, it misses the message forever.

🧠 Think of it like a YouTube channel

  • You subscribe to a YouTube channel.
  • When the YouTuber publishes a new video, you get a notification **instantly**.
  • Redis Pub/Sub works exactly like this:

Redis channel = YouTube channel

Subscriber = Viewer who subscribed

Publisher = YouTuber who posts videos

Message = New video

⭐ Basic Terms

Term Meaning
Channel A named topic (e.g., "news", "chatRoom1")
Publisher Sends a message to a channel
Subscriber Listens to one or more channels
Message The data published

1. Pub/Sub Overview and Need 📢

Definition

Redis Pub/Sub is a messaging paradigm where senders (Publishers) are not programmed to send messages to specific receivers. Instead, the published messages are categorized into **Channels**, and receivers (**Subscribers**) express interest in one or more channels.

  • Publisher: Sends a message to a specific channel.
  • Channel: A named queue or topic (e.g., chat:general, alerts:stock:TSLA).
  • Subscriber: Listens to one or more channels and receives all messages sent to them.

Why is Pub/Sub Needed?

Pub/Sub is crucial for achieving decoupling and real-time event handling in applications:

  • Decoupling: Publishers and Subscribers don't know anything about each other's existence. The Publisher doesn't need to know who is listening or how many services are subscribed. It just publishes the data to Redis, and Redis handles the distribution.
  • Real-Time Notifications: It's the most efficient way to instantly push data or event notifications to multiple clients (e.g., updating a live dashboard, triggering a function in a microservice, or sending a chat message) without polling.
  • Low Latency: Since Redis holds the connection open, messages are delivered with extremely low latency, making it faster than traditional HTTP polling.

Key Limitation: Redis Pub/Sub is **fire-and-forget**. If a Subscriber disconnects and misses a message, Redis **does not store** that message for later delivery. For persistent messaging, you'd use Redis Streams or Lists.

2. Working with Redis Pub/Sub via redis-cli

Pub/Sub operates using three main commands: PUBLISH, SUBSCRIBE, and PSUBSCRIBE.

Command Role Action Syntax
SUBSCRIBE Subscriber Registers a client to listen for messages on specific channels. SUBSCRIBE channel1 [channel2 ...]
PSUBSCRIBE Subscriber Registers a client to listen using **pattern matching** (wildcards, *). PSUBSCRIBE pattern1 [pattern2 ...]
PUBLISH Publisher Sends a message to a specific channel. PUBLISH channel message

redis-cli Example Flow

You must open **two separate redis-cli terminals** to observe the Pub/Sub mechanism in real-time.

Terminal 1: The Subscriber

Subscribe to a channel: Once you run this command, the client enters a blocking state, waiting for messages.

# Bash 
$ redis-cli
> SUBSCRIBE updates:prices alerts:system
Reading messages... (press Ctrl-C to quit)
1) "subscribe"
2) "updates:prices"
3) (integer) 1
1) "subscribe"
2) "alerts:system"
3) (integer) 2
# Now the terminal is waiting...

Terminal 2: The Publisher

Publish a message to updates:prices: The message is instantly received by Terminal 1.

# Bash 
$ redis-cli
> PUBLISH updates:prices "BTC price changed to 65000"
(integer) 1  # The '1' indicates 1 subscriber received the message

Terminal 1 Output (After Publish)

...
1) "message"
2) "updates:prices"
3) "BTC price changed to 65000"

Publish a message to an unsubscribed channel: The message is ignored by Terminal 1.

# Bash 
$ redis-cli
> PUBLISH non:subscribed:channel "Test"
(integer) 0 # The '0' indicates 0 subscribers received the message

Using Pattern Matching (PSUBSCRIBE):

In a **third terminal**, subscribe using a pattern:

# Bash 
$ redis-cli
> PSUBSCRIBE alerts:*
Reading messages... (press Ctrl-C to quit)
1) "psubscribe"
2) "alerts:*"
3) (integer) 1

In the Publisher terminal, publish to alerts:system:

# Bash 
$ redis-cli
> PUBLISH alerts:system "Server 1 is overheating!"
(integer) 2 # Both the original 'alerts:system' subscriber and the 'alerts:*' pattern subscriber received it.

The Pattern Subscriber (Terminal 3) will show:

1) "pmessage"       # Indicates a pattern match message
2) "alerts:*"       # The pattern that matched
3) "alerts:system"  # The actual channel name
4) "Server 1 is overheating!"

3. Working with Redis Pub/Sub in Node.js

Since a Subscriber client enters a **blocking state**, it is best practice to use **two separate Redis client connections** in your Node.js application: one for subscribing/listening and one for publishing/writing data.

We'll use the **ioredis** library.

Node.js Example Setup

// Install: npm install ioredis # JavaScript 
const Redis = require('ioredis');

// 1. Setup the Publisher Client (Used for all non-PubSub commands and PUBLISH)
const publisher = new Redis();

// 2. Setup the Subscriber Client (Used ONLY for SUBSCRIBE/PSUBSCRIBE)
const subscriber = new Redis();

Node.js Publisher/Subscriber Code

# JavaScript 
// --- SUBSCRIBER CODE ---

// 1. Define the channel to listen to
const channelName = 'user:notifications';

// 2. Handle connection events (optional)
subscriber.on('ready', () => {
    console.log(`Subscriber ready, listening on channel: ${channelName}`);
    // Subscribe to the channel
    subscriber.subscribe(channelName, (err, count) => {
        if (err) {
            console.error("Subscription error:", err);
            return;
        }
        console.log(`Subscribed successfully to ${count} channel(s).`);
    });
});

// 3. Handle incoming messages
subscriber.on('message', (channel, message) => {
    console.log(`\n[Subscriber Received]`);
    console.log(`Channel: ${channel}`);
    console.log(`Message: ${message}`);
    // In a real application, you would process the message here (e.g., push to a WebSocket)
});

// --- PUBLISHER CODE (Simulated Delay) ---

async function simulatePublishing() {
    console.log("\n--- Publisher Starting Simulation ---");
    
    // Wait a moment for the subscriber to connect and subscribe
    await new Promise(resolve => setTimeout(resolve, 2000)); 

    // Message 1
    console.log(`[Publisher Sending] Message 1 to ${channelName}...`);
    let receivers = await publisher.publish(channelName, JSON.stringify({
        userId: 42,
        event: "new_follower",
        time: new Date().toISOString()
    }));
    console.log(`Message 1 delivered to ${receivers} subscriber(s).`);

    await new Promise(resolve => setTimeout(resolve, 2000)); 

    // Message 2
    console.log(`[Publisher Sending] Message 2 to ${channelName}...`);
    receivers = await publisher.publish(channelName, "Your profile was updated.");
    console.log(`Message 2 delivered to ${receivers} subscriber(s).`);

    // We can also use psubscribe on the client to listen to user:*
    // If the subscriber did psubscribe('user:*'), it would receive these messages as well.

    // Note: Do NOT call publisher.quit() immediately, as the subscriber is still running.
    // In a real app, these would be separate processes/services.
}

simulatePublishing();
