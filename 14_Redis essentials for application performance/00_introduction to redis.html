1. What is Redis?

Redis (Remote Dictionary Server) is an **open-source**, **in-memory data store**.[1] unlike traditional databases (like SQL or MongoDB) that store data on a hard disk, Redis stores data in **RAM (Random Access Memory)**.[1][2][3]

It is primarily used as:

  • Cache: To store **frequently accessed data** so your app doesn't have to query a slow database repeatedly.[1]
  • Message Broker: For real-time messaging (**Pub/Sub**) and job queues.
  • Session Store: To manage user login sessions in web applications.

2. How Redis Works (Internal Architecture)

Redis is built for **speed**. Here is the core logic behind it:

  • In-Memory Storage: It keeps all data in **RAM**. Accessing RAM is roughly **100,000 times faster** than accessing a standard hard disk.
  • Key-Value Structure: It acts like a giant JSON object or a Python dictionary. You give it a **key** (like user:101) and it gives you the **value instantly**.
  • Single-Threaded Event Loop: Redis mostly uses a **single CPU core** to handle requests. This sounds like a downside, but because RAM is so fast and Redis uses **non-blocking I/O**, it avoids the "context switching" overhead of multi-threaded systems. It can handle **millions of requests per second**.
  • Persistence: Even though it runs in RAM, it can save data to the disk periodically (using **RDB snapshots** or **AOF logs**) so you don't lose data if the server restarts.

3. How Redis Makes Applications Faster

Imagine your application is a restaurant:

  • Without Redis (Database only): Every time a customer asks for a menu, the waiter has to walk to the basement archive (Hard Disk), find the menu, and walk back. This takes time (milliseconds to seconds).
  • With Redis (Caching): The waiter keeps a copy of the menu in their pocket (RAM). When a customer asks, they hand it over **instantly (microseconds)**.

Real-world impact:

  • Reduces Database Load: Instead of hitting your main database 100 times for the same user profile, you hit it once, save it in Redis, and serve the next 99 requests from Redis.
  • Low Latency: Redis responses are often **sub-millisecond**, making apps feel "snappy."

4. Simple Example: Using Redis CLI

If you have Redis installed, you can use the **Command Line Interface (redis-cli)** to test it immediately.

Command:

Bashredis-cli

Inside the CLI:

Bash# 1. Set a value (Key: "username", Value: "Alice")
127.0.0.1:6379> SET username "Alice"
OK

# 2. Get the value back
127.0.0.1:6379> GET username
"Alice"

# 3. Check if a key exists (1 means yes, 0 means no)
127.0.0.1:6379> EXISTS username
(integer) 1

# 4. Delete the key
127.0.0.1:6379> DEL username
(integer) 1

5. Simple Example: Using Redis in Node.js

To use Redis in a Node.js application, you typically use the redis package.

Step 1: Install the library

Bashnpm install redis

Step 2: Create the script (e.g., app.js)

Modern Redis clients (v4+) use **async/await**.

JavaScriptconst redis = require('redis');

async function run() {
    // 1. Create a client
    const client = redis.createClient({
        url: 'redis://localhost:6379' // Default URL
    });

    // Handle connection errors
    client.on('error', (err) => console.log('Redis Client Error', err));

    // 2. Connect to Redis
    await client.connect();
    console.log('Connected to Redis...');

    // 3. SET a value
    // We are setting key 'framework' to value 'NodeJS'
    await client.set('framework', 'NodeJS');
    console.log('Value set!');

    // 4. GET the value
    const value = await client.get('framework');
    console.log(`Retrieved value: ${value}`);

    // 5. Disconnect
    await client.disconnect();
}

run();

Step 3: Run the script

Bashnode app.js

Output:

TextConnected to Redis...
Value set!
Retrieved value: NodeJS

Essential Redis Terminology

  • 1. Basic Data Concepts

    • Key: The unique identifier used to retrieve data (e.g., user:101). Keys are binary-safe (can be a string, an image file content, etc., but usually strings).
    • Value: The actual data stored inside a key.
    • Namespace: A convention of using colons to group keys logically, acting like folders. Example: users:profiles:101 vs users:settings:101.
    • Atomic: This refers to how Redis processes commands. An operation is "atomic" if it either fully happens or doesn't happen at all. No other command can interrupt it while it is running.

  • 2. Data Structures (The Values)

    Redis is a "Data Structure Server." The value can be complex:

    • String: Basic text or binary data (most common).
    • Hash: A collection of field-value pairs (maps directly to a JSON object). Good for storing an object like a "User Profile."
    • List: A linked list of strings (ordered by insertion). Good for Queues (**First In, First Out**).
    • Set: An unordered collection of unique strings. Good for tags or filtering (e.g., "user_ids_who_liked_post").
    • Sorted Set (ZSet): Like a Set, but every item has a **"Score."** Redis keeps them sorted by score. Good for Leaderboards.

  • 3. Caching & Lifespan Terms

    These are crucial when using Redis to make apps faster:

    • TTL (Time To Live): A countdown timer attached to a key. When the timer hits zero, the key is automatically deleted. Usage: "Keep this session active for 1 hour."
    • Expiration: The event of a key being deleted because its TTL ended.
    • Eviction: What happens when Redis runs out of memory (RAM). Redis must delete old data to make room for new data.
    • LRU (Least Recently Used): The most common "Eviction Policy." Redis deletes the keys that haven't been used for the longest time first.

  • 4. Persistence (Saving Data)

    Since Redis is in-memory, if you pull the plug, data vanishes. Persistence prevents that.

    • RDB (Redis Database): A **snapshot strategy**. Redis saves a copy of all data to the hard drive every X minutes. Faster, but you might lose a few minutes of data if the server crashes.
    • AOF (Append Only File): A **log strategy**. Redis logs every single write command to a file. Slower, but safer (less data loss).

  • 5. Architecture & Scaling

    • Redis Instance: A single running copy of Redis.
    • Master (Primary): The main Redis node where you write data.
    • Replica (Slave): A read-only copy of the Master. Data is automatically copied from Master to Replica.
    • Sentinel: A system that watches your Master. If the Master crashes, Sentinel automatically promotes a Replica to be the new Master (**High Availability**).
    • Cluster/Sharding: Splitting your data across multiple Redis nodes because it is too big to fit in the RAM of just one computer.

  • 6. Communication Patterns

    • Pub/Sub (Publish/Subscribe): A messaging pattern.
      • **Publisher:** Sends a message to a "Channel".
      • **Subscriber:** Listens to that "Channel" and receives the message instantly.
    • Pipelining: Sending multiple commands to the server at once without waiting for the replies of the previous ones. This creates a massive speed boost.

  • Summary Example

    If a developer says: "We are using Hashes to store user data with a 1-hour TTL. To handle high traffic, we set up a Master-Replica architecture with Sentinel for failover."

    Translation: They store user objects in Redis, the data auto-deletes after 1 hour, they have a main server and backup servers for reading, and an automated system to fix things if the main server crashes.
