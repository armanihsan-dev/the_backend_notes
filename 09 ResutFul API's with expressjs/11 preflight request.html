PreFlight Request

A preflight request is a type of OPTIONS request that a browser automatically sends before the actual request (like GET, POST, PUT, etc.) to a server. This happens when the actual request is "not-so-simple." The preflight request is a security measure to ensure the server understands and accepts the actual request's parameters before the browser sends it, which helps prevent unintended side effects on the server.

When your browser makes a request to a server (for example, sending data with POST), it doesn’t always just send it right away.

Why?

Because the browser wants to make sure the server is okay with it first. So it asks politely first — like saying:

  • 👉 Browser: “Hey server, I’m about to send you this kind of request (method, headers, body). Is that okay?”
  • 👉 Server: “Yes, that’s fine. Go ahead.”

This first check is called the preflight request (it uses the HTTP OPTIONS method).

Why it matters (security part):

Without this step, a malicious website could trick your browser into sending dangerous requests to another server without you knowing. Preflight makes sure the server explicitly says:

  • “I accept requests from your website (origin).”
  • “I allow this HTTP method (like PUT, DELETE, etc.).”
  • “I’m okay with these custom headers.”

Only if the server agrees, the real request is sent.

✅ In short:
The preflight request is like asking permission first, so the browser doesn’t accidentally do something the server never allowed.

Why Preflight Requests Exist

Preflight requests are a core part of the Cross-Origin Resource Sharing (CORS) mechanism. CORS is a browser security feature that prevents a webpage from making requests to a different domain than the one that served the page. When a browser wants to make a cross-origin request, it checks with the server first. A "simple" request can be sent without a preflight, but "not-so-simple" requests must be prefaced by one.

Simple requests are those that meet specific criteria:

  • Methods: GET, HEAD, or POST.
  • Headers: Only CORS-safelisted request-headers (e.g., Accept, Content-Type, Content-Language). The only Content-Type allowed is application/x-www-form-urlencoded, multipart/form-data, or text/plain.

If a request doesn't meet all these criteria, it's considered "not-so-simple". Examples include:

  • Using methods like PUT, DELETE, or PATCH.
  • Including custom headers (e.g., X-Custom-Header).
  • Using a Content-Type of application/json.

In these cases, the browser sends the preflight OPTIONS request first. This request includes headers like Access-Control-Request-Method and Access-Control-Request-Headers to inform the server of the actual request's method and headers.

How to Handle Preflight Requests in Express.js

You need to configure your Express.js server to correctly respond to these OPTIONS requests. A correct response tells the browser it's safe to proceed with the actual request.

The simplest way to handle CORS, including preflight requests, is by using the cors middleware.

1. Install the cors middleware:

Bash

npm install cors

2. Use the middleware in your Express app:

JavaScript

const express = require('express');
const cors = require('cors');
const app = express();

// Use the cors middleware
app.use(cors());

// Now, your routes will automatically handle preflight requests.
// For example, this PUT route will work correctly from a different origin.
app.put('/api/data', (req, res) => {
  res.send('Data updated!');
});

app.listen(3000, () => {
  console.log('Server is running on port 3000');
});

The cors middleware is smart enough to detect an OPTIONS request and respond with the necessary CORS headers, such as:

  • Access-Control-Allow-Origin: Specifies which origins are allowed to access the resource.
  • Access-Control-Allow-Methods: Lists the HTTP methods allowed for the resource.
  • Access-Control-Allow-Headers: Lists the headers allowed in the actual request.
  • Access-Control-Max-Age: Caches the preflight response for a specified number of seconds to avoid repeated preflights.

3. Manually Handling Preflight Requests (if not using the cors middleware):

If you choose not to use the middleware, you must handle the OPTIONS requests yourself. You can create a dedicated route handler for the OPTIONS method on each route that might receive a preflight.

JavaScript

const express = require('express');
const app = express();

// A function to set the CORS headers
const setCORSHeaders = (res) => {
  res.setHeader('Access-Control-Allow-Origin', '*'); // Or a specific origin
  res.setHeader('Access-Control-Allow-Methods', 'GET, POST, PUT, DELETE, OPTIONS');
  res.setHeader('Access-Control-Allow-Headers', 'Content-Type, X-Custom-Header');
};

// A route that needs to handle a preflight request
app.options('/api/data', (req, res) => {
  // Set CORS headers for the preflight response
  setCORSHeaders(res);
  // End the response
  res.status(204).end(); // 204 No Content is a common status for preflight success
});

// The actual PUT route
app.put('/api/data', (req, res) => {
  // Set CORS headers for the actual response too
  setCORSHeaders(res);
  res.send('Data updated!');
});

app.listen(3000, () => {
  console.log('Server is running on port 3000');
});

While this manual method provides more control, it's cumbersome and can lead to errors. The cors middleware is the standard and recommended practice for handling preflight and other CORS-related issues in Express.js.
