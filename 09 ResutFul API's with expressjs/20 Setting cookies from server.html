Third-party cookies are cookies placed by a domain other than the one a user is currently visiting. They are primarily used for cross-site tracking, personalized advertising, and analytics.

What are Third-Party Cookies?

A first-party cookie is a cookie set by the website you are currently visiting. For example, when you go to example.com, the cookies set by example.com are first-party cookies. These are used for things like remembering your login status or items in your shopping cart.

A third-party cookie is a cookie set by a domain different from the one in the address bar. This typically happens when a website includes content from a third-party server, such as an ad network, a social media widget, or an analytics service.

Example:

Imagine you visit example-news.com. This website includes an ad from ad-network.com and a Facebook "Like" button. When your browser loads the page, it also makes requests to ad-network.com and facebook.com to fetch that content. These third-party servers can then set cookies on your browser. The cookies from ad-network.com and facebook.com are third-party cookies.

The primary use of third-party cookies is tracking. When you visit another site that also includes content from the same ad-network.com, the ad network can read the cookie it previously set and recognize you. This allows it to build a profile of your browsing history across multiple websites to deliver targeted advertising.

How to Handle and Set Cookies from a Server (Express.js)

The most common way to handle cookies in Node.js with Express.js is by using the cookie-parser middleware.

1. Installation and Setup

First, you need to install Express and cookie-parser: 

npm install express cookie-parser

Next, require the packages and tell your Express app to use the middleware: 

const express = require('express');
const cookieParser = require('cookie-parser');
const app = express();

app.use(cookieParser());

2. Setting a Cookie

To set a cookie, you use the res.cookie() method on the response object. You provide a name, a value, and an optional options object. 

app.get('/set-cookie', (req, res) => {
  // Sets a simple cookie with a name and value
  res.cookie('username', 'JohnDoe');
  res.send('Cookie has been set!');
});

The options object allows you to control the cookie's behavior and security. Common options include:

  • maxAge: The maximum age of the cookie in milliseconds.
  • expires: A date object for when the cookie should expire.
  • httpOnly: If true, the cookie cannot be accessed by client-side JavaScript. This is a crucial security measure.
  • secure: If true, the cookie will only be sent over HTTPS.
  • path: The path for which the cookie is valid. The default is /.
  • domain: The domain for which the cookie is valid.

Example with options:

app.get('/set-secure-cookie', (req, res) => {
  res.cookie('token', 'some-secret-token', {
    maxAge: 900000, // Expires in 15 minutes (15 * 60 * 1000)
    httpOnly: true, // Not accessible by JavaScript
    secure: true, // Only sent over HTTPS
    sameSite: 'strict' // Restricts cross-site requests
  });
  res.send('Secure cookie set!');
});

3. Reading a Cookie

The cookie-parser middleware populates the req.cookies object with the cookies sent by the client. You can access them by their name. 

app.get('/read-cookie', (req, res) => {
  const username = req.cookies.username;
  if (username) {
    res.send(`Welcome back, ${username}!`);
  } else {
    res.send('No username cookie found.');
  }
});

4. Clearing/Deleting a Cookie

To clear a cookie, you use the res.clearCookie() method, specifying the name of the cookie and the same options it was set with (at a minimum, the path and domain). 

app.get('/clear-cookie', (req, res) => {
  res.clearCookie('username');
  res.send('Cookie has been cleared.');
});

Important Note: The res.clearCookie() method will only work if the client is on the same path and domain that the cookie was originally set for.

How to handle third party cookies from server

Handling third-party cookies from a server is a complex process primarily because of modern browser privacy restrictions. You can't directly "handle" a cookie set by a different domain. The server can only interact with first-party cookies that it sets itself. The key to handling third-party cookies is to manage the interaction between the domains, often through server-side redirects or by using an API.

The Challenge of Third-Party Cookies

Third-party cookies are set by a domain different from the one in the address bar. For example, if a user is on example.com but an ad is loaded from ads.com, the cookie set by ads.com is a third-party cookie. The server for example.com has no direct access to this cookie.

Modern browsers are phasing out third-party cookies due to privacy concerns and user tracking. Initiatives like Google's Privacy Sandbox and Apple's Intelligent Tracking Prevention (ITP) are actively blocking or restricting these cookies, making their traditional use for cross-site tracking obsolete.

Alternative Server-Side Approaches

Since direct third-party cookie handling is being phased out, developers are turning to alternative, more privacy-conscious methods. The general strategy is to either make the third-party cookie a first-party cookie or to use server-to-server communication.

1. The Server-Side Redirect Method (Turning a Third-Party into a First-Party Cookie)

A common workaround involves a redirect that allows the third-party to set a cookie as a first-party cookie. This requires server-side logic and is often used by analytics and advertising platforms.

How it works:

  • A user's browser makes a request to a third-party service (e.g., ads.com).
  • Instead of setting a third-party cookie, the ads.com server responds with a redirect to a specific URL on the original website (example.com). This URL includes a unique identifier (token) as a query parameter.
  • The example.com server receives the request with the token.
  • The example.com server then sets a cookie with the token. Since the cookie is set by example.com, it is a first-party cookie.
  • The example.com server then makes a server-to-server request back to ads.com, passing the token.
  • ads.com can now associate the user with the token, allowing it to track the user's activity on example.com via its own first-party cookie, effectively achieving the same result as a third-party cookie without the privacy risks.

2. Server-to-Server Communication

Instead of relying on browser-based cookies for cross-site communication, many services are moving to server-to-server APIs.

How it works:

  • A user's browser interacts with example.com.
  • When an event needs to be tracked (e.g., a purchase), example.com's server sends a direct API request to the tracking service's server (e.g., analytics.com).
  • This server-to-server communication bypasses the user's browser entirely. No third-party cookies are needed. The data is transferred securely between the two servers.

This method is more reliable and privacy-friendly than third-party cookies. It also avoids any issues with browser-side blocking and allows for more complex data transfer.

3. CNAME Cloaking (A less common and controversial method)

Some services use a technique called CNAME cloaking to make a third-party domain appear as a subdomain of the first-party site. This essentially tricks the browser into treating a third-party cookie as a first-party cookie. However, this method is being targeted by browsers' anti-tracking measures and is generally not recommended as a long-term solution.

Conclusion

In summary, you don't "handle" third-party cookies from a server in the traditional sense because of browser restrictions. Instead, you work around them by using techniques that either convert the cookie to a first-party one or, more commonly, by transitioning to server-to-server communication for data exchange. The industry is moving towards a future without third-party cookies, making these alternative methods the standard for server-side data handling.

How to handle third party cookies on front-end

Handling third-party cookies on the front end is becoming increasingly difficult due to modern browser privacy measures. You can't directly read, set, or delete a third-party cookie from your own website's JavaScript. The server that owns the third-party cookie is the only one that can modify it.

Here's how front-end code interacts with third-party cookies and the strategies used to work around browser restrictions:

1. How the Front End Receives a Third-Party Cookie

A third-party cookie is not something your front-end code sets. Instead, it's a byproduct of your browser making a request to a different domain.

Example:

Your website yoursite.com embeds an ad from adnetwork.com using an <iframe> or an <img> tag. When your browser requests the content from adnetwork.com, the adnetwork.com server can include a Set-Cookie header in its response. The browser will then store this cookie, marking it as belonging to adnetwork.com. 

<!-- yoursite.com's HTML -->
<img src="https://adnetwork.com/ad-pixel.gif">

2. Why You Can't Handle It

The fundamental rule of cookies is the Same-Origin Policy. This security principle prevents JavaScript on yoursite.com from accessing data (including cookies) belonging to adnetwork.com. This is a crucial security measure to prevent a malicious website from stealing sensitive information from other sites.

Because of this, document.cookie on yoursite.com will only show cookies set by yoursite.com. It will not show cookies from adnetwork.com, even though they are stored in the same browser.

3. Front-End Strategies and Modern Workarounds

Since you can't directly manipulate third-party cookies on the front end, modern strategies focus on making the third-party cookie a first-party one or using browser APIs that are more privacy-centric.

I. The "CORS" Approach

While you can't access a third-party cookie directly, a third-party service might allow your front-end code to make a cross-origin request to its domain, and it can then read its own cookie.

For example, a marketing analytics script might make a fetch request to analytics.com. The analytics.com server receives this request and, if it was sent with the credentials: 'include' option, it can read its own cookie. 

// This is client-side code on yoursite.com
fetch('https://analytics.com/track', {
  method: 'POST',
  mode: 'cors',
  credentials: 'include', // This allows the third-party cookie to be sent
  body: JSON.stringify({ event: 'button_click' })
})
.then(response => response.json())
.then(data => console.log('Data sent to analytics service.'));

The credentials: 'include' option is essential. It tells the browser to attach cookies and authorization headers to the cross-origin request. However, this only works if the third-party server has the correct Cross-Origin Resource Sharing (CORS) headers (Access-Control-Allow-Credentials: true) enabled.

II. The First-Party Cookie Workaround (via Server-Side Proxy)

A more robust and modern approach is to bypass the third-party cookie entirely by creating a server-side proxy on your own domain.

  • Your front-end code on yoursite.com makes a request to a specific endpoint on your own server, for example, /track.
  • Your server (on yoursite.com) receives the request and then makes a server-to-server request to the third-party service (analytics.com).
  • The third-party service responds to your server, which then processes the response and sends a cookie back to the user. Because this cookie is now coming from yoursite.com, it's a first-party cookie.

This method is more reliable and is immune to the ongoing browser restrictions on third-party cookies. The front end is never directly interacting with the third-party domain; all communication is proxied through your own server.

III. Browser Restrictions

It's important to be aware of how browsers are tightening restrictions on third-party cookies.

  • Intelligent Tracking Prevention (ITP): Safari and Firefox have been aggressively blocking third-party cookies for years.
  • Google's Privacy Sandbox: Google is currently in the process of phasing out third-party cookies in Chrome, replacing them with new APIs designed for privacy-preserving advertising.

Key takeaway: The front-end developer's role has shifted from directly handling third-party cookies to implementing solutions that use first-party cookies or server-side proxies to achieve the same goals, all while respecting user privacy.
