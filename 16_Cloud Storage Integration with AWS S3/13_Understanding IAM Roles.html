🔑 AWS IAM Roles: A Deep Dive

1. What is a Role in AWS IAM?

A Role in AWS Identity and Access Management (IAM) is an identity that you create in your AWS account that has specific permissions. Unlike an IAM user, a role is not uniquely associated with one person. Instead, it is designed to be assumed by anyone or anything that needs temporary access to perform specific AWS actions.

  • Role vs. User:
  • IAM User: A long-term credential for a single human user or application, with static access keys and a password.
  • IAM Role: A temporary credential that can be assumed by various identities (users, services, applications) to grant temporary, time-bound access without sharing long-term credentials.

2. How a Role Works?

The mechanism by which a role grants access is called assuming a role.

  • Identity: An entity (like an IAM user, an AWS service, or an application running on an EC2 instance) needs to perform an action.
  • Request: The entity calls the AWS Security Token Service (STS) API action, specifically AssumeRole.
  • Authentication: AWS verifies the entity's identity and checks the Role's Trust Policy to ensure the entity is allowed to assume it.
  • Temporary Credentials: If authorized, STS returns a set of temporary security credentials (an access key ID, a secret access key, and a session token).
  • Access: The entity uses these temporary credentials to make subsequent AWS API calls. These credentials are valid only for a defined duration (up to 12 hours by default) and only grant the permissions defined in the Role's Permissions Policy.

3. Core Components of a Role

An IAM Role is defined by two primary policies:

Component Definition Purpose
Trust Policy (or Assume Role Policy) A JSON policy document attached to the role that specifies who (which principals/identities) is allowed to assume the role. Defines the trusted principals that can exchange their own credentials for the role's temporary credentials.
Permissions Policy A JSON policy document attached to the role that specifies what actions and resources the role can access. Defines the permissions that the principal receives once the role is successfully assumed.

Key takeaway: The Trust Policy controls who can assume the role, and the Permissions Policy controls what they can do after assuming it.

4. Why Use IAM Roles?

IAM roles are the cornerstone of the principle of least privilege and secure access management in AWS.

  • Delegation: Allow users in one AWS account to access resources in a different account (Cross-Account Access).
  • Secure Access for AWS Services: Allow AWS services (e.g., EC2, Lambda, ECS) to securely interact with other AWS services (e.g., S3, DynamoDB) without embedding static credentials. (This uses Service-Linked Roles or Service Roles).
  • Federation: Grant external identities (e.g., corporate users via SAML) temporary access to your AWS account.
  • Temporary Access: Eliminate the need to manage and distribute long-term static credentials (access keys), greatly reducing the risk of a security breach.

5. Example Scenarios

Scenario 1: Granting an EC2 Instance Access to S3

This is the most common use case for a Service Role. We attach a role to an EC2 instance so that an application running on the instance can securely read and write to an S3 bucket.

Step-by-Step with AWS CLI:

A. Define the Trust Policy (ec2-trust-policy.json):
This policy allows the EC2 service (ec2.amazonaws.com) to assume the role. 

{
    "Version": "2012-10-17",
    "Statement": [
        {
        "Effect": "Allow",
        "Principal": { "Service": "ec2.amazonaws.com" },
        "Action": "sts:AssumeRole"
        }
    ]
}

B. Create the IAM Role:

aws iam create-role \
    --role-name "S3ReadOnlyAccessRole" \
    --assume-role-policy-document file://ec2-trust-policy.json

C. Define the Permissions Policy (s3-read-policy.json):
This policy grants read-only access to all S3 buckets. 

{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "s3:GetObject",
                "s3:ListBucket"
            ],
            "Resource": "*"
        }
    ]
}

D. Attach the Permissions Policy to the Role:

# First, create the policy
aws iam create-policy \
    --policy-name "S3ReadOnlyPolicy" \
    --policy-document file://s3-read-policy.json \
    --query 'Policy.Arn' --output text

# Then, attach the policy (replace <Policy-ARN> with the output from above)
aws iam attach-role-policy \
    --role-name "S3ReadOnlyAccessRole" \
    --policy-arn "arn:aws:iam::123456789012:policy/S3ReadOnlyPolicy"

E. Attach the Role to an EC2 Instance:
(This is done via an Instance Profile, which is a container for the role used when attaching it to an EC2 instance. This typically happens when launching the instance.) 

# Example command during instance launch
aws ec2 run-instances \
    --image-id ami-xxxxxxxxxxxxxxxxx \
    --instance-type t2.micro \
    --iam-instance-profile Name="S3ReadOnlyAccessRole"

Scenario 2: Cross-Account Access Delegation

An IAM user in Account A (The Trusting Account) wants to temporarily access resources in Account B (The Trusted Account).

In Account B (The Trusted Account):

A. Define the Trust Policy (cross-account-trust.json):
This policy trusts the root account or a specific user/role from Account A. 

{
    "Version": "2012-10-17",
    "Statement": [
        {
        "Effect": "Allow",
        "Principal": { "AWS": "arn:aws:iam::111122223333:root" }, 
        "Action": "sts:AssumeRole",
        "Condition": {
            "Bool": { "aws:MultiFactorAuthPresent": "true" }
        }
        }
    ]
}

Note: The principal 111122223333:root represents all identities in Account 111122223333, but best practice is to restrict it to a specific IAM User or Role's ARN.

B. Create the Role in Account B (The Trusted Account): 

aws iam create-role \
    --role-name "CrossAccountAccessRole" \
    --assume-role-policy-document file://cross-account-trust.json

C. Attach the Permissions Policy in Account B:
Attach a policy (e.g., AmazonS3FullAccess) that defines what the user from Account A can do in Account B.

In Account A (The Trusting Account):

The IAM user in Account A must have a policy that grants them permission to call sts:AssumeRole on the specific role ARN in Account B. 

{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": "sts:AssumeRole",
            "Resource": "arn:aws:iam::444455556666:role/CrossAccountAccessRole"
        }
    ]
}

D. Assuming the Role (The Action):
The IAM user in Account A executes the following command: 

aws sts assume-role \
    --role-arn "arn:aws:iam::444455556666:role/CrossAccountAccessRole" \
    --role-session-name "SessionForAccountAUser" \
    --query 'Credentials' --output json

This returns the temporary credentials (AccessKeyId, SecretAccessKey, SessionToken), which the user/script can then use to interact with Account B's resources.

6. Security Benefits

The core security benefits of using IAM Roles center on eliminating long-term credentials.

  • No Stored Credentials: For EC2/Lambda/ECS, the code doesn't store sensitive access keys on disk. AWS handles the secure exchange for temporary credentials via the instance metadata service.
  • Time-Bound Access: Temporary credentials automatically expire, reducing the window of opportunity for an attacker if they are compromised.
  • Principle of Least Privilege: A role's permissions are tightly scoped to only what is needed for a specific task, and they are only available when the role is actively assumed.
  • Simplified Auditing: Role assumption events are logged in AWS CloudTrail, clearly showing who (the original identity) assumed the role and what actions they performed.
