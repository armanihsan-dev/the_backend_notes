What Are IAM Policies?

IAM Policies are documents that formally define permissions and specify which actions are allowed or denied on which AWS resources, under what conditions, and for which principals (users, groups, or roles).

They are the primary means of granting permissions in AWS. When a principal attempts to access an AWS resource (e.g., trying to stop an EC2 instance or read from an S3 bucket), AWS evaluates the relevant policies to decide whether the action is permitted or denied.

Why Do We Need Policies in S3?

Because S3 has no idea who should access your data by default.

By default:

  • ❌ No one can read
  • ❌ No one can upload
  • ❌ No one can delete

Policy is the only way to tell AWS: who is allowed to do what.

The Core Problem Policies Solve

Imagine S3 without policies:

  • Any app could read your files
  • Any user could delete buckets
  • AWS services couldn’t talk to each other
  • No security boundary

💥 Total chaos

Policies create rules and boundaries.

What a Policy Actually Controls

A policy answers 4 questions:

  • WHO → Principal
  • WHAT → Action
  • WHERE → Resource
  • WHEN → Condition

Every S3 access request is checked against these rules.

Real-World Reasons We Use Policies in S3

Let’s go practical.

1️⃣ Protect Your Data (Most Important)

S3 often stores:

  • User photos
  • Documents
  • Videos
  • Backups

Without policy:

❌ Anyone with credentials could access everything.

With policy:

"Action": "s3:GetObject",
"Resource": "arn:aws:s3:::private-bucket/*"

Only allowed identities can read files.

2️⃣ Give Your Node.js App Limited Access

Your backend should NOT have full S3 access.

❌ Bad:

"s3:*"

✅ Good:

 
"s3:PutObject",
"s3:GetObject"

👉 Policy ensures:

  • Backend can upload
  • Backend cannot delete entire bucket

IAM Policy JSON Structure

IAM policies are written in JavaScript Object Notation (JSON). The basic structure consists of a top-level element for the version and a list of one or more "statements." 

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowListAndReadS3",
      "Effect": "Allow",
      "Action": [
        "s3:ListAllMyBuckets",
        "s3:GetObject"
      ],
      "Resource": [
        "arn:aws:s3:::my-example-bucket",
        "arn:aws:s3:::my-example-bucket/*"
      ]
    },
    {
      "Sid": "DenyDeleteBucket",
      "Effect": "Deny",
      "Action": "s3:DeleteBucket",
      "Resource": "arn:aws:s3:::*"
    }
  ]
}

🧐

Explanation of Each Field

Top-Level Fields

Field Required? Description
Version Yes Specifies the version of the policy language. The current version is 2012-10-17. Using the latest version is highly recommended.
Statement Yes Contains the main array of policy statements. Each statement defines a specific set of permissions.
Id No An optional identifier for the policy itself (not the statement).

Statement Fields (Inside the Statement Array)

Field Required? Description
Sid No Statement ID. A friendly, optional name for the statement. AWS recommends including an Sid for clarity and easier reference.
Effect Yes Specifies whether the statement results in an Allow or an explicit Deny of access.
Principal Conditional Required in Resource Policies (like S3 Bucket Policies) to specify who is allowed or denied access. Not used in identity-based policies.
Action Yes Specifies the specific AWS API actions that will be allowed or denied. For example: ec2:RunInstances, s3:GetObject, s3:* (all S3 actions).
Resource Yes Specifies the AWS resources that the Action applies to. Resources are specified using their Amazon Resource Name (ARN). A wildcard (*) can be used to denote all resources.
Condition No Specifies any conditions that must be met for the policy statement to take effect. For example, access only from a specific IP address, or only during a certain time of day.
NotAction No An advanced element that specifies a list of actions except the ones listed.
NotResource No An advanced element that specifies a list of resources except the ones listed.

Types of IAM Policies

IAM policies are generally categorized based on how they are attached and what they do.

1. Identity-Based Policies

  • Attachment: Attached directly to an IAM User, Group, or Role.
  • Purpose: Control what actions the identity can perform and what resources they can access.
    • Managed Policies: Created and managed by AWS (e.g., AdministratorAccess) or by you (Customer Managed Policies).
    • Inline Policies: Embedded directly within a specific user, group, or role.

2. Resource-Based Policies

  • Attachment: Attached directly to an AWS resource (e.g., an S3 bucket, SQS queue, or KMS key).
  • Purpose: Control which principals (from the same or other AWS accounts) can access the resource and what actions they can perform.
  • Key Field: Must contain the Principal element to specify the identities being granted permissions. S3 Bucket Policies are the most common example.

3. Permissions Boundaries

  • Attachment: Attached to an IAM User or Role.
  • Purpose: A maximum set of permissions that an identity-based policy can grant. It does not grant permissions on its own; it only limits the effective permissions of the identity.

4. Service Control Policies (SCPs)

  • Attachment: Attached to an Organizational Unit (OU) or the root of an AWS Organization.
  • Purpose: Define the maximum available permissions for all IAM principals in the affected accounts. They act as "guardrails" and cannot grant permissions, only filter them (much like a Permissions Boundary, but for an entire account/OU).

🔑

Key Differences: IAM Policy vs. S3 Bucket Policy

The primary difference lies in their attachment point, the principal they govern, and their evaluation logic.

Feature Identity-Based Policy (IAM Policy) Resource-Based Policy (S3 Bucket Policy)
Attachment An IAM User, Group, or Role. An AWS Resource (specifically, an S3 Bucket).
Governs What the identity can do (outbound permissions). Who can access the resource (inbound permissions).
Key Element Focuses on Action and Resource. Must include a Principal element.
Cross-Account Difficult to use for cross-account access (requires assuming a role). Easily allows cross-account access by specifying an external Principal.
Default Implicit Deny is the default. Access is only granted if an Allow is found. Implicit Deny is the default. Access is only granted if an Allow is found.
Conflict If a statement applies to a request: Deny always overrides Allow.

Effective Permissions Logic

For a principal to access an S3 bucket, they must be allowed by both their IAM Policy (if one applies) AND the S3 Bucket Policy (if one exists).

  • Case 1: Both Policies Exist
    • The request must be explicitly Allowed by at least one IAM Policy AND at least one S3 Bucket Policy.
    • An explicit Deny in *either* policy takes precedence and denies access.
  • Case 2: Only IAM Policy Exists
    • The request is evaluated solely against the IAM Policy.
  • Case 3: Only S3 Bucket Policy Exists
    • The request is evaluated solely against the S3 Bucket Policy.

AWS CLI Example: Attaching an IAM Policy

This command creates a Customer Managed Policy and then attaches it to an IAM role.

1. Create the Policy JSON file (my-read-policy.json)

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowS3Read",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-data-bucket/*"
    }
  ]
}

2. Create the Policy using AWS CLI

aws iam create-policy \
    --policy-name MyS3ReadOnlyPolicy \
    --policy-document file://my-read-policy.json

3. Attach the Policy to a Role

aws iam attach-role-policy \
    --role-name MyAppRole \
    --policy-arn arn:aws:iam::123456789012:policy/MyS3ReadOnlyPolicy

AWS CLI Example: Applying an S3 Bucket Policy

This command applies a policy to an existing S3 bucket, allowing a specific external IAM user (ExternalUser) to read objects from it.

1. Create the Bucket Policy JSON file (external-read-bucket-policy.json) 

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowExternalUserRead",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::987654321098:user/ExternalUser" 
        // 987654321098 is the external AWS account ID
      },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-cross-account-bucket/*"
    }
  ]
}

2. Apply the Policy to the S3 Bucket using AWS CLI

aws s3api put-bucket-policy \
    --bucket my-cross-account-bucket \
    --policy file://external-read-bucket-policy.json
