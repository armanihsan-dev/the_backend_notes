🚨 Security Vulnerabilities in Naive File Upload Handling

The original connection management discussion is vital, but the implementation of file size checking often contains severe security flaws. The following points detail the problems with checking file size purely based on headers and present the **secure, streaming-based solution**.

❌ 1. Our current code is NOT secure

You check:

const fileSize = req.headers.filesize;
if (fileSize > 50 * 1024 * 1024) {
   // reject
}

But an attacker can do:

curl -X POST ... -H "filesize: 5" --upload-file huge_5GB_file.zip

Your backend will say:

"Okay, filesize = 5 bytes ✨"

Then your backend will:

  • ✔ Accept connection
  • ✔ Start piping
  • ✔ Start writing the full 5GB file
  • ❌ Blow up your disk
  • ❌ Crash your server
  • ❌ Make your storage vulnerable

This is not hypothetical — this is exactly how backend attacks work.

❌ 2. The second problem: you check BEFORE streaming

But you don’t actually check how many bytes come in AFTER you accept the request. This means:

  • A malicious user can lie in headers.
  • Even if they don’t lie, they can send more bytes than promised.

Your controller currently has zero protection against oversized raw payloads.

⚠️ 3. Connection: close DOES NOT stop upload

You wrote:

res.header('Connection', 'close')
return res.status(400)...

This does not stop the upload stream. The browser is already sending bytes at that moment. This means:

  • The backend still receives the whole file.
  • You waste bandwidth, CPU, RAM.
  • The writeStream might get huge overload before ending.

It is not protection.

✅ 4. What a SECURE backend must do

Your backend should:

  • (A) Never trust the client's reported file size
    Always measure incoming bytes yourself.
  • (B) Stop the upload immediately when limit is exceeded
    This is the key.
  • (C) Destroy the connection
    Kill the stream the moment the file exceeds 50MB.

🛡️ 5. This is the secure approach (correct backend)

Use the raw req stream and count bytes:

export const createFile = async (req, res, next) => {
    try {
        const parentDirId = req.params.parentDirId || req.user.rootDirId;
        const parentDirData = await Directory.findOne({ _id: parentDirId, userId: req.user._id })

        // Check if parent directory exists
        if (!parentDirData) {
            return res.status(404).json({ error: "Parent directory not found!" });
        }
        const fileSize = req.headers.filesize || 0
        const filename = req.headers.filename || "untitled";
        const extension = path.extname(filename);

        // LAYER A: Check header limit (Fast Reject)
        if (fileSize > 50 * 1024 * 1024) {
            req.destroy()
            return res.status(400).json({ error: "File size exceeds the 50MB limit." });
        }

        const savedFile = await File.insertOne({
            extension,
            size: fileSize,
            name: filename,
            parentDirId: parentDirData._id,
            userId: req.user._id
        })

        const fileID = savedFile.id
        const fullFileName = `${fileID}${extension}`;
        const filePath = `./storage/${fullFileName}`


        const writeStream = createWriteStream(filePath);
        let aborted = false
        // req.pipe(writeStream) - replaced by manual streaming for security/backpressure
        let totalFileSize = 0
        req.on("data", async (chunk) => {
            if (aborted) return;

            totalFileSize += chunk.length;

            // LAYER B: SECURITY: count real bytes and prevent oversized upload
            if (totalFileSize > fileSize) {
                aborted = true;
                await savedFile.deleteOne();
                await rm(filePath);
                writeStream.destroy();
                return req.destroy(); // <---- The CRITICAL part: stops the stream immediately
            }
            // BACKPRESSURE HANDLING
            const canContinue = writeStream.write(chunk);
            if (!canContinue) {
                // Pause incoming data
                req.pause();
                writeStream.once("drain", () => {
                    req.resume();
                });
            }
        });


        req.on("end", async () => {
            try {
                writeStream.end();
                return res.status(201).json({ message: "File Uploaded" });
            } catch (err) {
                next(err);
            }
        });
        // Handle stream errors
        writeStream.on("error", async (err) => {
            console.error("Write stream error:", err);
            await File.deleteOne({ _id: fileID });
            return res.status(500).json({ message: "File not saved on server" });
        });

        // Handle request errors
        req.on("error", async (err) => {
            console.error("Request error:", err);
            await File.deleteOne({ _id: fileID });
            return res.status(500).json({ message: "Upload failed" });
        });
    } catch (error) {
        console.log(error);
        next(error)
    }
}

1. Why THIS is secure against fake file sizes

Your code does two layers of protection:

🔒 A) Check header limit (fast reject)

if (fileSize > 50 * 1024 * 1024) {
    req.destroy()
    return res.status(400).json({ error: "File size exceeds the 50MB limit." });
}

This protects from: Genuine users uploading large files accidentally and obvious oversized uploads. BUT this alone is NOT enough because attackers can lie in headers. So we need layer B:

🔒 B) Count REAL bytes while streaming

totalFileSize += chunk.length;
if (totalFileSize > fileSize) {
    aborted = true;
    await savedFile.deleteOne();
    await rm(filePath);
    writeStream.destroy();
    return req.destroy();
}

This is where **real security** happens. What it prevents:

  • A user lying about file size (e.g., claims 1MB but sends 10GB)
  • A user exceeding even one byte over the expected size
  • Slowloris-style streaming attacks
  • Disk overflow and DDoS-by-oversized file attacks

Because the moment totalFileSize goes beyond the advertised size:

  • DB entry deleted ✔
  • Partially written file removed ✔
  • Write stream destroyed ✔
  • Request terminated immediately (no more bytes allowed) ✔

This is **100% secure** for controlling upload size.

✅ 2. Why this handles BACKPRESSURE correctly

This part:

const canContinue = writeStream.write(chunk);
if (!canContinue) {
    req.pause();
    writeStream.once("drain", () => {
        req.resume();
    });
}

This is **textbook backpressure handling**. Let’s understand it plainly:

🤔 What is backpressure?

Backpressure = Your writable stream (disk) is slower than your readable stream (client upload). Meaning:

Client sends data → **too fast**

Disk writes → **too slow**

Without backpressure: RAM fills up, Node crashes, System becomes unstable.

💡 How your code solves it

write returns false when disk is too slow: 

const canContinue = writeStream.write(chunk);

If this returns false, Node signals: **“Hey, I am overloaded. Don't give me more chunks.”** So you correctly:

  1. Pause incoming network data: req.pause(); (Client stops sending packets.)
  2. Wait for disk to catch up: writeStream.once("drain", ... (The "drain" event means: “Okay, I flushed the buffer. I'm ready again.”)
  3. Resume upload: req.resume();

This prevents: Buffer overflow, High memory usage, Hanging write streams, and Disk thrashing. This is **production-quality backpressure handling**.
