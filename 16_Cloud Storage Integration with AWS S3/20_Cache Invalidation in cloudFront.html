CloudFront Cache Invalidation

CloudFront is Amazon Web Services' (AWS) Content Delivery Network (CDN) service. Cache invalidation is the mechanism used to **force the removal of content** from CloudFront's edge caches before its set expiration time (Time-to-Live or TTL) is reached.

This is critical when you need users to immediately see updated content from your origin server (e.g., an updated image, a new CSS file, or a major bug fix).

1. The Need for Invalidation

CloudFront caches content in **Edge Locations** (global data centers) for a specific duration, determined by the content's TTL, typically set via Cache-Control or Expires headers from your origin.

  • Expiration (TTL): This is the **primary** way caching is managed. Once the TTL expires, the next request for the object will trigger CloudFront to send a request to the origin to check for a newer version (a process called revalidation).
  • Invalidation: This is an **on-demand action** used to remove or mark cached content as **stale immediately**, bypassing the TTL. You use it when you update content on your origin server and need the changes to propagate globally right away.

2. The Invalidation Process

When you submit an invalidation request, CloudFront doesn't physically delete the files from every edge location instantly. Instead, it marks them as **invalid or stale**.

The process generally follows these steps:

Request Submission

  • You initiate an invalidation request using the AWS Management Console, the AWS Command Line Interface (CLI), or an AWS SDK (API call). You specify the **object paths** you want to invalidate.
  • Specificity: You can invalidate specific files (e.g., /images/logo.png) or use a wildcard (*) to invalidate a directory or all content (e.g., /js/* or /*).

Propagation and Re-caching

  • Propagation: CloudFront receives the request and sends a message to all of its Edge Locations globally, informing them that the specified content paths are no longer valid.
  • Status Change: The status of the invalidation request changes to **In Progress** and eventually to **Completed**. This typically takes a few minutes to propagate across the entire network.
  • First Viewer Request (Post-Invalidation): The next time a viewer requests one of the invalidated objects:
    • The Edge Location finds the object but sees it is marked as stale/invalid.
    • It immediately **forwards the request to your Origin Server**.
    • The Origin Server returns the latest version of the file to the Edge Location.
  • Re-caching: The Edge Location stores the new version in its cache and serves it to the viewer, starting a new TTL period for the updated object. Subsequent requests will be served directly from the cache again.

3. Best Practice: Versioning vs. Invalidation

While invalidation is effective, it is an asynchronous process that can take time to complete, and AWS charges for the number of invalidation paths submitted above a certain free tier.

The recommended best practice to manage content updates is **File Versioning** (or cache-busting):

Strategy Mechanism CloudFront Action Best For
Versioning Change the file name/path every time the content changes (e.g., /js/app.v1.js to /js/app.v2.js). CloudFront treats the new URL as a completely **new object** and fetches it from the origin on the first request. The old version simply remains in the cache until its natural TTL expires. Static assets (CSS, JS, images). It's instant and avoids invalidation costs.
Invalidation Explicitly tell CloudFront to mark an existing file path as stale. CloudFront is forced to go back to the origin for the **next** request for that specific path. **Infrequently changing files** where the URL cannot be changed (like the root index.html) or emergency removal of content.

In short, invalidations are an event-driven override of the standard expiration (TTL)-based cache management.

Working with CloudFront Invalidation via Node.js SDK

...managing CloudFront cache invalidation in a Node.js environment using the @aws-sdk/client-cloudfront package. This approach uses the AWS SDK v3, which relies on a service client and a specific Command for each action.

📦 1. Installation

First, ensure you have the correct package installed:

        
npm install @aws-sdk/client-cloudfront

⚙️ 2. Essential Components & Definitions

To create an invalidation request, you primarily use three components:

Component Description
CloudFrontClient The main client object. It is initialized once and handles configuration (region, credentials, etc.) for all subsequent CloudFront API calls.
CreateInvalidationCommand The specific command used to submit a cache invalidation request to CloudFront.
InvalidationBatch The core data structure containing the request details: the list of paths to invalidate and a unique reference ID.

Key Parameters for InvalidationBatch

Parameter Type Required Description
CallerReference string Yes A unique, case-sensitive identifier for the invalidation request. A timestamp (like Date.now().toString()) is often used to guarantee uniqueness.
Paths object Yes Contains the list of file paths to invalidate.
Paths.Quantity number Yes The number of paths in the Paths.Items array.
Paths.Items string[] Yes An array of file paths to invalidate (e.g., ["/index.html", "/assets/*"]). Paths must start with a /.

💻 3. Node.js Invalidation Example

The following is a clear example function in Node.js that handles both specific file invalidation and full distribution invalidation using a wildcard. 

        
import {
  CloudFrontClient,
  CreateInvalidationCommand,
  CreateInvalidationCommandInput,
} from "@aws-sdk/client-cloudfront";

// Replace with your actual distribution ID
const CLOUDFRONT_DISTRIBUTION_ID = "E3R4EXAMPLEID123";

// 1. Initialize the client (Note: CloudFront is a global service, 
//    but the client usually defaults to us-east-1 if no region is specified).
const client = new CloudFrontClient({});

/**
 * Creates an invalidation request for the specified paths on a CloudFront distribution.
 * * @param paths An array of strings representing the cache paths to invalidate.
 */
async function createCloudFrontInvalidation(paths: string[]): Promise<void> {
  // Ensure paths are prefixed with a leading slash, as required by CloudFront API
  const correctedPaths = paths.map(path => path.startsWith('/') ? path : `/${path}`);

  // 2. Define the input parameters for the command
  const params: CreateInvalidationCommandInput = {
    DistributionId: CLOUDFRONT_DISTRIBUTION_ID,
    InvalidationBatch: {
      // Use a unique reference (e.g., timestamp) to identify this request
      CallerReference: String(Date.now()),
      Paths: {
        Quantity: correctedPaths.length,
        Items: correctedPaths,
      },
    },
  };

  try {
    // 3. Create and send the command
    const command = new CreateInvalidationCommand(params);
    const response = await client.send(command);

    console.log("Invalidation initiated successfully.");
    console.log("Invalidation ID:", response.Invalidation?.Id);
    console.log("Status:", response.Invalidation?.Status);
    console.log("Location:", response.Location);

  } catch (error) {
    console.error("Error creating CloudFront invalidation:", error);
    // You might throw the error or handle it gracefully
    throw error; 
  }
}

// --- USAGE EXAMPLES ---

/** * Case A: Invalidate Specific Files
 * This is useful for single-file updates like a logo or a CSS file.
 */
async function invalidateSpecificFiles() {
  const specificPaths = [
    "/index.html",
    "/assets/images/logo.png",
    "/js/app.js",
  ];
  console.log("--- Invalidating Specific Files ---");
  await createCloudFrontInvalidation(specificPaths);
}

/** * Case B: Invalidate a Whole Directory or Entire Distribution
 * Use the wildcard character (*).
 * Invalidate all files in the distribution (recommended path for a full flush).
 */
async function invalidateEntireDistribution() {
  // The path "/*" invalidates all files under the distribution root.
  const wildcardPath = ["/*"]; 
  console.log("\n--- Invalidating Entire Distribution (/*) ---");
  await createCloudFrontInvalidation(wildcardPath);
}

// Run the examples
// invalidateSpecificFiles();
// invalidateEntireDistribution(); 

// Example of invalidating a folder and all its contents
async function invalidateFolder() {
  const folderPath = ["/blog/posts/*"]; 
  console.log("\n--- Invalidating the 'blog/posts' directory ---");
  await createCloudFrontInvalidation(folderPath);
}

// invalidateFolder();

Important Notes on Invalidation Paths:

  • Leading Slash: All paths in the Items array **must** begin with a forward slash (/).
  • Wildcard (*): CloudFront supports a single wildcard (*) at the end of the path.
    • To invalidate **all files** in your distribution, use the path: /*
    • To invalidate all files in a specific folder, use: /folder-name/*
