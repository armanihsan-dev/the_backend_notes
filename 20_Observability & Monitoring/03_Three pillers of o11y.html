THREE PILLARS OF OBSERVABILITY

METRICS, LOGS, AND TRACES EXPLAINED

📊 METRICS: THE SYSTEM'S VITAL SIGNS

Metrics are numerical measurements collected over time. They're like the dashboard in a car - speed, RPM, fuel level, temperature.

Key Characteristics

  • Aggregated - They summarize many events into single numbers
  • Time-series - Values with timestamps allow trend analysis
  • Lightweight - Minimal storage and processing overhead

Common Metric Types

Counters

Request count, error count (always increase)

Gauges

Current memory usage, active connections (go up and down)

Histograms

Request latency distribution (p50, p95, p99)

Rates

Requests per second, error rate percentage

Real-world Example

metric: http_requests_total
value: 15432
labels: 
  endpoint: /api/users
  method: GET
  status: 200
timestamp: 2024-01-15T10:30:00Z
When Metrics Alone Fail

They tell you that latency is spiking, but not why. A p99 of 5 seconds could mean:

  • One slow database query affecting everyone
  • A few users with huge data sets
  • Network congestion to a specific region

🪵 LOGS: THE SYSTEM'S DIARY

Logs are discrete events with timestamps and structured (or unstructured) data. They're like security camera footage - detailed but bulky.

Key Characteristics

  • Event-based - Each log represents something that happened
  • Context-rich - Can contain variable data, stack traces, user IDs
  • High volume - Can generate terabytes of data

Log Levels and Their Meaning

DEBUG - "Entering payment processing function"
INFO  - "User 12345 completed checkout"
WARN  - "Database query took 2 seconds (threshold: 1s)"
ERROR - "Failed to charge credit card: insufficient funds"
FATAL - "Payment service crashed, restarting"

Structured Logging Example

{
  "timestamp": "2024-01-15T10:30:01.123Z",
  "level": "ERROR",
  "service": "payment-processor",
  "trace_id": "abc-123-def",
  "user_id": 12345,
  "message": "Credit card declined",
  "error_code": "card_declined",
  "provider": "stripe",
  "amount": 99.99
}
When Logs Alone Fail

Searching through millions of log lines to understand a slow request is like finding a needle in a haystack. You see individual events but lose the causal chain.

🧵 TRACES: THE SYSTEM'S STORYBOARD

Traces follow a single request through every service and component. They're like a GPS track of your journey through a city.

Key Concepts

  • Trace - The complete journey of a request
  • Span - A single unit of work within the trace
  • Parent-child relationships - Shows which calls triggered which

Trace Structure Example

Trace ID: request-789
Total time: 2.3s

Span A: /api/order [2.3s] (entire request)
  ├─ Span B: authenticate() [50ms]
  ├─ Span C: validate_order() [100ms]
  ├─ Span D: check_inventory() [800ms]
  │    └─ Span E: database query [750ms] ← bottleneck!
  └─ Span F: process_payment() [1.3s]
       └─ Span G: external payment API [1.2s]
When Traces Alone Fail

They show you where time was spent but not what happened during that time. The database query took 750ms - was it locked? Missing index? Network issue?

THE POWER OF COMBINING PILLARS

🔍 Debugging Scenario: Slow User Login

Step 1 - Metrics Detect the Problem 
Graph shows: login_latency_p99 spiked from 200ms to 5s at 10:30 AM
Step 2 - Traces Localize the Bottleneck 
Trace for a slow login shows:
- auth service: 4.8s total
  - password check: 50ms
  - user profile fetch: 4.7s ← problem area
    - database query: 4.6s
Step 3 - Logs Provide Context 
Search logs with trace_id from the slow query:
{
  "timestamp": "10:30:01",
  "query": "SELECT * FROM users WHERE id = 12345",
  "execution_time": "4.6s",
  "rows_returned": 1,
  "index_used": "none"  // ← Ah! Missing index!
}
✅ Resolution

Add an index on the users table. Metrics confirm latency drops back to normal.

UNDERSTANDING EVENTS IN CONTEXT

📊 Events from Metrics (Alerting)

When a metric crosses a threshold, it generates an event:

Metric: cpu_usage > 80% for 5 minutes
    ↓
Event: "High CPU alert" created
    ↓
Alert sent to on-call engineer
    ↓
Timeline annotated in dashboard

🪵 Logs as Events (Audit Trail)

Every significant state change should be logged:

{
  "event": "deployment_started",
  "version": "2.1.0",
  "timestamp": "2024-01-15T10:00:00Z"
}
{
  "event": "deployment_completed",
  "version": "2.1.0",
  "result": "success",
  "duration_seconds": 45
}

🧵 Trace Annotations as Events

Marking important moments within traces:

with tracer.start_span("process_payment") as span:
    span.set_tag("payment_method", "credit_card")
    span.set_tag("amount", 99.99)
    
    result = payment_service.charge()
    
    if result.failed:
        span.set_tag("error", True)
        span.log_kv({"event": "payment_failed", 
                     "reason": result.error_message})
The MELT Acronym Reality Check

While MELT (Metrics, Events, Logs, Traces) is memorable, it's important to understand:

Events are not a separate data type - they're a use case applied to the three pillars:

  • Metrics + threshold = Alert event
  • Log entry = Debug/audit event
  • Trace annotation = Request lifecycle event

Think of it This Way

Pillar Question Answered
Metrics What's happening?
Logs What happened?
Traces How did it happen?
Events What should I care about?

PRACTICAL IMPLEMENTATION TIPS

1. Correlation is King

Always include correlation IDs across pillars:

Request Headers:
  X-Trace-ID: trace-789
    
Metrics:
  http_requests_total{trace_id="trace-789"}
  
Logs:
  {"trace_id": "trace-789", "message": "..."}
  
Traces:
  Trace ID: trace-789

2. Sampling Strategies

You can't trace everything in high-volume systems:

  • Head-based sampling: Decide at request start (e.g., trace 1% of requests)
  • Tail-based sampling: Keep interesting traces (slow/error) after they complete
  • Structural sampling: Trace specific endpoints or user types

3. Log Levels in Production

ERROR   → Always, with full context
WARN    → Always, but may be sampled if high volume
INFO    → Critical business events only
DEBUG   → Never in production (unless temporarily enabled for specific users)

4. Metrics Cardinality Warning

Be careful with label combinations:

Bad:  http_requests_total{user_id="12345"}  ← Millions of unique users
Good: http_requests_total{user_tier="premium"}  ← Small set of values

THE ULTIMATE GOAL

The three pillars aren't just about collecting data - they're about answering three fundamental questions during an incident:

Metrics

"Is there really a problem?"

(Detection)

Traces

"Where in the system is it happening?"

(Localization)

Logs

"What exactly went wrong there?"

(Diagnosis)

Without All Three, You're Flying Blind
  • Metrics only: You know it's broken but not why
  • Logs only: You have details but no context or trends
  • Traces only: You have the path but miss the big picture
💡 The Golden Rule

Observability is not about having all the data. It's about having the right data, in the right format, at the right time, with the right connections between the three pillars.
