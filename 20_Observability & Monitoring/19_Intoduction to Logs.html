SOFTWARE LOGGING & PINO

THE COMPLETE GUIDE TO STRUCTURED LOGGING IN NODE.JS

1. What is meant by Logging in Software?

Logging is the practice of recording events, states, or transactions that occur during an application's execution. Think of it as your application writing entries into a digital diary.

What gets logged?

  • Incoming requests (e.g., GET /users)
  • Database queries (e.g., SELECT * FROM orders)
  • Errors and exceptions (e.g., Connection refused)
  • User actions (e.g., User "john" logged in)
  • System state changes (e.g., Cache cleared)

Example of a raw log line:

2026-04-22T10:32:00Z INFO User logged in successfully

2. Why Logging Exists

Logging exists to answer four critical questions when something goes wrong or needs analysis:

Question What logs reveal
What happened? "Database timeout error"
When did it happen? Timestamp: 10:32:00.123
Why did it fail? "Invalid password hash"
What was the system doing? Previous 10 log entries show a slow query

Without logs: Debugging production issues becomes guesswork. You cannot reproduce every user's exact sequence of actions locally.

3. Problem with Traditional Logging

Traditional (unstructured) logging uses plain strings that are easy for humans to read but difficult for machines to parse.

Example of traditional log:

User Faraz logged in at 10:32 from IP 192.168.1.1
Error connecting to database at 10:33

The problems:

Problem Explanation
Hard to search Grepping for user=Faraz fails because the format is inconsistent
Hard to analyze at scale Counting errors requires brittle regex patterns
No structure You cannot filter by level=="error" AND user=="Faraz"
Inconsistent format One developer writes "User X logged in", another writes "Login: X"
Bottom line:

Traditional logs work for small projects but break in production with multiple servers and millions of requests.

4. Structured Logging

Structured logging stores logs as structured data (usually JSON) instead of plain . Each log entry has predictable fields.

Example of structured log (JSON):

{
  "level": "info",
  "timestamp": "2026-04-22T10:32:00Z",
  "message": "User logged in",
  "user": "Faraz",
  "ip": "192.168.1.1",
  "session_id": "abc123"
}

Why it's powerful:

  • ✅ Machine-parsable – Tools can index every field
  • ✅ Queryable – level:"error" AND user:"Faraz"
  • ✅ Consistent – Every log has level, timestamp, message
  • ✅ Rich con – Add any metadata without breaking parsers

Example (Node.js with pino)

pino is a fast, low-overhead structured logging library for Node.js. 

import pino from "pino";

const logger = pino({
  level: "info",
  timestamp: pino.stdTimeFunctions.isoTime
});

// Simple log
logger.info("Server started on port 3000");

// Structured log with additional fields
logger.info({
  user: "Faraz",
  action: "login",
  ip: "192.168.1.1"
}, "User logged in");

// Error logging
try {
  throw new Error("Database connection failed");
} catch (err) {
  logger.error({
    err: err.message,
    query: "SELECT * FROM users",
    user: "Faraz"
  }, "Database error occurred");
}

Output (actual JSON lines):

{"level":30,"time":"2026-04-22T10:32:00.000Z","msg":"Server started on port 3000"}
{"level":30,"time":"2026-04-22T10:32:01.000Z","user":"Faraz","action":"login","ip":"192.168.1.1","msg":"User logged in"}
{"level":50,"time":"2026-04-22T10:32:02.000Z","err":"Database connection failed","query":"SELECT * FROM users","user":"Faraz","msg":"Database error occurred"}

pino is popular because it's 10x faster than alternatives like Winston, making it suitable for high-throughput production systems.

5. Why Logs are STILL important (even if you have metrics)

Many engineers think: "I have metrics (CPU, error rate, latency). Why do I need logs?"

Here's why logs remain irreplaceable:

🧨 1. Metrics tell you what, Logs tell you why

Metrics Logs
Error rate = 5% "Database timeout after 30s"
Latency p99 = 2s "Query on table 'orders' missing index"
CPU = 90% "Infinite loop in function calculateTax()"

Example: Your dashboard shows a spike in 500 errors. Metrics cannot tell you it's because a specific user sent a malformed payload. Logs can.

🧨 2. Debugging production issues

When a bug only happens in production:

  • You cannot attach a debugger (performance impact, security)
  • You cannot reproduce the exact sequence
  • Logs are your only witness

🧨 3. Edge cases & rare bugs

Metrics aggregate data → they hide outliers. One weird request in a million won't move your metrics, but logs capture every single event.

Real example: A race condition occurs only when two specific APIs are called within 50ms. Metrics show nothing unusual. Logs with timestamps reveal the pattern.

🧨 4. Auditing & compliance

Regulations like GDPR, HIPAA, SOC2 require:

  • Who accessed what data?
  • When did they access it?
  • What changes did they make?

Metrics cannot answer these. Logs are the audit trail.

Final Comparison Table

Aspect Metrics Logs
What it answers "Something is wrong" "Exactly what and why"
Granularity Aggregated (averages, percentiles) Per-event (every single request)
Storage cost Low (numbers) High (/JSON)
Query speed Fast Slower (but searchable)
Use case Alerting, dashboards Debugging, auditing, root cause
Example error_rate > 0.05 {"error":"DB timeout","query":"..."}
One-Line Takeaway

Metrics tell you your car's check engine light is on. Logs tell you it's because cylinder #3 is misfiring due to a faulty spark plug. You need both to fix the problem.

Why "Pino" ?

Log Levels in Pino - Complete Guide

What Are Log Levels?

Log levels are priorities assigned to log messages that determine their importance and when they should be recorded. They help filter noise from critical information.

Pino's Log Levels (from lowest to highest priority)

Level Value Use Case
trace 10 Very detailed debugging, function entry/exit, variable states
debug 20 Debugging information for developers during development
info 30 Normal application events (user logged in, server started)
warn 40 Suspicious but non-critical issues (deprecated API usage)
error 50 Errors that need attention but app continues running
fatal 60 Catastrophic failures that crash the application

How It Works

Rule: Only messages at or above the current log level are logged.

Example: If level is info (30), you'll see info, warn, error, fatal but NOT debug or trace.

Basic Level Configuration

const pino = require('pino');
// Set minimum log level
const logger = pino({ level: 'info' });
logger.trace('Not shown');    // level 10 < 30 ❌
logger.debug('Not shown');    // level 20 < 30 ❌
logger.info('Shown');         // level 30 >= 30 ✅
logger.warn('Shown');         // level 40 >= 30 ✅
logger.error('Shown');        // level 50 >= 30 ✅
logger.fatal('Shown');        // level 60 >= 30 ✅

Practical Use Cases

1. TRACE - Deep Debugging

// Use for function entry/exit, detailed flow
function calculateTotal(items) {
  logger.trace({ items }, 'Entering calculateTotal');
  
  const total = items.reduce((sum, item) => {
    logger.trace({ item, currentSum: sum }, 'Adding item');
    return sum + item.price;
  }, 0);
  
  logger.trace({ total }, 'Exiting calculateTotal');
  return total;
}

2. DEBUG - Development Information

// Use during development, disable in production
const logger = pino({ level: 'debug' });
function processOrder(order) {
  logger.debug({ orderId: order.id }, 'Processing order');
  
  if (order.items.length === 0) {
    logger.debug('Order has no items, skipping');
    return;
  }
  
  // Business logic...
  logger.debug('Order processed successfully');
}

3. INFO - Normal Application Events

// Track important business operations
logger.info('Server started on port 3000');
logger.info({ userId: 123 }, 'User registered successfully');
logger.info({ orderId: 'ORD-789' }, 'Order placed');
logger.info('Database connected');

4. WARN - Concerning But Not Fatal

// Use for recoverable issues, deprecations, rate limits
logger.warn('API rate limit at 80%');
logger.warn({ endpoint: '/old-api' }, 'Using deprecated endpoint');
logger.warn('User attempted invalid password 3 times');
logger.warn('Request took 5 seconds (slower than usual)');

5. ERROR - Recoverable Errors

// Use for operation failures that don't crash the app
try {
  await sendEmail(user.email);
} catch (err) {
  logger.error({ err, userId: user.id }, 'Failed to send email');
  // Continue execution, maybe queue for retry
}
// Database query fails but app handles it
db.query(sql).catch(err => {
  logger.error({ err, query: sql }, 'Database query failed');
  return fallbackData;
});

6. FATAL - Application-Killing Errors

// Use when app cannot continue
function initializeApp() {
  try {
    connectToDatabase();
  } catch (err) {
    logger.fatal({ err }, 'Cannot connect to database');
    process.exit(1); // Exit after fatal error
  }
}
// Missing critical configuration
if (!process.env.JWT_SECRET) {
  logger.fatal('JWT_SECRET environment variable missing');
  process.exit(1);
}

Pino Transports - Complete Guide

What is a Transport?

A transport is where your logs go. It's the destination/output for your log messages. Transforms the log stream and sends it somewhere - console, file, network, external services, etc.

Why Use Transports?

  • Separation of concerns - Logging logic separate from application
  • Flexible outputs - Same logs to multiple destinations
  • Performance - Asynchronous processing doesn't block your app
  • Production ready - Rotate, compress, forward logs

Basic Transport Concepts

const pino = require('pino');
// Default transport = stdout (console)
const logger = pino(); // Logs to console
// Custom transport
const transport = pino.transport({
  target: 'pino/file'  // Built-in file transport
});
const logger = pino(transport);

Built-in Transports

1. Console (Default)

// No explicit transport needed
const logger = pino(); // Logs to process.stdout

2. File Transport

const transport = pino.transport({
  target: 'pino/file',
  options: {
    destination: './logs/app.log',  // File path
    mkdir: true,                     // Create directory if missing
    append: true,                    // Append to existing file
    sync: false                      // Async writing (default)
  }
});
const logger = pino(transport);

3. Pretty Print (Human Readable)

const transport = pino.transport({
  target: 'pino-pretty',
  options: {
    colorize: true,
    translateTime: 'SYS:standard',
    ignore: 'pid,hostname',
    singleLine: false
  }
});
const logger = pino(transport);

Single vs Multiple Transports

Single Transport

// One destination
const transport = pino.transport({
  target: 'pino/file',
  options: { destination: './app.log' }
});

Multiple Transports

// Multiple destinations simultaneously
const transport = pino.transport({
  targets:[
    { target: 'pino/file', options: { destination: './app.log' } },
    { target: 'pino-pretty', options: { colorize: true } },
    { target: 'pino/file', options: { destination: 1 } } // stdout
  ]
});

Custom Transports

Basic Custom Transport

const { Transform } = require('stream');
// Create custom transform stream
const myTransport = new Transform({
  transform(chunk, enc, cb) {
    // Modify or process log
    const log = JSON.parse(chunk);
    log.timestamp = new Date().toISOString();
    
    // Send somewhere (e.g., external API)
    console.log('Custom:', JSON.stringify(log));
    cb();
  }
});
const logger = pino(myTransport);
logger.info('Going through custom transport');

External Service Transport (HTTP)

const transport = pino.transport({
  target: 'pino-http',
  options: {
    url: 'https://log-api.example.com/ingest',
    headers: { 'API-Key': 'your-key' }
  }
});

Level-Based Filtering in Transports

// Different levels to different destinations
const transport = pino.transport({
  targets:[
    {
      target: 'pino/file',
      level: 'error',  // Only errors to error.log
      options: { destination: './error.log' }
    },
    {
      target: 'pino/file',
      level: 'info',   // Info and above to app.log
      options: { destination: './app.log' }
    },
    {
      target: 'pino-pretty',
      level: 'debug',  // Only debug in development
      options: { colorize: true }
    }
  ]
});

What is Redaction?

Redaction = automatically replacing sensitive values in your logs with a placeholder like [Redacted] or completely removing them.

Without redaction:

{"user":{"name":"John","password":"supersecret123","email":"john@example.com"}}

With redaction:

{"user":{"name":"John","password":"[Redacted]","email":"john@example.com"}}

📚 Basic Setup

Simple Array Syntax

const pino = require('pino');
const logger = pino({
  redact: ['password', 'token', 'secret']
});
// These will be redacted
logger.info({ password: '12345', user: 'john' });
logger.info({ token: 'abc123', data: 'test' });

Object Syntax (Advanced Control)

const logger = pino({
  redact: {
    paths: ['password', 'user.password', 'headers.authorization'],
    censor: '[HIDDEN]',      // Custom placeholder (default: '[Redacted]')
    remove: false             // false = replace value, true = remove key entirely
  }
});

🛤️ Path Syntax (The Most Important Part)

Paths tell Pino exactly where to find sensitive data in your log objects .

Dot Notation

redact: ['user.password']           // { user: { password: "secret" } }
redact: ['req.headers.authorization']  // HTTP request headers

Bracket Notation (for hyphens or special chars)

redact: ['user["api-key"]']         // Property with hyphen
redact:['headers["x-api-token"]']  // Header with hyphen

Wildcards * (Redact all matching keys)

redact: ['user.*.password']         // Any nested password
redact: ['*.password']              // Password at any level
redact: ['data[*].secret']          // Array elements

Array Index Notation

redact: ['users[0].password']       // First user's password
redact: ['users[*].password']       // All users' passwords

What are Child Loggers?

A child logger inherits properties from a parent logger and can add its own con. It's used to add consistent conual information to a group of log entries without repeating the same data every time.

Why Use Child Loggers?

  • Add con - Request IDs, user IDs, transaction IDs
  • Inherit configuration - Same log level, redact rules, etc.
  • Correlate logs - Easily trace related log entries
  • Reduce repetition - No need to pass con manually

Basic Child Logger Creation

const pino = require('pino');
const parent = pino();
// Create child with additional con
const child = parent.child({ module: 'auth' });
child.info('User logged in');
// Output: {"module":"auth","msg":"User logged in", ...}
// Parent remains unaffected
parent.info('Parent log');
// Output: {"msg":"Parent log", ...}  // No 'module' field

Real-World Examples

1. Request Tracking (Express.js)

const pino = require('pino');
const logger = pino();
app.use((req, res, next) => {
  // Create child logger for this request
  const requestLogger = logger.child({
    reqId: req.id,
    method: req.method,
    url: req.url,
    ip: req.ip
  });
  
  // Attach to request object
  req.logger = requestLogger;
  
  requestLogger.info('Request started');
  next();
});
app.get('/users', (req, res) => {
  req.logger.info('Fetching users');  // Includes reqId, method, etc.
  // Business logic...
  req.logger.info('Users fetched successfully');
});

2. User Con

class UserService {
  constructor(userId) {
    // Create child with user con
    this.logger = rootLogger.child({ 
      userId: userId,
      service: 'UserService'
    });
    this.logger.debug('UserService initialized');
  }
  
  async updateProfile(data) {
    this.logger.info({ data }, 'Updating user profile');
    try {
      await db.update(data);
      this.logger.info('Profile updated successfully');
    } catch (err) {
      this.logger.error({ err }, 'Failed to update profile');
    }
  }
}
const userService = new UserService(12345);
userService.updateProfile({ name: 'John' });
// All logs will include {userId:12345, service:'UserService'}

3. Transaction Logging

const rootLogger = pino();
function processOrder(orderId) {
  // Create transaction-specific logger
  const transactionLogger = rootLogger.child({
    transactionId: orderId,
    component: 'order-processor'
  });

  updateInventory(orderId, transactionLogger);

  logger.info('Validating payment');  // Inherits transactionId
  // Payment validation logic
}

Chaining Child Loggers

const root = pino();
// Level 1: Request con

const boundLogger = root.child({
  reqId: 'req-123',

What is pino-http?

pino-http is a dedicated Express middleware that automatically logs all HTTP requests and responses with Pino.

Without pino-http (Manual)

import pino from 'pino';
import express from 'express';
const logger = pino();
const app = express();
// Manual logging - repetitive and easy to miss
app.use((req, res, next) => {
  const start = Date.now();
  logger.info({ method: req.method, url: req.url }, 'Request started');
  
  res.on('finish', () => {
    const duration = Date.now() - start;
    logger.info({ 
      method: req.method, 
      url: req.url, 
      status: res.statusCode,
      duration 
    }, 'Request completed');
  });
  next();
});

With pino-http (Automatic)

import pino from 'pino';
import pinoHttp from 'pino-http';
import express from 'express';
const logger = pino();
const app = express();
// Single line - logs everything automatically
app.use(pinoHttp({ logger }));
// That's it! Every request/response is now logged

    : undefined

What is Pino-Pretty?

Pino-pretty is a formatter that converts Pino's JSON log output into human-readable, colored, multi-line text.

One Sentence Summary

Pino-pretty takes ugly JSON logs and makes them look beautiful for humans reading them in development.

The Problem Pino-Pretty Solves

Without Pino-Pretty (Raw JSON)

{"level":30,"time":1699999999999,"pid":1234,"hostname":"my-pc","req":{"method":"GET","url":"/users"},"res":{"statusCode":200},"responseTime":5.2,"msg":"request completed"}
Problem

Hard to read — all in one line, no colors, not human-friendly.

With Pino-Pretty

[2024-01-15 10:30:45] INFO: request completed
  req: {
    "method": "GET",
    "url": "/users"
  }
  res: {
    "statusCode": 200
  }
  responseTime: 5.2ms
Result

Easy to read — multi-line, colored, structured.

What Pino-Pretty Does

1. Converts JSON to Readable Text

// Input (JSON)
{"level":30,"msg":"User logged in","userId":123}

// Output (pretty)
[2024-01-15 10:30:45] INFO: User logged in
  userId: 123

2. Adds Colors (in terminal)

// Different colors for different log levels
ERROR - Red text
WARN  - Yellow text
INFO  - Green text
DEBUG - Blue text

3. Formats Timestamps

// Input
{"time":1699999999999}

// Output
[2024-01-15 10:30:45.123 +0500]

4. Pretty-Prints Objects

// Input
{"user":{"name":"John","age":30,"email":"john@example.com"}}

// Output
  user: {
    "name": "John",
    "age": 30,
    "email": "john@example.com"
  }

Save Log to File Without JSON

Use multiple targets to pretty-print to both console and file simultaneously:

import pino from 'pino';

const isDevelopment = process.env.NODE_ENV !== 'production';

export const logger = pino({
  level: isDevelopment ? 'debug' : 'info',
  transport: {
    targets: [
      // Console: Pretty print
      {
        target: 'pino-pretty',
        level: 'info',
        options: {
          colorize: true,
          translateTime: 'SYS:standard',
          ignore: 'pid,hostname',
          singleLine: false,
          destination: 1  // stdout
        }
      },
      // File: Also pretty print (not JSON)
      {
        target: 'pino-pretty',
        level: 'info',
        options: {
          colorize: false,  // No colors in file
          translateTime: 'SYS:standard',
          ignore: 'pid,hostname',
          singleLine: false,
          destination: './logs/app.log',  // Direct to file
          mkdir: true,
          append: true
        }
      }
    ]
  }
});
Key Difference

Set colorize: false for the file target — ANSI color codes look like garbage in a plain text file.

Using pino-multi-stream for Better Structured Log Files

Installation

npm i pino-multi-stream

For full control over how logs are written to files, you can create a custom Transform stream that pretty-prints JSON before writing it to disk. 

import pino from 'pino';
import fs from 'node:fs';
import { Transform } from 'node:stream';

const isDevelopment = process.env.NODE_ENV !== 'production';

// Custom stream that pretty-prints JSON
class PrettyJSONStream extends Transform {
  _transform(chunk, encoding, callback) {
    try {
      const log = JSON.parse(chunk);
      // Remove pid and hostname if you want
      delete log.pid;
      delete log.hostname;
      const prettyJSON = JSON.stringify(log, null, 2) + '\n\n';
      callback(null, prettyJSON);
    } catch (err) {
      callback(null, chunk);
    }
  }
}

// Create streams
const prettyJSONStream = new PrettyJSONStream();
const fileStream = fs.createWriteStream('./logs/app.log', { flags: 'a' });
prettyJSONStream.pipe(fileStream);

// Create console pretty stream
const prettyStream = pino.transport({
  target: 'pino-pretty',
  options: {
    colorize: true,
    translateTime: 'SYS:standard',
    ignore: 'pid,hostname'
  }
});

export const logger = pino({
  level: isDevelopment ? 'debug' : 'info'
}, pino.multistream([
  { stream: prettyStream },      // Console
  { stream: prettyJSONStream }   // File (pretty JSON)
]));

How It Works

Stream Destination Format
prettyStream Console (stdout) Colored, human-readable text
prettyJSONStream ./logs/app.log Indented JSON (2 spaces), no colors
Why This Approach?

The built-in pino.transport() targets run in a worker thread and don't support custom stream classes. Using pino.multistream() with a manual Transform gives you full control over the file format.
