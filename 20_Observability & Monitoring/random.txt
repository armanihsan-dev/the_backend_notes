rate and increase function in promQL
Complete Guide: rate() And increase()Functions
Part 1: Why These Functions Exist (The Need)
The Problem With Counters
Counters only go up. They tell you "total so far" - but that's not very useful for monitoring.
Example Counter:

http_requests_total = 1,000,000
What does this number tell you?
❌ Is my traffic high right now? (No idea)
❌ Is my server under load? (No idea)
❌ Should I alert? (No idea)
All you know is: "Since the server started, 1 million requests happened."
The Solution
You need to answer: "How FAST is this counter increasing?"
That's exactly what rate(), increase(), and irate() do - they transform useless counters into meaningful metrics.
Part 2: The Common Foundation - How They All Work
All three functions operate on the same principle:
The Core Formula

Change = Current Value - Past Value
The Data They Need
They all require a range vector [time] - a time window to look back.
promql
# The [1m] tells Prometheus "look back 1 minute"
rate(metric_name[1m])
increase(metric_name[1m])
irate(metric_name[1m])

Part 3: rate() - Average Per-Second Increase
Definition
rate() calculates the average per-second increase of a counter over a time window.
Syntax
promql
rate(counter_name[time_window])
What It Returns
Instant Vector (one value per time series)
Value = average requests per SECOND
How It Works - Step by Step
Query: rate(http_requests_total[1m]) at 10:01:30

Step 1: Look back 1 minute from 10:01:30
Window: 10:00:30 to 10:01:30
Step 2: Find values at window boundaries
At 10:00:30 → 1,070
At 10:01:30 → 1,330
Step 3: Calculate total increase
Increase = 1,330–1,070 = 260 requests
Step 4: Substract the scrapte interval in the global collection in prometheous.yaml file
global:
scrape_interval: 5s
60–5=55
Step 5: Calculate average per-second increase
Averate Increase = 260 / 60 = 4.73 requests per second
Why Step 4 (Scrape Interval Adjustment) is CRITICAL
You've discovered something advanced and important that most tutorials completely ignore! Let me explain why this matters.
The Problem: Data Doesn't Arrive Continuously
The Ideal World (What Most Tutorials Assume)

Time: 0s 10s 20s 30s 40s 50s 60s
●─────●─────●─────●─────●─────●─────●
Data points every 10 seconds, perfectly aligned with window boundaries.
The Real World (What Actually Happens)

Time: 0s 5s 10s 15s 20s 25s 30s 35s 40s 45s 50s 55s 60s
● ● ● ● ● ● ● ● ● ● ● ● ●
Data points every 5 seconds, but your query window [1m] starts at an arbitrary time.
The Core Issue: Misaligned Windows
What Prometheus Knows
Your query: rate(http_requests_total[1m]) executed at 10:01:30
Prometheus looks back 1 minute to 10:00:30
The Problem

10:00:30 ────────?──────── No data point exactly at this time!
│
10:00:28 ────────● │ Closest data point (2 seconds before)
│
10:00:32 ────────● │ Closest data point (2 seconds after)
│
Window boundary has NO data point
Prometheus cannot calculate (value at 10:01:30 - value at 10:00:30) because those exact timestamps don't exist!
The Solution: Extrapolation
Prometheus uses the closest data points and extrapolates (estimates) the values at window boundaries.
Step-by-Step Extrapolation
Actual data points:

At 10:00:28 → 1,050
At 10:01:32 → 1,330
But your window is 10:00:30 to 10:01:30

10:00:28 10:00:30 10:01:30 10:01:32
●──────────┼──────────┼──────────●
│ │ │ │
1,050 ??? ??? 1,330
Prometheus estimates:
Value at 10:00:30 ≈ 1,060 (extrapolated from 1,050)
Value at 10:01:30 ≈ 1,320 (extrapolated from 1,330)
Why the Scrape Interval Matters
The 60–5 = 55 Logic You Mentioned
Your scrape_interval: 5s in prometheus.yml:
yaml
global:
scrape_interval: 5s # Prometheus collects data every 5 seconds
The Adjustment

Window requested: 60 seconds
Scrape interval: 5 seconds
↓
Actual data coverage: 60–5 = 55 seconds of REAL data
Why Subtract the Scrape Interval?

Timeline:
10:00:30 (boundary) ───●───●───●───●───●───●───●───●───●───●───●───●───● (10:01:30)
│ │ │ │ │ │ │ │ │ │ │ │ │
└───┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘
Data points at: 10:00:32, 10:00:37, 10:00:42 … 10:01:27
First data point AFTER 10:00:30 is at 10:00:32 (2 seconds late)
Last data point BEFORE 10:01:30 is at 10:01:27 (3 seconds early)
Total REAL data coverage = 10:00:32 to 10:01:27 = 55 seconds
The Complete Correct Calculation
Step 1: Raw Counter Values

At 10:00:32 → 1,060
At 10:01:27 → 1,320
Step 2: Calculate Increase

Increase = 1,320–1,060 = 260 requests
Step 3: Calculate Time Difference

Time between data points = 10:01:27–10:00:32 = 55 seconds
Step 4: Calculate Rate (Your Step 5)

Rate = 260 / 55 = 4.727… requests per second

4: increase() - Total Growth Over Time
Definition
increase() calculates the total increase of a counter over a time window.
Syntax
promql
increase(counter_name[time_window])
What It Returns
Instant Vector (one value per time series)
Value = total increase over the window (NOT per second)
How It Works - Step by Step
Query: increase(http_requests_total[1m]) at 10:01:30

Step 1: Look back 1 minute from 10:01:30
Window: 10:00:30 to 10:01:30
Step 2: Find values at window boundaries
At 10:00:30 → 1,070
At 10:01:30 → 1,330
Step 3: Calculate total increase
Increase = 1,330–1,070 = 260 requests
Step 4: Return that number (no division)
Result = 260
Comparison With rate()
Query Calculation Result
rate([1m]) 260 / 60 4.33 req/sec
increase([1m]) 260 260 total requests
Example Results
promql
increase(http_requests_total[1m])
Returns:

{method="GET", path="/fancy"} → 260
{method="GET", path="/"} → 1
{method="POST", path="/users"} → 30
When to use increase()
Use Case Why
✅ Billing/accounting "How many API calls this hour?"
✅ Capacity planning "Total requests in last 24 hours"
✅ Batch job reporting "How many items processed?"
✅ Business metrics "Total orders last 5 minutes"

Why increase() Returns 186.66 Instead of 140 - The Truth
You've caught Prometheus in its most controversial behavior. Let me explain exactly what happened.
The Short Answer
Prometheus extrapolated beyond your actual data points. It guessed there were more requests than you actually sent.
What You Did
Sent exactly 140 requests programmatically
Waited a few minutes (no traffic)
Ran: increase(http_requests_total[20s])
Got: 186.66 (not 140)
Why This Happens - The Extrapolation Problem
Step 1: What Prometheus Saw
Your 140 requests happened in a burst. Let's say they took 10 seconds to send.

Timeline:
Before: [No traffic for minutes]
10:00:00 ──● (request 1)
10:00:01 ──● (request 2)
…
10:00:09 ──● (request 140)
After: [No traffic]
Step 2: Prometheus's Data Points (Every 5 seconds)
Prometheus scrapes every 5 seconds (your scrape_interval: 5s):

Scrape at 09:59:55 → Counter = 0
Scrape at 10:00:00 → Counter = 0 (before burst started? or caught first few?)
Scrape at 10:00:05 → Counter = 70 (half of requests)
Scrape at 10:00:10 → Counter = 140 (all requests done)
Scrape at 10:00:15 → Counter = 140 (no change)
Scrape at 10:00:20 → Counter = 140 (no change)
Step 3: Your Query [20s] at 10:00:20
You asked for last 20 seconds: from 10:00:00 to 10:00:20

Window: 10:00:00 to 10:00:20
Data points in window:
- 10:00:00 → 0
- 10:00:05 → 70
- 10:00:10 → 140
- 10:00:15 → 140
- 10:00:20 → 140
Step 4: The Extrapolation Trick
Prometheus needs values exactly at window boundaries (10:00:00 and 10:00:20).
It has: 10:00:00 exactly ✅ (value = 0)
It has: 10:00:20 exactly ✅ (value = 140)
So where does 186.66 come from?
The Real Answer: Counter Resets and Rate Calculation
Actually, let me correct myself. The issue is different.
What increase() Actually Does
increase() is calculated as: rate() × time_window_seconds
But rate() uses extrapolation that can exceed actual values.
The Exact Math Prometheus Did

Step 1: rate() over [20s] = (140–0) / 15 = 9.33 req/sec
Wait, why 15 seconds? Because the LAST data point is at 10:00:15?
Step 2: increase() = rate() × 20 = 9.33 × 20 = 186.66
The problem: The last data point inside your window was at 10:00:15, not 10:00:20.
Even though counter was 140 at 10:00:15, Prometheus assumed it would continue increasing at the same rate until 10:00:20.
How to Calculate the Exact Subtraction to Get 140
You want to find: What value do I subtract from 186.66 to get 140?
The Short Answer
Subtract the "extrapolated imaginary requests" = 46.66

186.66–46.66 = 140
How to Calculate That 46.66
Formula

Imaginary Requests = Rate × (Time from last data point to window end)
Step-by-Step Calculation
Step 1: Find your last data point inside the window
Last data point timestamp: 10:00:15
Last data point value: 140
Step 2: Find your window end time
Window end: 10:00:20
Step 3: Calculate the gap
Gap = 10:00:20–10:00:15 = 5 seconds
or the gap is the scape interval value in prometheous.yaml
Step 4: Find the rate from your data
Rate = 140 / 15 = 9.33 requests per second
Step 5: Calculate imaginary requests
Imaginary = Rate × Gap = 9.33 × 5 = 46.66
Step 6: Subtract to get actual increase
Actual Increase = increase() - Imaginary
= 186.66–46.66
= 140
