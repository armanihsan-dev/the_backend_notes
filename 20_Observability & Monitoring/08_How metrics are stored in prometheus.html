HOW METRICS ARE STORED IN PROMETHEUS

STORAGE, STRUCTURE & QUERYING — CONCISE EDITION

1. METRIC STORAGE

Prometheus stores metrics in a custom-built, high-performance time series database (TSDB) designed for efficiency. The core idea is to optimize for how monitoring data is typically written (ingested constantly) and queried (recent data is accessed most often).

What Gets Stored

process_cpu_seconds_total{instance="localhost:4000"} 0.03 @ 1742820845

        METRIC NAME                  LABELS           VALUE  TIMESTAMP

Physical Storage Layers

In Memory

Last 2 hours of data for fast access

On Disk

Compressed 2-hour blocks for long-term storage

WAL

Write-Ahead Log for crash recovery

Efficiency

Only 1–2 bytes per sample (highly compressed)

2. UNDERSTANDING process_cpu_seconds_total

Reading the Metric

First point:  0.015 @ 1742820845
Second point: 0.030 @ 1742820852
PartMeaning
0.015Total CPU seconds used so far
@ 1742820845Unix timestamp when measured
Difference0.015s of CPU used between measurements

It's a COUNTER (Like an Odometer)

  • Only increases — never goes down
  • Shows cumulative time since process started
  • Need rate() or increase() to make it useful
Odometer Analogy

Just like a car odometer shows total miles driven (not current speed), process_cpu_seconds_total shows total CPU time used — not current CPU usage. You need rate() to get "speed."

3. UNDERSTANDING increase()

increase(process_cpu_seconds_total[1m]) = 0.302
ValueInterpretation
0.302 secondsCPU time used in the last 60 seconds
59.698 secondsApp was idle
~0.5%CPU utilization

Quick Value Guide

4. QUERY TYPES

Instant Query — current value 
process_cpu_seconds_total
Range Query — values over time 
process_cpu_seconds_total[5m]
# Returns: 0.015 @ t1, 0.030 @ t2, 0.045 @ t3
Rate Query — per-second increase 
rate(process_cpu_seconds_total[1m])    # Average over 1m
irate(process_cpu_seconds_total[5m])   # Instant rate (better for spikes)

5. LABEL FILTERING

{job="my-express-app"}                              # All metrics with this label
process_cpu_seconds_total{instance="localhost:4000"} # Specific instance
{job=~"my-.*"}                                       # Regex match
{job!="my-express-app"}                              # Not equal
OperatorMeaningExample

!=Not equaljob!="app"

7. PRACTICAL QUERIES FOR YOUR APP

# CPU total (raw counter)
process_cpu_seconds_total

# CPU used in last minute
increase(process_cpu_seconds_total[1m])

# CPU rate (per second)
rate(process_cpu_seconds_total[1m])

# CPU percentage
rate(process_cpu_seconds_total[1m]) * 100

# Memory in MB
process_resident_memory_bytes / 1024 / 1024

10. KEY TAKEAWAYS

  • ✅ process_cpu_seconds_total = cumulative CPU time (always increases)
  • ✅ increase(metric[1m]) = how much CPU was used in the last minute
  • ✅ rate(metric[1m]) = CPU usage per second
  • ✅ 0.3s CPU per minute = healthy idle app
  • ✅ 5s+ increase = after hitting a CPU-heavy endpoint
💡 Golden Rule

Raw counter values are meaningless on their own. Always wrap counters in rate() or increase() to get actionable insight from them.
