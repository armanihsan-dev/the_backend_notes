DISTRIBUTED TRACING

A COMPLETE GUIDE TO TRACES, SPANS, AND HOW TO INSTRUMENT YOUR APPLICATION

PART 1: WHAT ARE TRACES?

A trace is a complete record of a single operation's journey through your system from start to finish. It captures every step, how long each step took, and how steps relate to each other.

Simple Analogy

Think of a trace like GPS tracking for a package delivery:

Package delivery trace:
08:00 - Package picked up from warehouse (start)
08:15 - Arrived at sorting facility
08:30 - Loaded onto delivery truck
09:00 - Out for delivery
10:30 - Delivered to customer (end)

Total time: 2 hours 30 minutes

Similarly, a trace for an API request might look like:

GET /api/users request trace:
  0ms - Request received by API Gateway
  5ms - Authentication check started
 15ms - Authentication completed
 20ms - Database query started
120ms - Database query completed
125ms - Response formatted
130ms - Response sent to client

Total time: 130ms

Why Tracing is the Third Pillar

Pillar Question It Answers Example
Metrics "What happened?" "Error rate increased to 10%"
Logs "Why did it happen?" "Database connection timeout error"
Traces "Where did the time go?" "450ms spent in database query, 50ms in API"
Key Insight

Metrics tell you something is wrong. Logs tell you what the error message was. Traces tell you exactly which step caused the problem.

PART 2: WHERE TRACING IS MOST USEFUL

Monolithic Application (Tracing is still useful)

Single application with everything inside:
┌─────────────────────────────────┐
│         Your App                │
│  Request → API → DB → Response  │
└─────────────────────────────────┘

What tracing shows you:
- Which API endpoint is slow
- Which database query is the bottleneck
- Where time is spent inside your code

Distributed System (Tracing becomes essential)

Multiple services talking to each other:
┌──────────┐    ┌──────────┐    ┌──────────┐
│   API    │───→│   Auth   │───→│   User   │
│ Gateway  │    │ Service  │    │ Service  │
└──────────┘    └──────────┘    └──────────┘
                                    │
                                    ↓
                              ┌──────────┐
                              │ Payment  │
                              │ Service  │
                              └──────────┘

❌ Without Tracing (The Nightmare)

  • Service A logs: "Request received"
  • Service B logs: "Auth passed" (different machine)
  • Service C logs: "Database error" (third machine)
  • No way to connect these events

✅ With Tracing (The Solution) 

One trace showing everything:
API Gateway:    0ms - Received request
Auth Service:   5ms - Auth started
Auth Service:  12ms - Auth completed
User Service:  20ms - Fetching user
User Service:  80ms - User fetched (60ms DB)
Payment:       90ms - Processing
Payment:      150ms - Processed
API Gateway:  155ms - Response sent

Bottleneck: User Service DB (60ms)

PART 3: TRACES VS LOGS VS METRICS

Logs — What happened

2024-01-15 10:30:00 INFO  Auth service: User 123 login attempt
2024-01-15 10:30:02 INFO  User service: Fetching user 123
2024-01-15 10:30:05 ERROR Payment service: Payment failed
2024-01-15 10:30:05 INFO  API Gateway: Returning error to client

Problem: You see events, but don't see that they're connected.

Metrics — System health

- Request rate: 100 req/sec
- Error rate: 5%
- Average latency: 150ms
- CPU usage: 70%

Problem: You know something is wrong, but not where.

Traces — The connected journey

Trace ID: abc-123 (User login request)
├── API Gateway: 0-150ms
    ├── Auth Service: 5-50ms
    │   ├── Database: 10-45ms
    │   └── Token generation: 45-50ms
    ├── User Service: 55-100ms
    │   └── Database: 60-95ms
    └── Payment Service: 105-145ms (ERROR here!)
        └── External API: 110-140ms (timeout)

Solution: You see the exact path, timing, and failure point.

PART 4: SPANS — THE BUILDING BLOCKS

A span represents a single unit of work or operation within a trace. Each trace is made up of multiple spans connected in a hierarchy.

Span Structure

{
    traceId:      "abc-123",                       // Which trace this belongs to
    spanId:       "span-456",                      // This span's unique ID
    parentSpanId: "span-123",                      // Who called this (null for root)
    name:         "GET /api/users",                // What operation this is
    startTime:    "2024-01-15T10:30:00.000Z",
    endTime:      "2024-01-15T10:30:00.130Z",
    duration:     "130ms",                         // Calculated from start-end
    attributes: {                                  // Additional context
        "http.method":      "GET",
        "http.status_code": 200,
        "user.id":          "123"
    },
    events: [                                      // Important moments during span
        { name: "DB query started",   timestamp: "..." },
        { name: "DB query completed", timestamp: "..." }
    ],
    status: "ok"                                   // ok, error, or unset
}

Parent-Child Relationship (The Tree Structure)

Trace ID: trace-123 (Complete request)

Root Span (Parent)
├── GET /api/users (duration: 130ms)
    │
    ├── Child Span 1
    │   └── Authentication middleware (duration: 15ms)
    │       │
    │       └── Grandchild Span
    │           └── Token validation (duration: 5ms)
    │
    ├── Child Span 2
    │   └── Database query (duration: 80ms)
    │
    └── Child Span 3
        └── Response formatting (duration: 20ms)

How Spans Connect (The ID System)

// Root span (no parent)
{
    traceId:      "trace-123",
    spanId:       "span-root",
    parentSpanId: null,          // This is the root!
    name:         "GET /api/users"
}

// Child span (parent is root)
{
    traceId:      "trace-123",   // Same trace ID
    spanId:       "span-auth",
    parentSpanId: "span-root",   // Links to root!
    name:         "Authentication"
}

// Grandchild span
{
    traceId:      "trace-123",   // Same trace ID
    spanId:       "span-db",
    parentSpanId: "span-auth",   // Links to auth span!
    name:         "Database query"
}
How it works

Even though each span is generated independently, they all share the same traceId and know their parent via parentSpanId. This allows tracing systems to reconstruct the entire tree.

PART 5: COMPLETE EXAMPLE — TRACES IN ACTION

Scenario: User logs into an e-commerce site

// Without tracing (can't see the problem)
User clicks login → 2 seconds later → "Login failed"

// With tracing (see exactly what happened)
Trace ID: login-trace-789
Duration: 2,150ms (too slow!)

Span 1 (Root): POST /api/login [0ms - 2,150ms]
    │
    ├─ Span 2: Authentication Service [10ms - 50ms]
    │   ├─ Check credentials  [15ms - 30ms]
    │   └─ Generate JWT token [32ms - 48ms]
    │
    ├─ Span 3: User Service [55ms - 2,100ms]  ← PROBLEM!
    │   ├─ Fetch user profile [60ms - 2,000ms] ← BOTTLENECK!
    │   │   └─ Database query [60ms - 2,000ms] ← SLOW QUERY
    │   └─ Update last login  [2,005ms - 2,095ms]
    │
    └─ Span 4: Session Service [2,105ms - 2,145ms]
        └─ Create session [2,108ms - 2,140ms]

Solution identified: Database query in User Service took 1,940ms!

PART 6: HOW TRACES ARE TRANSPORTED

Your Application
       │
       │ 1. Generate spans using OpenTelemetry SDK
       ↓
   OpenTelemetry SDK
       │
       │ 2. Export spans using OTLP protocol
       ↓
   OTLP Exporter (HTTP/gRPC)
       │
       │ 3. Send to collector (optional but recommended)
       ↓
   Grafana Alloy / Collector
       │
       │ 4. Process, batch, and forward spans
       ↓
   Grafana Tempo (Backend)
       │
       │ 5. Store and index spans
       ↓
   Grafana (Visualization)
       │
       │ 6. Query and display traces
       ↓
   Developer sees trace visualization

Protocol: OTLP (OpenTelemetry Protocol)

OTLP is the standard way to send telemetry data (traces, metrics, logs). 

// POST http://localhost:4318/v1/traces
{
  "resourceSpans": [{
    "resource": {
      "attributes": [
        { "key": "service.name", "value": { "stringValue": "my-api" } }
      ]
    },
    "scopeSpans": [{
      "spans": [{
        "traceId":            "abc123",
        "spanId":             "def456",
        "name":               "GET /users",
        "startTimeUnixNano":  "1705315200000000000",
        "endTimeUnixNano":    "1705315200130000000"
      }]
    }]
  }]
}

PART 7: INSTRUMENTATION

Method 1: Auto-Instrumentation (No code changes)

import { NodeSDK } from '@opentelemetry/sdk-node';
import { ExpressInstrumentation } from '@opentelemetry/instrumentation-express';
import { HttpInstrumentation } from '@opentelemetry/instrumentation-http';

const sdk = new NodeSDK({
    instrumentations: [
        new ExpressInstrumentation(),  // Auto-trace Express routes
        new HttpInstrumentation()      // Auto-trace HTTP calls
    ]
});

sdk.start();

// Your normal Express code — everything is now traced automatically!
app.get('/users', (req, res) => {
    // Spans created automatically for:
    // - HTTP request
    // - Express route handler
    // - Any database calls (if instrumented)
    res.json(users);
});

Method 2: Manual Instrumentation (Custom spans)

import { trace } from '@opentelemetry/api';

app.post('/api/process-order', async (req, res) => {
    const tracer = trace.getTracer('my-app');

    await tracer.startActiveSpan('process-order', async (span) => {
        span.setAttribute('order.id', req.body.orderId);
        span.setAttribute('user.id', req.user.id);

        // Step 1: Validate order
        await tracer.startActiveSpan('validate-order', async (validateSpan) => {
            const isValid = await validateOrder(req.body);
            validateSpan.setAttribute('order.valid', isValid);
            validateSpan.end();
        });

        // Step 2: Process payment
        await tracer.startActiveSpan('process-payment', async (paymentSpan) => {
            const result = await processPayment(req.body.amount);
            paymentSpan.setAttribute('payment.success', result.success);
            paymentSpan.end();
        });

        // Step 3: Update inventory
        await tracer.startActiveSpan('update-inventory', async (inventorySpan) => {
            await updateStock(req.body.items);
            inventorySpan.end();
        });

        span.end();
    });

    res.json({ success: true });
});

PART 8: BACKEND SYSTEM — GRAFANA TEMPO

Tempo receives spans → groups by traceId → reconstructs traces → stores them → serves queries

Input: Individual spans (sent from your app)
    ↓
Process: Groups spans with same traceId together
    ↓
Output: Complete trace tree ready for visualization

Querying Tempo

# Find a trace by ID
curl http://localhost:3200/api/traces/trace-123

# Find traces by tags
curl http://localhost:3200/api/search?tags=service.name=my-api&limit=20

# Find traces within time range
curl http://localhost:3200/api/search?start=2024-01-15T10:00:00Z&end=2024-01-15T11:00:00Z

PART 9: REAL-WORLD EXAMPLE — COMPLETE SETUP

Express App with Tracing

import express from 'express';
import { trace } from '@opentelemetry/api';

const app = express();

// Middleware: creates a span for every request
app.use((req, res, next) => {
    const tracer = trace.getTracer('express-api');

    tracer.startActiveSpan(`${req.method} ${req.path}`, (span) => {
        span.setAttribute('http.method', req.method);
        span.setAttribute('http.url', req.url);
        span.setAttribute('http.user_agent', req.headers['user-agent']);

        const startTime = Date.now();

        res.on('finish', () => {
            span.setAttribute('http.status_code', res.statusCode);
            span.setAttribute('http.duration_ms', Date.now() - startTime);
            span.end();
        });

        next();
    });
});

// Route — automatically part of the trace!
app.get('/api/users/:id', async (req, res) => {
    const tracer = trace.getTracer('user-service');

    const user = await tracer.startActiveSpan('db-fetch-user', async (span) => {
        span.setAttribute('user.id', req.params.id);
        const user = await db.users.findById(req.params.id);
        span.setAttribute('db.rows_fetched', user ? 1 : 0);
        span.end();
        return user;
    });

    res.json(user);
});

PART 10: SUMMARY

Concept Definition Example
Trace Complete record of one operation's journey A user login request across API Gateway, Auth, User, Payment services
Span Single step within a trace Database query, HTTP call, authentication check
traceId Unique ID for the entire trace "abc-123-def-456" — all spans share this
spanId Unique ID for a single span "span-789"
parentSpanId Links a span to its parent Points to the span that called this one
OTLP Protocol for sending trace data HTTP/gRPC endpoint: /v1/traces
Tempo Backend that stores traces Receives spans, reconstructs traces
Instrumentation Code that generates spans Auto-instrumentation or manual span creation
💡 One-Line Summary 
A trace is a complete, hierarchical timeline of an operation (like an API
request), made up of connected spans that show every step, how long each
step took, and how steps relate to each other.

KEY QUESTION IT ANSWERS:
  "Where did the time go?" — across your entire system.

CORE COMPONENTS:
  Trace → made of Spans → connected by traceId + parentSpanId

TOOLCHAIN:
  App → OpenTelemetry SDK → OTLP → Alloy → Tempo → Grafana
