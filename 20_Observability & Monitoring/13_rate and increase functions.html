RATE() & INCREASE()

PROMETHEUS COUNTER FUNCTIONS — HOW THEY REALLY WORK

WHY THESE FUNCTIONS EXIST

The Problem With Counters

Counters only go up. They tell you "total so far" — but that's not very useful for monitoring. 

http_requests_total = 1,000,000
What This Number Tells You
  • ❌ Is my traffic high right now? — No idea
  • ❌ Is my server under load? — No idea
  • ❌ Should I alert? — No idea

All you know is: "Since the server started, 1 million requests happened." You need to answer: "How FAST is this counter increasing?" That's exactly what rate() and increase() do — they transform useless raw counters into meaningful metrics.

The Common Foundation

Both functions operate on the same core principle:

Core Formula 
Change = Current Value - Past Value

Both require a range vector [time] — a time window to look back: 

# The [1m] tells Prometheus "look back 1 minute"
rate(metric_name[1m])
increase(metric_name[1m])

WHAT IS rate()?

rate() calculates how fast a counter is increasing per second over a given time window. It answers the question: "How many requests per second am I getting right now?"

Syntax

rate(counter_name[time_window])

What It Returns

Instant Vector

One value per time series — the average per-second rate of increase over the window. You can graph this directly.

rate() — STEP-BY-STEP CALCULATION

Let's walk through exactly what Prometheus does when you run rate(http_requests_total[1m]) at 10:04:30.

Sample Data

Time Total Requests (Counter)
10:03:00 1,000
10:03:15 1,030
10:03:30 1,070
10:03:45 1,120
10:04:00 1,180
10:04:15 1,250
10:04:30 1,330

The Calculation

Query: rate(http_requests_total[1m]) at 10:04:30

Step 1 — Define the window
        Look back 1 minute: 10:03:30 → 10:04:30

Step 2 — Find boundary values
        At 10:03:30 → 1,070
        At 10:04:30 → 1,330

Step 3 — Calculate total increase
        Increase = 1,330 - 1,070 = 260 requests

Step 4 — Divide by window in seconds
        Rate = 260 / 60 = 4.33 requests per second

Example Results

rate(http_requests_total[1m])
{method="GET",  path="/fancy"} → 4.33
{method="GET",  path="/"}      → 0.016
{method="POST", path="/users"} → 0.5

THE EXTRAPOLATION PROBLEM

Most tutorials skip this, but it's critical to understand why rate() doesn't always give you a "clean" number.

The Core Issue: Misaligned Windows

Your query window boundaries (e.g. exactly 10:00:30) almost never align with actual scrape timestamps. Prometheus scrapes on its own schedule — not on your query's schedule. 

Query: rate(http_requests_total[1m]) at 10:01:30
Prometheus looks back to: 10:00:30

The Problem:
  10:00:30 ────────?──────── No data point exactly here!
  10:00:28 ────────●         Closest point (2 seconds before)
  10:00:32 ────────●         Closest point (2 seconds after)

Prometheus CANNOT calculate (value at 10:01:30 - value at 10:00:30)
because those exact timestamps don't exist in the database!

The Solution: Extrapolation

Prometheus estimates the values at window boundaries using the closest real data points. 

Actual data points:
  At 10:00:28 → 1,050
  At 10:01:32 → 1,330

Your window: 10:00:30 to 10:01:30

10:00:28    10:00:30    10:01:30    10:01:32
    ●──────────┼──────────┼──────────●
    │          │          │          │
 1,050      ???          ???      1,330

Prometheus estimates:
  Value at 10:00:30 ≈ 1,060  (extrapolated from 1,050)
  Value at 10:01:30 ≈ 1,320  (extrapolated from 1,330)

SCRAPE INTERVAL ADJUSTMENT — WHY IT MATTERS

Advanced Concept

This is something most tutorials completely ignore. Understanding it explains why rate() divides by 55 instead of 60 when your scrape interval is 5s.

The 60 - 5 = 55 Logic

With scrape_interval: 5s in your prometheus.yml: 

global:
  scrape_interval: 5s  # Prometheus collects data every 5 seconds
Timeline (scrape every 5s):
10:00:30 (boundary) ───●───●───●───●───●───●───●───●───●───●───●───●───● (10:01:30)
                       │   │   │   │   │   │   │   │   │   │   │   │   │
Data points at: 10:00:32, 10:00:37, 10:00:42 ... 10:01:27

First data point AFTER  10:00:30 → at 10:00:32  (2 seconds late)
Last  data point BEFORE 10:01:30 → at 10:01:27  (3 seconds early)

Total REAL data coverage = 10:00:32 to 10:01:27 = 55 seconds

The Complete Correct Calculation

Step 1 — Raw counter values
        At 10:00:32 → 1,060
        At 10:01:27 → 1,320

Step 2 — Calculate increase
        Increase = 1,320 - 1,060 = 260 requests

Step 3 — Calculate actual time difference
        Time = 10:01:27 - 10:00:32 = 55 seconds

Step 4 — Calculate rate
        Rate = 260 / 55 = 4.727 requests per second
Parameter Value Why
Window requested 60 seconds Your [1m]
Scrape interval 5 seconds scrape_interval: 5s
Actual data coverage 55 seconds 60 - 5 = 55
Divisor used by Prometheus 55 Real time between data points

WHEN TO USE rate()

Use Case Why
✅ Alerting on traffic drops "Rate fell below 10 req/sec"
✅ Autoscaling decisions "Rate > 100 req/sec → scale up"
✅ Dashboard graphs Shows smooth traffic trends
✅ Comparing traffic over time Consistent per-second unit

WHAT IS increase()?

increase() calculates the total increase of a counter over a time window. Unlike rate(), it does not divide by time — it returns the raw count of how much the counter grew.

Syntax

increase(counter_name[time_window])

What It Returns

Instant Vector

One value per time series — the total count increase over the window. No division. Just the raw growth number.

Under the Hood

increase(x[t]) is literally just rate(x[t]) × t. It uses the same extrapolation logic as rate(), which is why it can return non-integer values even for integer counters.

increase() — STEP-BY-STEP CALCULATION

Query: increase(http_requests_total[1m]) at 10:01:30

Step 1 — Define the window
        Look back 1 minute: 10:00:30 → 10:01:30

Step 2 — Find boundary values
        At 10:00:30 → 1,070
        At 10:01:30 → 1,330

Step 3 — Calculate total increase
        Increase = 1,330 - 1,070 = 260 requests

Step 4 — Return that number (no division)
        Result = 260

Example Results

increase(http_requests_total[1m])
{method="GET",  path="/fancy"} → 260
{method="GET",  path="/"}      → 1
{method="POST", path="/users"} → 30

increase() vs rate() — SIDE BY SIDE

Query Calculation Result Unit
rate([1m]) 260 / 60 4.33 requests / second
increase([1m]) 260 × 1 260 total requests
The Relationship 
increase(x[t])  =  rate(x[t])  ×  t (in seconds)
increase(x[1m]) =  rate(x[1m]) × 60

WHEN TO USE increase()

Use Case Why
✅ Billing / accounting "How many API calls this hour?"
✅ Capacity planning "Total requests in last 24 hours"
✅ Batch job reporting "How many items processed?"
✅ Business metrics "Total orders in last 5 minutes"

THE 186.66 MYSTERY — WHY increase() LIES

You sent exactly 140 requests programmatically, waited a few minutes (no traffic), then ran: 

increase(http_requests_total[20s])

And got 186.66 instead of 140. Here's exactly why.

What Prometheus Saw

Your 140 requests happened in a burst (~10 seconds). With scrape_interval: 5s:

Scrape Time Counter Value Note
09:59:55 0 Before burst
10:00:00 0 Burst just starting
10:00:05 70 Half of requests sent
10:00:10 140 All requests done
10:00:15 140 No change
10:00:20 140 No change

Your Query [20s] at 10:00:20

Window: 10:00:00 → 10:00:20
Data points inside window:
  10:00:00 → 0
  10:00:05 → 70
  10:00:10 → 140
  10:00:15 → 140
  10:00:20 → 140  ← last data point is AT the boundary ✅

Why 186.66 and Not 140?

The last data point with a changing value was at 10:00:10 (value = 140). The data points at 10:00:15 and 10:00:20 are flat (no change).

Prometheus calculates rate() using the slope of the data. The slope was computed over the rising portion (0 → 140 in 10 seconds), then extrapolated forward to fill the full 20-second window. 

Step 1 — rate() over [20s]
        rate = (140 - 0) / 15 = 9.33 req/sec
        (Why 15? The last data point Prometheus used was at 10:00:15)

Step 2 — increase() = rate() × window
        increase = 9.33 × 20 = 186.66
The Root Cause

The last data point inside your window was at 10:00:15, not 10:00:20. Even though the counter was already 140 at 10:00:15, Prometheus assumed it would continue increasing at the same rate until 10:00:20 — adding imaginary requests.

THE EXACT MATH — HOW TO GET BACK TO 140

You want to understand: what are the 46.66 imaginary requests that Prometheus added?

Formula

Imaginary Requests Formula 
Imaginary Requests = Rate × (Window End - Last Data Point Timestamp)

Step-by-Step

Step 1 — Last data point inside the window
        Timestamp: 10:00:15
        Value:     140

Step 2 — Window end time
        10:00:20

Step 3 — Calculate the gap
        Gap = 10:00:20 - 10:00:15 = 5 seconds
        (This equals your scrape_interval!)

Step 4 — Find the rate from your data
        Rate = 140 / 15 = 9.33 requests per second

Step 5 — Calculate imaginary requests
        Imaginary = 9.33 × 5 = 46.66

Step 6 — Subtract to get actual increase
        Actual = increase() - Imaginary
               = 186.66 - 46.66
               = 140 ✅

Summary

Value Meaning
186.66 What increase([20s]) returned
46.66 Imaginary requests Prometheus extrapolated
140 Requests you actually sent
5s The gap = your scrape interval
💡 Golden Rule

increase() and rate() are estimates, not exact counts. The extrapolation error is proportional to your scrape interval. Use longer windows to reduce the relative error. 

Shorter window [20s] + scrape 5s  → error can be ~33%
Longer  window [5m]  + scrape 5s  → error is only ~1.6%
