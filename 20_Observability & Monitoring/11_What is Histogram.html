WHAT IS A HISTOGRAM?

UNDERSTANDING DISTRIBUTIONS, BUCKETS & PERCENTILES

WHAT IS A HISTOGRAM?

A histogram is a graph that shows how data is distributed across ranges (called bins or buckets).

In Observability (O11y)

A Histogram is a metric type that samples observations (like request durations or response sizes) and counts them in configurable buckets. It gives you visibility into the distribution of your data — not just averages.

The Marble Analogy

Think of sorting marbles into buckets by size:

42
Small
35
Medium
15
Large
8
X-Large

You see not just the average marble size, but how many are small, medium, or large.

THE AVERAGE TRAP

Imagine you have 100 API requests:

  • 99 requests complete in 10ms (fast ✅)
  • 1 request takes 10,000ms (slow ❌)
Average = (99 × 10ms + 10,000ms) / 100 = 109ms
The Problem

The average says 109ms — which sounds slow. But 99% of users had a 10ms experience. The one slow request is hiding in the average, making everything look worse than it is.

What Histograms Show You Instead

Average

  • Single number: 109ms
  • Hides outliers
  • Misleading picture
  • Can't detect tail latency

Histogram

  • p50: 10ms (typical user)
  • p95: 10ms (95% of users)
  • p99: 10ms (99% of users)
  • p99.9: 10,000ms (outlier exposed!)

BUCKETS EXPLAINED

// Buckets in seconds
const buckets = [0.01, 0.05, 0.1, 0.5, 1, 2, 5];
//               10ms  50ms 100ms 500ms  1s  2s  5s

How a Request Gets Counted

When a request takes 0.25 seconds (250ms):

0.01s
✗ 250ms > 10ms — not counted
0.05s
✗ 250ms > 50ms — not counted
0.1s
✗ 250ms > 100ms — not counted
0.5s
✓ 250ms ≤ 500ms — counted +1
1s
✓ 250ms ≤ 1s — counted +1
2s
✓ 250ms ≤ 2s — counted +1
5s
✓ 250ms ≤ 5s — counted +1

A 250ms request increments all buckets ≥ 250ms. This is what makes it a cumulative histogram.

CUMULATIVE COUNTING

After 1000 requests, your bucket counts might look like this:

http_request_duration_seconds_bucket{le="0.01"}  = 200   # 200 requests under 10ms
http_request_duration_seconds_bucket{le="0.05"}  = 550   # 550 requests under 50ms
http_request_duration_seconds_bucket{le="0.1"}   = 800   # 800 requests under 100ms
http_request_duration_seconds_bucket{le="0.5"}   = 950   # 950 requests under 500ms
http_request_duration_seconds_bucket{le="1"}     = 980   # 980 requests under 1s
http_request_duration_seconds_bucket{le="2"}     = 995   # 995 requests under 2s
http_request_duration_seconds_bucket{le="5"}     = 999   # 999 requests under 5s
http_request_duration_seconds_bucket{le="+Inf"}  = 1000  # all 1000 requests
http_request_duration_seconds_sum               = 234.5  # total seconds
http_request_duration_seconds_count            = 1000    # total requests
Reading the Data
  • 800 out of 1000 requests finished under 100ms → 80% fast
  • 950 out of 1000 finished under 500ms → 95% acceptable
  • 5 requests took longer than 2s → tail latency problem

PERCENTILES (p95, p99)

Percentiles tell you: "X% of requests completed within this time."

Percentile Meaning Who It Represents
p50 (median) 50% of requests are faster than this The typical user
p95 95% of requests are faster than this The slow 5%
p99 99% of requests are faster than this The unlucky 1%
p99.9 99.9% of requests are faster than this Extreme edge cases
Why p99 Matters More Than Average

At 1000 requests/second, your p99 latency affects 10 users every second. Those users are real people having a bad experience — and they're the ones most likely to complain or churn.

CODE EXAMPLE (ES6)

import express from 'express';
import client from 'prom-client';

const app = express();
const register = new client.Registry();
client.collectDefaultMetrics({ register });

// ─── Define the Histogram ──────────────────────────────────────
const httpRequestDuration = new client.Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration in seconds',
  labelNames: ['method', 'route', 'status_code'],
  buckets: [0.01, 0.05, 0.1, 0.5, 1, 2, 5]  // 10ms → 5s
});

register.registerMetric(httpRequestDuration);

// ─── Middleware to measure every request ──────────────────────
app.use((req, res, next) => {
  const end = httpRequestDuration.startTimer();

  res.on('finish', () => {
    end({
      method: req.method,
      route: req.route ? req.route.path : req.path,
      status_code: res.statusCode
    });
  });

  next();
});

// ─── Routes ───────────────────────────────────────────────────
app.get('/', (req, res) => res.json({ message: 'Hello!' }));

app.get('/slow', (req, res) => {
  setTimeout(() => res.json({ message: 'slow response' }), 2000);
});

// ─── /metrics endpoint ────────────────────────────────────────
app.get('/metrics', async (req, res) => {
  res.set('Content-Type', register.contentType);
  res.end(await register.metrics());
});

app.listen(3000, () => console.log('Server on http://localhost:3000'));

CODE WALKTHROUGH — LINE BY LINE

Step 1: Create the Histogram

const httpRequestDuration = new client.Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration in seconds',
  labelNames: ['method', 'route', 'status_code'],
  buckets: [0.01, 0.05, 0.1, 0.5, 1, 2, 5]
});
  • name — the metric name Prometheus will store. Convention: snake_case ending with the unit (_seconds)
  • help — description shown in /metrics output as a # HELP comment
  • labelNames — dimensions you can filter by in PromQL (method, route, status)
  • buckets — the time boundaries in seconds. Each value is an upper limit (le = "less than or equal")

Step 2: The Middleware

app.use((req, res, next) => {
  const end = httpRequestDuration.startTimer(); // ← starts a stopwatch

  res.on('finish', () => {   // ← fires when response is fully sent
    end({
      method: req.method,                          // GET, POST, etc.
      route: req.route ? req.route.path : req.path, // /api/users
      status_code: res.statusCode                  // 200, 404, 500
    });
  });

  next();
});
How startTimer() Works
  • startTimer() records the current time and returns an end() function
  • When end(labels) is called, it calculates Date.now() - startTime in seconds
  • That duration is then placed into the correct bucket automatically
  • res.on('finish') ensures we measure the full response time, not just when the handler runs

Step 3: The /slow Route (for testing)

app.get('/slow', (req, res) => {
  setTimeout(() => res.json({ message: 'slow response' }), 2000);
});

This route deliberately waits 2 seconds before responding. When you hit it, the histogram will record a ~2s observation, which lands in the le="2" and le="5" buckets — making it easy to see tail latency in Prometheus.

Step 4: The /metrics Endpoint

app.get('/metrics', async (req, res) => {
  res.set('Content-Type', register.contentType); // tells browser it's plain text
  res.end(await register.metrics());             // dumps all metric values
});

Prometheus scrapes this endpoint every 15 seconds (by default). Every time it scrapes, it reads the current bucket counts and stores them as a time-series data point.

CHECKING METRICS IN PROMETHEUS UI (localhost:9090)

Once your app is running and Prometheus is scraping it, open http://localhost:9090 in your browser.

Step 1: Generate Traffic First

Hit your routes a few times so there's data to see:

# Fast requests
curl http://localhost:3000/
curl http://localhost:3000/
curl http://localhost:3000/

# Slow request (2 seconds)
curl http://localhost:3000/slow

Step 2: Explore the Raw Metric

In the Prometheus UI search bar, type:

http_request_duration_seconds_bucket
What You'll See

A table of every bucket for every label combination. For example: 

http_request_duration_seconds_bucket{instance="localhost:3000", le="0.01",  method="GET", route="/",     status_code="200"} 3
http_request_duration_seconds_bucket{instance="localhost:3000", le="0.05",  method="GET", route="/",     status_code="200"} 3
http_request_duration_seconds_bucket{instance="localhost:3000", le="0.1",   method="GET", route="/",     status_code="200"} 3
http_request_duration_seconds_bucket{instance="localhost:3000", le="0.5",   method="GET", route="/",     status_code="200"} 3
http_request_duration_seconds_bucket{instance="localhost:3000", le="+Inf",  method="GET", route="/",     status_code="200"} 3
http_request_duration_seconds_bucket{instance="localhost:3000", le="1",     method="GET", route="/slow", status_code="200"} 0
http_request_duration_seconds_bucket{instance="localhost:3000", le="2",     method="GET", route="/slow", status_code="200"} 1
http_request_duration_seconds_bucket{instance="localhost:3000", le="+Inf",  method="GET", route="/slow", status_code="200"} 1

The / route: all 3 requests landed in the le="0.01" bucket (under 10ms). The /slow route: 0 in le="1" but 1 in le="2" — confirming it took ~2 seconds.

Step 3: Check the _sum and _count

http_request_duration_seconds_sum
http_request_duration_seconds_count
What These Mean
  • _count — total number of requests observed (same as a Counter)
  • _sum — total seconds spent across all requests combined
  • Dividing _sum / _count gives you the average (but use percentiles instead!)

Step 4: Query p95 Latency

This is the most useful query. Paste it into the Prometheus search bar: 

histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[1m]))
Reading the Result

If the result is 0.0082 — that means 95% of your requests completed in under 8.2ms. If you then hit /slow and re-run, you'll see the p95 jump to ~2s.

Switch to the Graph tab in Prometheus UI to see this change over time as a line chart.

Step 5: Filter by Route

Narrow down to a specific endpoint:

histogram_quantile(0.99,
  rate(http_request_duration_seconds_bucket{route="/slow"}[1m])
)

Common Gotcha

If you see "no data" in Prometheus, it usually means:

  • Your app isn't running or isn't reachable at the configured target
  • Prometheus hasn't scraped yet — wait 15 seconds and refresh
  • You haven't hit any routes yet — generate some traffic first
  • The metric name is wrong — check http://localhost:3000/metrics directly

READING REAL PROMETHEUS OUTPUT

Let's decode this exact output you see in Prometheus:

http_request_duration_seconds_bucket{le="0.5",  method="GET", route="/read", status_code="304"} 0
http_request_duration_seconds_bucket{le="1",    method="GET", route="/read", status_code="304"} 0
http_request_duration_seconds_bucket{le="2.5",  method="GET", route="/read", status_code="304"} 0
http_request_duration_seconds_bucket{le="5",    method="GET", route="/read", status_code="304"} 1
http_request_duration_seconds_bucket{le="10",   method="GET", route="/read", status_code="304"} 1

What is le?

le = "less than or equal"

le is the upper boundary of each bucket. le="5" means: "how many requests took 5 seconds or less?"

⚠️ Are the Values in Seconds or Milliseconds?

The metric name tells you the unit

The metric is called http_request_duration_seconds. So all le values are in SECONDS, not milliseconds.

le valueMeans
le="0.5"500 milliseconds (0.5 seconds)
le="1"1000 milliseconds (1 second)
le="2.5"2500 milliseconds (2.5 seconds)
le="5"5000 milliseconds (5 seconds)
le="10"10000 milliseconds (10 seconds)

Decoding the Values (0, 0, 0, 1, 1)

Now let's read each line one by one:

le="0.5" → 0
0 requests finished in ≤ 500ms
le="1" → 0
0 requests finished in ≤ 1 second
le="2.5" → 0
0 requests finished in ≤ 2.5 seconds
le="5" → 1
✓ 1 request finished in ≤ 5 seconds ← first bucket with a count!
le="10" → 1
✓ 1 request finished in ≤ 10 seconds (same request, cumulative)

What This Tells You

Conclusion

The GET /read request with status 304 took between 2.5 and 5 seconds.

  • It did NOT finish in 0.5s, 1s, or 2.5s (all zeros)
  • It DID finish by 5s (count jumped to 1)
  • The count stays 1 at le="10" — same request, just also fits in the bigger bucket
  • So the actual duration was somewhere in the range 2.5s < duration ≤ 5s

How to Calculate the Exact Range

Histograms don't store the exact duration — they only store which bucket it fell into. To find the range: 

Find the first bucket where count > 0:
  le="5" has count = 1  ← this is the upper bound

Find the previous bucket (still 0):
  le="2.5" has count = 0  ← this is the lower bound

Conclusion: the request took between 2.5s and 5s

In milliseconds: between 2500ms and 5000ms

Why is status_code 304?

HTTP 304 Not Modified

A 304 response means the browser already has a cached version of the resource and the server confirmed it hasn't changed. No body is sent — just the status code. This is normal for static files and GET requests with caching headers.

WHEN TO USE A HISTOGRAM

✅ Use Histogram For

  • HTTP request durations
  • Database query times
  • Response payload sizes
  • Queue wait times
  • Any value with a distribution

❌ Don't Use Histogram For

  • Counting events (use Counter)
  • Current state (use Gauge)
  • Values that don't have a range
  • Low-volume, high-precision needs (use Summary)
💡 Golden Rule

Never alert on average latency. Always alert on p95 or p99. Averages lie — percentiles tell the truth about what your real users are experiencing.
