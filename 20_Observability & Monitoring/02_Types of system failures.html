TYPES OF SYSTEM FAILURES

UNDERSTANDING FAILURE MODES IN PRODUCTION SYSTEMS

1️⃣ COMPLETE FAILURES (HARD FAILURES)

These are the "site is down" scenarios. The service is completely unavailable - maybe the process crashed, the server died, or the network is partitioned.

Example Scenario

A Java process runs out of memory and the OOM killer terminates it. All requests immediately fail with connection refused errors.

Why They're Actually "Good"

They're impossible to ignore. Everyone knows something is wrong, and investigation starts immediately. There's no ambiguity about the system state.

2️⃣ PARTIAL FAILURES (GRAY-ZONE FAILURES)

The system works for some requests but not others. This is common in distributed systems where only specific components fail.

Example Scenario

A microservice's /users endpoint works perfectly, but /orders times out because the order database is having issues. Users can log in but can't see their purchase history.

Detection Challenge

Average response times might still look acceptable because the working endpoints dilute the metrics. You need endpoint-specific monitoring to catch these failures.

3️⃣ PERFORMANCE FAILURES (SLOW BUT ALIVE)

The system is technically functional but operating below acceptable speed thresholds.

Example Scenario

An API that usually responds in 100ms now takes 5 seconds. It's still returning correct data, so monitoring checks (is it up?) pass, but user experience is terrible.

The Trust Erosion Factor

Users won't see error messages, but they'll start questioning reliability. Slow performance often causes more user churn than brief outages. 

Normal:  Request → [100ms] → Response ✓
Degraded: Request → [5000ms] → Response ⚠️
(Still "working" but unusable)

4️⃣ INTERMITTENT FAILURES (HEISENBUGS)

Named after Heisenberg's uncertainty principle - these failures change behavior when observed. They're maddeningly inconsistent.

Example Scenario

A race condition that only occurs when two specific requests hit at exactly the same microsecond. When you add logging to debug it, the timing changes and the bug disappears.

Why They're Hard to Fix

Traditional debugging relies on reproduction. With Heisenbugs, the act of trying to observe them changes the conditions that cause them.

  • Timing-dependent race conditions
  • Concurrency issues that vanish under debugging
  • Load-dependent failures that don't reproduce in test environments

5️⃣ DEGRADATION FAILURES (SLOW DEATH)

The system gradually deteriorates over time, like a slow leak.

Example Scenario

A service that leaks memory slowly. After deployment, it runs fine for 3 days, then response times start creeping up. By day 7, it's unusable and crashes.

The Trap

Engineers might blame the last deployment (from day 3), but the real issue is cumulative behavior. The code was "working" for days after deployment. 

Day 1: Memory 20% | Response 100ms ✓
Day 3: Memory 45% | Response 150ms ⚠️
Day 5: Memory 70% | Response 500ms ⚠️
Day 7: Memory 95% | Response 8000ms ❌ CRASH

6️⃣ DEPENDENCY FAILURES (NOT YOUR FAULT, STILL YOUR PROBLEM)

Your code is perfect, but something your system relies on is failing.

Example Scenario

Your payment service is flawless, but the third-party credit card processor is having an outage. Your users can't complete purchases, and they're tweeting angrily at you, not the processor.

Key Insight

In production, your SLOs (Service Level Objectives) don't care about fault boundaries. If your system depends on it, its failure is your failure.

Common Dependencies

  • Third-party APIs
  • Cloud provider services
  • Database systems
  • Message queues

Mitigation Strategies

  • Circuit breakers
  • Fallback mechanisms
  • Graceful degradation
  • Timeout configurations

7️⃣ CHANGE-INDUCED FAILURES (AFTER DEPLOYMENT)

Failures that appear after a code or configuration change.

Example Scenario

You deploy a new feature that's perfectly tested, but it changes database query patterns. Under real production load, these new queries cause deadlocks that never appeared in staging.

The Tricky Part

The code change might be correct but interacts with production scale/traffic in unexpected ways. Rollback "fixes" it, but you haven't really solved the underlying issue. 

Staging (100 users):  Query takes 50ms ✓
Production (10K users): Query causes deadlock ❌

The code is "correct" but doesn't scale

8️⃣ SILENT FAILURES (THE MOST DANGEROUS)

Failures that don't manifest as errors but corrupt data or degrade functionality invisibly.

Example Scenario

A background job that processes user uploads silently fails to process 5% of images. No errors are thrown, logs look normal, but users slowly notice their images aren't showing up.

The Real Danger

By the time you detect these, the damage (data corruption, user trust loss) has already happened. Prevention through validation and reconciliation is critical.

  • Data corruption: Wrong values written silently
  • Missing data: Records not processed without errors
  • Logic errors: Wrong calculations that pass validation
  • Security issues: Permissions not enforced correctly

THE BIG PICTURE: WHY THIS FRAMEWORK MATTERS

Understanding these categories helps you:

1. Build Better Monitoring

You need different signals for each type:

Failure Type Monitoring Strategy
Complete Failures Uptime checks, health endpoints
Partial Failures Endpoint-specific metrics
Performance Failures Latency percentiles (p95, p99)
Silent Failures Data validation checks, reconciliation
Degradation Resource usage trends over time

2. Debug More Effectively

The failure type guides your investigation approach:

  • Intermittent? Look for concurrency/race conditions
  • Degradation? Check resource usage trends
  • Change-induced? Compare pre/post deployment metrics
  • Dependency? Check external service status

3. Set Realistic Expectations

Production systems are never 100% healthy; they exist on a spectrum of degraded states. Understanding failure modes helps you communicate system health accurately.

4. Design Better Systems

Knowing failure modes helps you build redundancy, circuit breakers, and graceful degradation into your architecture from the start.

💡 The Golden Rule

Every production system will fail. The question is not "if" but "when" and "how." Understanding failure types transforms you from reactive firefighter to proactive system designer.
