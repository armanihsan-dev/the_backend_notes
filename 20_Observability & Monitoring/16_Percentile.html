THE SIMPLE DEFINITION

Definition

A percentile is your position in a sorted list, expressed as a percentage instead of a position number. 

Percentile = (Values below you / Total values) × 100

The Conversion

PositionPercentileMeaning
Position 50p50Taller than 50% of people
Position 75p75Taller than 75% of people
Position 90p90Taller than 90% of people
Position 99p99Taller than 99% of people

WHAT IS LATENCY?

Definition

Latency is the time it takes for a system to respond to a request — measured from the moment the client sends the request to the moment it receives the full response.

The Simple Analogy

You order a pizza. You start the timer when you place the order. You stop the timer when the pizza arrives at your door. That duration is latency.

What Contributes to Latency?

ComponentWhat It IsTypical Cost
Network travelTime for bytes to travel client → server1–50ms
Server processingCPU time to handle the request logic1–500ms
Database queryTime waiting for DB to return data1ms–5s
External API callWaiting for a third-party service10ms–10s
Network returnTime for response bytes to travel back1–50ms
Latency vs Response Time

These terms are often used interchangeably. Strictly speaking, latency is the network delay only, while response time includes processing. In observability, we almost always mean total response time when we say latency.

WHAT IS LATENCY PERCENTILE?

Definition

A latency percentile is the answer to: "What response time is X% of my requests completing within?" It applies the percentile concept directly to response time measurements collected from real requests.

How It Works — Step by Step

Imagine your server handled 10 requests with these response times:

Request #Response TimeSorted Position
req-78ms1 (fastest)
req-212ms2
req-915ms3
req-118ms4
req-522ms5 ← p50
req-335ms6
req-848ms7
req-661ms8
req-489ms9 ← p90
req-10430ms10 ← p99 (slowest)
 
p50 = 22ms   → 50% of requests finished in 22ms or less
p90 = 89ms   → 90% of requests finished in 89ms or less
p99 = 430ms  → 99% of requests finished in 430ms or less
The Key Insight

p99 = 430ms does not mean most users wait 430ms. It means 1 in 100 users waits that long. The other 99 users got their response in 89ms or less. Latency percentiles let you see both the typical experience and the worst-case experience at the same time.

✅ Small Gap — Healthy

p50 =  20ms
p99 =  80ms
gap = 60ms

Consistent performance. Even your slowest users have a good experience.

❌ Large Gap — Investigate

p50 =   20ms
p99 = 4500ms
gap = 4480ms

High variance. Something is causing occasional massive slowdowns — DB timeouts, GC pauses, cold starts.

LATENCY SLOs — SETTING TARGETS

A Service Level Objective (SLO) is a target you set for your latency percentiles. It defines what "good enough" looks like for your users.

Example SLO

"99% of requests must complete within 500ms"

This means your p99 latency must stay at or below 500ms. If it exceeds 500ms, your SLO is breached and an alert should fire.

Common Latency SLO Targets by Service Type

Service Typep50 Targetp95 Targetp99 Target

REST API (with DB)< 100ms< 500ms< 1000ms

The PromQL SLO Check

# Alert if p99 latency exceeds 500ms
histogram_quantile(
  0.99,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le)
) > 0.5
Why p99 and Not p100?

p100 (the maximum) is almost useless for SLOs — a single network hiccup or server restart can spike it to 30 seconds. p99 gives you a statistically stable view of your worst-case experience without being thrown off by one-off outliers.

HOW PROMETHEUS CALCULATES PERCENTILES

Prometheus doesn't store every individual request. Instead it stores counts in pre-defined buckets — each bucket counts how many requests completed within that threshold.

The Histogram Buckets

Bucket (le=)Count of RequestsMeaning
le="0.01" (10ms)9090 requests finished in ≤10ms
le="0.05" (50ms)9595 requests finished in ≤50ms
le="0.1" (100ms)9898 requests finished in ≤100ms
le="0.5" (500ms)9999 requests finished in ≤500ms
le="1" (1000ms)100100 requests finished in ≤1000ms

Finding p95 From Buckets

Total requests = 100
95% of 100    = 95th request

Find the bucket that first contains 95 requests:
  le="0.01" → 90  (not enough)
  le="0.05" → 95  ✅ found it!

Therefore: p95 ≈ 50ms
Meaning: 95% of requests completed within 50ms.
What le Means

le stands for "less than or equal". Each bucket is cumulative — le="0.05" contains all requests that took 50ms or less, not just exactly 50ms.

PROMQL EXAMPLES

Example 1 — p95 for All Requests

histogram_quantile(
  0.95,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le)
)
→ 0.25  (95% of requests complete within 250ms)

Example 2 — p99 Per Route

histogram_quantile(
  0.99,
  sum by (path, le) (rate(http_request_duration_seconds_bucket[5m]))
)
{path="/"}      → 0.1   (100ms p99 — healthy)
{path="/fancy"} → 0.5   (500ms p99 — acceptable)
{path="/users"} → 2.0   (2000ms p99 — SLOW! investigate)

Example 3 — Check if p99 Meets Your SLO

histogram_quantile(
  0.99,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le)
) <= 0.5
1 = True  → p99 ≤ 500ms  ✅ SLO met
0 = False → p99 > 500ms  ❌ ALERT!

SUMMARY

A percentile tells you the value below which a certain percentage of your data falls.

Why Not Just Use Averages?

Averages hide slow requests. A single 10-second request drowned in thousands of 10ms requests will barely move your average — but that user just had a terrible experience. Percentiles reveal what averages conceal.
