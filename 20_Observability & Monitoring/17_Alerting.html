PROMETHEUS ALERTING RULES & ALERTMANAGER — FROM ZERO TO HERO

WHAT ARE THESE COMPONENTS?

Prometheus Alert Rules

Conditions you define using PromQL that tell Prometheus when to trigger an alert. For example: "Alert if the server has been down for 5 minutes" or "Alert if CPU usage exceeds 80%."

Alertmanager

A separate service that handles alerts sent by Prometheus. It manages:

  • Deduplication — removing duplicate alerts
  • Grouping — bundling similar alerts together
  • Routing — sending to Slack, email, webhooks
  • Silencing — muting alerts during maintenance
Webhooks

HTTP POST requests that Alertmanager sends to a URL you specify. Your application (e.g. your Express.js app) receives these POST requests and can take action — sending notifications, logging, or triggering automated responses.

STEP 1 — CONFIGURE PROMETHEUS

Your prometheus.yml needs three key sections for alerting:

global:
  scrape_interval: 15s
  evaluation_interval: 10s  # How often Prometheus checks alert conditions

# Tell Prometheus where Alertmanager is running
alerting:
  alertmanagers:
    - static_configs:
        - targets:
            - 'localhost:9093'  # Default Alertmanager port

# List of files containing your alert rules
rule_files:
  - 'alert_rules.yml'

scrape_configs:
  - job_name: 'my-express-app'
    static_configs:
      - targets: ['localhost:4000']

Key Fields Explained

FieldWhat It Does
evaluation_intervalHow often Prometheus checks if alert conditions are met
alerting.alertmanagersThe Alertmanager endpoint(s) Prometheus sends fired alerts to
rule_filesYAML files containing your alert rule definitions

STEP 2 — CREATE ALERT RULES

Create a file called alert_rules.yml:

groups:
  - name: http_alerts
    rules:

      # Alert when /fail endpoint returns 500 errors too often
      - alert: HighFailureRate
        expr: rate(http_requests_total{status_code="500"}[1m]) > 0
        for: 1m
        labels:
          severity: critical
          service: express-app
        annotations:
          summary: "High failure rate on {{ $labels.instance }}"
          description: "Failure rate is {{ humanize $value }} errors per second"

      # Alert when your Express app is down
      - alert: ExpressAppDown
        expr: up{job="my-express-app"} == 0
        for: 30s
        labels:
          severity: critical
        annotations:
          summary: "Express app is down"
          description: "The app on {{ $labels.instance }} has been down for 30s"

      # Alert when /fail endpoint gets too many requests
      - alert: TooManyFailures
        expr: rate(http_requests_total{path="/fail"}[2m]) > 5
        for: 10s
        labels:
          severity: warning
        annotations:
          summary: "High request rate to /fail endpoint"
          description: "{{ $labels.path }} is receiving {{ humanize $value }} req/s"

Rule Components Explained

FieldRequiredWhat It Does
alert✅ YesName of the alert — appears in Alertmanager UI
expr✅ YesPromQL expression — alert fires when this returns a value
forOptionalCondition must stay true for this duration before firing
labelsOptionalKey-value pairs for categorization and routing
annotationsOptionalHuman-readable info shown in notifications
The for: Duration

Without for, a single bad data point fires the alert immediately — causing noisy false positives. With for: 1m, the condition must stay true for a full minute before Prometheus considers it a real problem. 

expr fires  →  PENDING state  →  (for: 1m passes)  →  FIRING state
                                        ↑
                              if condition clears here, alert is cancelled

Alert States

StateMeaning
PENDINGCondition is true but for duration hasn't elapsed yet
FIRINGCondition has been true for the full for duration — alert sent to Alertmanager
RESOLVEDCondition is no longer true — Alertmanager sends a resolve notification

STEP 3 — CONFIGURE ALERTMANAGER

Create alertmanager.yml:

global:
  resolve_timeout: 5m  # How long to wait before marking an alert as resolved

route:
  receiver: 'webhook_receiver'
  group_by: ['alertname', 'severity']  # Group alerts with same name + severity
  group_wait: 10s        # Wait before sending initial notification (allows batching)
  group_interval: 5m     # Wait before sending updated notifications
  repeat_interval: 4h    # Re-send the same alert if still firing after 4h

  # Route critical alerts to the same receiver (can add more routes here)
  routes:
    - match:
        severity: critical
      receiver: 'webhook_receiver'
      continue: true

receivers:
  - name: 'webhook_receiver'
    webhook_configs:
      - url: 'http://localhost:4000/alert'
        send_resolved: true  # Also notify when alert resolves

Configuration Fields Explained

FieldWhat It Does
receiverDefault destination for all alerts (webhook, Slack, email)
group_byLabels used to group related alerts into one notification
group_waitInitial delay — lets related alerts batch together before sending
group_intervalHow long to wait before sending updates to an existing group
repeat_intervalHow often to re-notify about a still-firing alert
send_resolvedSend a notification when the alert condition clears
group_wait vs group_interval

group_wait applies to the first notification of a new group. group_interval applies to subsequent updates. Keep group_wait short (10–30s) so you're not waiting too long for the first alert.

STEP 4 — RUN EVERYTHING

Start each component in order:

1. Start Alertmanager

alertmanager --config.file=alertmanager.yml

2. Start Prometheus

prometheus --config.file=prometheus.yml

3. Start Your Express App

node app.js

Nothing Happening?

Check that evaluation_interval in prometheus.yml is set and Prometheus can reach Alertmanager at localhost:9093. Visit localhost:9090/targets to confirm your app is being scraped successfully.

WHAT THE WEBHOOK RECEIVES

When an alert fires, Alertmanager sends a JSON POST request to your /alert endpoint. Here's the full payload structure: 

{
  "version": "4",
  "groupKey": "{}:{alertname=\"HighFailureRate\"}",
  "status": "firing",
  "receiver": "webhook_receiver",
  "groupLabels": {
    "alertname": "HighFailureRate"
  },
  "commonLabels": {
    "alertname": "HighFailureRate",
    "severity": "critical",
    "service": "express-app"
  },
  "commonAnnotations": {
    "summary": "High failure rate on localhost:4000",
    "description": "Failure rate is 0.5 errors per second"
  },
  "alerts": [
    {
      "status": "firing",
      "labels": { "alertname": "HighFailureRate", "severity": "critical" },
      "annotations": { "summary": "High failure rate on localhost:4000" },
      "startsAt": "2024-01-01T10:00:00Z",
      "endsAt": "0001-01-01T00:00:00Z"
    }
  ]
}

Payload Fields Explained

FieldWhat It Contains
status"firing" or "resolved"
groupLabelsLabels used to group this batch of alerts
commonLabelsLabels shared by all alerts in this group
commonAnnotationsAnnotations shared by all alerts in this group
alerts[]Array of individual alert objects in this group
alerts[].startsAtWhen the alert started firing
alerts[].endsAt0001-... means still firing; real time means resolved
💡 Golden Rule

The full alerting pipeline in one line:

PromQL condition fires
  → Prometheus waits for `for:` duration
    → Alert sent to Alertmanager
      → Alertmanager groups + waits `group_wait`
        → Webhook POST sent to your app
          → Your app handles it (Slack, log, ticket)
