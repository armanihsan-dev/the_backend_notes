GRAFANA ALLOY

SENDING LOGS TO LOKI USING GRAFANA ALLOY — THE COMPLETE GUIDE

WHAT IS GRAFANA ALLOY?

Grafana Alloy is an OpenTelemetry-native telemetry collector. Think of it as a dedicated pipeline agent that sits between your app and your observability backends (Loki, Prometheus, Tempo, etc.) 

Your App → [writes logs] → app.log → [Alloy reads & processes] → Loki
Key Idea

Alloy is the evolution of the older Grafana Agent. It's not just for logs — it collects logs, metrics, and traces all in one place.

PINO-LOKI TRANSPORT VS. GRAFANA ALLOY

❌ pino-loki Transport Approach 

Your App (Node.js)
    ↓
pino logger
    ↓
pino-loki transport  ← app does extra work
    ↓
Loki

✅ Grafana Alloy Approach 

Your App (Node.js)
    ↓
pino logger
    ↓
app.log (file on disk)  ← app just writes
    ↓
Alloy (separate process)  ← heavy lifting
    ↓
Loki

Problems with pino-loki Transport

  • Your Node.js process handles formatting logs AND shipping them to Loki
  • If Loki is down, your app might slow down or lose logs
  • If your app crashes, buffered logs in memory are lost forever
  • Hard to change log destination without redeploying your app
  • Every service in your stack needs its own transport configured

Benefits of Grafana Alloy

  • App and log shipping are completely decoupled
  • If Loki goes down, Alloy buffers and retries — zero log loss
  • If your app crashes, logs are already safely on disk
  • Change log destination without touching or redeploying your app
  • One Alloy instance can collect logs from multiple apps at once
  • Alloy also collects metrics and traces — single agent for everything
Separation of Concerns

Your app shouldn't care about where logs go. Alloy enforces this principle — your app writes to a file, and Alloy handles the rest.

WHAT IS A "COMPONENT" IN ALLOY CONFIG?

This is the most important concept. In Alloy, everything is a component. A component is a named, reusable building block with:

  • A type — what it does
  • A name — your label for it
  • inputs — arguments/config
  • outputs — receivers it can forward data to

The syntax is always:

component_type "name" {
  // config
}

Looking at the config, there are 3 components:

Component Type Job
loki.source.file "app_log" Source Tails a log file and forwards lines downstream
loki.process "pino_pipeline" Processor Transforms raw log lines through multiple stages
loki.write "local_loki" Writer Pushes processed logs to Loki's HTTP API

Component 1 — loki.source.file "app_log"

loki.source.file "app_log" {
  targets    = [{ __path__ = "...app.log", app = "express-app" }]
  forward_to = [loki.process.pino_pipeline.receiver]
}
  • Type: loki.source.file — knows how to tail a log file (like tail -f)
  • Name: "app_log" — your label, could be anything
  • Job: watches the file, reads new lines, forwards them downstream
  • forward_to — this is how components are wired together

Component 2 — loki.process "pino_pipeline"

loki.process "pino_pipeline" {
  stage.json      { ... }   // parse JSON
  stage.timestamp { ... }   // extract timestamp
  stage.template  { ... }   // convert numeric level → text
  stage.labels    { ... }   // attach labels
  stage.label_drop{ ... }   // remove unwanted labels
  forward_to = [loki.write.local_loki.receiver]
}
  • Type: loki.process — a processing pipeline
  • Name: "pino_pipeline"
  • Job: transforms raw log lines through multiple stages before sending
  • Each stage.* is a mini-step inside the pipeline

Why Processing is Needed

Your raw pino log looks like this:

{"level":30,"time":1781089708733,"msg":"Incoming request"}

Loki doesn't understand "level":30. The pipeline converts it so Loki gets:

label: level=info
timestamp: 2025-01-01T...  (converted from UnixMs)

Component 3 — loki.write "local_loki"

loki.write "local_loki" {
  endpoint {
    url = "http://localhost:3100/loki/api/v1/push"
  }
}
  • Type: loki.write — knows how to push logs to Loki's HTTP API
  • Name: "local_loki"
  • Job: takes processed log entries and sends them to Loki

HOW COMPONENTS ARE WIRED TOGETHER

Components talk to each other via receivers. The pattern component_type.name.receiver is how you reference another component's input. 

loki.source.file "app_log"
        │
        │  forward_to = [loki.process.pino_pipeline.receiver]
        ▼
loki.process "pino_pipeline"
        │
        │  forward_to = [loki.write.local_loki.receiver]
        ▼
loki.write "local_loki"
        │
        ▼
      Loki

So loki.process.pino_pipeline.receiver means:

  • component type: loki.process
  • name: pino_pipeline
  • .receiver = its input endpoint
Visual Graph UI

This is why the Alloy UI at http://localhost:12345 shows a visual graph — the config literally describes a data flow graph between components. Think of it like connecting lego blocks.

COMPLETE GRAFANA ALLOY CONFIG

// Read log lines from a specific file on disk.
loki.source.file "app_log" {
  targets = [
    {
      __path__ = "F:/learningsWebDevelopment/Node.js/section_21 O11y/07_Sending express logs to loki/logs/app.log",
      app      = "express-app",
    },
  ]

  tail_from_end = false
  forward_to    = [loki.process.pino_pipeline.receiver]
}

// Process each log line before sending it to Loki.
loki.process "pino_pipeline" {
  stage.json {
    expressions = {
      level = "",
      time  = "",
    }
  }

  stage.timestamp {
    source = "time"
    format = "UnixMs"
  }

  stage.template {
    source   = "level"
    template = "{{ if eq .Value \"10\" }}trace{{ else if eq .Value \"20\" }}debug{{ else if eq .Value \"30\" }}info{{ else if eq .Value \"40\" }}warn{{ else if eq .Value \"50\" }}error{{ else if eq .Value \"60\" }}fatal{{ else }}unknown{{ end }}"
  }

  stage.labels {
    values = {
      level = "",
    }
  }

  stage.label_drop {
    values = ["filename"]
  }

  forward_to = [loki.write.local_loki.receiver]
}

// Send the final processed logs to Loki.
loki.write "local_loki" {
  endpoint {
    url = "http://localhost:3100/loki/api/v1/push"
  }
}

// Alloy's own internal logging.
logging {
  level  = "debug"
  format = "logfmt"
}
