MONKEY PATCHING

COMPLETE GUIDE — DEFINITION, SYNTAX, EXAMPLES, AND REAL-WORLD USE CASES

PART 1: WHAT IS MONKEY PATCHING?

Monkey patching is the technique of dynamically modifying or replacing properties, methods, or behavior of an existing object, class, or module at runtime — without changing the original source code.

Simple Definition

You take something that already exists — an object, a class, a built-in function — and you swap out or wrap one of its parts while the program is running, without touching the original file or library.

Real-World Analogy

Imagine a coffee machine that brews plain coffee. Monkey patching is like taping a new button on the side that secretly intercepts the "brew" press, adds a shot of espresso, then lets the original brew happen — all without opening the machine or reading its manual. 

Original machine:  brew() → plain coffee
After patching:    brew() → [add espresso] → plain coffee → espresso coffee

HOW IT WORKS IN JAVASCRIPT

JavaScript objects are just collections of key-value pairs. Properties (including methods) can be reassigned at any time. Monkey patching exploits this — you simply overwrite a property with your own function. 

// Original object
const obj = {
    greet() {
        return 'Hello';
    }
};

console.log(obj.greet()); // "Hello"

// Monkey patch — replace the method
obj.greet = function () {
    return 'Hello, World!';
};

console.log(obj.greet()); // "Hello, World!"

The original greet function is gone — replaced entirely. This is the simplest form of monkey patching.

SYNTAX EXPLAINED

There are three common syntactic patterns. Each does something slightly different.

Pattern 1: Simple Replacement

Completely replaces the original method. The old behavior is lost.

target.methodName = function (...args) {
    // your new implementation
};

Pattern 2: Wrap & Call Original (Most Common)

Saves a reference to the original, runs your code before/after, then calls the original. The old behavior is preserved. 

const original = target.methodName;           // 1. save the original

target.methodName = function (...args) {      // 2. replace with wrapper
    // --- your code BEFORE ---
    console.log('called with', args);

    const result = original.apply(this, args); // 3. call the original

    // --- your code AFTER ---
    console.log('returned', result);

    return result;                             // 4. return the original result
};
Part What it does
original Holds a reference to the function being replaced so it isn't lost
...args Captures all arguments so they can be passed to the original unchanged
original.apply(this, args) Calls the original with the correct this context and arguments
return result Ensures callers still get the original return value

Pattern 3: Using a Proxy (Modern)

ES6 Proxy wraps an entire object and intercepts any operation on it — cleaner and more powerful than manual patching. 

const proxy = new Proxy(target, {
    get(obj, prop) {
        const value = obj[prop];
        if (typeof value === 'function') {
            return function (...args) {
                console.log(`${prop} called`);
                return value.apply(obj, args);
            };
        }
        return value;
    }
});

PART 2: EXAMPLES

Example 1 — Patching a Plain Object

Add logging to a single method on an existing object.

const calculator = {
    add(a, b) {
        return a + b;
    }
};

// Monkey patch: wrap add() with logging
const _originalAdd = calculator.add;

calculator.add = function (a, b) {
    console.log(`add called with: ${a}, ${b}`);
    const result = _originalAdd.apply(this, [a, b]);
    console.log(`add returned: ${result}`);
    return result;
};

calculator.add(2, 3);
// add called with: 2, 3
// add returned: 5

Example 2 — Patching a Class Prototype

Patching the prototype affects all instances of the class — past, present, and future. 

class User {
    constructor(name) {
        this.name = name;
    }

    greet() {
        return `Hi, I'm ${this.name}`;
    }
}

// Patch the prototype — affects ALL instances
const _originalGreet = User.prototype.greet;

User.prototype.greet = function () {
    const result = _originalGreet.call(this);
    return result + ' 👋';
};

const alice = new User('Alice');
const bob   = new User('Bob');

console.log(alice.greet()); // "Hi, I'm Alice 👋"
console.log(bob.greet());   // "Hi, I'm Bob 👋"
Important

Prototype patches affect every instance of that class, including instances created in third-party libraries you don't control. Use with care.

Example 3 — Patching a Built-in (console.log)

A classic example: intercepting console.log to add timestamps or send logs somewhere else. 

const _originalLog = console.log;

console.log = function (...args) {
    const timestamp = new Date().toISOString();
    _originalLog.apply(console, [`[${timestamp}]`, ...args]);
};

console.log('Server started');
// [2025-01-15T10:30:00.000Z] Server started

console.log('User logged in', { id: 42 });
// [2025-01-15T10:30:01.000Z] User logged in { id: 42 }

Example 4 — Patching a Node.js Module

In Node.js, require() returns a cached module object. You can patch its exports just like any other object. 

// fs-patch.js — patch fs.readFile to add logging
const fs = require('fs');

const _originalReadFile = fs.readFile;

fs.readFile = function (path, options, callback) {
    console.log(`[fs] Reading file: ${path}`);

    const start = Date.now();

    // Handle optional `options` argument
    const done = typeof options === 'function' ? options : callback;

    _originalReadFile.call(fs, path, options, function (err, data) {
        console.log(`[fs] Read ${path} in ${Date.now() - start}ms`);
        done(err, data);
    });
};

// Now any code that uses fs.readFile gets automatic logging
const fs2 = require('fs'); // same cached instance — already patched!
fs2.readFile('./data.txt', 'utf8', (err, data) => {
    console.log(data);
});
// [fs] Reading file: ./data.txt
// [fs] Read ./data.txt in 3ms
// (file contents)
Why This Works in Node.js

Node.js caches modules after the first require(). Every subsequent require('fs') returns the same object, so patching it once affects all consumers automatically.

Example 5 — The Safe Wrap Helper (Reusable Pattern)

Instead of repeating the save-original + replace dance everywhere, extract it into a reusable helper. 

// A generic wrap utility
function wrap(obj, methodName, wrapper) {
    const original = obj[methodName];
    obj[methodName] = function (...args) {
        return wrapper(original.bind(this), ...args);
    };
}

// Usage — wrap fetch to add timing
wrap(globalThis, 'fetch', async function (original, ...args) {
    const start = Date.now();
    console.log(`[fetch] → ${args[0]}`);

    const response = await original(...args);

    console.log(`[fetch] ← ${args[0]} (${Date.now() - start}ms) ${response.status}`);
    return response;
});

// All calls to fetch() now have automatic timing logs
fetch('https://api.example.com/users');
// [fetch] → https://api.example.com/users
// [fetch] ← https://api.example.com/users (120ms) 200

PART 3: MONKEY PATCHING IN OBSERVABILITY

This is the most important real-world use case in the context of this course. Auto-instrumentation in OpenTelemetry works entirely via monkey patching. 

You write:
  import { NodeSDK } from '@opentelemetry/sdk-node';
  new NodeSDK({ instrumentations: [new HttpInstrumentation()] }).start();

What OpenTelemetry actually does internally:
  const _original = http.request;

  http.request = function (...args) {
      const span = tracer.startSpan('HTTP GET');       // start a span
      const result = _original.apply(this, args);      // call original
      result.on('response', (res) => {
          span.setAttribute('http.status_code', res.statusCode);
          span.end();                                   // end the span
      });
      return result;
  };

You never wrote that code — OpenTelemetry's instrumentation library patched http.request for you at startup. Every HTTP call your app makes is now automatically traced.

What Gets Patched by Auto-Instrumentation

Library What is patched What you get
http / https http.request Span for every outgoing HTTP call
express Router middleware chain Span for every incoming route handler
pg (PostgreSQL) Client.prototype.query Span for every SQL query with statement text
mongoose Model method prototypes Span for every DB operation
redis Command send internals Span for every cache get/set

MONKEY PATCHING IN TESTING

Testing libraries use monkey patching to replace real dependencies (like HTTP calls or database connections) with controlled fakes. 

// production code
import { sendEmail } from './emailService.js';

export async function registerUser(user) {
    await db.save(user);
    await sendEmail(user.email, 'Welcome!');
    return { success: true };
}

// test — monkey patch sendEmail so no real email is sent
import * as emailService from './emailService.js';

test('registerUser sends a welcome email', async () => {
    let sentTo = null;

    // Patch sendEmail with a spy
    const _original = emailService.sendEmail;
    emailService.sendEmail = async (to, subject) => {
        sentTo = to; // capture the call
    };

    await registerUser({ email: 'user@example.com' });

    console.assert(sentTo === 'user@example.com', 'Email was not sent');

    emailService.sendEmail = _original; // always restore!
});
Always Restore

When patching for tests, always restore the original after the test runs. Leaving a patch in place leaks state into other tests and causes hard-to-debug failures.

PRELOADING — PATCHING BEFORE YOUR APP STARTS

Preloading is the technique of loading and executing a script before your application's own code runs. In Node.js this is done with the --require (CommonJS) or --import (ESM) CLI flags.

Why It Matters for Monkey Patching

For a monkey patch to intercept every call, it must run before any other module loads. If your patch runs after express or http has already been imported, some code may already hold a direct reference to the original function — and your patch misses it. Preloading solves this by guaranteeing the patch is applied first.

The Problem Without Preloading

// app.js
import http from 'http';                  // ← http loaded here
import './my-patch.js';                   // ← patch runs AFTER

// my-patch.js arrives too late!
// http is already in memory, other modules may already
// hold a reference to the original http.request

The Solution: --require Flag (CommonJS)

The --require flag tells Node.js to execute a file before loading the entry point. Your patch is applied before any application module can run. 

node --require ./patch.js app.js

# With npm scripts in package.json:
# "start": "node --require ./patch.js app.js"

Execution order with --require:

1. Node.js starts
2. patch.js runs  ← patches http.request, pg.query, etc.
3. app.js starts  ← all modules loaded AFTER the patch is in place
4. Every call to http.request is now intercepted ✅

The Solution: --import Flag (ESM)

For ES module projects ("type": "module" in package.json), use --import instead: 

node --import ./patch.js app.js

A Minimal Preload Patch File

// patch.js — loaded via --require before anything else
const http = require('http');

const _original = http.request;

http.request = function (...args) {
    console.log('[patch] http.request intercepted');
    return _original.apply(this, args);
};

console.log('[patch] http.request patched ✅');
# Run your app with the patch preloaded
node --require ./patch.js server.js

# Output:
# [patch] http.request patched ✅
# Server listening on port 3000
# [patch] http.request intercepted   ← fires on every outgoing request

Preloading vs Importing Inside the App

Import inside app.js Preload via --require
When it runs Wherever the import statement sits Before any app code runs
Risk of missing calls Yes — modules loaded before it are unpatched No — guaranteed first
App code change needed Yes No — zero app code change
Use case Simple, single-file patches Instrumentation, global patches

Preloading in OpenTelemetry (The Real-World Example)

This is exactly how OpenTelemetry auto-instrumentation is meant to be used. The SDK must be initialized and all patches applied before your app imports express, http, pg, etc. 

// instrumentation.js — the preload file
import { NodeSDK } from '@opentelemetry/sdk-node';
import { HttpInstrumentation } from '@opentelemetry/instrumentation-http';
import { ExpressInstrumentation } from '@opentelemetry/instrumentation-express';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';

const sdk = new NodeSDK({
    traceExporter: new OTLPTraceExporter({ url: 'http://localhost:4318/v1/traces' }),
    instrumentations: [
        new HttpInstrumentation(),     // patches http.request
        new ExpressInstrumentation(),  // patches express router
    ],
});

sdk.start(); // ← patches are applied RIGHT HERE, before app.js runs
# Run with preload — instrumentation applies before app code
node --import ./instrumentation.js app.js

# Or in package.json:
# "start": "node --import ./instrumentation.js app.js"
Full Flow 
node --import ./instrumentation.js app.js
    │
    ├─ 1. instrumentation.js runs
    │       sdk.start() patches:
    │         http.request        ← wrapped
    │         express router      ← wrapped
    │
    ├─ 2. app.js runs
    │       import express        ← already patched version
    │       import http           ← already patched version
    │
    └─ 3. Every request/response
              automatically creates spans → sent to Tempo via OTLP

PART 4: WHEN TO USE IT

✅ Good Uses

  • Auto-instrumentation (OpenTelemetry)
  • Mocking dependencies in tests
  • Polyfilling missing browser/Node APIs
  • Adding logging/timing to third-party code you can't edit
  • Hot-fixing a library bug while waiting for upstream fix

❌ Bad Uses

  • Patching production code that you could just edit directly
  • Patching built-in prototypes (Array.prototype, Object.prototype)
  • Patching without restoring (leaks state)
  • Using it as a shortcut to avoid refactoring
  • Patching shared singletons in multi-tenant systems

💡 One-Line Summary 
Monkey patching = replacing a function on a live object at runtime,
usually by saving the original and wrapping it with new behavior.

THE GOLDEN RULE:
  Always save the original. Always call it. Always restore in tests.

  const orig = obj.method;
  obj.method = function (...args) {
      // before
      const result = orig.apply(this, args);
      // after
      return result;
  };
