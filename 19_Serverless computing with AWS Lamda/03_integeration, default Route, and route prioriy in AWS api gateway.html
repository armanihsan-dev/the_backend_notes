WHAT IS INTEGRATION IN API GATEWAY?

Integration is the connection between your API Gateway route and the backend service that actually processes the request. It's the bridge that makes your API functional.

Simple Definition

Think of integration as the "what happens next" after API Gateway receives a request. Without integration, your API is just an empty shell that can't do anything useful.

Visual Flow

User calls: https://api.example.com/users/123
                    ↓
          API Gateway (route: /users/{id})
                    ↓
          INTEGRATION (connects to...)
                    ↓
          Your Backend (Lambda, EC2, etc.)
                    ↓
          Returns response to user

TYPES OF INTEGRATIONS

1. Lambda Function (Most Common)

Connects your API directly to AWS Lambda serverless functions.

// When user calls your API, Lambda runs this code
exports.handler = async (event) => {
    const userId = event.pathParameters.id;
    
    // Your business logic here
    const user = await getUserFromDatabase(userId);
    
    return {
        statusCode: 200,
        body: JSON.stringify({ 
            id: userId, 
            name: user.name,
            email: user.email 
        })
    };
};

✅ Best For:

  • Serverless architectures
  • Event-driven applications
  • Pay-per-use pricing model
  • Auto-scaling requirements

2. HTTP Endpoint (Your Express.js on EC2)

Routes requests to an existing HTTP server running on EC2, containers, or on-premises.

API Gateway → http://your-ec2-ip:3000/users/123

Example:
GET /users/123 → http://10.0.1.50:3000/api/users/123

✅ Best For:

  • Existing REST APIs
  • Legacy systems integration
  • Third-party API proxying
  • Microservices on containers

3. AWS Service (Direct Integration)

Directly connects to AWS services like DynamoDB, SQS, SNS without Lambda.

API Gateway → DynamoDB (read/write directly)
API Gateway → SQS (send messages)
API Gateway → S3 (upload/download files)

✅ Best For:

  • Simple CRUD operations
  • Queue message publishing
  • Reducing Lambda costs
  • Low-latency requirements

4. Mock Integration (For Testing)

Returns predefined responses without calling any backend. Perfect for development and testing.

{
  "statusCode": 200,
  "body": {
    "message": "This is a mock response",
    "data": {
      "id": 123,
      "name": "Test User"
    }
  }
}

✅ Best For:

  • Frontend development before backend is ready
  • API documentation examples
  • Testing API Gateway configuration
  • Prototyping

BEFORE VS AFTER INTEGRATION

❌ Without Integration

GET /users/123 
    ↓
API Gateway 
    ↓
??? (Error: 404 or 500)
    ↓
No response or error

Your API route exists but does nothing. Requests fail with errors.

✅ With Integration

GET /users/123 
    ↓
API Gateway 
    ↓
Lambda Function 
    ↓
Database Query
    ↓
Returns User Data

Your API is fully functional and returns actual data.

HOW TO ADD INTEGRATION

Console Steps
  1. Create a route (e.g., GET /users/{id})
  2. Attach integration to that route
  3. Choose integration type:
    • Lambda (for serverless)
    • HTTP (for EC2/Express)
    • AWS Service (for DynamoDB, etc.)
  4. Configure the target (Lambda name, HTTP URL, etc.)
  5. Deploy your API

Why It Matters

Adding integration makes your API actually work. Without it, you just have empty routes. With integration, you connect your frontend to your backend logic and data.

Key Takeaway

Integration is the bridge between your API endpoint and the code/service that does the real work!

WHAT IS A DEFAULT ROUTE?

A default route (also called a catch-all or fallback route) is a route that handles any requests that don't match any of your other defined routes.

Simple Analogy

Regular Routes

Specific departments in a building (Sales, Support, HR)

Default Route

A general receptionist who says "I'll help you" when you don't know which department to ask for

HOW DEFAULT ROUTE WORKS

Visual Example

Incoming Requests:
┌─────────────────┐
│ /users/123      │ ──→ Matches → Users Route
├─────────────────┤
│ /orders/456     │ ──→ Matches → Orders Route
├─────────────────┤
│ /products/789   │ ──→ Matches → Products Route
├─────────────────┤
│ /random/stuff   │ ──→ NO MATCH → DEFAULT ROUTE
└─────────────────┘

❌ Without Default Route

GET /unknown/path
       ↓
API Gateway checks all routes
       ↓
No matching route found
       ↓
Returns 403 Forbidden or 404

✅ With Default Route

GET /unknown/path
       ↓
API Gateway checks all routes
       ↓
No matching route found
       ↓
FALLS BACK TO DEFAULT ROUTE
       ↓
Returns custom response

COMMON DEFAULT ROUTE EXAMPLES

1. Proxy Default Route (Catch-All)

Route: /{proxy+}
Method: ANY
Purpose: Catches EVERYTHING not matched elsewhere

2. 404 Handler Default Route

// Lambda function for default route
exports.handler = async (event) => {
    return {
        statusCode: 404,
        body: JSON.stringify({
            error: "Route not found",
            path: event.rawPath,
            message: "The requested resource does not exist"
        })
    };
};

3. Redirect Default Route

// Redirect to homepage
exports.handler = async (event) => {
    return {
        statusCode: 301,
        headers: {
            Location: "https://example.com"
        }
    };
};

Configuration in AWS Console

Routes:
├── GET /users/*          (specific)
├── POST /orders/*        (specific)
├── GET /products/*       (specific)
└── $default             (default route - catches everything else)

WHY USE A DEFAULT ROUTE?

Reason Explanation
Prevent 403 Errors Without default route, unmatched requests get 403 Forbidden
Better UX Show custom "Not Found" page instead of generic error
Analytics Track how many users hit invalid routes
Future-Proofing Handle new routes gracefully without breaking
Security Log and monitor unexpected requests

When to Use Default Route

✅ Good Use Cases

  • Single Page Applications (SPAs) - serve index.html for all routes
  • API versioning fallback
  • Custom 404 pages
  • Legacy route handling

❌ Avoid When

  • You want strict API contracts
  • Security requires explicit allow-listing
  • You're building a public API that should be predictable

ROUTE PRIORITY IN AWS API GATEWAY

Route priority determines the order in which routing rules are evaluated when a request hits your custom domain. Think of it as a ranking system where rules with higher importance (lower numbers) get checked first.

🎯 How Priority Works

Priority Rules
  • Lower number = Higher priority
  • Priority 1 is evaluated before priority 50
  • Priority 100 is evaluated after priority 50
  • Valid priority range: 1 to 1,000,000
Priority Order:
1 (First) → 10 → 50 → 100 → 500 → 1000000 (Last)

THE EVALUATION FLOW

When a request arrives, API Gateway:

  1. Looks at all routing rules in priority order (lowest to highest)
  2. Checks each rule's conditions (headers, base path, or both)
  3. Stops at the FIRST match - executes that rule's action
  4. If no rules match, falls back to API mappings (depending on routing mode)

📋 Key Rules About Priority

Rule Description
Unique priorities No two rules can have the same priority number
Leave gaps Use 10, 20, 30 instead of 1,2,3 - makes reordering easier
Default/catch-all Use a high number (e.g., 500) for rules with no conditions
First match wins Evaluation stops at first matching rule

💡 REAL-WORLD EXAMPLE

Scenario: API Versioning with A/B Testing

Priority Conditions Action
10 Header: x-version = beta Route to Beta API
20 Header: x-version = v2 Route to V2 API
30 Path starts with /v2/* Route to V2 API
40 Path starts with /v1/* Route to V1 API
500 No conditions (catch-all) Route to V1 API

What Happens:

Request Path Headers Result Why?
#1 /api/users x-version: beta Beta API Priority 10 matches first
#2 /v2/orders (none) V2 API Priority 30 matches
#3 /v1/products (none) V1 API Priority 40 matches
#4 /unknown (none) V1 API Falls to catch-all (500)

🎯 BEST PRACTICES

✅ Do This

  • Leave gaps between priorities (10, 20, 30) - gives room to insert new rules
  • Use high numbers for catch-all rules (500+) - ensures specific rules match first
  • Test in non-production first - priority changes impact live traffic immediately
  • Monitor with logs - Use $context.customDomain.routingRuleIdMatched

❌ Avoid This

  • Using consecutive numbers (1,2,3,4) - hard to reorder
  • Changing priorities in production without testing
  • Having overlapping conditions without clear priority
  • Forgetting to add a catch-all rule

⚠️ Important Notes

Critical Points
  • Evaluation stops at first match - Even if a request matches multiple rules, only the highest priority (lowest number) matching rule executes
  • Conditions must ALL match - If a rule has multiple conditions, they must ALL be true
  • No match = 403 - Without a default/catch-all rule, unmatched requests return 403 Forbidden
  • Changes take effect immediately - Reordering rules instantly affects traffic
