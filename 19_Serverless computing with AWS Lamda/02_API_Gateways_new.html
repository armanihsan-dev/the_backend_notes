API GATEWAY

THE SINGLE ENTRY POINT FOR MICROSERVICES

WHAT IS AN API GATEWAY?

An API Gateway is a server that acts as a single entry point for all client requests in a microservices architecture. It receives all API requests, routes them to the appropriate microservices, and returns the responses to the clients.

Core Concept

The API Gateway is essentially a reverse proxy with additional capabilities like authentication, monitoring, rate limiting, and request transformation. It sits between clients and your backend services, managing all interactions.

SIMPLE ANALOGY

❌ Without API Gateway

You'd need to know exactly which floor/department to visit for each task in a large office building. Clients must know the location and address of every microservice.

✅ With API Gateway

You go to the reception desk, and the receptionist directs you to the right department. Clients only need to know one address - the gateway handles the rest.

KEY FUNCTIONS OF AN API GATEWAY

1. Request Routing

  • Receives all client requests at a single endpoint
  • Determines which microservice should handle each request based on URL path, headers, or other criteria
  • Forwards requests to appropriate services with proper transformation

2. Authentication & Authorization

  • Verifies client identity using JWT tokens, API keys, OAuth, or other mechanisms
  • Checks if client has permission to access specific resources
  • Reduces security burden on individual microservices by centralizing auth logic

3. Rate Limiting

  • Controls how many requests a client can make within a time window
  • Prevents system overload and DDoS attacks
  • Ensures fair usage among all clients with quota management

4. Request/Response Transformation

  • Converts protocols (e.g., HTTP to gRPC, REST to GraphQL)
  • Modifies request/response formats for compatibility
  • Adds/removes headers, query parameters, or body fields

5. Load Balancing

  • Distributes requests across multiple service instances
  • Improves availability and scalability through intelligent routing
  • Handles failover when service instances become unavailable

6. Caching

  • Stores frequent responses in memory or distributed cache
  • Reduces load on backend services significantly
  • Improves response time for cached requests

7. Monitoring & Logging

  • Tracks API usage patterns and metrics
  • Collects performance data (latency, error rates, throughput)
  • Logs requests/responses for debugging and audit trails

Step-by-Step Flow:

① Client Request

  • Mobile app, web browser, or another service sends an HTTP request
  • Example: GET /api/orders/123

② API Gateway Processing

  • Authenticates the request (checks API key/JWT token)
  • Validates request format and parameters
  • Checks rate limits for the client
  • Logs the incoming request

③ Service Discovery

  • Determines which microservice handles order requests
  • Finds available instances of the order service
  • Selects instance based on load balancing algorithm

④ Request Forwarding

  • Transforms request if needed (e.g., adds headers, changes format)
  • Routes to appropriate service instance
  • Example: Forwards to http://order-service:8080/orders/123

⑤ Service Processing

  • Order service processes the request
  • Might call other services (database, payment service, inventory)
  • Returns response to gateway

⑥ Response Aggregation (if needed)

  • Some requests might need data from multiple services
  • Gateway can combine responses into a single response
  • Example: Order details + payment status + shipping info

⑦ Return Response

  • Transforms response format if needed
  • Adds any necessary headers (CORS, caching)
  • Sends back to client

REAL-WORLD EXAMPLE

Let's say you're building an e-commerce application: 

Mobile App ──┐
Web Browser ─┼──► API Gateway ──┬──► User Service (login, profile)
Third Party ─┘                   ├──► Product Service (search, details)
                                 ├──► Order Service (place order, history)
                                 └──► Payment Service (process payment)

Scenario: User Places an Order

Order Flow
  1. App sends request to /api/orders with order details
  2. API Gateway:
    • Authenticates the user (JWT token validation)
    • Checks if user can place orders (authorization)
    • Validates order data format
    • Routes to Order Service
  3. Order Service creates order and may call:
    • Product Service (verify availability)
    • Payment Service (process payment)
    • Inventory Service (update stock)
  4. Response flows back through gateway to app

HOW API GATEWAY KNOWS WHERE TO ROUTE REQUESTS

1. Route Configuration (Most Common)

The gateway maintains a configuration file that maps incoming requests to specific services: 

# Example configuration (like a phonebook)
routes:
  - path: "/api/users/*"
    service: "user-service"
    url: "http://user-service:8080"
    
  - path: "/api/orders/*"
    service: "order-service" 
    url: "http://order-service:8081"
    
  - path: "/api/products/*"
    service: "product-service"
    url: "http://product-service:8082"
Routing Logic

When a request comes in:

  • Request: GET /api/users/123
  • Matches: /api/users/* pattern
  • Routes to: http://user-service:8080/users/123

NODE.JS IMPLEMENTATION EXAMPLE

// gateway.js - Simple Express-based API Gateway
const express = require('express');
const proxy = require('express-http-proxy');
const app = express();

// Route configuration (like a phonebook)
const ROUTES = {
  '/api/users': 'http://localhost:3001',    // User Service
  '/api/orders': 'http://localhost:3002',   // Order Service
  '/api/products': 'http://localhost:3003'  // Product Service
};

// Middleware: Authentication
app.use((req, res, next) => {
  const token = req.headers['authorization'];
  
  if (!token) {
    return res.status(401).json({ error: 'No token provided' });
  }
  
  // Verify token (simplified)
  // In production: use JWT verification
  console.log('✓ Token verified');
  next();
});

// Middleware: Rate Limiting
const rateLimit = require('express-rate-limit');
const limiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 100 // limit each IP to 100 requests per windowMs
});
app.use(limiter);

// Dynamic routing based on path
app.use('/api/:service', (req, res, next) => {
  const basePath = `/api/${req.params.service}`;
  const targetUrl = ROUTES[basePath];
  
  if (targetUrl) {
    console.log(`Routing ${req.method} ${req.url} → ${targetUrl}`);
    
    // Proxy to appropriate service
    return proxy(targetUrl, {
      proxyReqPathResolver: (req) => {
        return req.originalUrl.replace(basePath, '');
      }
    })(req, res, next);
  }
  
  res.status(404).json({ error: 'Service not found' });
});

// Health check endpoint
app.get('/health', (req, res) => {
  res.json({ status: 'healthy', timestamp: new Date() });
});

app.listen(3000, () => {
  console.log('🚀 API Gateway running on port 3000');
  console.log('📋 Available routes:', Object.keys(ROUTES));
});

BENEFITS & CHALLENGES

Benefits

✅ Simplifies Client Code

Clients don't need to know about service architecture, locations, or protocols. Single endpoint for everything.

✅ Centralized Security

Authentication and authorization handled in one place. Easier to audit and maintain security policies.

✅ Cross-Cutting Concerns

Logging, monitoring, rate limiting, and caching handled centrally instead of in each service.

✅ Protocol Translation

Convert between different protocols (REST, gRPC, GraphQL) transparently for clients.

✅ Reduced Round Trips

Can aggregate multiple service responses into one, reducing network overhead.

✅ Service Evolution

Backend services can change without affecting clients. Gateway handles versioning.

Challenges

❌ Single Point of Failure

Must be highly available. Requires redundancy, load balancing, and failover mechanisms.

❌ Potential Bottleneck

Can become performance bottleneck if not properly scaled. Requires careful capacity planning.

❌ Increased Complexity

One more component to manage, monitor, and maintain. Adds operational overhead.

❌ Development Overhead

Must keep routes updated as services change. Configuration management is critical.

WHEN TO USE AN API GATEWAY

Use API Gateway When:
  • You have multiple microservices that need a unified interface
  • You need centralized security/authentication across services
  • You want to simplify client access and hide backend complexity
  • You need API analytics and monitoring in one place
  • You're building for multiple client types (web, mobile, third-party)
  • You need rate limiting and throttling capabilities
  • You want to implement API versioning strategies
Don't Use It When:
  • You have a simple application with just one or two services
  • Your services are not exposed externally (internal only)
  • You need ultra-low latency and can't afford the extra hop
  • Your team lacks experience managing additional infrastructure
