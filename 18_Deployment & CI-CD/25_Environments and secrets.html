ENVIRONMENTS & SECRETS

MASTER CONFIGURATION MANAGEMENT IN CI/CD

WHAT ARE ENVIRONMENTS IN GITHUB? 🌍

Environments in GitHub are deployment targets that represent different stages of your application lifecycle. Think of them as isolated containers where your code runs with specific configurations and protection rules.

Common Environment Examples

  • Development: Where developers test new features
  • Staging: Pre-production environment for final testing
  • Production: Live environment serving real users
Why Use Environments?

Environments allow you to:

  • Store environment-specific variables and secrets
  • Add protection rules (required reviewers, wait timers)
  • Track deployment history for each environment
  • Control who can deploy to specific environments

How Environments Work in Workflows

jobs:
  deploy-to-production:
    environment: production  # References the 'production' environment
    runs-on: ubuntu-latest
    steps:
      - name: Deploy
        run: echo "Deploying to production with environment-specific config"

When you specify an environment in your workflow, GitHub automatically applies that environment's variables, secrets, and protection rules. This ensures safe, controlled deployments across different stages.

1. ENV VARIABLES: WORKFLOW CONFIGURATION

Definition

ENV variables are defined directly in your workflow YAML files. They're like local variables in your code - visible, version-controlled, and easy to modify.

In CI/CD Context

ENV variables control how your pipeline executes. They're like the settings panel for your automation - determining build modes, paths, and runtime behavior.

Basic Usage

name: ENV Variables Demo

env:
  NODE_ENV: production
  BUILD_PATH: ./dist
  CACHE_ENABLED: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Use ENV variables
        run: |
          echo "Environment: ${{ env.NODE_ENV }}"
          echo "Build Path: ${{ env.BUILD_PATH }}"

Common Use Cases

# Multi-stage deployment paths
env:
  DEPLOY_PATH: ${{ 
    github.ref == 'refs/heads/main' && '/var/www/prod' ||
    '/var/www/dev'
  }}

# Build optimization
env:
  BUILD_PARALLEL: "4"
  MEMORY_LIMIT: "4G"

2. VARS VARIABLES: REPOSITORY CONFIGURATION STORE

Definition

VARS variables are non-sensitive configuration values stored in GitHub's UI (not in code). They're like application configuration files that live outside your codebase.

In CI/CD Context

VARS variables define where your code goes and how it connects to external systems. They're like the address book and routing table for your deployments.

How to Set Them Up

Repository VARS:

Settings → Secrets and variables → Actions → Variables → New repository variable

Environment VARS:

Settings → Environments → [Environment Name] → Add Variable

Usage in Workflows

jobs:
  deploy:
    environment: production
    runs-on: ubuntu-latest
    steps:
      - name: Access VARS
        run: |
          echo "API URL: ${{ vars.API_BASE_URL }}"
          echo "Region: ${{ vars.AWS_REGION }}"
          echo "DB Host: ${{ vars.DB_HOST }}"

Real-World Configuration

Repository VARS (Global):

API_BASE_URL = https://api.company.com
CDN_URL = https://cdn.company.com
LOG_LEVEL = INFO
SUPPORT_EMAIL = support@company.com

Environment VARS (Staging):

API_URL = https://staging-api.company.com
DB_HOST = staging-db.company.com
S3_BUCKET = company-staging-assets

Environment VARS (Production):

API_URL = https://api.company.com
DB_HOST = prod-db-cluster.company.com
S3_BUCKET = company-prod-assets

3. SECRETS: THE VAULT OF SENSITIVE DATA

Definition

SECRETS are encrypted variables stored in GitHub's UI for sensitive data. They're never shown in logs and are decrypted only when used in workflows.

In CI/CD Context

SECRETS provide secure authentication and authorization for pipeline operations. They're like the keys, badges, and passwords that allow your pipeline to interact with secured systems.

How to Set Them Up

Repository SECRETS:

Settings → Secrets and variables → Actions → Secrets → New repository secret

Environment SECRETS:

Settings → Environments → [Environment Name] → Add Secret

Usage in Workflows

jobs:
  deploy:
    environment: production
    runs-on: ubuntu-latest
    steps:
      - name: Use Secrets Safely
        env:
          API_KEY: ${{ secrets.API_KEY }}
          DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
        run: |
          # Secrets are masked in logs as ***
          echo "Deploying with credentials..."

Common SECRETS Examples

Repository SECRETS:

  • NPM_TOKEN - For publishing packages
  • DOCKERHUB_TOKEN - For pushing Docker images
  • SONAR_TOKEN - For code quality analysis
  • SLACK_WEBHOOK_URL - For notifications

Environment SECRETS (Production):

  • PROD_DB_PASSWORD - Production database password
  • AWS_ACCESS_KEY_ID - Production AWS access
  • STRIPE_SECRET_KEY - Payment processing
  • JWT_SECRET - Authentication tokens

SETUP GUIDE

Multi-Environment Pipeline Example

name: Multi-Environment Deployment

jobs:
  deploy-staging:
    environment: staging
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to Staging
        env:
          DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
        run: |
          deploy --env=staging \
            --url=${{ vars.API_URL }} \
            --bucket=${{ vars.S3_BUCKET }}
  
  deploy-production:
    environment: production
    needs: deploy-staging
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to Production
        env:
          DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
        run: |
          deploy --env=production \
            --url=${{ vars.API_URL }} \
            --bucket=${{ vars.S3_BUCKET }}

BEST PRACTICES

✅ DO's

# GOOD: Use env context for secrets
- name: Safe Secret Usage
  env:
    API_KEY: ${{ secrets.API_KEY }}
  run: |
    curl -H "Authorization: Bearer $API_KEY" https://api.example.com

# GOOD: Use action inputs
- name: Deploy with Secret
  uses: some-action@v1
  with:
    api-key: ${{ secrets.API_KEY }}

❌ DON'Ts

# BAD: Don't echo secrets directly
- name: Bad Practice
  run: |
    echo "Token is: ${{ secrets.API_KEY }}"
    # Even though masked, avoid exposing in commands

COMPARISON: ENV VS VARS VS SECRETS

Feature ENV VARS SECRETS
Storage YAML file GitHub UI GitHub UI (encrypted)
Visibility Public in repo Hidden from code Encrypted & masked
Version Control Yes (in Git) No No
Use Case Build config URLs, IDs, names Passwords, tokens, keys
Access ${{ env.VAR }} ${{ vars.VAR }} ${{ secrets.VAR }}
Log Masking No No Yes (shows ***)
Environment Specific No Yes Yes
Examples NODE_ENV, BUILD_PATH API_URL, S3_BUCKET DB_PASSWORD, API_KEY

Quick Decision Guide
  • Sensitive data? → Use SECRETS
  • Environment-specific config? → Use VARS
  • Build/workflow settings? → Use ENV
