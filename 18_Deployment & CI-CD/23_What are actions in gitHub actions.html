WHAT ARE ACTIONS? 🤔

Core Definition

Actions are reusable units of code that perform specific tasks within GitHub Actions workflows. Think of them as pre-built functions or plugins that you can drop into your automation pipelines.

Analogy

If GitHub Actions is a restaurant kitchen:

  • Workflows = Recipes (sequence of steps)
  • Jobs = Meal courses (appetizer, main, dessert)
  • Steps = Individual cooking tasks
  • Actions = Pre-made ingredients/sauces (you don't make them from scratch)

KEY CHARACTERISTICS OF ACTIONS

1. Reusability

# Instead of writing this every time:
steps:
  - run: |
      git fetch
      git checkout main
      git pull origin main
      
# You use an action:
steps:
  - uses: actions/checkout@v4  # One line instead of multiple commands

2. Versioned

Actions have version tags (@v2, @v3.1, main) for stability.

3. Shareable

Actions can be:

  • Public (GitHub Marketplace)
  • Private (within your organization)
  • Local (within your repository)

TYPES OF ACTIONS

1. JavaScript Actions

- uses: actions/setup-node@v3  # JavaScript-based
  with:
    node-version: '18'

Structure:

action.yml          # Metadata
index.js            # Main code
package.json        # Dependencies

2. Docker Container Actions

- uses: docker://alpine:latest  # Runs in container
  with:
    entrypoint: /bin/sh
    args: -c "echo Hello"

3. Composite Actions

# Combines multiple steps
- uses: my-org/my-composite-action@v1

MOST COMMON & ESSENTIAL ACTIONS

1. actions/checkout@v4 - The Foundation

Purpose: Check out your repository code onto the runner.

- name: Checkout code
  uses: actions/checkout@v4
  with:
    # Optional parameters:
    fetch-depth: 0          # Get all history
    ref: 'feature-branch'   # Checkout specific branch
    submodules: recursive   # Include submodules
    
# Without this action:
- run: |
    git init
    git remote add origin https://github.com/${{ github.repository }}
    git fetch --all
    git checkout ${{ github.sha }}

Use Case: Every workflow needs this to access your code.

2. actions/setup-node@v3 - Language Setup

Purpose: Set up Node.js with caching.

- name: Setup Node.js
  uses: actions/setup-node@v3
  with:
    node-version: '18.x'    # Specific version
    cache: 'npm'            # Enable npm caching
    cache-dependency-path: '**/package-lock.json'

# What it does automatically:
# 1. Downloads and installs Node.js
# 2. Adds to PATH
# 3. Sets up npm/yarn caching
# 4. Configures registry if needed

Use Case: Node.js projects (React, Vue, Angular, Express, etc.)

3. actions/setup-python@v4 - Python Setup

- name: Setup Python
  uses: actions/setup-python@v4
  with:
    python-version: '3.10'
    cache: 'pip'  # Caches pip packages

4. docker/setup-buildx@v2 - Docker Build

Purpose: Set up Docker Buildx for multi-architecture builds.

- name: Set up Docker Buildx
  uses: docker/setup-buildx@v2
  with:
    driver-opts: |
      image=moby/buildkit:latest
      
# Without this:
# - Install Docker
# - Configure buildx
# - Set up caching
# - Handle QEMU for cross-platform builds

Use Case: Building Docker images for multiple platforms (ARM/AMD).

GITHUB APP VS ACTIONS

Comparison Table

Aspect GitHub Actions GitHub Apps
Location Inside GitHub External servers
Execution Temporary runners Persistent services
Trigger Workflow events Webhooks
Configuration YAML files App settings page
Persistence Ephemeral Long-running
Cost Minutes usage Your infrastructure
Use Case CI/CD, automation Integrations, bots

GitHub Actions:

  • Are: Reusable automation components
  • Live: In .github/workflows/ or Marketplace
  • Run: On GitHub's infrastructure
  • Best for: CI/CD pipelines, automated testing, building

GitHub Apps:

  • Are: External integrations
  • Live: On external servers
  • Run: Continuously as services
  • Best for: Third-party integrations (Netlify, Render, Slack bots)
Netlify/Render Detection

They primarily use GitHub Apps with webhooks, but increasingly support GitHub Actions for more flexible deployment pipelines.

The choice depends on:

  • Complexity needed (simple → App, complex → Actions)
  • Control desired (managed → App, custom → Actions)
  • Existing pipeline (standalone → App, integrated → Actions)

Both approaches coexist because they serve different needs in the GitHub ecosystem!

THE SECRET: GITHUB APPS HANDLE EVERYTHING

When you connect Netlify/Render to GitHub, you're actually installing a GitHub App, not just adding a webhook manually.

2. GitHub Creates the Webhook Automatically

Once you authorize, GitHub's API does this automatically:

// GitHub's internal process for app installation:
async function installGitHubApp(appId, repositoryId, userId) {
  // 1. Create installation record
  const installation = await githubApi.createInstallation({
    app_id: appId,
    repository_ids: [repositoryId]
  });
  
  // 2. AUTO-CREATE webhook for the repository
  await githubApi.createWebhook({
    repository_id: repositoryId,
    config: {
      url: "https://api.netlify.com/webhook/github", // Netlify's endpoint
      content_type: "json",
      secret: "randomly_generated_secret",
      insecure_ssl: "0"
    },
    events: [
      "push",
      "pull_request",
      "deployment_status",
      "repository"  // For repo creation/deletion
    ]
  });
  
  // 3. Generate access token for the app
  const token = await githubApi.createInstallationToken(installation.id);
  
  return { installation, token };
}
