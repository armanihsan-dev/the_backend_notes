PART 1: WHAT IS ZERO DOWNTIME DEPLOYMENT?

The Problem with Regular Deployments

  • Stop server → Users see "Cannot connect"
  • Update code → Still down
  • Start server → 5-10 seconds downtime
  • Result: Angry users, lost revenue

Zero Downtime Solution

  • Multiple instances running simultaneously
  • Rolling updates - update one instance at a time
  • Load balancing - distribute traffic
  • Result: Users never notice updates
Real-Life Analogy

Regular Deployment: Close restaurant → Renovate → Reopen (customers wait outside)

Zero Downtime: Keep serving customers while renovating one table at a time

PART 2: PM2 CLUSTER MODE EXPLAINED

What is PM2 Cluster Mode?

PM2 creates multiple copies (workers) of your Node.js app and distributes incoming requests between them. 

Single Instance:               Cluster Mode (4 instances):
+-----------------+          +-----------------+
|   User Request  |          |   User Request  |
+-----------------+          +-----------------+
         ↓                           ↓
+-----------------+          +-----------------+
|   Node.js App   |          |   PM2 Master    |
|   (Single)      |          |  (Load Balancer)|
+-----------------+          +-----------------+
                                      ↓
                    +-----------------------------------+
                    | Worker1 | Worker2 | Worker3 | Worker4 |
                    +-----------------------------------+
                            (4 instances of your app)

Benefits of Cluster Mode

  • CPU Utilization: Use all CPU cores (4 cores = 4 workers)
  • High Availability: If one worker crashes, others continue
  • Zero Downtime: Update workers one by one
  • Better Performance: Handle more concurrent requests

PART 3: ECOSYSTEM CONFIGURATION

Create ecosystem.config.js

// ecosystem.config.js
module.exports = [{
  name: "mern-app",
  script: "./server/server.js",
  
  // CLUSTER CONFIGURATION
  instances: "max",              // Create one instance per CPU core
  exec_mode: "cluster",          // Enable cluster mode
  
  // PRODUCTION SETTINGS
  watch: false,                  // Don't auto-restart in production
  max_memory_restart: "1G",      // Restart if memory > 1GB
  max_restarts: 10,              // Max restarts in 60s
  min_uptime: "30s",             // Consider app stable after 30s
  
  // Logging
  log_date_format: "YYYY-MM-DD HH:mm:ss",
  error_file: "/home/ubuntu/.pm2/logs/mern-app-error.log",
  out_file: "/home/ubuntu/.pm2/logs/mern-app-out.log",
  combine_logs: true,            // Merge logs from all instances
  merge_logs: true,
  
  // Environment variables
  env: {
    NODE_ENV: "production",
    PORT: 5000,
    NODE_OPTIONS: "--experimental-modules"  // For ES6 modules
  },
  
  // Development environment (pm2 start ecosystem.config.js --env development)
  env_development: {
    NODE_ENV: "development",
    PORT: 3000
  },
  
  // Test environment
  env_test: {
    NODE_ENV: "test",
    PORT: 4000
  },
  
  // Graceful shutdown
  kill_timeout: 5000,            // Wait 5s before force kill
  listen_timeout: 10000,         // Time to wait for app to be ready
  
  // Advanced
  node_args: [
    "--max-old-space-size=1024", // 1GB memory limit
    "--experimental-modules"     // Enable ES6 modules
  ],
  
  // Deployment
  post_deploy: "npm install && pm2 reload ecosystem.config.js --env production",
  deploy: {
    production: {
      user: "ubuntu",
      host: ["your-ec2-ip"],
      ref: "origin/main",
      repo: "git@github.com:yourusername/mern-app.git",
      path: "/home/ubuntu/mern-app",
      "post-deploy": "npm install && npm run build && pm2 reload ecosystem.config.js --env production"
    }
  }
}];
Common Key Settings Explained
  • instances: "max" = Create one instance per CPU core
  • exec_mode: "cluster" = Enable cluster mode
  • watch: false = Don't auto-restart in production
  • max_memory_restart = Auto-restart if memory leaks

PART 5: HOW PM2 FINDS AND RUNS YOUR SCRIPT

The Search Process - Step by Step

1. You type: pm2 start ecosystem.config.js
   ↓
2. PM2 looks in CURRENT directory for ecosystem.config.js
   ↓
3. Finds it! Reads the configuration
   ↓
4. Sees: script: "./server/server.js"
   ↓
5. PM2 calculates ABSOLUTE path:
   Current Directory: /home/ubuntu/mern-app
   + 
   Relative Path: ./server/server.js
   =
   Absolute Path: /home/ubuntu/mern-app/server/server.js
   ↓
6. Checks if file exists
   ↓
7. Starts Node.js with that file

How Cluster Mode Works Internally

Before Cluster:               After Cluster Mode:
+-----------------+          +-----------------+
|   User Request  |          |   User Request  |
+-----------------+          +-----------------+
         ↓                           ↓
+-----------------+          +-----------------+
|   Node.js App   |          |   PM2 Master    |
|   (Single)      |          |  (Load Balancer)|
+-----------------+          +-----------------+
                                      ↓
                    +-----------------------------------+
                    | Worker1 | Worker2 | Worker3 | Worker4 |
                    +-----------------------------------+
                            (4 instances of your app)

Key Components:

  • Master Process: Manages workers, listens on port 5000
  • Worker Processes: Actual app instances (2, 4, 8, etc.)
  • IPC: Inter-process communication between master and workers

PART 7: THE MAGIC BEHIND PM2 RELOAD

What Happens WITHOUT PM2 Reload:

Normal pm2 restart:

1. Stop ALL workers at once:  [X][X][X][X]  (ALL DEAD!)
2. Users see: "Cannot connect to server"
3. Start new workers:         [1][2][3][4] (Starting...)
4. Downtime: 5-10 seconds

What Happens WITH PM2 Reload (The Magic):

Step-by-Step Visualization:

BEFORE:           [Worker1][Worker2][Worker3][Worker4]
                  All serving users

STEP 1:           [Worker1][Worker2][Worker3][Worker4]
                  ↑ Start NEW Worker5 in background
                  (Old workers still running!)

STEP 2:           [Worker1][Worker2][Worker3][Worker4][Worker5]
                  New worker ready, start accepting connections
                  PM2 stops sending NEW users to Worker1

STEP 3:           [X][Worker2][Worker3][Worker4][Worker5]
                  Worker1 finishes current requests → Gracefully stops
                  Users moved to other workers

STEP 4: Repeat for all workers one by one...
                  [X][X][X][X][Worker5][Worker6][Worker7][Worker8]

FINAL:            [Worker5][Worker6][Worker7][Worker8]
                  All old workers replaced, ZERO downtime!

PART 9: COMMON COMMANDS

# Start/Stop/Restart
pm2 start ecosystem.config.js   # Start cluster
pm2 stop mern-app              # Stop all instances
pm2 restart mern-app           # Restart (downtime)
pm2 reload mern-app            # Zero downtime reload

# Scale up/down
pm2 scale mern-app +2          # Add 2 more workers
pm2 scale mern-app -1          # Remove 1 worker
pm2 scale mern-app 8           # Set to exactly 8 workers

# Maintenance
pm2 save                       # Save current process list
pm2 startup                    # Auto-start on reboot
pm2 resurrect                  # Restore saved processes

PART 10: TROUBLESHOOTING

Common Issues & Solutions:

1. Port already in use:

# Find what's using port 5000
sudo lsof -i :5000
sudo netstat -tulpn | grep :5000

# Kill process
sudo kill -9 $(sudo lsof -t -i:5000)

2. Memory issues:

// In ecosystem.config.js
max_memory_restart: "500M",  // Lower memory limit
instances: 2,                // Reduce instances

3. Slow deployments:

# Use --parallel for faster reloads
pm2 reload ecosystem.config.js --parallel 2

4. Check cluster health:

// Create health endpoint in your server.js
app.get('/health', (req, res) => {
  res.json({ 
    status: 'healthy',
    timestamp: new Date(),
    instance: process.env.INSTANCE_ID || 'master'
  });
});

// Test from terminal
curl http://localhost:5000/health

SUMMARY

Key Points:

  • PM2 Cluster Mode = Multiple app instances for zero downtime
  • pm2 reload = The magic command for zero downtime
  • instances: "max" = Use all CPU cores
  • Nginx = Front-facing load balancer
  • Health checks = Essential for reliability

When to Use:

  • ✅ Production deployments - No downtime
  • ✅ High traffic apps - Better load handling
  • ✅ Critical services - Always available
  • ✅ Microservices - Easy scaling

When NOT to Use:

  • ❌ Development - Use single instance
  • ❌ Memory-intensive apps - Each instance uses memory
  • ❌ Simple apps - Overkill for small projects
Pro Tip

Start with 2-4 instances, monitor memory usage, and adjust based on your EC2 size (t2.micro = 1-2 instances, t2.large = 4-8 instances).
