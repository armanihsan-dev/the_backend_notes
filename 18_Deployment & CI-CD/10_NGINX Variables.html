Part 3: Understanding NGINX Variables

1️⃣ What are variables in NGINX? (Clear definition)

NGINX variables are runtime placeholders that hold request-specific or connection-specific values.

They:
  • Start with $
  • Are evaluated per request
  • Change dynamically for each client

Example: $host, $uri, $remote_addr

Think of them like:

  • req.headers.host
  • req.url
  • req.ip

...in Node.js.

2️⃣ Why variables exist (use cases)

Variables let you:

  • Forward client info to backend
  • Route traffic dynamically
  • Customize headers
  • Log intelligently
  • Build condition-based configs (without if hell)

3️⃣ Variable syntax (important rules)

Basic usage:

proxy_set_header Host $host;

Inside strings:

add_header X-Request "$request_method $uri";

Default value fallback:

proxy_set_header Host $host:$server_port;
⚠️ Variables are read-only (you don’t assign like JS).

4️⃣ Categories of NGINX variables (you should know this)

  • A) Client & request variables
  • B) URI & routing variables
  • C) Header variables
  • D) Proxy-related variables
  • E) Connection variables

5️⃣ Most common variables (YOU WILL USE THESE)

🔹 Client / request info

Variable Meaning
$remote_addr Client IP
$remote_port Client port
$request_method GET / POST
$request_uri Full URI with query
$uri URI without query
$args Query string
$scheme http / https
$host Requested host

Example:

add_header X-Debug-Client "$remote_addr";

🔹 Header variables

NGINX exposes headers like this: $http_<header_name>

Example: $http_user_agent, $http_authorization, $http_cookie

Use case:

proxy_set_header Authorization $http_authorization;

🔹 URI & routing variables

Variable Meaning
$request_uri /api/users?id=1
$uri /api/users
$is_args ? or empty
$args id=1

Rebuild full URL: $uri$is_args$args

6️⃣ Proxy-related variables (MOST IMPORTANT FOR YOU)

These are core reverse proxy variables.

🔹 $proxy_add_x_forwarded_for

Appends client IP to existing X-Forwarded-For:

proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

Result: X-Forwarded-For: clientIP, proxyIP

🔹 $remote_addr vs $proxy_add_x_forwarded_for

Variable Meaning
$remote_addr Direct client IP
$proxy_add_x_forwarded_for Proxy chain
Never use $remote_addr alone in proxy chains.

🔹 $scheme

Used to tell backend if request was HTTPS:

proxy_set_header X-Forwarded-Proto $scheme;

Node uses this for: Secure cookies, Redirects, Absolute URLs.

🔹 $host

proxy_set_header Host $host;

Keeps original domain for: Multi-tenant apps, Auth callbacks, CORS.

🔹 $server_port

proxy_set_header X-Forwarded-Port $server_port;

7️⃣ Variables related to upstream (advanced)

Variable Meaning
$upstream_addr Backend server
$upstream_status Backend status code
$upstream_response_time Backend latency

Logging example:

log_format proxylog '$remote_addr $upstream_addr $upstream_status $upstream_response_time';
access_log /var/log/nginx/access.log proxylog;

8️⃣ Custom variables using map (VERY powerful)

Example: detect mobile users

map $http_user_agent $is_mobile {
    default 0;
    "~*iphone|android" 1;
}

# Use it:
add_header X-Mobile $is_mobile;

9️⃣ Common real-world proxy config (with variables)

location / {
    proxy_pass http://127.0.0.1:3000;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

This is not optional — it’s required for sane backends.

1️⃣0️⃣ Common mistakes (learn from others)

  • ❌ Using $http_host instead of $host
  • ❌ Forgetting $proxy_add_x_forwarded_for
  • ❌ Assuming variables are global
  • ❌ Using if instead of map
  • ❌ Hardcoding values instead of variables
Final mental model (lock this in):

Variables = live request data. They are evaluated per request. NGINX routes, logs, and proxies using them.

Once you master variables, you can: Build dynamic routing, Debug traffic, Secure headers, and Optimize proxies.
