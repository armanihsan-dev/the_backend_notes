Part 4: NGINX Logging & Debugging

1️⃣ Two types of logs in NGINX (clear definition)

✅ Access Log

Records every request NGINX successfully processes (and even failed HTTP responses).

Think: Who requested, What they requested, When, From where, What response was returned.

📄 Default file: /var/log/nginx/access.log

❌ Error Log

Records internal NGINX problems and upstream failures.

Think: Why something broke, Why a request failed before reaching backend, Why NGINX couldn’t talk to Node.

📄 Default file: /var/log/nginx/error.log

2️⃣ Access log – what exactly is logged?

Default format (simplified):

127.0.0.1 - - [01/Feb/2026:10:20:15 +0000] "GET /api/users HTTP/1.1" 200 345

Let’s decode this piece by piece:

Part Meaning
127.0.0.1 Client IP ($remote_addr)
[date] Request time
"GET /api/users" Method + URL
200 HTTP status
345 Response size (bytes)

3️⃣ Error log – what shows up here?

Examples you WILL see:

Backend down

connect() failed (111: Connection refused) while connecting to upstream

👉 Node app not running or wrong port.

Timeout

upstream timed out (110: Connection timed out)

👉 Backend slow or blocked.

Permission issue

open() "/var/www/html/index.html" failed (13: Permission denied)

👉 Linux file permissions.

4️⃣ How NGINX decides what goes where

Scenario Access Log Error Log
200 OK ✅ ❌
404 Not Found ✅ ❌
502 Bad Gateway ✅ ✅
Upstream crash ❌ ✅
Config syntax error ❌ ✅

5️⃣ Log levels (VERY IMPORTANT)

Error log has levels:

error_log /var/log/nginx/error.log warn;

Levels (from least → most verbose):

Level Logs
emerg NGINX can’t start
alert Serious failure
crit Critical errors
error Standard errors
warn Warnings
notice Important info
info Info
debug Everything

Production best practice: error_log /var/log/nginx/error.log error;

Debugging: error_log /var/log/nginx/error.log debug;

6️⃣ Custom access logs (THIS IS WHERE POWER COMES)

Define a log format:

log_format main '$remote_addr - $remote_user [$time_local] '
                '"$request" $status $body_bytes_sent '
                '"$http_referer" "$http_user_agent"';

Use it:

access_log /var/log/nginx/access.log main;

7️⃣ Proxy-aware access logs (real-world)

When using Node behind NGINX, default logs are not enough.

Add upstream info:

log_format proxy_log
  '$remote_addr - [$time_local] '
  '"$request" $status '
  'upstream:$upstream_addr '
  'up_status:$upstream_status '
  'resp_time:$upstream_response_time';

access_log /var/log/nginx/access.log proxy_log;

Now you can answer: Was NGINX slow? Was Node slow? Which backend failed?

8️⃣ Debugging common problems using logs

❌ 502 Bad Gateway

tail -f /var/log/nginx/error.log

Look for: connect() failed (111: Connection refused). Fix: Node app down or wrong proxy_pass.

❌ Slow requests

tail -f /var/log/nginx/access.log

Check: resp_time:5.234. 👉 Backend is slow.

❌ Wrong client IP in Node

Access log shows: 127.0.0.1. Fix: app.set("trust proxy", true);

9️⃣ Disable logs selectively (advanced)

Don’t log health checks:

location /health {
    access_log off;
    return 200;
}

1️⃣0️⃣ Rotate logs (VERY IMPORTANT)

NGINX logs grow fast. Linux handles this via logrotate.

Config: /etc/logrotate.d/nginx

Never delete logs manually in production.
Final mental model (lock this in):

Access log = what happened. Error log = why it broke.

If you master: Reading access logs, Filtering error logs, and Adding upstream data—you are already ahead of many “senior” devs.
