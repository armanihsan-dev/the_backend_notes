NGINX Configuration: Directives, Blocks, and Contexts

Understanding NGINX configuration structure is essential for effective server management. Let me break down these core concepts:

📊Overview: Configuration Hierarchy

structure.conf 
nginx
# Top-level context
# │
# ├── Directives (key-value pairs)
# │
# ├── Blocks (contain directives)
# │
# └── Contexts (contain blocks & directives)

1️⃣DIRECTIVES (The Building Blocks)

What is a Directive?

A directive is a configuration setting in NGINX that tells the server how to behave. It's a key-value pair.

Syntax:

syntax.conf 
directive_name value;
#    ↑              ↑
#  Key          Value(s)
#               (ends with semicolon)

Types of Directives:

1. Simple Directives (Single value)

worker_processes 4;          # Number of worker processes
error_log /var/log/nginx/error.log warn;  # Error log location & level
keepalive_timeout 65s;       # Timeout value

2. Array/List Directives (Multiple values)

error_log logs/error.log notice info debug;  # Multiple log levels

# Multiple MIME types
types {
    text/html  html htm shtml;
    text/css   css;
    image/gif  gif;
}

3. Action Directives (Trigger specific actions)

return 301 https://$server_name$request_uri;  # Redirect
rewrite ^/old/(.*)$ /new/$1 permanent;        # URL rewrite

Directive Inheritance Rules:

http {
    # Parent context sets default
    sendfile on;  
    
    server {
        # Child inherits sendfile=on
        # Can override if allowed
        # Some directives cannot be overridden!
    }
}

Key Points:

  • Most directives can be overridden in child contexts
  • Some directives cannot be inherited (context-specific)
  • Directives are case-sensitive
  • Always end with semicolon ;

2️⃣BLOCKS (The Containers)

What is a Block?

A block is a container that groups related directives together. It's defined by curly braces {}.

Syntax:

block_name {
    directive1 value;
    directive2 value;
    # Nested blocks possible
    nested_block {
        directive3 value;
    }
}

Common Blocks:

1. Events Block (Connection processing)

events {
    worker_connections 1024;  # Max connections per worker
    use epoll;               # Event method (Linux)
    multi_accept on;         # Accept multiple connections
}

2. HTTP Block (Web traffic)

http {
    include mime.types;      # Include MIME types
    default_type application/octet-stream;
    
    # Multiple server blocks inside
    server {
        # Server configuration
    }
}

3. Server Block (Virtual host)

server {
    listen 80;
    server_name example.com www.example.com;
    
    location / {
        # Location block
    }
}

4. Location Block (URL matching)

location /api/ {
    proxy_pass http://backend;
    # Only applies to URLs starting with /api/
}

location ~ \.php$ {
    fastcgi_pass unix:/var/run/php-fpm.sock;
    # Regex match for PHP files
}

5. Upstream Block (Load balancing)

upstream backend_servers {
    server 10.0.0.1:8080 weight=3;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080 backup;
    
    # Load balancing method
    least_conn;
}

3️⃣CONTEXTS (The Scopes/Environments)

What is a Context?

A context defines the scope where directives can be used. Think of it as a configuration environment with specific rules about what can be configured.

The Hierarchy Tree:

nginx
# MAIN CONTEXT (Global/Outer-most)
# ├── events {}
# ├── http {}
# │   ├── server {}
# │   │   ├── location {}
# │   │   ├── location {}
# │   │   └── if {}  # Limited context
# │   └── upstream {}
# ├── stream {}
# │   ├── server {}
# │   └── upstream {}
# └── mail {}

Core Contexts:

1. Main Context (Global Configuration)

# Directly in nginx.conf (no braces)
user www-data;                    # Run as this user
worker_processes auto;            # Auto-detect CPU cores
pid /run/nginx.pid;               # PID file location
error_log /var/log/nginx/error.log warn;  # Global error log

# These can ONLY be in main context
daemon on;                        # Run as daemon
master_process on;                # Master-worker architecture

Directives ONLY allowed in Main Context:

  • user
  • worker_processes
  • error_log (can also be in other contexts)
  • pid
  • pcre_jit
  • thread_pool

2. Events Context (Connection Processing)

events {
    # How NGINX handles connections
    worker_connections 768;      # Max connections per worker
    accept_mutex on;            # Serialize accept() to avoid thundering herd
    use epoll;                  # Event model (Linux only)
    multi_accept on;            # Accept all pending connections
}

Directives ONLY allowed in Events Context:

  • worker_connections
  • use
  • accept_mutex
  • multi_accept
  • accept_mutex_delay

3. HTTP Context (Web Server Configuration)

http {
    # Global HTTP settings
    include mime.types;
    default_type application/octet-stream;
    
    # Log formats
    log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                    '$status $body_bytes_sent "$http_referer" '
                    '"$http_user_agent" "$http_x_forwarded_for"';
    
    access_log /var/log/nginx/access.log main;
    
    # Can contain multiple servers
    server {
        listen 80;
        # ... server config
    }
}

4. Server Context (Virtual Host)

server {
    # Defines ONE virtual host
    listen 80;
    server_name example.com www.example.com;
    root /var/www/example.com;
    index index.html index.htm;
    
    # Can contain multiple locations
    location / {
        try_files $uri $uri/ =404;
    }
}

5. Location Context (URL-Specific Rules)

location [modifier] uri {
    # Applies to specific URIs
}

# Examples:
location = /exact { }           # Exact match (highest priority)
location ^~ /static/ { }        # Prefix match (no regex check)
location ~ \.php$ { }           # Case-sensitive regex
location ~* \.(jpg|png|gif)$ { } # Case-insensitive regex
location / { }                  # Prefix match (lowest priority)

6. Upstream Context (Backend Servers)

upstream backend {
    # Load balancing configuration
    server backend1.example.com weight=5;
    server backend2.example.com;
    server 192.168.0.1 backup;
    
    # Load balancing method
    least_conn;  # or: ip_hash, hash $request_uri consistent;
    
    # Health checks
    health_check interval=5s fails=3 passes=2;
}

7. Stream Context (TCP/UDP Proxy)

stream {
    # For non-HTTP traffic (TCP/UDP)
    upstream database_cluster {
        server db1.example.com:3306;
        server db2.example.com:3306;
    }
    
    server {
        listen 3306;
        proxy_pass database_cluster;
    }
}

8. Mail Context (Mail Proxy)

mail {
    server_name mail.example.com;
    auth_http localhost:9000/auth;
    
    server {
        listen 25;
        protocol smtp;
        smtp_auth login plain cram-md5;
    }
}

📚Practical Examples

Complete Configuration Structure:

# ===== MAIN CONTEXT =====
user nginx;
worker_processes auto;
error_log /var/log/nginx/error.log warn;
pid /var/run/nginx.pid;

# ===== EVENTS CONTEXT =====
events {
    worker_connections 1024;
    multi_accept on;
    use epoll;
}

# ===== HTTP CONTEXT =====
http {
    # Global HTTP settings
    include /etc/nginx/mime.types;
    default_type application/octet-stream;
    
    log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                    '$status $body_bytes_sent "$http_referer" '
                    '"$http_user_agent" "$http_x_forwarded_for"';
    
    access_log /var/log/nginx/access.log main;
    
    sendfile on;
    tcp_nopush on;
    keepalive_timeout 65;
    
    # ===== SERVER BLOCK 1 =====
    server {
        listen 80;
        server_name example.com;
        
        # ===== LOCATION BLOCK =====
        location / {
            root /usr/share/nginx/html;
            index index.html index.htm;
            try_files $uri $uri/ =404;
        }
        
        # ===== ANOTHER LOCATION BLOCK =====
        location /api/ {
            # ===== UPSTREAM BLOCK (can be inside or outside) =====
            proxy_pass http://backend_servers;
            
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
        }
        
        # ===== REGEX LOCATION BLOCK =====
        location ~ \.php$ {
            fastcgi_pass unix:/var/run/php-fpm.sock;
            include fastcgi_params;
        }
    }
    
    # ===== SERVER BLOCK 2 (Another virtual host) =====
    server {
        listen 80;
        server_name app.example.com;
        
        location / {
            proxy_pass http://localhost:3000;
        }
    }
    
    # ===== UPSTREAM BLOCK (Shared across servers) =====
    upstream backend_servers {
        least_conn;
        server 10.0.1.10:8080;
        server 10.0.1.11:8080;
        server 10.0.1.12:8080 backup;
    }
}

# ===== STREAM CONTEXT (Separate from HTTP) =====
stream {
    upstream mysql_servers {
        server db1.example.com:3306;
        server db2.example.com:3306;
    }
    
    server {
        listen 3306;
        proxy_pass mysql_servers;
    }
}

🔍Context Inheritance & Precedence

How Inheritance Works:

http {
    # Parent: Sets default for all children
    gzip on;
    gzip_types text/plain text/css;
    
    server {
        # Child: Inherits gzip=on
        # Can override gzip_types
        gzip_types text/plain text/css application/json;
        
        location / {
            # Grandchild: Inherits from both parent and child
            # gzip=on, gzip_types=text/plain text/css application/json
            
            # Can add more
            gzip_vary on;
        }
    }
}

Precedence Rules:

  • Direct context wins over inherited
  • More specific context wins over general
  • Later declarations win over earlier (within same context)
location / {
    add_header X-Custom "default";  # 1. Set
}

location /api/ {
    add_header X-Custom "api";      # 2. Overrides for /api/
    add_header X-API "yes";         # 3. Additional header
}

# For /api/test:
# X-Custom: "api" (more specific wins)
# X-API: "yes"

⚠️Common Pitfalls

1. Missing Semicolons

# WRONG
root /var/www/html  # Missing ;
# RIGHT
root /var/www/html;

2. Directive in Wrong Context

# WRONG: worker_connections in main context
worker_connections 1024;  # Should be in events {}

# RIGHT
events {
    worker_connections 1024;
}

3. Conflicting Directives

location / {
    try_files $uri $uri/ =404;
    # Can't use both try_files and proxy_pass
    proxy_pass http://backend;  # ERROR!
}

# Solution: Use either/or
location / {
    # Option 1: Static files
    try_files $uri $uri/ =404;
}

location /api/ {
    # Option 2: Proxy
    proxy_pass http://backend;
}

4. Context Nesting Errors

# WRONG: Can't nest server in location
location / {
    server {  # ERROR!
        listen 80;
    }
}

# WRONG: Can't put stream in http
http {
    stream {  # ERROR!
        # ...
    }
}

🎯Best Practices

1. Organize with Includes

# nginx.conf (clean main file)
http {
    include /etc/nginx/conf.d/*.conf;
    include /etc/nginx/sites-enabled/*;
}

# /etc/nginx/conf.d/security.conf
add_header X-Frame-Options SAMEORIGIN;
add_header X-Content-Type-Options nosniff;

# /etc/nginx/sites-available/example.com
server {
    listen 80;
    server_name example.com;
    include /etc/nginx/snippets/ssl.conf;
    include /etc/nginx/snippets/security-headers.conf;
}

2. Use Meaningful Context Separation

# GOOD: Clear separation
http {
    # Global settings
    gzip on;
    
    # Virtual host 1
    server {
        server_name api.example.com;
        location /v1/ { ... }
        location /v2/ { ... }
    }
    
    # Virtual host 2  
    server {
        server_name app.example.com;
        location / { ... }
    }
}

3. Test Configurations

# Always test before applying
sudo nginx -t

# Test specific configuration file
sudo nginx -t -c /path/to/nginx.conf

# Reload gracefully
sudo nginx -s reload

💡Pro Tips

1. Debug Context Issues

# See full config with includes resolved

2. Use Variables Across Contexts

# Define at http level
http {
    map $http_user_agent $is_bot {
        default 0;
        ~*bot 1;
        ~*crawler 1;
    }
    
    server {
        location / {
            # Use in server/location context

                return 403 "No bots allowed";
            }
        }
    }
}

            }
        }
    }
}

Short Response: Worker Processes

Worker Processes in NGINX

What are Worker Processes?

Worker processes are the actual workers that handle client requests in NGINX. They run the event loop to process connections.

Key Points:

  • Master process reads config, manages workers
  • Worker processes handle actual requests (multiple connections each)
  • Each worker is single-threaded but handles thousands of connections
  • Workers are independent - if one crashes, others keep running

Configuration in nginx.conf

# Main context (top of nginx.conf)
worker_processes auto;  # Best for most setups

# OR specify exact number
worker_processes 4;     # For 4 CPU cores

# Advanced settings
worker_processes 8;     # For 8 CPU cores
worker_cpu_affinity auto;  # Bind workers to specific CPUs
worker_rlimit_nofile 65535;  # Increase file descriptor limit

Recommended Settings:

1. Auto-detect (Best for most)

worker_processes auto;

2. Manual (Fine-tuned)

worker_processes 4;  # For 4-core server

3. With CPU affinity (High-performance)

worker_processes 4;
worker_cpu_affinity 0001 0010 0100 1000;  # Pin to CPUs 0-3

Check Current Configuration:

# See worker count
ps aux | grep nginx

# Count processes
ps aux | grep nginx | grep -v grep | wc -l

# Check CPU cores
nproc

Rule of Thumb:

  • Start with auto (NGINX detects CPU cores)
  • Test with different values for your workload
  • Monitor CPU usage - all workers busy = need more workers or optimization

Simple setup:

# /etc/nginx/nginx.conf
user www-data;
worker_processes auto;  # ← That's it!
pid /run/nginx.pid;

events {
    worker_connections 1024;
}

NGINX will automatically set workers equal to your CPU cores. Test with nginx -t and reload!

Short Response: Static Server Config

NGINX Configuration for Static Site (localhost:80)

1. Install & Start NGINX

sudo apt update
sudo apt install nginx -y
sudo systemctl start nginx

2. Create Static Site Files

sudo mkdir -p /var/www/mysite
sudo nano /var/www/mysite/index.html

index.html:

<!DOCTYPE html>
<html>
<head><title>My Static Site</title></head>
<body>
    <h1>Welcome to My Site!</h1>
    <p>Served by NGINX</p>
</body>
</html>

3. Configure NGINX (nginx.conf)

# Main context - Global settings
user www-data;
worker_processes auto;
error_log /var/log/nginx/error.log;

# Events context - Connection handling
events {
    worker_connections 1024;
}

# HTTP context - Web server settings
http {
    include mime.types;
    default_type application/octet-stream;
    
    # Logging
    access_log /var/log/nginx/access.log;
    
    # Performance
    sendfile on;
    tcp_nopush on;
    keepalive_timeout 65;
    
    # Gzip compression
    gzip on;
    gzip_types text/plain text/css application/json;
    
    # Server block - Virtual host for localhost:80
    server {
        listen 80;
        server_name localhost;
        
        # Root directory for files
        root /var/www/mysite;
        
        # Default index files
        index index.html index.htm;
        
        # Location block for all requests
        location / {
            # Try serving requested file, then directory, then 404
            try_files $uri $uri/ =404;
        }
        
        # Cache static assets
        location ~* \.(jpg|jpeg|png|gif|ico|css|js)$ {
            expires 1y;
            add_header Cache-Control "public, immutable";
        }
        
        # Deny access to hidden files
        location ~ /\. {
            deny all;
        }
    }
}

4. Apply Configuration

# Test config syntax
sudo nginx -t

# Reload NGINX
sudo systemctl reload nginx

# OR restart completely
sudo systemctl restart nginx

5. Test Your Site

# Visit in browser: http://localhost

# Or use curl
curl http://localhost

# Check logs
tail -f /var/log/nginx/access.log
tail -f /var/log/nginx/error.log

Key Directives Explained:

Directive Purpose Context
server {} Defines virtual host HTTP
listen 80 Listens on port 80 Server
root /path Directory for files Server/Location
index index.html Default file to serve Server/Location
try_files File serving logic Location
expires 1y Browser caching Location

Optional: Enable Directory Listing

location /files/ {
    autoindex on;  # Show file listing
    autoindex_exact_size off;  # Show human-readable sizes
}

That's it! Your static site is now live at http://localhost:80
