FUNDAMENTALS - WHY SSL EXISTS

🔓 HTTP vs HTTPS

HTTP (Hypertext Transfer Protocol):

  • Unencrypted protocol for transferring web pages
  • Data travels in plain text - readable by anyone intercepting
  • Port 80
  • Vulnerable to eavesdropping, man-in-the-middle attacks

HTTPS (HTTP Secure):

  • HTTP + SSL/TLS encryption layer
  • Encrypts all communication between client and server
  • Port 443
  • Provides: Confidentiality (encryption), Integrity (data tamper-proof), Authentication (server identity verification)

ENCRYPTION TYPES

🔐 Symmetric vs Asymmetric Encryption

Symmetric Encryption:

// Same key for encryption and decryption
const key = 'shared-secret-key';
const encrypted = encrypt(data, key);
const decrypted = decrypt(encrypted, key);
Pros Cons Examples
Fast, efficient for large data Key distribution problem - how to securely share the key? AES, DES, ChaCha20

Asymmetric Encryption (Public-key cryptography):

// Key pair: Public (shared) + Private (secret)
const {publicKey, privateKey} = generateKeyPair();

// Encrypt with public key, decrypt with private key
const encrypted = encrypt(data, publicKey);
const decrypted = decrypt(encrypted, privateKey);
Pros Cons Examples
Solves key distribution problem 100-1000x slower than symmetric RSA, ECC, DH

🔑 Public Key vs Private Key

Public Key:

  • Can be freely distributed
  • Used to encrypt data (only matching private key can decrypt)
  • Used to verify digital signatures
  • Stored in certificates

Private Key:

  • MUST be kept secret
  • Used to decrypt data encrypted with matching public key
  • Used to create digital signatures
  • Never shared, protected by server
Analogy

Think of a lockbox:

Public key = open lockbox (anyone can put messages in)

Private key = key to open lockbox (only you can read messages)

DIGITAL CERTIFICATES

📜 What is a Digital Certificate?

A digital certificate is an electronic document that uses a digital signature to bind a public key with an identity. It's like a digital passport that proves the authenticity of a website, organization, or individual.

Certificate Structure (X.509 Standard):

Certificate:
    Data:
        Version: 3 (0x2)
        Serial Number: 12:34:56:78:90:ab:cd:ef
        Signature Algorithm: sha256WithRSAEncryption
        Issuer: CN=DigiCert SHA2 Secure Server CA
        Validity:
            Not Before: Jan  1 00:00:00 2024 GMT
            Not After : Jan  1 23:59:59 2025 GMT
        Subject: CN=example.com, O=Example Corp, C=US
        Subject Public Key Info:
            Public Key Algorithm: rsaEncryption
                RSA Public-Key: (2048 bit)
        X509v3 extensions:
            X509v3 Subject Alternative Name:
                DNS:example.com, DNS:www.example.com
            X509v3 Key Usage:
                Digital Signature, Key Encipherment
            X509v3 Extended Key Usage:
                TLS Web Server Authentication
    Signature Algorithm: sha256WithRSAEncryption

🔍 Certificate Fields Explained

Field Purpose Example
Subject (CN) Domain/entity the certificate is issued to CN=example.com
Issuer Certificate Authority that signed it CN=Let's Encrypt Authority X3
Serial Number Unique identifier for the certificate 03:77:21:8A:B2:C4:D5:E6
Validity Period When certificate is valid (Not Before/After) 90 days for Let's Encrypt
Public Key The actual public key for encryption 2048-bit RSA key
Signature CA's digital signature proving authenticity SHA256withRSA signature
SAN (Subject Alternative Names) Additional domains covered by certificate www.example.com, api.example.com

🔐 How Certificates Work

  1. Key Generation: Server generates public/private key pair
  2. CSR Creation: Certificate Signing Request with public key + domain info
  3. CA Validation: CA verifies domain ownership and identity
  4. Certificate Issuance: CA signs the certificate with their private key
  5. Installation: Certificate installed on server with private key
  6. Client Verification: Browser validates certificate chain and signature

🔗 Trust Chain (Certificate Chain)

Root CA Certificate (Self-signed, embedded in browsers/OS)
      ↓ Signs
Intermediate CA Certificate (Issued by Root CA)
      ↓ Signs  
Server Certificate (Issued to your domain)

Example Chain:
┌─────────────────────────────────────┐
│ DigiCert Global Root CA             │ ← Root (in browser trust store)
│ Self-signed, 2048-bit RSA           │
└─────────────────┬───────────────────┘
                  │ Signs
┌─────────────────▼───────────────────┐
│ DigiCert SHA2 Secure Server CA      │ ← Intermediate
│ Signed by Root CA                   │
└─────────────────┬───────────────────┘
                  │ Signs
┌─────────────────▼───────────────────┐
│ example.com                         │ ← End-entity (your certificate)
│ Signed by Intermediate CA           │
└─────────────────────────────────────┘

Why Chain of Trust Works:

  1. Root Trust: Browsers/OS come with pre-installed Root CA certificates
  2. Chain Validation: Each certificate in chain is verified against its parent
  3. Signature Verification: Digital signatures prove authenticity
  4. Validity Checks: Expiration dates and revocation status checked

🔍 Certificate Validation Process

Browser Certificate Validation:

1. Certificate Chain Building
   ├── Start with server certificate
   ├── Find intermediate certificates
   └── Trace to trusted root CA

2. Signature Verification
   ├── Verify each certificate signature
   ├── Use parent's public key
   └── Ensure chain integrity

3. Validity Checks
   ├── Check expiration dates
   ├── Verify domain name matches
   └── Check certificate purpose

4. Revocation Checking
   ├── OCSP (Online Certificate Status Protocol)
   ├── CRL (Certificate Revocation List)
   └── OCSP Stapling (if available)

5. Trust Decision
   ├── All checks pass → Trusted
   └── Any check fails → Warning/Error

TLS HANDSHAKE

🤝 TLS 1.3 Handshake Process

Client                                      Server
------                                      ------
ClientHello
(Random, Cipher Suites)  --------------->
                                            ServerHello
                                            (Random, Chosen Cipher Suite)
                         <---------------
                                            Certificate*
                                            CertificateVerify*
                         <---------------
                                            Finished
                         <---------------
Client Key Exchange*     ---------------->
Finished                 ---------------->
                         <---------------
[Application Data]       <---------------> [Application Data]

🔄 Key Exchange Methods

Method Description Security
RSA Client encrypts pre-master secret with server's public key (TLS 1.2, deprecated in 1.3) No PFS
DHE Diffie-Hellman Ephemeral - New key for each session Perfect Forward Secrecy
ECDHE Elliptic Curve DHE - Same but with smaller keys Perfect Forward Secrecy

CIPHER SUITES

🔧 Cipher Suite Format

Format: TLS_KeyExchange_Auth_Encryption_MAC

Example: TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256

Component Example Purpose
Key Exchange ECDHE Elliptic Curve Diffie-Hellman Ephemeral
Authentication RSA Server proves identity
Encryption AES-128-GCM Symmetric encryption
MAC SHA256 Message integrity

Modern cipher suites prioritize:

  • Perfect Forward Secrecy
  • Authenticated encryption (AEAD)
  • Strong algorithms (avoid RC4, 3DES, MD5)

CERTIFICATE REVOCATION

❌ Why Certificates Get Revoked

  • Private Key Compromise: Private key stolen or exposed
  • CA Compromise: Certificate Authority's systems breached
  • Affiliation Change: Organization no longer owns domain
  • Superseded: Certificate replaced by newer one
  • Cessation of Operation: Organization stops using certificate
  • Certificate Hold: Temporary suspension

📋 Certificate Revocation List (CRL)

A CRL is a list of revoked certificates published by the CA. Browsers download and check this list periodically.

CRL Structure:
-----BEGIN X509 CRL-----
MIICjTCCAXUCAQEwDQYJKoZIhvcNAQELBQAwXjELMAkGA1UEBhMCVVMxCzAJBgNV
BAgMAlVTMQswCQYDVQQHDAJVUzELMAkGA1UECgwCVVMxCzAJBgNV...

Revoked Certificates:
- Serial: 1234567890ABCDEF, Revocation Date: 2024-01-15
- Serial: FEDCBA0987654321, Revocation Date: 2024-01-20
-----END X509 CRL-----

CRL Limitations:

  • Large file size (can be MBs)
  • Infrequent updates (daily/weekly)
  • Privacy concerns (reveals all revoked certificates)
  • Performance impact on browsers

⚡ Online Certificate Status Protocol (OCSP)

OCSP allows real-time checking of certificate revocation status without downloading entire CRL.

OCSP Request/Response Flow:

1. Browser → OCSP Responder: "Is certificate X revoked?"
   POST /ocsp HTTP/1.1
   Host: ocsp.digicert.com
   Content-Type: application/ocsp-request
   
2. OCSP Responder → Browser: "Certificate status"
   HTTP/1.1 200 OK
   Content-Type: application/ocsp-response
   
   Response: Good | Revoked | Unknown

📎 OCSP Stapling

Server fetches OCSP response and "staples" it to the TLS handshake, eliminating need for browser to contact OCSP responder.

Benefits of OCSP Stapling:

  • Performance: Faster handshake (no additional OCSP request)
  • Privacy: Browser doesn't contact OCSP responder
  • Reliability: Works even if OCSP responder is down
  • Scalability: Reduces load on OCSP responders
# Enable OCSP Stapling in Nginx
server {
    ssl_stapling on;
    ssl_stapling_verify on;
    ssl_trusted_certificate /path/to/chain.pem;
    resolver 8.8.8.8 8.8.4.4 valid=300s;
    resolver_timeout 5s;
}

SESSION KEYS & PERFECT FORWARD SECRECY

🔐 Session Key Derivation Process

  1. Pre-master secret: Generated via key exchange
  2. Master secret: Derived from pre-master + client/server randoms
  3. Session keys: Derived from master secret (multiple keys for encryption/MAC in each direction)
# Simplified key derivation
master_secret = PRF(pre_master_secret, "master secret", client_random + server_random)
client_write_key = PRF(master_secret, "client write key", client_random + server_random)
server_write_key = PRF(master_secret, "server write key", client_random + server_random)

🛡️ Perfect Forward Secrecy (PFS)

Definition: Compromising long-term private key doesn't compromise past session keys

How it works:

  • Each session uses unique, temporary key pairs (ephemeral keys)
  • Session keys derived from temporary keys, not server's permanent private key
  • Old sessions cannot be decrypted even if server key is compromised
  • Implementation: Use ECDHE or DHE key exchange

HANDS-ON PRACTICE

🔨 1. Generate Self-signed Certificate

# Generate private key
openssl genrsa -out private.key 2048

# Generate CSR (Certificate Signing Request)
openssl req -new -key private.key -out csr.csr
# Fill in: Country, State, Locality, Organization, Common Name (domain)

# Generate self-signed certificate
openssl x509 -req -days 365 -in csr.csr -signkey private.key -out certificate.crt

# Or in one command:
openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem -days 365 -nodes

⚡ Enable HTTPS in Node.js

// https-server.js
const https = require('https');
const fs = require('fs');

const options = {
  key: fs.readFileSync('private.key'),
  cert: fs.readFileSync('certificate.crt'),
  // Optional: add intermediate certificates

  res.writeHead(200);
  res.end('Hello HTTPS World!');

// For development (bypass self-signed warning)

NGINX CONFIGURATION

🌐 Enable HTTPS in Nginx

# /etc/nginx/sites-available/your-site
server {
    listen 443 ssl http2;
    server_name yourdomain.com;
    
    ssl_certificate /path/to/certificate.crt;
    ssl_certificate_key /path/to/private.key;
    
    # Optional: improve security
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-RSA-AES128-GCM-SHA256:ECDHE-RSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers off;
    
    # HSTS (optional but recommended)
    add_header Strict-Transport-Security "max-age=63072000" always;
    
    location / {
        proxy_pass http://localhost:3000;
        proxy_set_header Host $host;
    }
}

# Redirect HTTP to HTTPS
server {
    listen 80;
    server_name yourdomain.com;
    return 301 https://$server_name$request_uri;
}

    echo "Checking $host..."

    fi
done

🏢 Private Certificate Authorities

Organizations can create their own Certificate Authority for internal use, providing complete control over certificate issuance.

Setting up Private CA with OpenSSL:

# 1. Create CA directory structure
mkdir -p ca/{certs,crl,newcerts,private}
touch ca/index.txt
echo 1000 > ca/serial

# 2. Generate CA private key
openssl genrsa -aes256 -out ca/private/ca.key.pem 4096
chmod 400 ca/private/ca.key.pem

# 3. Create CA certificate
openssl req -config openssl.cnf -key ca/private/ca.key.pem \
  -new -x509 -days 7300 -sha256 -extensions v3_ca \
  -out ca/certs/ca.cert.pem

# 4. Create intermediate CA (optional but recommended)
openssl genrsa -aes256 -out intermediate/private/intermediate.key.pem 4096
openssl req -config intermediate/openssl.cnf -new -sha256 \
  -key intermediate/private/intermediate.key.pem \
  -out intermediate/csr/intermediate.csr.pem

# 5. Sign intermediate certificate
openssl ca -config openssl.cnf -extensions v3_intermediate_ca \
  -days 3650 -notext -md sha256 \
  -in intermediate/csr/intermediate.csr.pem \
  -out intermediate/certs/intermediate.cert.pem

DANE uses DNS to specify which certificates are valid for a domain, providing an alternative to the traditional CA system.

# DANE TLSA Record Examples

)

# Pin CA certificate

    FEDCBA0987654321... ; SHA-256 hash of CA certificate

# Pin public key

SECURITY AWARENESS

🎭 Man-in-the-Middle (MITM) Attacks

How it works:

  • Attacker intercepts communication
  • Presents fake certificate to client
  • Decrypts, reads/modifies, re-encrypts traffic

Prevention:

  • Valid certificates from trusted CAs
  • Certificate pinning
  • HSTS
  • Public key pinning (HPKP) - deprecated but worth knowing

📌 Certificate Pinning

// Application-level pinning
const expectedHash = 'sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=';

fetch('https://api.example.com', {
  agent: new https.Agent({
    checkServerIdentity: (hostname, cert) => {
      const pin = crypto.createHash('sha256').update(cert.raw).digest('base64');
      if (pin !== expectedHash) {
        throw new Error('Certificate pin mismatch');
      }
    }
  })
});

⚠️ Why Expired Certs Break Sites

  • Validity Period: Certificates have explicit notBefore/notAfter dates
  • Security Reason: Limits damage if private key is compromised
  • Browsers: Strictly enforce validity periods
  • Grace Period: None for publicly trusted certificates

🚫 Why Browsers Show "Not Secure"

  • HTTP Sites: No encryption at all
  • HTTPS Issues:
    • Expired certificate
    • Domain mismatch (cert issued for different domain)
    • Self-signed certificate (no CA trust)
    • Revoked certificate (CRL/OCSP check)
    • Weak encryption (SHA1, RC4, etc.)
    • Missing intermediates (broken chain)
    • Mixed content (HTTPS page loads HTTP resources)

✅ For Production HTTPS:

  • Use TLS 1.2 or 1.3 (disable SSLv3, TLS 1.0, 1.1)
  • Enable HSTS with appropriate max-age
  • Configure secure cipher suites
  • Use strong private key (≥2048-bit RSA or ≥256-bit ECC)
  • Set up automatic certificate renewal
  • Redirect HTTP → HTTPS
  • Include full certificate chain
  • Keep private keys secure (proper permissions)
  • Monitor certificate expiration
  • Implement OCSP stapling

🔧 Common Issues & Fixes:

Error Cause Fix
NET::ERR_CERT_DATE_INVALID Certificate expired Renew certificate
NET::ERR_CERT_AUTHORITY_INVALID Missing intermediate Install full chain
Mixed content warnings HTTP resources on HTTPS page Update all resources to use HTTPS
Cipher mismatch Incompatible cipher suites Update server cipher configuration
SNI required Multiple domains, one IP Ensure client sends Server Name Indication

🛡️ Security Best Practices:

  • Always use HTTPS - even for static sites
  • Enable HTTP/2 or HTTP/3 over HTTPS
  • Regularly update TLS configurations
  • Monitor for vulnerabilities (Heartbleed, DROWN, etc.)
  • Use certificate transparency monitoring
