NGINX Deep Dive: The Complete Guide

1️⃣ Introduction to NGINX

What is NGINX?

NGINX (pronounced "engine-x") is a high-performance, open-source web server, reverse proxy, load balancer, and HTTP cache. Originally created as a web server, it has evolved into a multi-purpose tool that sits between clients and backend servers.

Purpose & Philosophy

NGINX was designed with asynchronous, event-driven architecture at its core, allowing it to handle thousands of concurrent connections with minimal resource usage. Unlike traditional servers that create a new process/thread per connection, NGINX uses a small number of worker processes with event loops.

Why was NGINX created?

  • To solve the C10K problem (handling 10,000+ simultaneous connections)
  • Address Apache's limitations in high-concurrency scenarios
  • Improve resource efficiency for serving static content
  • Provide better scalability for modern web applications

Problems NGINX Solves

  • Concurrent connection handling - Efficiently serves thousands of simultaneous users
  • Resource optimization - Low memory footprint per connection
  • Latency reduction - Faster response times through efficient architecture
  • Security - Acts as a protective barrier for backend servers
  • Simplified SSL management - Centralized TLS termination

📜 History & Background

Creator & Timeline

  • Created by: Igor Sysoev (Russian developer)
  • First released: October 2004
  • Initial goal: Solve performance issues on Russian portal Rambler.ru (handling ~500M requests/day)
  • Current status: Maintained by NGINX, Inc. (acquired by F5 Networks in 2019)

Programming Language

Written in: C (with some C++)

  • Why C? Maximum performance, direct system call access, minimal overhead
  • Portability: Runs on Unix-like systems (Linux, BSD, macOS) and Windows

The C10K Problem

The Challenge (circa 1999): How to handle 10,000 simultaneous connections?
Apache's Approach: One thread/process per connection → Memory bloat, context-switching overhead
NGINX Solution: Event-driven, asynchronous architecture → Few worker processes handle all connections

How NGINX Solves C10K:

  • Master-Worker Architecture: Master manages config, workers handle requests
  • Event-Driven Model: Uses epoll (Linux), kqueue (BSD) for non-blocking I/O
  • Connection Pooling: Reuses connections, no per-connection overhead
  • Zero-Copy Operations: Uses sendfile() for direct kernel-to-kernel transfers

Companies Using NGINX

  • Netflix → Serves 100+ billion requests/day
  • Airbnb → Edge proxy and load balancing
  • Dropbox → Handles petabytes of file transfers
  • WordPress.com → Serves millions of blogs
  • GitHub → Reverse proxy for Git operations
  • Cloudflare → Powers their CDN infrastructure

2️⃣ Core Capabilities of NGINX

1. Static File Serving

server {
    location /static/ {
        root /var/www/html;
        expires 30d;  # Browser caching
        access_log off;
    }
}

2. Reverse Proxy

location /api/ {
    proxy_pass http://backend_server;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}

3. Load Balancing

upstream backend {
    least_conn;  # Load balancing algorithm
    server 10.0.0.1:3000;
    server 10.0.0.2:3000 backup;
}

location / {
    proxy_pass http://backend;
}

4. SSL/TLS Termination

server {
    listen 443 ssl http2;
    ssl_certificate /etc/ssl/certs/domain.crt;
    ssl_certificate_key /etc/ssl/private/domain.key;
    
    # Modern TLS configuration
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-RSA-AES256-GCM-SHA512:DHE-RSA-AES256-GCM-SHA512;
}

5. HTTP Caching

proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=my_cache:10m;

location / {
    proxy_cache my_cache;
    proxy_cache_valid 200 302 10m;
    proxy_cache_use_stale error timeout;
}

6. Rate Limiting & Security

# Rate limiting
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

location /api/ {
    limit_req zone=api burst=20 nodelay;
}

# Basic security
add_header X-Frame-Options "SAMEORIGIN";
add_header X-Content-Type-Options "nosniff";
add_header X-XSS-Protection "1; mode=block";

3️⃣ NGINX with Node.js

Why Not Node.js Directly on Port 80/443?

┌─────────────┐     Direct Connection     ┌─────────────┐
│   Client    │ ────────────────────────► │   Node.js   │
│             │                           │  (Port 443) │
└─────────────┘                           └─────────────┘
    Problems:
    • Node.js needs root access for port 80/443
    • No protection against DDoS/attacks
    • Single point of failure
    • Manual SSL management required

Reverse Proxy Architecture

┌─────────┐    HTTPS    ┌─────────┐    HTTP     ┌─────────┐
│ Client  │ ──────────► │  NGINX  │ ──────────► │ Node.js │
│         │   (443)     │         │   (3000)    │         │
└─────────┘             └─────────┘             └─────────┘
                        • SSL Termination
                        • Load Balancing
                        • Caching
                        • Rate Limiting
                        • Static Files

Sample Configuration:

upstream node_app {
    server 127.0.0.1:3000;
    server 127.0.0.1:3001;
    keepalive 64;  # Connection pooling
}

server {
    listen 80;
    server_name example.com;
    return 301 https://$server_name$request_uri;
}

server {
    listen 443 ssl http2;
    server_name example.com;
    
    ssl_certificate /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    
    location / {
        proxy_pass http://node_app;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_cache_bypass $http_upgrade;
    }
}

7️⃣ Installing & Managing NGINX on Ubuntu

# Install NGINX
sudo apt update && sudo apt install nginx -y

# Service Management
sudo systemctl start nginx
sudo systemctl stop nginx
sudo systemctl reload nginx # Graceful
sudo nginx -t # Test configuration

Directory Structure

  • /etc/nginx/nginx.conf: Main configuration
  • /etc/nginx/sites-available/: Available server blocks
  • /etc/nginx/sites-enabled/: Active server blocks (symlinks)
  • /var/log/nginx/: Access & error logs
