MongoDB BSON Deep Dive Notes: The Binary Format 💾

1. What is BSON?

  • BSON stands for Binary JSON.
  • It’s a binary-encoded serialization format used by MongoDB to represent documents and make data storage and transport efficient.
  • Think of it like JSON’s “binary cousin.”
  • JSON = human-readable (text-based).
  • BSON = machine-readable (binary, compact, faster).
  • MongoDB doesn’t actually store your data as plain JSON strings — it converts them into BSON internally.

2. Why BSON over JSON?

JSON is great, but it has limitations:

  • Limited data types: JSON only supports strings, numbers, booleans, arrays, objects, and null.
  • Inefficient storage: JSON is text-based and takes more space.
  • Slow parsing: Machines have to interpret text, which is slower.

BSON improves on these by:

  • Supporting richer data types (like Date, ObjectId, Binary, Decimal128, etc.).
  • Using binary encoding for compactness and speed.
  • Adding length prefixes so MongoDB can skip or jump over fields quickly.

3. Structure of BSON Document

A BSON document is a sequence of elements. Each element is:

<type><field name><value>
  • Type: 1 byte that says what kind of value (string, int32, ObjectId, etc.).
  • Field name: C string (UTF-8 + null terminator).
  • Value: Depends on type (binary, int, double, etc.).

At the document level:

  • The document starts with an int32 total size.
  • Then contains elements one after another.
  • Ends with a 0x00 (null byte).

4. Supported Data Types in BSON (beyond JSON)

Here’s where BSON shines. Some key types:

  • ObjectId: 12-byte unique identifier (default _id field in MongoDB).
  • Date: Stored as a 64-bit integer (milliseconds since Unix epoch).
  • Int32 / Int64 / Double / Decimal128: Multiple numeric types.
  • Binary Data: Can store arbitrary byte arrays.
  • Timestamp: Special type used for replication/operations.
  • Regex: Stores regular expressions natively.
  • Null, Boolean, Array, Embedded Document: Same as JSON but binary encoded.

Example (conceptually in BSON form):

{
  "_id": ObjectId("507f1f77bcf86cd799439011"),
  "name": "Alice",
  "age": 29,
  "isActive": true,
  "balance": Decimal128("12345.67"),
  "createdAt": ISODate("2025-09-29T12:00:00Z"),
  "tags": ["user", "premium"],
  "profile": { "email": "alice@example.com", "phone": null }}
// Internally, this is stored in BSON with type codes + binary values.

5. Example: JSON vs BSON Encoding

JSON: { "x": 5 }

In BSON (hex representation):

0x0C 0x00 0x00 0x00   // total document size (12 bytes)
0x10                  // type: int32 (BSON Type Code)
'x' 0x00              // field name "x"
0x05 0x00 0x00 0x00   // value: 5
0x00                  // end of document

Notice:

  • It’s not human-readable.
  • But machines can parse it instantly without string scanning.

6. Why Does MongoDB Use BSON Internally?

  • Efficient storage: Compact binary representation.
  • Efficient traversal: BSON has length prefixes → MongoDB can skip fields quickly.
  • Rich types: Supports types JSON cannot.
  • Indexing: BSON makes comparisons and indexing faster (e.g., ObjectId vs string ID).
  • Transport: BSON is used in MongoDB’s wire protocol between client ↔ server.

7. BSON vs JSON vs Extended JSON

  • JSON: What you write in queries ({ "name": "Alice" }).
  • BSON: What MongoDB stores internally and transmits.
  • Extended JSON: A way to represent BSON types in JSON so they don’t lose meaning.

Example (Extended JSON):

{ "createdAt": { "$date": "2025-09-29T12:00:00Z" } }
// Because JSON alone cannot represent a native Date.

8. Real-World Analogy

JSON = a human-readable menu card.

BSON = the actual food items prepared compactly for the kitchen.

Extended JSON = when you take BSON food and try to describe it back on paper with special notation.

✅ Summary:

BSON = “Binary JSON.” It’s how MongoDB internally represents documents — compact, fast, and richer than JSON. Without BSON, MongoDB couldn’t efficiently handle large data, indexing, or advanced types.

Node.js Driver: JSON to BSON Conversion 💻

1. Flow of Data (Node.js → MongoDB Server)

When you write something like:

await db.collection("users").insertOne({ name: "Alice", age: 25 });

you’re passing a JavaScript object ({ name: "Alice", age: 25 }). MongoDB only understands BSON over its wire protocol. The conversion happens in the MongoDB Node.js Driver.

2. Who Does the Conversion?

  • The **MongoDB Node.js Driver** (official library: `mongodb`) is responsible.
  • Inside the driver, there’s a **BSON serialization/deserialization engine** (implemented in JavaScript and sometimes in native C++ for speed).
  • That engine converts your plain JavaScript objects → BSON → sends over TCP/IP to the MongoDB server.

3. Libraries Involved

When you npm install mongodb, you also get the **`bson` package**. This package defines:

  • Encoders: Take JavaScript/JSON objects and encode them into BSON binary (bson.serialize()).
  • Decoders: Take BSON binary (from MongoDB responses) and turn it back into JavaScript objects (bson.deserialize()).

Example with `bson` Package:

const { BSON } = require('bson');
const obj = { name: "Alice", age: 25 };

// Convert JS object to BSON
const bsonData = BSON.serialize(obj);
// Output: BSON bytes: 

// Convert BSON back to JS
const backToJs = BSON.deserialize(bsonData);
// Output: JS object: { name: 'Alice', age: 25 }

BSON Jumping: The Length Prefix for Fast Queries 🚀

What is meant by BSON add length prefix so MongoDB can skip or jump over fields quickly?

JSON Problem: To find a field in JSON, the computer must scan character by character (e.g., scan "Alice" letter by letter to get to "age"). This is slow.

{ "name": "Alice", "age": 25 } // Linear Scan Required

BSON Solution: BSON stores the length of the field's value upfront. This length acts as a "skip counter" for MongoDB.

How MongoDB Jumps Over Fields

BSON field structure always contains the **field name** and then the **value** (which has a length prefix for variable types like strings/arrays/docs).

// BSON Layout (Simplified View for { "name": "Alice", "age": 25, "city": "London" })
// Note: String length includes null terminator (\0)
// Field 1:
   Type: string
   Field name: "name"
   String length: 6   <-- JUMP COUNTER
   Value: "Alice\0"
// Field 2:
   Type: int32
   Field name: "age"
   Value: 25          <-- Fixed size (4 bytes) is the JUMP COUNTER
// Field 3:
   Type: string
   Field name: "city"
   String length: 7
   Value: "London\0"

How MongoDB Finds "city" (The Jump Process)

  1. Start at Field 1 ("name"):
    • Read field name: "name" $\rightarrow$ Not "city".
    • Read length prefix: 6 bytes.
    • JUMP: Cursor skips exactly 6 bytes forward in one step $\rightarrow$ lands at Field 2.
  2. Move to Field 2 ("age"):
    • Read field name: "age" $\rightarrow$ Not "city".
    • Read type: `int32` $\rightarrow$ Fixed size is 4 bytes.
    • JUMP: Cursor skips exactly 4 bytes forward $\rightarrow$ lands at Field 3.
  3. Move to Field 3 ("city"):
    • Read field name: "city" $\rightarrow$ **Match found!** ✅
    • Read length prefix (7) to decode the value ("London").

Crucial Point: MongoDB **always reads the field name** to compare. It uses the **length prefix** (or fixed size) only to **skip the value** efficiently when the field is not the target.

Analogy: Searching for a person in a list of name-tags. Each tag says: [Name][Tag Size][Tag Content]. You check the Name. If it's the wrong person, you skip the "Tag Content" based on the "Tag Size" without reading it.

BSON Types Table and $type Query Operator

BSON Types Table 📑

Every field in BSON starts with a 1-byte type code that tells MongoDB how to interpret the following bytes.

Hex Code Alias Name Description
0x01double64-bit IEEE 754 floating point number
0x02stringUTF-8 string with length prefix
0x03objectEmbedded document (sub-document)
0x04arrayOrdered list (keys "0", "1", etc.)
0x05binDataBinary data (e.g., for UUIDs)
0x07objectId12-byte ObjectId (timestamp + machine ID + PID + counter)
0x08boolBoolean (0x00 = false, 0x01 = true)
0x09dateUTC datetime stored as 64-bit integer (ms since Unix epoch)
0x0AnullNull value
0x0BregexRegular expression (pattern + options)
0x10int32-bit signed integer
0x11timestampInternal MongoDB timestamp (replication/oplog use)
0x12long64-bit signed integer
0x13decimalIEEE 754-2008 Decimal128 (high precision decimal)
0xFFminKeySpecial lowest value (used in sorting)
0x7FmaxKeySpecial highest value (used in sorting)

Using the $type Operator in Queries

The $type operator lets you query documents based on the **BSON type** of a field, which is critical when fields might store mixed types.

// Syntax:
db.collection.find({ field: { $type: <type_alias_or_code> } })

Query Examples:

  • Find documents where 'age' is a string: 
    db.users.find({ age: { $type: "string" } })
  • Find documents where 'age' is a 32-bit integer: 
    db.users.find({ age: { $type: "int" } }) // Alias Name
db.users.find({ age: { $type: 16 } }) // Numeric Code (0x10)
  • Exact Match (Type AND Value): Use $type combined with $eq to ensure both the type and the value are matched (e.g., preventing a string "25" from matching an integer 25). 
    db.users.find({ age: { $type: "int", $eq: 25 } })
