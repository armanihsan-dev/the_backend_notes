MongoDB Authentication & Authorization Deep Dive

The core of security in MongoDB is **Authentication** (verifying the user's identity) and **Authorization** (determining what the authenticated user is allowed to do). MongoDB implements Authorization using **Role-Based Access Control (RBAC)**.

Here is a deep dive into how to set up and manage this in MongoDB using mongosh and how to connect using the Node.js Driver.

1. Core Security Concepts in MongoDB

Concept Description
Authentication The process of verifying a user's identity. This is typically done with a **username and password**. The default mechanism is **SCRAM** (Salted Challenge Response Authentication Mechanism).
Authorization The process of granting an authenticated user the right to perform specific operations on specific resources.
**User** An entity created in a specific database (the **authentication database**, often admin), associated with a username, password, and one or more roles.
**Role** A set of **privileges** (allowed operations) that are scoped to a specific resource (database, collection, or cluster).

2. Setting up Security with mongosh

By default, MongoDB runs **without access control enabled**, meaning anyone can connect to the server and do anything. This must be changed for production environments.

Step 2.1: Enable Access Control

You must edit your MongoDB configuration file (mongod.conf or similar) and restart the server to enable access control (authorization).

YAML
security:
  authorization: enabled

Export to Sheets

Restart your MongoDB server (sudo systemctl restart mongod on Linux, for example). Once restarted, clients can connect, but they must authenticate as a valid user to perform any operations.

Step 2.2: Create the User Administrator

Since access control is now enabled, you must create a user with privileges to manage other users. You can only do this because of a temporary **localhost exception** which allows a connection on the loopback interface to create the first user.

Connect to mongosh without credentials (only works locally and if no users exist yet):

Bash
mongosh

Switch to the admin database:

JavaScript
use admin

Create the user administrator. The userAdminAnyDatabase role is crucial as it grants privileges to create other users and roles across all databases.

JavaScript
db.createUser(
   {
      user: "adminUser",
      pwd: passwordPrompt(), // Prompts for password securely
      roles: [
         { role: "userAdminAnyDatabase", db: "admin" },
         { role: "readWriteAnyDatabase", db: "admin" } // Optional: For full admin access
      ]
   }
)

**Note:** After this, the localhost exception is removed. You must now authenticate to do anything, even from the local host.

Step 2.3: Create Application-Specific Users

Create users with the **principle of least privilege**, meaning they only get the roles (permissions) necessary for their job.

Connect and authenticate as your adminUser:

Bash
mongosh -u "adminUser" -p --authenticationDatabase "admin"

Switch to your application database (e.g., appDB):

JavaScript
use appDB

Create a user for your Node.js application that only needs to read and write on appDB:

JavaScript
db.createUser(
   {
      user: "appReadWriteUser",
      pwd: passwordPrompt(),
      roles: [
         { role: "readWrite", db: "appDB" }
      ]
   }
)

3. Connecting and Authenticating with the Node.js Driver

The official MongoDB Node.js Driver uses a **Connection URI** that includes authentication details.

Connection URI Format

The standard format for authenticating with a username and password is: 

mongodb://<username>:<password>@<host>:<port>/<database>?authSource=<authDB>
URI Component Description
<username>:<password> The user's credentials.
<host>:<port> The server address and port (default is localhost:27017).
/<database> The database the application primarily connects to.
authSource=<authDB> **Crucial:** The database where the user was created (e.g., admin or appDB). This defaults to the database in the path.

Node.js Driver Example

You should use environment variables (e.g., in a .env file) to store credentials, not hardcode them.

Install the driver: npm install mongodb

Example Connection (using appReadWriteUser):

JavaScript
const { MongoClient } = require('mongodb');

// Replace placeholders with your actual values (use environment variables!)
const username = "appReadWriteUser";
const password = "yourStrongPassword";
const host = "localhost:27017";
const authDb = "appDB"; // User was created in appDB

// Connection URI
const uri = `mongodb://${username}:${password}@${host}/appDB?authSource=${authDb}`;

const client = new MongoClient(uri);

async function run() {
  try {
    // Connect to the MongoDB cluster
    await client.connect();
    console.log("Successfully connected and authenticated.");

    const db = client.db('appDB');
    const collection = db.collection('documents');

    // This operation will succeed because appReadWriteUser has 'readWrite' role on 'appDB'
    const result = await collection.insertOne({ data: 'secret' });
    console.log(`Document inserted with ID: ${result.insertedId}`);

    // If appReadWriteUser tried to run an operation on a different DB (e.g., 'admin'), it would fail with an authorization error.

  } catch (e) {
    console.error("Connection or operation failed:", e);
  } finally {
    // Ensures that the client will close when you finish/error
    await client.close();
  }
}

run();

4. Role-Based Access Control (RBAC) Details

MongoDB's authorization is handled by the server based on the **roles** assigned to the authenticated user.

Built-in Roles

MongoDB provides many built-in roles that grant common sets of privileges. Some key ones include:

Role Scope Description
read Database Allows read access to data and meta-data on the specified database.
readWrite Database Allows read and write access on the specified database.
userAdmin Database Allows managing users and roles on the specified database.
userAdminAnyDatabase Cluster (on admin DB) Allows managing users and roles on any database.
dbAdminAnyDatabase Cluster (on admin DB) Allows performing administrative operations on any database.

User-Defined Roles

You can also create **custom roles** to define highly granular permissions.

Create a Custom Role in mongosh (e.g., on the appDB):

JavaScript
use appDB
db.createRole(
   {
      role: "appDBOnlyReadRole",
      privileges: [
         { resource: { db: "appDB", collection: "data" }, actions: [ "find" ] }
      ],
      roles: []
   }
)

Create a User with the Custom Role:

JavaScript
db.createUser(
   {
      user: "appReadOnlyUser",
      pwd: passwordPrompt(),
      roles: [
         { role: "appDBOnlyReadRole", db: "appDB" }
      ]
   }
)

This new user, appReadOnlyUser, can only perform the find operation on the data collection within the appDB database. Any attempt to write data or read from a different collection will result in an **Authorization Failure**.

Starting MongoDB with Authentication

To secure MongoDB by requiring users to authenticate before accessing databases, enable authentication with either:

Method 1: --auth Flag (Terminal-Based)

Run MongoDB daemon with --auth flag to enforce authentication:

bash
mongod --auth

This makes MongoDB require a user login for any database operation.

Method 2: Configuration File (mongod.conf)

Add this under the security section in the configuration file:

text
security:
  authorization: enabled

Then restart MongoDB to apply changes. This is equivalent to the --auth flag but preferred for persistent setup.

Creating the Admin User in admin Database (Root Privileges)

After authentication is enabled, create an admin user who has full root privileges to manage users and databases:

Open the MongoDB shell:

bash
mongosh

Switch to admin database (special database for admin users):

javascript
use admin

Create the admin user with root role (full privileges):

javascript
db.createUser({
  user: "admin",
  pwd: "admin",
  roles: [{ role: "root", db: "admin" }],
});

This user manages authentication and authorization.

Connecting to MongoDB with Authentication

To access MongoDB once authentication is enabled, users must log in.

Method 1: Mongo shell authentication using db.auth() inside shell:

javascript
db.auth("username", "password");

or

javascript
db.auth({ user: "username", pwd: "password" });

Method 2: Logging in from terminal when starting mongosh:

bash
mongosh -u "username" -p "password" --authenticationDatabase "admin"

Method 3: Connection strings for drivers and tools (e.g., Node.js driver, MongoDB Compass):

text
mongodb://username:password@host:port/authenticationDatabase

or

text
mongodb://username:password@host:port/database?authSource=authenticationDatabase

authenticationDatabase is the database where the user was created (often admin).

To check logged-in user info:

javascript
db.runCommand({ connectionStatus: 1 }).authInfo;

Creating Other Users with Different Roles

Users with roles other than root can have specific permissions scoped to databases.

Example: Create a user with readWrite access on storageApp database:

javascript
use storageApp
db.createUser({
  user: "anurag",
  pwd: "anurag",
  roles: [{ role: "readWrite", db: "storageApp" }],
});

Example: Create a database administrator for storageApp:

javascript
use storageApp
db.createUser({
  user: "dbAdminUser",
  pwd: "secureDBPass",
  roles: [{ role: "dbAdmin", db: "storageApp" }],
});

Roles define specific permissions like reading, writing, or administrative tasks on databases.

Updating User Roles

To modify a user's roles (for example, to grant additional permissions), use updateUser():

Example: Add dbAdmin role to user anurag while keeping existing roles:

javascript
db.updateUser("anurag", {
  roles: [
    { role: "readWrite", db: "storageApp" },
    { role: "dbAdmin", db: "storageApp" },
    { role: "readWrite", db: "test" },
  ],
});

Listing Users

To list all users in the current database:

javascript
db.getUsers();

To list all users across the entire MongoDB server (all databases):

javascript
use admin
db.system.users.find();

Testing Authentication for Other Users

To test a normal user's access, log in specifying the correct database and credentials:

bash
mongosh -u "Anurag" -p "password123" --authenticationDatabase "storageApp"

Test read and write operations:

javascript
db.products.insertOne({ name: "Laptop", price: 1000 });
db.products.find();

Users with readWrite role can read/write data but cannot modify database structure (like indexes).

Removing a User

To remove a user from the current database:

javascript
db.dropUser("Anurag");

Logout User

To log out the current session user in the shell:

javascript
db.logout();

Common MongoDB Roles and Their Meanings

MongoDB provides **Role-Based Access Control (RBAC)**, where users are assigned roles that determine their access level.

1. Database User Roles (For interacting with data)

Role Meaning
read Allows the user to **only read data** from the assigned database. Cannot write or modify data.
readWrite Allows the user to **read and write** data in the assigned database but cannot perform administrative tasks.

2. Database Administration Roles (For managing databases)

Role Meaning
dbAdmin Allows the user to **manage collections, indexes, and validation rules** but cannot read or modify data.
dbOwner Full control over a specific database, including managing users and roles for that database.
userAdmin Allows **managing users and roles for a specific database** but does not grant access to data.

3. Cluster Administration Roles (For managing MongoDB clusters)

Role Meaning
clusterAdmin Grants full control over the cluster, including managing shards, replica sets, and configuration settings.
clusterManager Allows managing the cluster but does not allow administrative tasks like user creation.
clusterMonitor Grants **read-only** access to cluster status and monitoring information.
hostManager Allows managing servers but **not** making database-level changes.

4. Backup and Restore Roles (For managing database backups)

Role Meaning
backup Allows the user to **perform backups** but does not allow modifying data.
restore Allows the user to **restore backups** but does not allow modifying collections directly.

5. All-Database Roles (For managing multiple databases)

Role Meaning
readAnyDatabase Grants **read access** to all databases on the server.
readWriteAnyDatabase Grants **read and write access** to all databases on the server.
userAdminAnyDatabase Allows creating and managing users **for all databases**.
dbAdminAnyDatabase Grants administrative privileges **for all databases**, including index and validation management.

6. Superuser Role (For full server access)

Role Meaning
root Grants **full access** to all databases, collections, users, and settings. The highest privilege level in MongoDB.

7. Custom Roles (For specific needs)

MongoDB allows creating **custom roles** with specific privileges:

javascript
db.createRole({
  role: "insertOnly",
  privileges: [{ resource: { db: "myDatabase", collection: "" }, actions: ["insert"] }],
  roles: []
})

Which Roles to Use?

  • For developers → readWrite
  • For database administrators → dbAdmin, userAdmin
  • For monitoring → clusterMonitor
  • For backups → backup, restore
  • For super admins → root

Additional MongoDB Roles Not Covered in the Previous List 🚀

MongoDB has several other built-in roles that may be useful in specific use cases. Below is a list of roles that were **not included** in the previous markdown file.

1. Internal Roles (Used by MongoDB internally)

Role Meaning
__system A special role with **unrestricted access**. This role is **not** meant to be assigned to users.

2. Roles Related to Specific Operations

Role Meaning
restore Grants the ability to **restore** database backups, but does not allow modifying collections.
readWriteAnyDatabase Provides **readWrite** access to **all** databases on the server.

3. Internal Replication & Sharding Roles (Used in Replica Sets & Sharded Clusters)

Role Meaning
readWriteInternal Grants read and write privileges to **internal system operations**.
enableSharding Allows enabling **sharding** for databases.
clusterMonitor Provides **read-only access** to cluster status and monitoring tools.
clusterManager Allows **managing** the cluster, but not modifying user permissions.
hostManager Grants permissions to manage servers but does **not** allow modifying database-level settings.

4. Auditing & Security Roles

Role Meaning
auditAdmin Allows managing **audit configurations** but does not modify user access.
backup Grants permission to **perform backups** of the database.

5. Special System Roles

Role Meaning
root The **highest-level** role with full access to **all** databases, collections, users, and settings.

Which Additional Roles Should You Use?

  • For managing replica sets → clusterMonitor, clusterManager
  • For backups and recovery → backup, restore
  • For security audits → auditAdmin
  • For sharding → enableSharding

These roles provide additional control in **specialized MongoDB deployments**.
