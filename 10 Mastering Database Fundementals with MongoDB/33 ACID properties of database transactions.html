ACID Properties of a Database Transaction

The **ACID properties** are a set of principles that guarantee the **validity** of database transactions. They ensure that data is **reliable** even during system failures or concurrent operations.

ACID is an acronym for:

  • Atomicity
  • Consistency
  • Isolation
  • Durability

1. Atomicity (All or Nothing)

**Definition:** Atomicity ensures that a transaction is treated as a **single, indivisible unit** of operations. All of the operations within the transaction must succeed, or if any part fails, the **entire transaction is aborted**, and the database state remains unchanged.

**Analogy:** Imagine a chemical reaction: either all the reactants combine to form the final product, or the reaction doesn't happen at all. There is no intermediate state where only half the product is formed.

Example: A Bank Transfer 🏦

Consider a transfer of $100 from Account A to Account B. This transaction involves two distinct database operations:

  • **Debit:** Subtract $100 from Account A.
  • **Credit:** Add $100 to Account B.

Scenario | Result

Scenario Result
Success: Both debit and credit operations complete. The database commits the transaction. The new balances are saved.
Failure (e.g., system crash after Debit but before Credit): Atomicity requires the database to automatically **rollback** the debit operation. Account A's balance is restored to its original value. The transaction is treated as if it never happened.

2. Consistency (Valid State)

**Definition:** Consistency ensures that a transaction, when successfully completed, moves the database from one **valid state** to another. It guarantees that all predefined rules, **constraints**, triggers, and cascades (like primary/foreign keys, and validation rules) are maintained.

**Analogy:** The rules of chess: a player cannot jump a pawn backward or move a king into check. Every successful move transitions the board into a new, valid state according to the rules.

Example: Account Balances and Constraints 🔒

Suppose your database has a constraint that says: "An account balance can never be negative."

Scenario | Result

Scenario Result
Transaction: Attempt to debit $500 from an account with only $300. The transaction will fail or be aborted **before** the debit operation is committed because completing it would violate the "no negative balance" constraint. **Consistency is preserved.**
Success: Debit $100 from $300. The new state is $200, which is valid and consistent with the rules.

3. Isolation (Independent Execution)

**Definition:** Isolation ensures that **concurrent transactions** do not interfere with each other. From the perspective of one transaction, it appears as if it's the **only transaction running** on the system.

**Analogy:** Multiple people using an ATM simultaneously. Each user's transaction (checking balance, withdrawing cash) is isolated from others, so one person doesn't see or interfere with another person's running process.

Example: Concurrent Updates 🛒

Two users, User X and User Y, try to buy the last available item (Stock = 1) at the exact same moment.

Time | User X's Transaction | User Y's Transaction | Isolation Result

Time User X's Transaction User Y's Transaction Isolation Result
T1 Read Stock (1) Read Stock (1) Low isolation levels would allow this, leading to error.
T2 Decrement Stock to 0 Decrement Stock to 0
T3 Commit Commit Both users think they successfully bought the item, but the stock is now -1.
ACID Isolation Solution: The database serializes the operations. User X gets a **lock** on the Stock record. User Y is forced to wait until User X commits. When User Y attempts to read the stock, it sees the updated value of 0, and the transaction fails immediately. **Only one successful purchase is committed.**

4. Durability (Permanent Record)

**Definition:** Durability guarantees that once a transaction has been **committed**, its changes are **permanent** and will survive any subsequent system failure, such as a power loss, crash, or reboot.

**Analogy:** Writing data to a stone tablet. Once the data is etched (committed), it is permanent, regardless of what happens to the environment (unlike chalk writing, which is not durable).

Example: Power Failure after Commit 💡

You just made a large deposit into your savings account.

Scenario | Result

Scenario Result
Commit: The transaction successfully commits. The database writes the confirmation to a **durable storage** (usually the transaction log).
Power Loss: The system crashes immediately after the bank sends the "Transaction Successful" message, but before the main database files could be fully updated.
Durability Solution: When the system reboots, the database management system (DBMS) checks the **transaction log**. It sees the deposit transaction was marked as committed. The DBMS then uses the log to **redo** any missing updates to the main data files, ensuring the deposited amount is permanently reflected in your account balance.
