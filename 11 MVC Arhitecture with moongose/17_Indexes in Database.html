Indexes in Database

That's a great set of questions about indexing! It's a critical concept in databases, and it's normal to find it confusing initially.

Here is a breakdown of database indexing, its purpose, and how to work with it in MongoDB.

What are Indexes and Why are They Needed?

A **database index** is a specialized data structure that stores a small, organized copy of data from one or more columns (or fields) of your main table or collection. This structure also includes **pointers** (or links) to the full records in the original location.

Think of it like the **index at the back of a book** 📚:

  • The **book** is your main table/collection of data.
  • The **index** is your database index. It lists keywords (the indexed field values) and the page numbers (pointers) where you can find the detailed information.

Need for Indexes

Indexes are needed primarily to **speed up data retrieval** (read operations). Without an index, when you search for a record (e.g., a customer by their name), the database must perform a **full table scan**—meaning it checks every single record in the table sequentially until it finds a match. This is very slow for large amounts of data.

How Indexing Makes Querying Fast

Indexing speeds up queries by replacing the slow **full table scan** with a much faster **index search** (often implemented using data structures like a **B-tree**).

  • Search Efficiency: Instead of checking every row, the database uses the index, which is sorted and structured (like a **B-tree**), to quickly narrow down the location of the desired data. Searching a B-tree is incredibly fast, typically completing in **logarithmic time** ($O(\log N)$), which is a huge improvement over the **linear time** ($O(N)$) of a full table scan.
  • Direct Access: Once the index finds the specific value you're looking for (e.g., "John Smith"), it uses the recorded pointer to jump directly to the exact physical location of the full record in the table/collection, avoiding any further unnecessary searching.

"ID is Indexed by Default"

The statement "**ID is indexed by default**" is generally **true** across most database systems (both relational like SQL and NoSQL like MongoDB).

  • In Relational Databases (like MySQL, PostgreSQL): The **Primary Key** (which is often named **id**) is automatically indexed. This is typically a **clustered index**, which determines the physical order of the data on disk, making lookups by ID extremely fast.
  • In MongoDB: The **_id** field is automatically created as a **unique index** on every collection. This is a non-clustered index by default and ensures every document has a unique identifier, which is critical for document retrieval.

Unique vs. Non-Unique Indexes

The key difference lies in the **constraint** they enforce on the data:

Feature Unique Index Non-Unique Index
Purpose Speeds up lookups **and** enforces that **no two documents/rows** can have the same value for the indexed field(s). Speeds up lookups **only**. Allows duplicate values for the indexed field(s).
Examples email, social security number, or a **Primary Key**. last_name, city, product_category.

Which Type of Index to Make?

You should create an index on a field if:

  • You frequently **filter** by that field (i.e., it appears in WHERE clauses in SQL or query objects in MongoDB).
  • You frequently **sort** results by that field (i.e., it appears in ORDER BY clauses or the MongoDB sort() method).

You should use a **Unique Index** specifically when:

  • The field **must** contain distinct values (e.g., enforcing that every user's email address is unique). This is about **data integrity** as much as performance.

You should use a **Non-Unique Index** when:

  • The field is frequently searched or sorted, but it's **expected** to have duplicate values (e.g., many users have the same city). This is purely for **performance**.

Working with Indexes in MongoDB (using mongosh)

In MongoDB, you use the db.collection.createIndex() method in mongosh to create indexes.

1. Creating a Simple Index

To create a non-unique, ascending index on the name field in a collection called users:

JavaScript
db.users.createIndex({ name: 1 })

{ name: 1 } specifies the field to index and the sort order (1 for ascending, -1 for descending).

2. Creating a Unique Index

To enforce uniqueness on the email field while also indexing it for fast lookups:

JavaScript
db.users.createIndex({ email: 1 }, { unique: true })

The second argument, { unique: true }, makes this a unique index.

3. Creating a Compound Index

To create an index on multiple fields, which is often useful for filtering on a combination of fields (e.g., searching by status and sorting by date):

JavaScript
db.orders.createIndex({ status: 1, order_date: -1 })

This creates a compound index on status (ascending) and order_date (descending).

4. Viewing Existing Indexes

To see all indexes on a collection:

JavaScript
db.users.getIndexes()

This will show the default _id index and any others you've created.

5. Dropping an Index

If an index is no longer needed (too much write overhead or not used in queries), you can drop it by name:

JavaScript
db.users.dropIndex("email_1") // Use the index name from getIndexes()
