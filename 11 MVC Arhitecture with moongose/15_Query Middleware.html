Mongoose Query Middleware Deep Dive 🪝

Mongoose Query Middleware, also known as hooks, are functions that are executed automatically before (pre) or after (post) specific query operations on your Mongoose models. They allow you to add custom logic to the data lifecycle in a centralized and reusable way, preventing repetitive code.

Definition and How It Works

Definition

Query middleware intercepts methods that operate on the query object, primarily affecting multiple documents or the structure of the query itself. This is distinct from Document Middleware, which runs on individual document instances (e.g., doc.save()).

How It Works

  • Attachment: You define the middleware on your Mongoose Schema using .pre() or .post().
  • Trigger: When a corresponding query method is called (e.g., Model.find(), Model.updateOne(), Model.deleteMany()), the middleware functions are executed.
  • this Context: Inside a query middleware function, the keyword this refers to the Mongoose Query object. This is the key difference from document middleware, where this refers to the document. Accessing the query object allows you to inspect or modify the query's parameters.
  • Flow Control (Pre-Hooks): In pre middleware, you must call the next() function to pass control to the next middleware in the chain or to execute the actual query. If you pass an error to next(err), the operation stops, and the error is passed up.
  • Execution (Post-Hooks): Post middleware runs after the query has finished. The result of the query is often passed as an argument to the post-hook function.

Methods that Trigger Query Middleware

Query middleware is supported for methods that return a Query object, including:

  • count, countDocuments
  • find, findOne, findById
  • update, updateOne, updateMany
  • deleteMany, deleteOne (when called directly on the model, e.g., Model.deleteMany())

Important Note: Methods like Model.findOneAndUpdate(), Model.updateOne(), and Model.deleteOne() (when called on the model) trigger query middleware, even though they may seem like document operations. Mongoose handles them as query operations by default.

Clear Syntax

You define query middleware on the Mongoose Schema.

Pre-Query Middleware Syntax

JavaScript 
// userSchema is your Mongoose Schema instance

userSchema.pre('find', function(next) {
    // 'this' is the Query object
    console.log('Running a find query!');

    // You can modify the query here, for example, adding a filter
    this.where({ isActive: true }); 
    
    // Must call next() to proceed
    next(); 
});

// Using a regex to apply to all 'find' operations (find, findOne, findById)
userSchema.pre(/^find/, function(next) {
    // this logic runs before find, findOne, findById, etc.
    this.select('-password'); // Always exclude the password field
    next();
});
  • 'find' is the hook name (Mongoose method).
  • The function receives a next callback.
  • this is the Query object, giving you access to methods like where(), select(), sort(), and getQuery().

Post-Query Middleware Syntax

JavaScript 
userSchema.post('find', function(docs, next) {
    // 'docs' is the array of documents returned by the find query
    console.log(`Found ${docs.length} documents.`);
    
    // You can modify the results here (less common, but possible)
    docs.forEach(doc => {
        doc.isProcessed = true;
    });

    // Only call next() if the function is asynchronous and takes next as a parameter
    // For synchronous post hooks or those returning a Promise, next() is optional/not needed.
    next(); 
});

The post-hook receives the result of the query (e.g., docs for a find, result for an update) and a next callback (if defined with 2 arguments).

Real-World Use Cases 💡

Query middleware is exceptionally powerful for enforcing global and consistent business logic across all relevant database reads or writes.

1. Implementing "Soft Delete" (Pre-Find/Read)

This is the most common use case. Instead of permanently deleting records, you mark them as deleted (deleted: true). You then use pre-query middleware to ensure that all read operations automatically exclude these soft-deleted records.

JavaScript 
// On your Schema:
userSchema.pre(/^find/, function(next) {
    // Only show documents where the 'deleted' field is NOT true
    // This runs for find(), findOne(), findById(), etc.
    this.where({ deleted: { $ne: true } }); 
    next();
});
// Now, when you call:
// await User.find({}); // It automatically runs as User.find({ deleted: { $ne: true } })

This single hook makes your entire application respect the soft-delete policy without having to manually add { deleted: { $ne: true } } to every single query.

2. Automatic Field Selection/Projection (Pre-Find/Read)

For security or performance, you might want to ensure sensitive fields are never accidentally included in query results unless explicitly requested.

JavaScript 
userSchema.pre(/^find/, function(next) {
    // Exclude 'ssn' (Social Security Number) and 'password' from all read queries
    this.select('-ssn -password'); 
    next();
});

3. Timestamp Management for Updates (Pre-Update)

While Mongoose's built-in timestamps: true handles createdAt and updatedAt for save()/create(), it doesn't automatically update a timestamp for update queries like Model.updateOne(). You can enforce this with query middleware.

JavaScript 
userSchema.pre('updateOne', function(next) {
    // 'this.getUpdate()' returns the update object (e.g., {$set: {field: 'value'}})
    // We add the 'updatedAt' field to the $set operator
    this.set({ updatedAt: new Date() });
    next();
});

4. Logging and Auditing (Post-Query)

You can log the outcome of a query for auditing purposes.

JavaScript 
userSchema.post(/^find/, function(docs) {
    // 'docs' is the result of the query
    console.log(`Query ran successfully. Returned ${docs.length} documents.`);
    // Or log to a dedicated audit file/service
    // auditService.logQuery({ method: 'find', resultsCount: docs.length });
});

Query Middleware allows for extremely flexible and global control over your database interactions, making your code DRY (Don't Repeat Yourself) and your data handling consistent.

Defining a Single Global Query Middleware ❓

Question: How can we define one single query middleware that runs for every query middleware, even we can use regex like /^find/?

That's an excellent question that highlights a common desire for global query logic!

The short answer is you cannot define a single middleware hook that runs for all query middleware operations (like find, update, delete, count, etc.) with a single regex pattern.

Mongoose's middleware system is structured around specific method names. The regex pattern (/^find/) only works for query methods that start with find (find, findOne, findById, findOneAndDelete, etc.).

However, there is a **Mongoose Plugin** approach that gives you a centralized way to apply logic across multiple query hooks without having to define them all manually on every schema.

Why a Single Regex Hook Won't Work

Mongoose defines query hooks based on the name of the underlying query function.

Query Method Hook Name Type of Operation
User.find() 'find' Read
User.updateMany() 'updateMany' Write
User.deleteOne() 'deleteOne' Write
User.countDocuments() 'countDocuments' Read

The regex userSchema.pre(/^find/, ...) captures all read operations that start with "find," but it fails to capture non-read operations like updateMany, deleteOne, countDocuments, or bulkWrite. To cover all query operations, you would need to specify each one.
