SSH (Secure Shell)

SSH, or Secure Shell, is a network protocol that allows two computers to communicate securely over an unsecured network. It provides strong authentication and encrypted data communication between devices.

How it Works

SSH operates on a client-server model. The SSH client connects to the SSH server and initiates a secure connection. The security of the connection is established through the use of public-key cryptography.

  • Handshake: The client contacts the server and they exchange information, including protocol version and cryptographic algorithms to be used.
  • Authentication: The server presents its public key to the client. The client can verify this key to ensure it's connecting to the correct server. For user authentication, the user typically provides a password or, more securely, a private key that corresponds to a public key stored on the server.
  • Secure Session: Once authenticated, an encrypted tunnel is established. All data—including commands, output, and file transfers—is encrypted before transmission and decrypted upon reception.

Why Backend Developers Use It

Backend developers frequently use SSH for several key reasons:

  • Remote Management: It's the standard for managing and controlling remote servers. Developers use it to access a server's command-line interface, install software, configure settings, and monitor system performance.
  • Secure File Transfer: SSH includes protocols like SFTP (SSH File Transfer Protocol) and SCP (Secure Copy Protocol), which allow for the secure transfer of files between a local machine and a remote server. This is essential for deploying code, uploading assets, and backing up data.
  • Security: Since SSH encrypts all data, it protects sensitive information like login credentials and configuration details from being intercepted by malicious actors. This is a critical security practice for any professional developer.
  • Port Forwarding: SSH can forward network traffic from one port to another, a technique known as port forwarding or tunneling. This is useful for accessing a service on a private network from a public one, or for securely accessing a local database.

How to access remote terminal using SSH?

Accessing a remote terminal using SSH is a fundamental skill for backend developers. The process involves using a command-line interface on your local machine to connect to a remote server.

The Basic SSH Command

To connect to a remote server, you'll use the ssh command followed by the server’s login information. The general syntax is:

ssh [username]@[hostname_or_IP_address]
  • [username]: The username you use to log in to the remote server.
  • [hostname_or_IP_address]: The IP address or domain name of the remote server.

For example, to connect to a server with the IP address 192.168.1.10 using the username jane_doe, you'd type:

ssh jane_doe@192.168.1.10

Authentication 🔐

After running the command, the server will need to authenticate you. This can be done in two primary ways:

  • Password Authentication: You'll be prompted to enter the password for the specified username on the remote server.
  • SSH Key Authentication: This is a more secure method and is highly recommended. You generate a pair of keys—a public key and a private key. The public key is placed on the remote server, and the private key is kept on your local machine. When you attempt to connect, the server uses the public key to verify that you have the corresponding private key, allowing you to log in without a password.

Common Command Options

  • Custom Port: If the SSH server is not running on the default port 22, you can specify a different port using the -p flag. For example, if the port is 2222: 
    ssh -p 2222 jane_doe@192.168.1.10
  • SSH Keys: To specify a specific private key file, use the -i flag: 
    ssh -i ~/.ssh/id_rsa_work jane_doe@192.168.1.10
  • Running a Single Command: You can run a command on the remote server without opening an interactive session by appending the command to the SSH line. For example, to list the contents of a directory: 
    ssh jane_doe@192.168.1.10 "ls -l /var/www"
  • Exiting the Session: When you're finished, simply type exit in the terminal to close the connection and return to your local machine's command line.

Troubleshooting: "sudo: ufw: command not found"

You said: sudo ufw allow ssh

sudo: ufw: command not found, why

Good catch 👍

The error: sudo: ufw: command not found means that UFW (Uncomplicated Firewall) is not installed on your Ubuntu system.

🔎 Why?

Some Ubuntu Server installations don’t include UFW by default. Instead, they rely on iptables or nftables directly. That’s why the ufw command isn’t found.

⚡ How to fix (if you want UFW):

Install it first:

sudo apt update
sudo apt install ufw -y

Then allow SSH:

sudo ufw allow ssh

Enable the firewall (⚠️ do this only after allowing SSH, otherwise you might lock yourself out):

sudo ufw enable

Check rules:

sudo ufw status verbose

✅ Alternative (if you don’t want UFW):

You can use iptables or nftables directly. For example, to allow SSH (port 22):

# iptables
sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT

# nftables
sudo nft add rule inet filter input tcp dport 22 accept

Wireshark: Checking Connection Between Ubuntu and Windows

You said: how to check connection between ubunto terminal and win terminal using wireshark

Nice one 👍 You want to verify the connection between an Ubuntu terminal and a Windows terminal using Wireshark.

Let’s go step by step so you can actually see packets flowing.

🟢 Step 1: Figure out IP addresses of both machines

On Ubuntu: hostname -I or ip addr show

On Windows (Command Prompt / PowerShell): ipconfig

Note down both IPs (e.g., Ubuntu = 192.168.10.20, Windows = 192.168.10.15).

🟢 Step 2: Test connectivity

From Ubuntu → Windows: ping

From Windows → Ubuntu: ping

If ping works, they can reach each other on the network.

🟢 Step 3: Start Wireshark Capture

Open Wireshark on one of the machines (Ubuntu or Windows). Select the network interface in use (usually eth0, wlan0 on Ubuntu, or Wi-Fi/Ethernet on Windows). Start the capture.

🟢 Step 4: Apply Display Filter

To see only traffic between the two machines, use:

ip.addr ==  && ip.addr ==

Example:

ip.addr == 192.168.10.20 && ip.addr == 192.168.10.15

🟢 Step 5: Generate Some Traffic

Try ping between the machines. Or start an SSH connection from Ubuntu to Windows (if OpenSSH server is installed on Windows) or vice versa. You’ll see packets like:

  • ICMP (for ping)
  • TCP/22 (for SSH)
  • TCP/445 (if using SMB file sharing)

🟢 Step 6: Analyze Packets

Ping test → look for ICMP Echo (ping) and ICMP Echo Reply. SSH → look for TCP Handshake (SYN, SYN/ACK, ACK) followed by encrypted traffic. Other protocols → depends on what services you are using.

Wireshark: Why Rows Have Different Colors

You said: why does wireshark used different color for each row

Great screenshot 👍 You’ve noticed Wireshark showing different row colors — that’s not random. Wireshark uses coloring rules to help you visually distinguish traffic types and problems quickly.

🎨 Why Wireshark Uses Colors

  • To make it easier to spot different protocols (TCP, UDP, ICMP, DNS, etc.).
  • To highlight warnings or errors (like retransmissions, resets).
  • To quickly separate client vs. server traffic.

🟢 Common Default Colors (Wireshark)

Wireshark comes with built-in rules (you can see them in View > Coloring Rules):

  • Light blue → UDP traffic
  • Dark blue → TCP traffic
  • Black background + red text → TCP problems (retransmission, duplicate ACK, reset, etc.)
  • Green → Successful TCP connections (handshakes, data exchange)
  • Light purple / violet → TLS/SSL encrypted traffic
  • Gray → Other/uncategorized traffic

🕵️ In your screenshot

  • Light blue (UDP) → e.g., DNS, QUIC, or other UDP-based protocols.
  • Dark blue / teal (TCP normal) → Normal TCP packets (ACKs, handshakes, application data).
  • Black + red row → A TCP error (in your case: [RST, ACK] → TCP connection reset).
  • Light purple rows → TLSv1.3 encrypted HTTPS traffic.

🔧 You can customize this

Go to View → Coloring Rules in Wireshark. You’ll see filters like: tcp → blue, udp → light blue, tcp.analysis.retransmission → black/red, http → green. You can add/remove/change colors based on your preference.

Troubleshooting: "I am unable to see SSH protocol row"

You said: i am uable to see SSH protocol row even the connection is established

Ah, good observation 👌

It’s normal that you don’t see a row labeled SSH in Wireshark, even if your SSH connection works. Let’s break down why:

🔎 Why you don’t see “SSH” in Wireshark

  • Protocol column shows TLS/HTTP often, not SSH

    Wireshark doesn’t always label SSH traffic as "SSH". It usually just shows it as TCP (port 22).

  • Encrypted traffic

    SSH encrypts everything after the initial handshake, so Wireshark can’t decode the application data. You’ll only see the TCP packets carrying encrypted payload.

  • Protocol detection depends on port

    By default, Wireshark recognizes SSH only on port 22. If your server is running SSH on another port (e.g., 2222), Wireshark will just show it as TCP unless you tell it otherwise.

🟢 How to confirm SSH traffic

Apply this filter in Wireshark: tcp.port == 22

This will show all packets to/from port 22.

Check for TCP handshake + encrypted application data:

  • You should see: SYN → SYN, ACK → ACK (TCP handshake)
  • Followed by "Encrypted packet" / "Application Data"

If using a custom SSH port: tcp.port ==

(Optional) Tell Wireshark to decode as SSH:

  • Right-click on a packet → Decode As…
  • Select Transport tab → choose SSH for port 22 (or your custom port).

Then Wireshark will mark it as SSH instead of generic TCP.

✅ Quick test

From Ubuntu, run: ssh user@

In Wireshark (on Windows or Ubuntu), filter: tcp.port == 22

You’ll see packets marked TCP → Encrypted SSH traffic.
