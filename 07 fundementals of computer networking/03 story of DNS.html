The Story of DNS

The story of the Domain Name System (DNS) is a tale of how the internet evolved from a small, research-oriented network into the global system we know today. It all started with a simple, but ultimately unscalable, system and the need for a better way to manage a growing network.

The Problem: The HOSTS.TXT File

In the early days of the internet (then known as ARPANET), computers were identified by a numerical address called an IP address. To make things easier for users, a simple text file named HOSTS.TXT was created. This file, maintained by the Stanford Research Institute, acted as a central directory, mapping human-readable names (like SRI) to their corresponding IP addresses.

As the internet grew, this manual, centralized approach became a major problem. Every time a new computer was added or a name changed, the HOSTS.TXT file had to be updated and redistributed to every computer on the network. This process was slow, inefficient, and couldn't keep up with the rapid expansion of the network. The file was becoming too large and was often out of date, making it a serious bottleneck for the internet's growth.

The HOSTS.TXT file had to be updated and redistributed to every computer on the network because it was a centralized, manual system for name resolution. It served as a single, static directory that mapped all hostnames to their corresponding IP addresses for the entire ARPANET (the precursor to the internet).

The Manual Process

In the early days of the network, a central authority, the Stanford Research Institute (SRI), maintained the master HOSTS.TXT file.

  • Static nature: The file was a simple text document. Any change to the network, such as a new computer being added or an existing one's name or address changing, required a manual edit of this single file.
  • Centralized authority: Only the SRI could make these changes to the master file.
  • Manual distribution: Once updated, the new version of the HOSTS.TXT file had to be physically or electronically copied and sent to every single computer on the network. There was no automated way for a computer to dynamically ask for an address. It had to have the entire, up-to-date file stored locally to function correctly.

As the network grew from dozens to hundreds and then thousands of computers, this process became a major bottleneck. It was slow, prone to errors, and simply couldn't keep pace with the rapid expansion of the internet. This inefficiency is what led to the development of the Domain Name System (DNS), which is a decentralized and hierarchical system that allows for local, dynamic management of names and addresses.

The Solution: A Distributed System

Recognizing this fundamental flaw, a computer scientist named Paul Mockapetris at the University of Southern California's Information Sciences Institute, proposed a new, decentralized system in 1983. He envisioned a system that would allow for local management of names and addresses, while still being accessible to everyone on the network. This was the birth of the Domain Name System (DNS).

Instead of one single, giant file, DNS created a distributed database that was organized in a hierarchy. This new system had several key features:

  • Hierarchical Structure: DNS introduced the concept of top-level domains (TLDs) like .com, .org, and .edu. This structured approach allowed for the delegation of authority, meaning that the responsibility for managing names was distributed across various organizations.
  • Domain Naming: Instead of a simple hostname, DNS introduced the idea of a fully qualified domain name (FQDN), such as www.example.com. This name is a logical, human-friendly representation that's much easier to remember than a string of numbers.
  • Name Servers: The system relied on name servers to store and provide information about domain names. When a user enters a domain name, their computer sends a query to a DNS server, which then "resolves" the name by finding the correct IP address. This process is a lot like using a phone book to find a person's phone number.

The Legacy

Mockapetris's invention solved the scalability problem of the early internet. It allowed the network to expand exponentially without being bogged down by a centralized directory. Today, DNS remains a fundamental pillar of the internet, silently working in the background to translate billions of domain names into IP addresses every single day. The system has continued to evolve with new technologies like DNSSEC for enhanced security, but its core principle—a distributed, hierarchical database for mapping names to addresses—is the same revolutionary idea that was born in 1983.

The Problem: The Need to Connect

Imagine the early days of the internet, when it was just a small network of computers used by researchers. Each computer was identified by a unique numerical address called an IP address (e.g., 192.0.2.1). Humans, however, find it much easier to remember names than long strings of numbers. So, researchers wanted a way to use simple, human-readable names like SRI-NIC instead of an IP address.

To solve this, a central authority—the Stanford Research Institute (SRI)—created a simple text file called HOSTS.TXT. This file was a list of every computer on the network, mapping its name to its IP address. For example:

192.0.2.1 SRI-NIC
192.0.2.2 MIT-MULTICS

The Flaw of HOSTS.TXT

Every time a new computer was added or a name was changed, the SRI had to manually update this single HOSTS.TXT file. Then, they had to send the new, updated file to every single computer on the network. As the network grew, this process became a huge problem:

  • Scalability: The file became too large and difficult to manage.
  • Latency: It took a long time to distribute the updated file to everyone, so the information was often out of date.
  • Centralization: The entire system relied on a single point of failure (the SRI). If the SRI's computer went down, no one could get the correct information.

This system was an obvious bottleneck and was not built to handle the explosive growth of the internet.

How DNS Solved the Problems

Instead of one giant list, DNS created a tree-like structure. Think of it like an organization chart:

  • Root Servers: At the very top of the hierarchy are the root servers. They don't store every name, but they know where to find the next level down.
  • Top-Level Domains (TLDs): Below the root are TLDs like .com, .org, and .edu. The root servers know which servers are responsible for managing each TLD.
  • Domain Name Servers: The servers for .com know who's in charge of google.com, and the servers for google.com know the IP address for www.google.com.

This new system solved all the problems of HOSTS.TXT:

  • Scalability: The system is distributed. Instead of one server managing everything, thousands of servers manage small parts of the internet, making it highly scalable.
  • Efficiency: When you type google.com into your browser, your computer doesn't need to download a massive file. It just asks a local DNS server, which then sends a few queries up the hierarchy to find the correct IP address. This happens in a fraction of a second.
  • Decentralization: There is no single point of failure. If one DNS server goes down, others can still function, and the system is designed to be resilient.

In short, HOSTS.TXT was an unsustainable, centralized phone book. DNS is an efficient, distributed network of phone books that can quickly find any number, anywhere in the world.

How HOSTS.TXT used to work?

The HOSTS.TXT file was a simple, static text file that served as an early form of a directory for the internet. It worked by creating a one-to-one mapping of human-readable hostnames to their corresponding numerical IP addresses.

Here's how it worked:

  • A Single, Central File: In the beginning, there was a single master HOSTS.TXT file maintained by the Stanford Research Institute. It was a comprehensive list of every computer on the ARPANET.
  • The Content: The file was structured with two columns: the IP address and the hostname. For example, a line might look like this: `192.0.2.1 SRI-NIC`.
  • The Process: When a user wanted to connect to a computer using its name (e.g., "SRI-NIC"), their computer would first consult its local copy of the HOSTS.TXT file. It would look up the name, find the corresponding IP address, and then use that address to establish the connection.

The fundamental flaw was that every time a change was made—a new computer was added, or an IP address was changed—the central file had to be manually edited, and then a copy of the new file had to be manually distributed to every single computer on the network. This process was slow, inefficient, and simply couldn't keep up as the network grew, eventually leading to the development of the decentralized Domain Name System (DNS).

The Process of Connecting to a Remote Computer

After obtaining the IP address from the HOSTS.TXT file, researchers would use a specific command-line tool, like Telnet, to connect to the remote machine. Telnet was the primary protocol used on the early ARPANET for remote login.

The Exact Process

The process was straightforward once the IP address was known:

  • Retrieve IP Address: The user would first look up the hostname of the computer they wanted to connect to in their local copy of the HOSTS.TXT file. For example, they might find that the hostname SRI-NIC corresponded to the IP address 10.0.0.1.
  • Use a Command-Line Tool: The user would then open a command-line interface on their own computer and type a command that included the IP address. For example, they might use the `TELNET` command followed by the IP address. 
    TELNET 10.0.0.1
  • Establish a Connection: This command would initiate a connection to the remote computer using its IP address. Once the connection was established, the user could log in and interact with the remote machine as if they were a local user. This process was fundamental to the early internet, allowing researchers to share resources and collaborate across vast distances.

How .com, .gov was introduced

The introduction of Top-Level Domains (TLDs) like .com and .gov was a key part of the move from the centralized HOSTS.TXT system to the decentralized Domain Name System (DNS). The idea was to create a structured and organized way to categorize websites and delegate authority for managing names.

The Birth of TLDs

In the mid-1980s, when the DNS was being developed, a group of foundational TLDs was created. They were introduced in 1985 with a specific purpose for each:

  • .com (commercial): Intended for commercial organizations and businesses. It was meant to be the home for companies looking to establish an online presence.
  • .edu (education): Reserved for educational institutions, particularly universities and colleges.
  • .gov (government): Exclusively for United States government agencies and entities.
  • .mil (military): Designated for the U.S. military and its related organizations.
  • .org (organization): Meant for non-profit organizations and other entities that didn't fit into the other categories.
  • .net (network): Originally for network service providers and infrastructure, but later opened up for general use.

The Original Intent vs. Today's Reality

The original idea was to keep these domains very strict in their use. For example, to get a .gov domain, you had to be a U.S. government entity. Similarly, .edu was for accredited educational institutions.

However, the internet grew in ways no one could have predicted. The .com domain, in particular, became the most popular and widely used TLD in the world. Its "commercial" purpose quickly expanded to include virtually any type of website, as businesses and individuals alike wanted to capitalize on its universal recognition. This trend led to a massive expansion of the TLD system, with hundreds of new generic TLDs (.online, .app, .blog) and country-code TLDs (.us, .uk, .jp) being introduced over time.

In short, the .com and .gov TLDs were introduced as part of the initial design of DNS to create a logical, hierarchical structure for the internet. This system replaced the single, flat HOSTS.TXT file and laid the groundwork for the modern, global internet.

How DNS works

DNS, or the Domain Name System, works like a phone book for the internet. Its main job is to translate human-friendly domain names (like www.google.com) into numerical IP addresses (like 142.250.191.132) that computers use to identify each other on the network. This process, called DNS resolution, happens automatically and is what allows you to access websites by typing in a name instead of a long series of numbers.

The Steps of DNS Resolution

When you type a domain name into your browser, a series of queries and responses takes place to find the correct IP address. This all happens in a fraction of a second.

  1. You type a domain name: You enter www.example.com into your browser. Your computer first checks its own local cache to see if it already knows the IP address for this domain. If it's there, the process ends. If not, it moves to the next step.
  2. The Query to the Recursive Resolver: Your computer sends a request to a recursive DNS resolver. This is usually a server managed by your internet service provider (ISP) or a public DNS provider like Google. The resolver's job is to do all the heavy lifting to find the IP address for you.
  3. The Query to the Root Server: The recursive resolver doesn't know the IP address either, so it sends a query to one of the root name servers. The root server doesn't know the specific IP address for www.example.com, but it knows which servers are responsible for the .com Top-Level Domain (TLD). It replies to the resolver with the address of a .com TLD server.
  4. The Query to the TLD Server: The recursive resolver then sends a new query to the .com TLD server. The TLD server doesn't know the full IP address for www.example.com, but it knows which servers manage the example.com domain. It responds to the resolver with the address of the example.com authoritative name server.
  5. The Query to the Authoritative Name Server: Finally, the recursive resolver queries the authoritative name server for example.com. This server is the definitive source for all information about the domain. It has the actual IP address for www.example.com and sends it back to the recursive resolver.
  6. The IP Address is Sent to Your Browser: The recursive resolver sends the IP address back to your browser. Your browser can now use this IP address to connect directly to the web server that hosts www.example.com and load the website. The resolver also stores the IP address in its cache for a short time, so it can answer the same query instantly if someone else asks for it.
