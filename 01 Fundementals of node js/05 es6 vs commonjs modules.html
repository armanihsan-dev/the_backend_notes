CommonJS vs. ES Modules

CommonJS and ES Modules (ESM) are two distinct module systems in JavaScript, each with its own design philosophy and use cases. CommonJS, primarily for server-side (Node.js), focuses on synchronous loading, while ESM, the official standard, supports both synchronous and asynchronous loading, making it suitable for both browser and server environments.

Brief Differences

  • Syntax:

    • CommonJS: Uses require() for importing and module.exports or exports for exporting. It's a function call for importing and an object assignment for exporting.
    • ES Modules: Uses import statements and export declarations. These are static keywords.

  • Accessing file and directory names:

    • CommonJS: Provides __filename and __dirname global variables, which give the absolute path to the current file and its directory, respectively.
    • ES Modules: Does not have __filename and __dirname globally. Instead, you can derive similar information using import.meta.url, which provides the URL of the current module.

In-depth Differences

Whether files are loaded synchronously or asynchronously

  • CommonJS: Modules are loaded synchronously. When a require() call is made, the execution of the current script pauses until the required module is fully loaded and executed. This behavior is well-suited for server environments where modules are typically loaded from the local file system.

  • ES Modules: Modules are loaded asynchronously. The import statements are processed during the "module loading" phase, which happens before the module's code actually executes. This non-blocking nature is crucial for browsers, as it prevents the main thread from being blocked while fetching modules over the network. In Node.js, even though file system access is fast, ESM still adheres to this asynchronous model.

File extension requirements

  • CommonJS:

    • Typically uses the .js extension. Node.js historically assumes .js files are CommonJS unless explicitly configured otherwise.
    • Can also use .cjs extension to explicitly denote a CommonJS module, regardless of package.json's type field.

  • ES Modules:

    • In Node.js, ES Modules often use the .mjs extension to explicitly signal that a file should be treated as an ES module.
    • Alternatively, a .js file can be treated as an ES module if the nearest package.json file contains "type": "module".
    • In browsers, script tags need type="module" to interpret the script as an ES module.

Import path behavior (e.g., what happens if we import app.mp4)

  • CommonJS:

    • More flexible with import paths. It can often resolve module paths without full file extensions (e.g., require('./utils') might resolve to utils.js, utils/index.js, or even utils.json).
    • Can directly require() non-JavaScript files like JSON (which are parsed into JavaScript objects).
    • Attempting to require() an arbitrary file type like app.mp4 would likely result in an error unless there's a custom loader or a specific Node.js behavior configured to handle it. By default, it expects JavaScript or JSON.

  • ES Modules:

    • Strict about full file paths and extensions in browser environments and increasingly in Node.js. For instance, import { foo } from './utils.js' is generally required, whereas import { foo } from './utils' might fail.
    • Does not natively support importing arbitrary file types like app.mp4 directly as part of the module graph. While modern environments might introduce "import assertions" or "import attributes" (e.g., import data from "./data.json" assert { type: "json" };), these are explicit mechanisms for specific non-JS types like JSON or WebAssembly. Importing an .mp4 would fundamentally not be a module.

Usage differences (e.g., the need to set "type": "module" in package.json)

  • CommonJS: Node.js historically defaults to CommonJS. No special configuration is needed for .js files to be treated as CommonJS.

  • ES Modules:

    • In Node.js, to enable ES Module syntax in .js files, you must add "type": "module" to your package.json file. Otherwise, .js files are interpreted as CommonJS by default.
    • In HTML, ES Modules are loaded via <script type="module" src="my-module.js"></script>.

The difference in the value of `this`

  • CommonJS: Inside a CommonJS module, the value of this at the top level (outside of any function) refers to module.exports. This allows for a shorthand to export values (e.g., this.foo = 'bar' is equivalent to exports.foo = 'bar').

  • ES Modules: Inside an ES Module, the value of this at the top level is undefined. This aligns with strict mode behavior, which ES Modules implicitly enforce.

Hoisting behavior

When JavaScript encounters an import statement, it creates a separate thread for it and executes the code of the imported module first during the memory creation phase. This means that module dependencies are resolved and linked before any of the module's code actually executes. This static nature allows for better tooling and optimizations like tree-shaking. However, it's important to differentiate this from variable/function hoisting within a script:

  • import and export declarations are "hoisted" in the sense that they are processed during the parsing phase, establishing the module's dependencies and exports before execution.
  • Variables declared with let and const and class declarations are still subject to the Temporal Dead Zone (TDZ), meaning they cannot be accessed before their declaration line within the module.

How `await` works at the top level

  • CommonJS: Top-level await is not supported in CommonJS modules. Using await outside of an async function at the top level of a CommonJS module will result in a SyntaxError.

  • ES Modules: Supports top-level await. This means you can use the await keyword directly in the body of an ES module (outside an async function). When an await is encountered, the module's execution pauses until the awaited Promise settles. Any module that imports a module with top-level await will also pause its execution until the awaited operation in the imported module completes. This is a powerful feature for initializing modules with asynchronous data. ⏳

Differences in exporting values

  • CommonJS:

    • Exports are dynamic. You assign properties to module.exports or exports at any point in the module's execution.
    • Exports are a copy of the value at the time of export. If the original value changes later in the exporting module, the imported value won't reflect that change unless it's an object/array (which are passed by reference).
    • There's essentially one "default" export, which is the module.exports object itself.
    • Example: 
      // myCJSModule.js
let count = 0;
module.exports.increment = () => { count++; };
module.exports.getCount = () => count;
// Or:
// exports.increment = () => { count++; };
// exports.getCount = () => count;

  • ES Modules:

    • Exports are static. You define what to export using export keywords, usually at the top level of the module. They represent live bindings to the original values. If the value of an exported variable changes in the exporting module, the imported value will reflect that change.
    • Supports both named exports (multiple exports by name) and a default export (one per module).
    • Example: 
      // myESMModule.js
export let count = 0; // Live binding
export function increment() {
    count++;
}
export default function greet() {
    console.log("Hello!");
}

The role of strict mode

  • CommonJS: Strict mode ("use strict";) must be explicitly declared at the top of a CommonJS module or within a function to apply its stricter parsing and error handling rules. Without it, the module runs in "sloppy" mode.

  • ES Modules: All ES Modules are automatically in strict mode by default. There is no need to add "use strict"; at the top of an ES module; it's implicit. This provides consistent and safer JavaScript behavior across all modules. 🔒
